# Claude Code と Antigravity の相互検証 設計書

- 何のための文書か: 一方のエージェントの成果物（設計書・コード・検証記録）を、もう一方のエージェントが見直すときの基本の決まりを決める。
- 関連: [AGENTS.md](../AGENTS.md)「併用ルール」「コミット手順」「事実と記録」、[design-review-steps.md](design-review-steps.md)（PR の前の見直しの段）、[design-stage20-reviews.md](design-stage20-reviews.md) 8〜11 節（Antigravity のレビューを受けた例）
- 作成日: 2026-11-28
- 状態: 起案（承認待ち。4 節）

## 1. 目的

- 同じエージェントが書いて同じエージェントが見直すと、同じ思い込みを見落としやすい。別のエージェントの目を入れて、設計・コード・結論の誤りを早く見つける。
- 受け取った指摘の扱いを、どちらのエージェントも同じ手順で行えるようにする。いまは手順が Claude Code のメモリにだけあり、Antigravity からは読めない（AGENTS.md「記録の置き場所」の方針に合わない）。

## 2. いまの形

- **Antigravity から Claude Code へ**: これまでに受けたのは、設計書のレビュー（Stage 20 の 3 回）と提案書（レイヴン S1、スキルの目録）。どれもオーナーが頼み、本文はリポジトリの外にあり、オーナーが Claude Code に渡した。ツールの名の無い外部のレビュー（[design-named-state-reviews.md](design-named-state-reviews.md) 9・10 節）も、同じ形で受けた。
- **受けた側の扱い**: Claude Code は指摘を 1 件ずつコード・データ・記録と照らして確かめ、判断を設計書の節に残した。Stage 20 の別紙 8 節の形（指摘ごとに「確かめたこと・判断・反映先」）が典型。確かめると、件数の前提が当たらない指摘や、指摘に無かった問題が見つかった（同 8 節の 1・2）。
- この扱いは、Claude Code のメモリ（「指摘は検証してから取り入れる」）にだけ書いてある。リポジトリの決まりには無い。
- **Claude Code から Antigravity へ**: Antigravity の成果物を Claude Code が見直した例は、上の提案書の判断のほかに無い。origin と main の履歴に `antigrav/` のブランチ・commit は無い（[design-workflow-simplification-19.md](design-workflow-simplification-19.md) 4 節）。
- **PR の前の見直し**: AGENTS.md「コミット手順」の整理とバグの 2 段は、Claude Code が自分の差分を自分の道具（`/simplify`・`/code-review`）で見る。別のエージェントの目は入らない。
- AGENTS.md「併用ルール」は、作業ツリー・ブランチ名・worktree の場所だけを決めている。

## 3. 論点

### 3.1 受け取った側の扱い（基本の決まり）

次の 5 つを、両エージェントが守る決まりにする。

1. 指摘は 1 件ずつ、関係するコード・データ・記録と照らして確かめる。採る・一部採る・採らないを決め、採らないときは理由を書く。根拠を確かめられない指摘は採らない（AGENTS.md「事実と記録」の「根拠のない変更は行わない」）。
2. 確定の結論・凍結の記録・AGENTS.md と食い違う指摘は、採る前にオーナーに確かめる（AGENTS.md「事実と記録」と同じ）。
3. 判断は指摘ごとに「確かめたこと・判断・反映先」の 3 つで残す（置き場所は 3.3 節）。
4. 見直しを頼む側は、自分の結論や推奨を先に渡さず、対象（設計書・差分・検証記録の ID）と問いを渡す。見る側が頼んだ側の考えに引っ張られないようにする。
5. 両者の判断が分かれ、同じ点で 2 回やりとりしても決まらないときは、両方の言い分と推奨をそろえてオーナーに上げる。

推奨: 5 つとも入れる。どれも、これまでの扱いを書き起こしたものか、AGENTS.md にある決まりの当てはめで、新しい手間は増えない。

### 3.2 いつ相互検証をするか

| 案  | 中身                                                                                                                                                                                    |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A   | オーナーが頼んだときだけ。頼む価値の高い場面を目安として挙げる（Stage 規模の設計書、確定の結論を棄却・訂正する変更、`packages/core/src/frame/`・`packages/core/src/sim/` の機構の変更） |
| B   | A の目安の場面では必ず行う。終わるまで PR を出さない                                                                                                                                    |
| C   | すべての PR で行う                                                                                                                                                                      |

推奨: 案 A。

- 受け渡しはいまオーナーが手で行っている（2 節）。B・C にすると、オーナーが受け渡すまで PR が止まり、「見直しから自動マージの予約まで止めずに進める」決まり（AGENTS.md「コミット手順」、[design-review-steps.md](design-review-steps.md) 3 節）とぶつかる。
- これまでの例（2 節）はどれもオーナーが頼んだもので、それで働いていた。
- C は、業務の簡素化（見直しの段を絞った [design-review-steps.md](design-review-steps.md) 2 節）と逆の向きになる。

### 3.3 指摘と判断の置き場所

| 案  | 中身                                                                                                                                                             |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A   | 指摘の本文はリポジトリの外のまま。判断は、対象の設計書に節（「起案後のレビュー（日付、Antigravity）」）として残す。設計書の無いコードの見直しは、PR の本文に残す |
| B   | 指摘の本文もリポジトリに入れる（`records/reviews/` に 1 件 1 ファイル、ID を振る）                                                                               |
| C   | PR のコメントでやりとりする                                                                                                                                      |

推奨: 案 A。

- これまでの形と同じで、道具を足さずに済む。判断の節に指摘の要点が残るので、本文が無くても後から追える。
- B は、新しい記録の型（ID・生成・検査）が要る。リポジトリは公開なので、外の本文をそのまま入れると、書いてはいけないこと（オーナーの所持など）が混ざるおそれもある。
- C は、Antigravity が GitHub に書き込むかが決まっていない（3.5 節）。

### 3.4 決まりを書く場所

| 案  | 中身                                                                                                                                                           |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A   | AGENTS.md「併用ルール」に、3.1 節の 5 つと 3.2・3.3 節の決定を数行で足す。Claude Code のメモリの「指摘は検証してから取り入れる」は、AGENTS.md を指すだけにする |
| B   | 手引き（`plan/cross-review-guide.md`）を新しく作り、AGENTS.md からは 1 行で指す                                                                                |

推奨: 案 A。決まりは 6〜8 行で収まり、別の文書を作るほどではない。両エージェントが毎回読む AGENTS.md に置けば、読み落としが無い。

### 3.5 確かめたいこと（オーナーへ）

- **Antigravity のいまの使い方**: レビューと提案書だけか、コードや記録を書くこともあるか。
  - レビューと提案書だけなら、この設計書の範囲で足りる。
  - Antigravity が `antigrav/` のブランチで PR を出すなら、その PR の前の見直し（AGENTS.md「コミット手順」の 2 段は Claude Code の道具で書いてある）をどうするかも決める必要がある。そのときは、Claude Code が `antigrav/` の PR のバグの段を受け持つ案を足す。

## 4. 決めてほしいこと

1. 3.1 節の 5 つの決まり（推奨: 5 つとも入れる）
2. いつ相互検証をするか（推奨: 案 A。オーナーが頼んだときだけ、目安の場面を挙げる）
3. 指摘と判断の置き場所（推奨: 案 A。判断を設計書の節か PR の本文に）
4. 決まりを書く場所（推奨: 案 A。AGENTS.md「併用ルール」に足す）
5. Antigravity のいまの使い方（3.5 節）

## 5. 採らない案

- **検証記録の読み取りを、もう一方のエージェントが独立に読み直す**: 録画から値を読む誤りには効くが、1 件ごとに読み取りの手間が倍になる。確定にできる条件（[verification-guide.md](verification-guide.md) 2.2 節）が、決めた回とは別の回での再現を求めているので、読み誤りはそこで多くが表に出る。疑わしいものは、3.2 節の案 A のとおりオーナーが個別に頼める。
