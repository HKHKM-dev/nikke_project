### 1.2 機械の検査（`packages/core/src/records/`）

- **`records:close`（`close.ts`）**: 予測ファイルの `predicted.at` が、録画の `date`（検証記録の日付以降に撮ったものだけ）と、この検証記録を `source` にする観測値の `readAt` のどれよりも後なら誤り。比べは**日の単位**で、同じ日は通る。
- **`records:new -- claim --from`（`drafts.ts`）**: `predicted.at` が観測値の `readAt` より後なら、`仮説` にする理由に挙げる。録画の `date` は見ない。理由は検証記録の観測値の全部で決まり、結論ごとの根拠には絞らない。
- **`records:check`（`predictions.ts`）**: 予測の指標と観測値を突き合わせ、合う仮説を数える。結び付いた観測値が予測より前に読まれたものかは見ない。
- **`predicted.commit`** は `records:predict` を回したときの HEAD（予測を計算したコードの版）で、予測ファイルを commit した commit ではない。スカッシュマージで、ブランチの commit は main から辿れなくなる（いまの予測ファイルにもそういうものがある）。

### 1.3 実際の運用

- 予測ファイルを持つ読み直しの検証記録は V-0090・V-0091・V-0092・V-0097（ほかに打ち切りの V-0088・V-0089）。どれも予測を commit してから既存の録画を読み、機械の検査を通って、読み直しの観測値を根拠に含む結論を確定にした（C-0109・C-0168・C-0171・C-0172・C-0193・C-0194。等級はどれも反復実測）。
- つまり、**機械は 2026-10-02 から「読む前の予測」を確定の条件として認めている**。skills-guide 1.8 節の文言（撮る前）と、V-0124 で書いた「録画が予測より前なので確定の条件を満たさない」（design-anis-star-s2-burst.md 4.1 節・V-0124・各結論の根拠）は、それより厳しい読み。文書と機械が食い違っている。

## 2. V-0124 で起きたこと

順に（commit は claude/anis-star-s2-burst ブランチ）:

1. 録画 162・163 を撮った（V-0121・V-0122 の撮影依頼）。
2. V-0122・V-0121 で `162-01`〜`162-03`・`163-01`〜`163-03` を読んだ。`162-01`（フルバーストの入りの間隔）が許容外で、これが V-0124 の仮説 G1（シューティングスターがゲージを溜める）の出どころになった。
3. 予測ファイル V-0124 を commit した（68ae12c）。`predicted.commit` は起案の commit（df4bb5d）。
4. 観測値 `162-04`〜`162-17`・`163-04`〜`163-09` を読んで commit した（ccefd77）。
5. 機械の判定: 日付の検査は通った（撮影・予測・読みが全部同じ日）。下書きを `仮説` にした理由は別で、許容外（`162-11`・`162-12`）と最小構成の警告（録画 162・163）。
6. 予測との比べに `162-01` が自動で結び付き、「許容内」と数えられた。`162-01` は予測より前に読んだ観測値（`source` は V-0122）なので、日付の検査の外にある。V-0124 の本文は「後付けの照合」と書いて人が区別した。

分かること:

- **(a) 日の単位では前後を区別できない**。撮影・予測・読みが同じ日なら、読み直しか撮る前かによらず検査は通る。V-0121・V-0122（同じ日に撮った新しい録画）の「撮る前」も、日付だけでは示せていない。
- **(b) 読み直しで問うべきは「比べる値を、予測の前に見ていたか」**。録画が予測より前にあることそのものではない。`162-01` は見ていた（仮説の出どころ）。`162-04` などの 1 ヒットの値は見ていなかった。
- **(c) 前に読んだ観測値が、予測の比べに紛れ込む**。いまの検査はこれを拾わない。

## 3. 予測の条件が守るもの

- 撮る前の予測が守るのは 2 つ。
  1. **合わせ込みを防ぐ**: 値を見てから解釈を選ばない（分かれ道を後から選ばない）。
  2. **撮る前に、その録画で仮説を見分けられるかを確かめる**（撮影の計画。design-stage20.md 3.2 節）。
- 新しい録画では、録画が予測の後にできるので、1 は録画があとから生まれたことで保証される。読む人の自制に頼らない。
- 読み直しでは、2 は撮影が済んでいるので当てはまらない。1 は「比べる値を予測の前に見ていない」ことに頼る。同じ録画のほかの値や残差を前に見ていることが多く、読む人の自制に頼る分、保証は弱い。
- **等級との関係**: `厳密一致`（合わせ込みの定数なしで端数まで合う）は、後から解釈を選んでも偶然には起きにくい（V-0124 の対立仮説は 1 割以上違う値を出していた）。`反復実測`（許容幅で合う）は、後から選ぶと合いやすい。読み直しの弱さが効くのは主に反復実測と、許容の広い指標。

C の印の候補:

- **C1 生成物の印**: [claims.md](claims.md) の結論の行に「読み直し」と出す（根拠の録画の `date` が検証記録の日付より前で、予測ファイルがあるとき）。データから引けるので、結論のファイルには書かない（1 つの事実は 1 か所）。
- **C2 等級で絞る**: 読み直しだけで確定にできるのは `厳密一致` のときだけ。`反復実測` は、予測の後に撮った録画を根拠に 1 本以上含むときに限る。1.3 節の 6 件はどれも反復実測なので、C-0171 のように新しい録画を根拠に含むもののほかは、仮説に戻すか撮るかを決めることになる。
- **C3 状態か等級を足す**（例: 状態「確定（読み直し）」）: 状態と等級の語彙・照合・テスト・画面のすべてに響く。推奨しない。

**推奨は B + C1**。

- 1.3 節のとおり、機械はすでに B の形で動いており、問題は文書との食い違いと、日の単位の検査の穴（2 節の (a)・(c)）にある。A はその運用を覆し、読み直しで決着してきた結論（弾丸命中率・RL のコアの外れ・着地の照準など）の扱いが割れる。
- 保証の弱さ（3 節）は、印で見えるようにすれば足りる。C2 は、C1 で読み直しだけに立つ確定がどれだけあるかを見てから決める（最小構成の警告を警告から始めたのと同じ進め方。design-records-automation.md 7 節の 5）。

## 5. 推奨案の機械（B1・B2・C1）

- **B1 予測の時点の控え**: `records:predict` が、予測ファイルの `predicted` に、そのとき既にある観測値のうち、検証記録の「録画」に挙げた録画のものの ID を `seen` として書く（読み直しの予測は録画が決まっているので、録画の一覧がそのまま使える）。データとして残るので、スカッシュマージの後も検査できる。
  - `records:close`・下書き: この検証記録を `source` にする観測値が `seen` に入っていれば誤り（予測の前に読んだ）。日の単位の検査は、`seen` を持たない古い予測ファイルのために残す。
  - `records:close` は、ブランチの上で git の履歴も見る: 予測ファイルに `predicted` を入れた commit が、観測値を足した commit の祖先であること（予測を commit してから読みを commit した）。マージの後は見られないので、閉じる前だけの検査にする。
- **B2 後付けの照合**: `records:check` は、予測の指標に結び付いた観測値が `seen` に入っていれば、その指標を「後付け」と出し、合う仮説の数と確定の条件に数えない（2 節の (c)。`162-01` の形）。
- **C1**: `claims.md` の生成で、確定の結論の根拠の観測値に、検証記録の日付より前の録画のものがあり、その検証記録に予測ファイルがあれば、行に「読み直し」と出す。
- **新しい録画の同じ日の前後**（2 節の (a) の前半）も B1 の控えで扱える: 予測の時点で `records/recordings/` に無かった録画は、撮る前と見なせる。ただし取り込みが撮影より遅れると見誤るので、録画の `original`（撮影の時刻を含む元のファイル名）と予測の commit の時刻を比べる検査を足すかは、実装の PR で決める（推奨は、まず控えだけ）。
- **文書**: skills-guide.md 1.8 節の条件を「予測を、比べる値を見る前に出している（新しい録画は撮る前、読み直しは読む前）」に、2 節に確定の条件と B1・B2 を足す。design-records-automation.md 3.2・3.6・3.7 節と records/verifications/README.md も同じ文言にする。
- **見出し「予測（撮る前に書く）」は変えない**。見出しは節の語彙で、意味は README で決める（読み直しでは「読む前」）。変えると語彙が 2 つになって検査が増え、閉じた記録を書き換えないと揃わない。
- テストは `close.ts`・`drafts.ts`・`predictions.ts` の単体テストに、読み直しの形（`seen` に入った観測値・後付けの指標・`seen` の無い古い予測ファイル）を足す。

## 6. 決めてほしいこと（推奨つき）

1. **読み直しの扱い**: A（人の判断にとどめる）/ B（読む前の予測を認める）/ C（B + 印か制限）。**推奨は B + C1**（4 節）。
2. **順序の確かめ方**: (a) 日の単位のまま / (b) 予測の時点の控え（`seen`）+ 閉じる前の git の順序 / (c) `predicted.at` と `readAt` を時刻まで持つ。**推奨は (b)**。(c) は手で書く観測値の `readAt` が日のままになり、自己申告である点は (a) と変わらない。(b) は控えがデータに残り、スカッシュの後も検査できる。
3. **予測より前に読んだ観測値に結び付いた予測の指標**: **推奨は「後付け」と出し、合う仮説と確定の条件に数えない**（B2）。
4. **等級で絞るか（C2）**: **推奨は、いまは絞らない**。C1 の印で読み直しだけに立つ確定の数を見てから決める。
5. **見出し**: **推奨は変えない**（5 節）。
6. **V-0124・V-0122 の結論**: B を採れば、V-0124 の C-0204・C-0205・C-0207・C-0209・C-0211 は条件を満たす（読みの commit が予測の commit の後で、比べた値は予測の前に見ていない）。根拠の文の「確定の条件を満たさないが、オーナーの判断で確定にした」は、実装の PR で「読み直し（予測の後に読んだ）」に直す（claude/anis-star-s2-burst のマージの後）。V-0122 の C-0202 は、確定の根拠にした値（デルタの II の時刻）が予測の指標でなく、撮った後に組んだ読み方なので、B でも条件を満たさない。オーナーの判断の確定のまま残す。**推奨はこのとおり**。

## この設計書の外

- 下書きの理由が検証記録の観測値の全部で決まり、結論ごとの根拠に絞らない（1.2 節）。V-0124 では、シューティングスターの `162-11`・`162-12` の許容外が、それと関係の無い S2 の結論（C-0204 など）の下書きにも理由として出る。結論ごとに絞るかは別に起こす。
