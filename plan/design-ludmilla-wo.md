## 2. 足す語彙

### 2.1 発数の弾丸チャージ: `ammoRefill` の `scaling: 'flat'`

```json
{
  "kind": "ammoRefill",
  "trigger": { "count": "normalHit", "everyRef": 5 },
  "target": "self",
  "scaling": "flat",
  "ref": 6
}
```

- 今の `ammoRefill` は「弾丸チャージ X%」（最大装弾数 × X% を切り捨てて足す。`frame/firstPass.ts` の `refillRounds`）。`scaling: 'flat'` のときは値をそのまま発数として足す（100 で割らない）。最大装弾数で止めるのは同じ（`refillAmmo`）。
- `scaling` の語は、最大装弾数▲の発数（`maxAmmo` の `flat`。Stage 10）に合わせた。`ammoRefill` に書ける `scaling` は `flat` だけ。
- 退化: 既存の定義（ノワール・紅蓮BS の %）は `scaling` を書いていないので変わらない。

### 2.2 コアの命中の回数: `ShotCountKind` の `coreHit`

```json
{
  "kind": "damage",
  "trigger": { "count": "coreHit", "everyRef": 1 },
  "damageType": "additional",
  "ref": 2,
  "gaugeHits": [0]
}
```

- モデルは 1 発がコアに当たるかを確率（コア命中率 p）で持ち、どの発が当たったかを持たない。そこで **コアの命中の回数を期待値で数える**: 自分の通常攻撃の 1 発ごとに、その発のコアの命中の期待値（弾丸命中率 × コア命中率。コア命中率は当たった発のうちコアに当たる割合。`damage.ts` の通常攻撃の式と同じ）を足し、足した値が N の倍数を越えた発で発火する（論点 1）。
  - 値は、その発のフレームの枠の条件。条件が自動の枠は、計画（`planLandings`）の着地点ごとの配分（常時の命中率▲を入れた値）で Σ 重み × 弾丸命中率 × コア命中率。手入力の枠は入力の値の積。敵にコアが無ければ 0（発火しない）。
  - 持続の命中率▲による上がりは数えに入れない（1 パス目のゲージと同じ理由。1 パス目は持続の `hitRate` の窓を追っていない。design-hit-rate-up-bullet-h2.md 4 節の 5）。ルドミラ自身は命中率▲を持たない。
  - SG（1 トリガーに複数のペレット）は考えない。`coreHit` の効果を持つ SG のキャラが出たときに決める。
- 置き場所: 1 パス目に、弾丸命中率の区間（`hitRateSpansOf`）と同じ形で、枠ごとのコア命中率の区間を渡す。射撃の出来事（`skills/triggers.ts` の `ShotEvent`）に、その発のコアの命中の期待値 `coreHits` を持たせ、回数トリガーは `coreHit` のときだけこれを足す。バッチの `triggerFrames`（calc もこれを通る）は、射撃の記録（`ShotLog`）に残した発ごとの値で同じ列を作る。sim と calc は同じ発火のフレームを見る。
- 退化: `normalShot`・`fullChargeShot`・`lastShot` の数え方は変えない（`normalHit` は 2.3 節）。

### 2.3 通常攻撃の命中の回数を期待値で数える（`normalHit` の数え方の変更）

- 今の `normalHit` は `normalShot` と同じ列（1 発 = 1 回）。これを、1 発ごとに **その発の弾丸命中率**（条件が自動の枠は 1 パス目のゲージと同じ区間の値、手入力の枠は入力の弾丸命中率）を足し、累計が N の倍数を越えた発で発火するように変える（コアの命中の回数と同じ数え方）。
- SG は 1 トリガーを 1 回として数える（ペレットのどれかが当たれば命中。的の表の SG の弾丸命中率はペレットの割合なので使わない）。
- 毎回（every = 1）の倍率ダメージは今までどおり 1 トリガーの値に畳み込む（その値はもう弾丸命中率を掛けている。`damage.ts` の `perShot`）。
- 弾丸命中率が 1 の枠（手入力の既定・的の表が 1 の帯）では今までと同じ。1 より小さい枠では、`normalHit` の回数トリガーを持つ定義（ミランダ S1・クルミ S1 など）の発火が遅れる。確定の結論の観測値と比べ直し、変わる数値は PR に書く。
- `damage.ts` の注記「命中を数えるトリガーは全弾命中のまま」を直す。

### 2.4 同じ発火の効果の順（`sequential` をスキルのスロットにも）

- 「下位効果のスタック適用」（`sequential`。今は burst スロットだけ）を、スキルのスロットにも書けるようにする。同じ発火の効果を書いた順に当て、後の `damage` は、同じ発火で前に書いた `timed` の値を足したバフで計算する（C-0163 と同じ形）。
- スキルのスロットでは、先頭が `burstDamage` である決まりは要らない。射撃の回数トリガーの窓は発火した発の次のフレーム（f + 1）から始まるので、「同じ発火で前に書いた `timed`」は f + 1 に始まる同じ枠・同じスロットの窓として拾う。
- 発火した発の通常攻撃そのものには乗せない（窓は f + 1 から。今のまま）。
- ルドミラ S1 は `sequential: true` で、受けるダメージ▲ → 追加ダメージの順に書く。受けるダメージ▲の付き直しは、今の `timed` と同じく窓を延ばすだけ（重ならない）とする。

### 2.5 calc: 自分の射撃の回数で開く窓を持つ枠は、全グループを射撃の列から数える

- 実装で見つけたこと（2026-10-04）: calc の既定（`hybrid`）は、射撃に効く持続バフのグループだけを射撃の列から数え、ほかは平均レートで数える（plan/design-calc-hybrid.md）。ルドミラの受けるダメージ▲は自分の射撃の回数で開き直るので、撃っている間だけ効く。平均レートで数えると、窓の中に撃っていない時間（リロード・MG のスピンアップ）の分まで発数を配り、手入力・出来事なしの単騎で sim と 12% ずれた。窓のグループだけを射撃の列から数えると、今度は窓の外の平均レートが残りの発数を外す。
- そこで、**自分の射撃の回数で開く窓が 1 つでも効く枠は、`hybrid` でも全グループを射撃の列から数える**（`calc/model.ts` の `hasOwnShotCountWindow`）。案 (b)（`firingSlots`）の条件に「自分の射撃の回数で開く窓」を足した形。
- 退化: 該当するのは、自分の射撃の回数で開く持続バフを持つ定義（モダニア S1・ヘルム S1 など）の枠だけ。敵を狙えない窓がある編成（射撃場の 3 分モード）は前から全グループを数えているので変わらない。手入力・出来事なしでは calc が sim に近づく。

## 3. 確かめ方

### 3.1 段 A: 既存の録画 099 の読み直し（単騎）

- 録画 099（単騎・AUTO・スペック固定・3 分モード）。読んだのはリロードの長さだけ（V-0058）。S1・S2 の値はまだ読んでいないので、予測を commit してから読めば根拠にできる（[skills-guide.md](skills-guide.md) 2 節）。
- 見るもの（読み方は HUD の総ダメージの増分。MG は 1 フレームに 1 発まで）:
  1. **マガジンの発数**: リロードの間の発数。弾丸チャージが説明文どおりなら、300 発のマガジンで撃てる発数が増える。回数を戦闘中ずっと数えるか、マガジンごとに数え直すかも、チャージの起きる発で見分けられる。
  2. **S1 の追加ダメージ**: 60 回命中ごとの大きい増分。値に受けるダメージ▲が乗るか（H1・H2）。乗らない読み（H1）と乗る読み（H2）は、各マガジンの最初の発火（前の窓が切れた後）で値が {02}% ぶん違う。発火の発が、射撃の回数でなく命中の回数で決まるか（外れた発を数えないか）も、外れの読める区間で見る。
  3. **受けるダメージ▲**: 発火の後の通常攻撃の 1 ヒットが {02}% 上がるか、発火した発そのものに乗るか、3 秒で切れるか、重ならないか。
  4. **S2 の追加ダメージ**: コアの 1 ヒットは胴体の 1 ヒットより大きいので、発ごとにコアかを数えられる。追加ダメージが「コアの実際の命中の 60 回目」で出るかを確かめる（ゲームの規則）。モデルの期待値の数え（2.2 節）は、発火の間隔の平均で比べる。
  5. 追加ダメージのクリティカル・コア・距離の乗り方は、モダニア S1（C-0105）と同じ前提で予測し、増分の格子で確かめる。
- バーストゲージ: 単騎のバースト III はバーストを撃てない。追加ダメージがゲージを溜めるか（`gaugeHits: [0]`。モダニア C-0105・ヘルム C-0104・紅蓮BS C-0085 と同じ読み）は、段 A ではゲージの表示が読めれば見る。読めなければ仮説のまま。

## 4. 実装

1. `skills/types.ts`: `ShotCountKind` に `coreHit`。`AmmoRefillEffect` に `scaling?: 'flat'`（検証: `ammoRefill` 以外の即時効果には書けない）。単体テスト。
2. `skills/resolve.ts`: `flat` の `ammoRefill` は値を 100 で割らない（発数）。`frame/firstPass.ts` の `refillRounds` の前で分ける。
3. `frame/landing.ts`: 枠ごとのコア命中率の区間（`coreHitRateSpansOf`。弾丸命中率の区間と同じ形）。手入力の枠は入力の値の 1 区間。

## 5. 論点

1. **コアの命中の回数を期待値で数えるか**。推奨は期待値の累計（2.2 節。モデルの 1 発がコアに当たる確率の持ち方と揃い、sim と calc が同じ発火を見る）。代案は「N ÷ p 発ごと（切り上げ）」（区間でコア命中率が変わると扱いにくい）、「全発をコアの命中として数える」（コア命中率が 1 の前提。MG の射撃場ではずれが小さいが、手入力の枠や他の的でずれる）。
2. **同じ発火の追加ダメージに受けるダメージ▲が乗るか**。推奨は今の語彙（乗らない。H1）で予測し、099 で H1・H2 を見分けてから決める。H2 なら、スキルのスロットにも `sequential` を書けるようにする（別の設計の節で足す）。
3. **「通常攻撃が N 回命中した時」を射撃の回数で数えるまま（全弾命中の前提）にするか**。推奨はこのまま（MG の弾丸命中率は 1 に近く、変えるとミランダ・クルミ・モダニアの定義の数値も動く）。`assumes` に書く。
4. **確かめ方**。推奨は段 A（録画 099 の読み直し）→ 段 B（ラム・デルタとの編成を新しく撮る）の順。段 B の編成は所持の確認が要る（ラム・デルタは録画に写っている）。
