## 1. 何が困っているか

ミランダ（32）の宝物版 S2（ウェイクアップ！）の 3 行目だけが、[skills.md](skills.md) で未対応（`unimplemented`）の notes のまま残っている。1・2 行目は V-0217（C-0323・C-0324）、バースト（宝物版）は V-0216・V-0218（C-0322）で定義済み。

説明文（`data/characters/32.json` の `treasure.skills.skill2`。Lv10）:

> ■フルバーストタイムが発動した時、自分を除く最終攻撃力が最も高い味方 {07 = 1} 機に（対象が足りない場合、自分も対象となる）「クリティカル確率 {08 = 85.42}％▲」「{09 = 1} 発間維持」

分解すると、どの部品もいまの語彙にある。

| 部品                                      | 語彙                                                                     | 根拠                        |
| ----------------------------------------- | ------------------------------------------------------------------------ | --------------------------- |
| フルバーストタイムが発動した時            | `trigger: "fullBurstStart"`                                              | C-0323（同じ S2 の 1 行目） |
| 自分を除く最終攻撃力が最も高い味方 1 機 … | `target: "topAttack"`・`targetCountRef: 7`・`excludeSelf: "unlessShort"` | C-0322（同じ言い回し）      |
| クリティカル確率 85.42%▲                  | `stat: "critRate"`・`ref: 8`                                             | C-0324（足し方。仮説）      |
| 1 発間維持                                | `durationShotsRef: 9`                                                    | C-0099（数え方）            |

足りないのは組み合わせだけ。`skills/types.ts` の `parseTimedDuration` が「発数の維持は `topAttack` に書けない」（`a duration in shots cannot target "topAttack"`）で落としている。`topAttack` の窓は `planBuffTimeline` の 2 段目（順位）で `effectWindows`（秒の窓）だけを作り、`durationShots` の窓は 1 段目の `distribute` で `shotCountWindows` だけを作るので、両方を通る道が無い。

- 説明文の走査（`data/characters/` の 203 体・基礎版と宝物版の全スロット）で、1 行に「最も高い / 最も低い / 一番」と「発間維持」が両方あるのはミランダの宝物版 S2 の 3 行目だけ。
- ゲーム内のヘルプ（[game-help.md](game-help.md)）に、順位の決まる時と発数の数え方の記述は無い。

## 2. 語彙（足すものは無い。組み合わせを許す）

新しい欄・stat・対象は足さない。`topAttack` と `durationShots` / `durationShotsRef` を同じ `timed` に書けるようにする。

```json
{
  "kind": "timed",
  "trigger": "fullBurstStart",
  "target": "topAttack",
  "targetCountRef": 7,
  "excludeSelf": "unlessShort",
  "stat": "critRate",
  "ref": 8,
  "durationShotsRef": 9
}
```

規則（論点 1〜3 の推奨どおりのとき）:

1. **対象は発火のフレームの順位で決める**（論点 1）。いまの `topAttack` の規則（[design-stage11.md](design-stage11.md) 18 節: 発火のフレーム `f` で効いている攻撃力の窓を入れた最終攻撃力・同値は枠の若い順・順位で決まる効果の窓は材料に入れない）と、`excludeSelf`（C-0322）をそのまま使う。
2. **窓は対象の枠の射撃で切る**。対象に決まった枠ごとに、その枠の射撃の列を `shotCountWindows` に渡す（C-0099: 付いた後の N 発目まで効き、N + 1 発目で戻る。窓の端はいまの `shotCountWindows` の規則のまま: N 発目のフレーム + 1 で閉じ、付いたフレームと同じフレームの射撃は 1 発目に数え、維持中にまた付いたら数え直す）。
3. **撃たない間は切れない**。対象が撃たなければ、次の発火（次のフルバースト）まで窓が開いたまま残る（説明文に秒の上限は無い）。
4. **会心率は 1 で頭打ちにする**（論点 2）。ミランダの 3 行目は素の 0.15 に足すと 1.0042 になる。

書けないまま残すもの（いまの規則を変えない）:

- 1 パス目のループで窓を追う stat（`attack`・射撃系・状態）の発数の維持は、対象にかかわらずいまどおり落とす。`critRate` は 1 パス目で追わないので、順位（2 段目）で窓を作れば足りる。
- 条件付き（`condition`）・`durationUntil` と `topAttack` の組み合わせはいまどおり落とす。

## 3. 実装（承認の後。sim → calc の順で、1 段ごとに `npm test`）

1. `skills/types.ts`: `parseTimedDuration` の `topAttack` の禁止を外す（stat の禁止は残す）。単体テスト（書ける・`attack` などは落ちる）。
2. `skills/timeline.ts`: 2 段目の `perTarget.forEach` で、`effect.durationShots` があれば `effectWindows` の代わりに `shotCountWindows(starts, shots[slotIndex]?.frames ?? [], n, frames)` を使う。`resolve.ts` の解決（1 パス目では 0）は変えない。
3. 会心率の頭打ち（論点 2 で推奨を選んだとき）: `skills/buffs.ts` の `applyCritBuffs` と、`damage.ts` の通常攻撃の会心の期待値（`crit.rate + normalCritRate`）で 1 を上限にする。`records/observations.ts` の `critRateAt` も同じ値にする。
4. 退化: 既存のテストが数値を変えずに通ることを確かめる。会心率が 1 を超える既存の編成があれば数値が変わるので、その場合は止めて報告する（定義の変更より先に確かめる）。
5. calc（`calc/model.ts`）: 窓は `planBuffTimeline` が作るので、区間の鍵はそのまま。整合のテストだけ足す。
6. 画面・CLI のラベル: 対象（順位）と「N 発間」の表示はどちらも既にある。組み合わせの表示を確かめる。
7. 定義: **根拠の結論ができてから**、`32.json` の `treasureSkills.skill2` に効果を足し、3 行目の notes（`unimplemented`）を消す。結論が無いうちは notes の理由を「語彙が無い」から「撮っていない」に直すだけにする（論点 3）。
8. 編成のテスト: ミランダ（宝物 3）+ 2 体で、自分を除く 1 位の枠にだけ、フルバーストの後の 1 発目にだけ会心率が足されること。sim と calc の一致。

## 4. 退化の見込み

- 3（頭打ち）は、会心率が 1 を超える区間がある編成だけ変わる（下がる）。4 で確かめる。

## 5. 検証（撮影が要る）

既存の録画では見られない。録画 245（V-0217・V-0218）の編成では、3 行目の対象はモデルの順位で I-DOLL・サン（スペック固定の最終攻撃力でデルタより上。`npm run sim -- --ids 32,20,308 --fixed-spec --controlled 3 --treasure 32:3` の順位の表）で、サンは撃たない操作枠だったので、効果は画に出ない（2 節の規則 3 で、次のフルバーストまで残るだけ）。

**案 A（推奨）**: 録画 245 の編成で、操作枠をミランダに替える。

- 編成: ミランダ（枠 1・宝物 3・**操作・撃たない**）+ デルタ（枠 2・AI）+ I-DOLL・サン（枠 3・AI）。射撃場・BigArms（灼熱）・3 分モード・スペック固定 ON・AUTO 射撃 OFF・オートバースト ON。
- 3 行目の対象は、自分を除く 1 位のサン（論点 1 の推奨）。ミランダは撃たないので、S1（通常攻撃の命中で数える効果。C-0186 は仮説）は発火せず、混ざらない。
- 見るもの: フルバーストごとに、**サンのフルバースト開始以後の 1 発目が会心か**（H1 なら会心率 1 で必ず会心）。2 発目以後のサンの発と、デルタの発は素の会心率（0.15）のまま。
- 見分け方: フルバースト 1 回で 1 発しか増えないので、件数は少ない。H0（効果なし）でサンの 1 発目が k 回とも会心になる確率は 0.15^k（k = 3 で 0.003、k = 4 で 0.0005）。3 分で 3 回以上のフルバーストがあれば足りる見込み（ミランダが撃たないのでゲージは録画 245 より遅い。足りなければ同じ条件で 2 本）。
- 対象がデルタになる読み（順位の決め方が違う）は、デルタのフルバースト開始以後の 1 発目が必ず会心になることで見分けられる（SR の 1 発は値が大きく、読みやすい）。
- 自分を除かない読み（ミランダが 1 位で対象）は、ミランダが撃たないので H0 と同じ見え方になる。C-0322 で同じ言い回しの読みは確定しているので、この 1 本では見分けない。
- 未確定の要素: サンのバーストの自分の最大装弾数▲（未実装）は、サンの射撃の数とリロードの位置を変えるが、1 発目が会心かには効かない。最小構成の警告（ミランダ・サン）は録画 245 と同じく出る見込みで、オーナーの判断が要る（論点 4）。
- 予測: 承認の後、2 節の語彙を入れてから `records/predictions/V-NNNN.json` に、H0（いまの定義）と H1（2 節の効果を `addEffects`）を書き、`critRateAt`（サンの 1 発目のフレーム・2 発目のフレーム、デルタの 1 発目のフレーム）で比べる。モデルは撃たない操作枠を扱わない（ミランダも撃つものとして時刻表を作る）ので、フルバーストの時刻は録画とずれる。比べるのは各回の 1 発目の会心の有無だけにし、フレームは録画の回ごとの 1 発目に合わせる（V-0217 の読み方 5 と同じ形）。

## 6. リスク

- サン（AR）の 1 発の値は小さく、デルタの発と同じフレームに乗ると分けにくい。V-0217 と同じく、デルタの系列を引いて分けられないものは使わない。
- サンはフルバーストを開く III で、バーストの動作の後に撃ち始める。1 発目がフルバーストの中のどこに来るかは録画で読む（モデルの時刻とは合わせない）。
- 会心率の頭打ち（論点 2）は、確率である以上 1 を超えられない、という読みで、この録画の H1 は 1 でも 1.0042 でも「必ず会心」で同じ見え方になる。頭打ちそのものの根拠にはならない。
- 順位を発ごとに決める読み（論点 1 の代案）は、この編成ではサンとデルタの順位が戦闘の中で入れ替わらない（どちらにもミランダのバーストの攻撃力▲が付く）ので、推奨と見え方が同じ。見分けるには順位が入れ替わる編成が要るが、使うキャラがミランダだけなので、見分けない。

## 7. 論点（推奨を先に書く）

1. **対象の順位をいつ決めるか**。
   - 推奨: 発火（フルバーストタイムの発動）のフレームで決め、その枠の射撃で N 発を数える。いまの `topAttack` の規則と同じで、「N 発間維持」は付いた枠の発を数えるもの（C-0099）なので、付いた後に対象が移るとは読まない。
   - 代案 a: 対象の枠の射撃のたびに順位を取り直し、その時の 1 位の発に効かせる（「付く」より「次の 1 位の 1 発」と読む）。実装は 2 段目と 1 段目の両方に手が入り、この編成（5 節）では推奨と見分けられない。
   - 代案 b: 順位は発火で決め、窓は秒（フルバーストの 10 秒）で切る（「1 発間」を無視する）。説明文に反するので推奨しない。
   - **決定（2026-10-06）: 推奨どおり**。
2. **会心率の頭打ち（1 を上限）を、この語彙と同じ PR で入れるか**。
   - 推奨: 入れる。会心率は確率なので 1 を超える値に意味が無く、ミランダの 3 行目は素の会心率と足して 1 を超える（1.0042）。頭打ちが無いと、期待値の会心の上乗せが 0.42% 分大きくなる。既存の編成で 1 を超える区間があれば数値が変わるので、3 節の 4 で確かめ、変わるなら止めて報告する。
   - 代案: 入れない（ミランダの 1 発分の 0.42% の過大を残し、頭打ちは別の課題にする）。
   - **決定（2026-10-06）: 推奨どおり**。
3. **結論ができるまでの定義**。
   - 推奨: 語彙（2 節）だけを入れ、`32.json` の 3 行目は notes（`unimplemented`）のまま、理由を「語彙が無い」から「撮っていない」に直す。効果は撮影で結論ができてから有効にする（V-0217 と同じ流れ）。
   - 代案: 1 節の部品がそれぞれ根拠のある結論に結び付くことを根拠に、推論の仮説の結論を作って有効にする（C-0325・C-0326 と同じ扱い。画面の `assumes` で仮定と出す）。撮影を待たずに数値に入るが、発数の窓と順位の組み合わせそのものは見ていない。
   - **決定（2026-10-06）: 推奨どおり**。
4. **撮り方**。
   - 推奨: 5 節の案 A（録画 245 の編成で、操作枠をミランダに替えて撃たない。1 本、フルバーストが 3 回に足りなければ 2 本）。最小構成の警告（ミランダ・サン）は、録画 245 と同じく、見る値（サンとデルタの 1 発目の会心の有無）に効く未確定の要素が 3 行目のほかに無い、という読みで通す。
   - 代案 B: サンを外し、III にデルタより最終攻撃力の低い、機構の確定したキャラを置いて、デルタ（SR）を対象にする。スペック固定では、定義のある III はどれもデルタ（63,368）より上（サン 67,895 が最も低い）なので、いまの手持ちの定義では組めない。
   - 代案 C: スペック固定 OFF で、デルタが III より最終攻撃力で上になる育成の組み合わせを使う。育成データが要り、モデルの順位の前提（育成の入力）が増える。
   - **決定（2026-10-06）: 推奨どおり**。
5. **backlog の行**。
   - 推奨: 承認の後は、6 節の「順位で決まる対象への発数の維持」の行を消し、ミランダの宝物版 S2 の 3 行目を「撮影（語彙はある）」の行に移す（撮影の後は「反復実測」などの行で扱う）。
   - **決定（2026-10-06）: 推奨どおり**。
