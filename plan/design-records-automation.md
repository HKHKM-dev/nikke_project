- 対象: `D:\nikke_project`（要件は `plan/requirements.md`, `plan/roadmap.md`）
- 状態: 起案（2026-10-01）。7 節の承認待ち
- 関連: [design-stage20.md](design-stage20.md)（記録の構造）、[skills-guide.md](skills-guide.md) 1 節（いまの手順）、[captures/index.md](captures/index.md)「解析ツール」、[records/verifications/README.md](../records/verifications/README.md)、[claims.md](claims.md) 冒頭（等級の決め方）
- 作成日: 2026-10-01

## Context

検証記録の書式・結論の検査・残差と一覧の生成は Stage 20 で機械化され、`npm run records:check` と `npm test` が守っている。その間の工程は手作業のままで、1 回の検証（V-0062〜V-0073 の SG の一連）を振り返ると、時間の大半は次の 2 つに使われている。

1. **録画を読んで観測値を書く**。`hud.ts` などの出力を見て、区間分けやペレットの分解を「使い捨てのスクリプト」で行い、値を `records/observations/` に手で写す。観測値の `method.tool` に「使い捨てのスクリプト」と書かれたものは、同じ値を機械で出し直せない。
2. **予測と結果を比べて、等級を決め、結論を書く**。予測は sim の出力を手で写し、結果が出てから「どの仮説と合ったか」「反復実測にできるか」を人が読み合わせる。

この設計書は、工程のうち機械で決まるものをスクリプトにし、人の判断が要るところには下書きと検査を添える流れを決める。モデルの値を動かす工程は含まない。

## 0. 今の流れと手作業の所在

| 工程                                  | いま                                                                 | 自動化の余地             |
| ------------------------------------- | -------------------------------------------------------------------- | ------------------------ |
| 1. 検証記録を起こす・ID を採番する    | 手書き。次の番号は一覧を見て決める                                   | 高                       |
| 2. 予測を書く                         | `sim-run.ts` を回し、数値を記録の「予測」に手で写す                  | 高                       |
| 3. 撮る                               | 人（撮影プロトコル）                                                 | なし                     |
| 4. 録画を取り込む                     | リネーム・`probe.ts` の出力を `records/recordings/` に手で写す       | 中                       |
| 5. 録画を読んで観測値を書く           | 解析ツールの出力を読み、区間分けや分解は使い捨てスクリプト。手で写す | **最大**                 |
| 6. モデルと比べる                     | `records:check` で残差を生成                                         | 済                       |
| 7. 予測と比べ、等級を決め、結論を書く | 人が判断し、`records/claims/` を手書き                               | 中（下書きと検査）       |
| 8. 記録の結果を書き、完了にする       | 手書き                                                               | 中（表は生成、散文は人） |
| 9. PR                                 | AGENTS.md の手順                                                     | 低                       |

## 1. 方針

- **機械で決まることは全部スクリプトにする**。採番・素性・読み取り・予測値・残差・等級の候補・整合の検査。
- **判断は人に残す**。問い・仮説・解釈、結論の文、等級の最終確認、状態を `確定` にすること。機械は下書きを出し、検査で誤りを落とす。
- **既存の規則を機械で守らせる**。「予測は撮る前に書く」「新しく確定にするのは等級 1〜3 のとき」「未確定の要素が 2 つ以上混ざる録画では結論を作らない」「残差を係数で埋めない」（AGENTS.md「事実と記録」）。いまは人が読んで守っているものを、検査に落とす。
- **読み取りは再現できる形にする**。読み方に名前と版を付け、同じ録画から同じ観測値を出し直せるようにする。目で数える値は無理に機械化せず、機械の値と区別が付けばよい。
- **既存の記録は書き換えない**。閉じた検証記録と観測値はそのまま。新しい流れは新しい検証から使い、旧の観測値はレシピの確認に使うだけにする（3.4 節）。

## 2. 全体の流れ

```
起案            npm run records:new -- verification "<題名>"      → records/verifications/V-NNNN-<名前>.md（調査中）
                npm run records:new -- claim --from V-NNNN        → records/claims/C-NNNN.json（仮説・推論）
予測の固定      npm run records:predict -- V-NNNN                 → records/predictions/V-NNNN.json（値・日付・commit）
撮る            人（撮影プロトコル）
取り込み        node tools/captures/intake.ts <元ファイル> --id NNN → リネーム・素性・records/recordings/NNN.json の骨
読み取り        node tools/captures/read.ts NNN --recipe <名前>    → records/observations/NNN.json に追記（method.tool にレシピ名と版）
判定の下書き    npm run records:check                             → 残差（いまのまま）+ 予測との突き合わせ・等級の候補・最小構成の警告
結論と結果      npm run records:new -- claim --from V-NNNN        → 根拠・等級の候補を埋めた仮説の結論。確定は人が書き換える
                検証記録の「結果」の表は生成ブロック、散文は人
閉じる          npm run records:close -- V-NNNN                   → 完了の条件の検査 → CI と同じ確認 → PR の題名
```

## 3. 各部の中身

### 3.1 起案（`records:new`）

- `verification "<題名>"`: `records/verifications/` の最大の番号 + 1 で採番し、README のひな形を状態 `調査中`・日付は今日で書き出す。短い名前は引数で受ける。
- `claim [--from V-NNNN]`: `records/claims/` の最大の番号 + 1 で採番する。`--from` があれば、話題はその検証記録の話題、`basis` にはその検証記録を `source` にする観測値の ID を並べ、`grade` は 3.5 節の候補、`state` は常に `仮説` で書く。無ければ空の骨（`state: 仮説`・`grade: 推論`）。
- 並行ブランチで同じ番号を使ったときの手順は design-stage20.md 3.6 節のまま。採番を機械にするのは、一覧を見て探す手間と、見落としを減らすため。

### 3.2 予測の固定（`records:predict`）

- **予測の条件**は `records/predictions/V-NNNN.json` に手で書く。観測値の `compare` と同じ語彙（`model`・`metric`・`args`・`setup`。`observations.ts` の `CompareSpec`・`CompareSetup`）で、比べる指標ごとに 1 行。仮説ごとにモデルの設定が違うとき（定義の `ref` の解釈が割れる、表の値の候補が複数など）は、`hypotheses` に名前と、その仮説で上書きする設定を書く。

```json
{
  "verification": "V-NNNN",
  "team": [271],
  "controlled": 1,
  "fixedSpec": true,
  "hypotheses": [
    { "id": "H1", "note": "…", "override": {} },
    { "id": "H2", "note": "…", "override": {} }
  ],
  "targets": [
    { "metric": "shotCount", "args": { "slot": 1 }, "setup": { "enemy": "range-bigarms-fire", "condition": "auto" } }
  ],
  "predicted": null
}
```

- コマンドは `team`・`setup` から sim（と calc）を回し、`predicted` に仮説 × 指標の値を、日付と `git rev-parse HEAD` と一緒に書き込む。手書きの部分（`hypotheses`・`targets`）は触らない。
- `predicted` が入ったファイルを、録画を取り込む前にコミットする。「撮る前に書いた」は、予測の commit の日付と観測値の `readAt`・録画の `date` の前後で検査する（3.7 節）。
- 検証記録の「予測」の節には、仮説ごとの見え方と見分け方（人の文）を書き、数値はこのファイルを ID で指す。数値を 2 か所に書かないのは「1 つの事実は 1 か所」の規則どおり。
- `override` で書けるのは `setup` の項目と、`--skill-levels`・`--near`・`--mid-far` など `sim-run.ts` の引数に対応するもの。モデルのコードや定義を仮説ごとに切り替える必要があるときは、このコマンドの範囲外で、検証記録に手で書く。

### 3.3 取り込み（`intake.ts`）

- 引数は元ファイルのパスと録画 id。命名規約（captures/index.md）でリネームし、`probe.ts` と同じ素性（長さ・フレーム数・fps・大きさ・sha256）を取り、`records/recordings/NNN.json` を書き出す。`team`・`target`・`mode`・`fixedSpec`・`conditionNote` は空で出し、`probe-result.ts` のキャラ同定の候補を標準出力に添える。人はそれを見て埋める。
- Drive への同期と台帳（`records:table`）はいまのまま。
- 録画の sha256 は 3.4 節のキャッシュの鍵にも使う。

### 3.4 読み取りのレシピ（`read.ts`）

- **レシピ**は「録画 → 観測値の列」の手順を 1 つのモジュールにしたもの。`tools/captures/recipes/<名前>.ts` に置き、`name`・`version`・`describe`（どの kind の観測値を何個出すか）・`run(recording, options)` を持つ。出力は `Observation[]` で、`method.tool` に `recipe:<名前>@<版>` を、`readAt` に今日を入れる。`source`・`compare` は引数で受ける。
- `read.ts NNN --recipe <名前> --source V-NNNN [--append]` は、レシピを回して `records/observations/NNN.json` に追記する。既に同じレシピ・同じ版の観測値があれば、値が同じなら何もせず、違えば差を出して止まる（人が `invalid` を付けるか、レシピの版を上げる）。
- 最初に起こすレシピは、V-0062〜V-0073 で繰り返した読み方。
  1. `hud-jumps`: HUD の総ダメージの増分（`hud.ts --mode jumps` の結果を、1 本 1 ファイルでキャッシュ）。
  2. `range-intervals`: 的のジャンプで区間に分ける（ジャンプの時刻は `aim.ts` の的の位置の跳ねか、増分の間隔の空きから）。
  3. `sg-pellets`: 区間ごとのトリガー数・当たったペレット数・会心・コアの分解。近は距離ボーナスで一意（V-0062・V-0069 の読み方）、スペック固定 OFF は会心の上乗せの形で一意（V-0070 の読み方）、それ以外は見積もり。出す観測値は `count`・`rate`・`hit`。
  4. `reload-segments`: `reload.ts --mode segments` の結果を `interval` の観測値に（V-0057・V-0068 の読み方）。
- **中間出力のキャッシュ**（hud の増分の列、aim の CSV）は、録画と同じ `E:/nikke_project_captures/derived/<録画 id>/` に置き、追跡しない。鍵は録画の sha256 とツールの版。クラウド環境では `fetch.ts` で録画を取り寄せてから作り直す。
- **目で数える値**（的の上の会心の数値、CORE HIT の文字など）はレシピの外。観測値の `method.note` に「目で数えた」と、見た画の作り方を書く。レシピの出す値と目の値を同じトリガーで突き合わせる検査（V-0073 の偶奇の確かめ）は、レシピの `check` として持てる。
- レシピの単体テストは、キャッシュの形の小さな fixture（数十トリガーぶん）を `tools/captures/recipes/__tests__/` に置いて回す。録画そのものは要らない。
- **旧の観測値での確認**: レシピで V-0062〜V-0073 の録画を読み直し、既存の観測値と同じ値になることを確かめる。違ったら、どちらが正しいかを調べて、新しい検証記録で訂正する（閉じた記録は書き換えない）。

### 3.5 判定の下書き（`records:check` の拡張）

- `records/predictions/` を読み、観測値（`source` が同じ検証記録）と突き合わせて、仮説 × 指標ごとに「観測値・予測・差・差 ÷ SE（観測値に `spread` の `ci95` があるとき）・一致か」を出す。一致の判定は観測値の `compare.tolerance` か `spread` で決め、どちらも無い指標は値を並べるだけにする。結果は `plan/verifications.md` のその検証記録の項に「予測との比べ」として生成する。
- **等級の候補**を機械で出す。上から順に当てはめ、最初に当てはまったもの（claims.md 冒頭の決め方）。
  1. `厳密一致`: 整数の指標（発の数・フレーム・ヒット数）で、差が 0。
  2. `反復実測`: 結論の `basis` に出てこない録画の観測値で、`compare` が許容内。`basis` の観測値 ID（`NNN-NN` の形）から録画の集合を取る。
  3. `データ明記`: 機械では判定しない（人が書く）。
  4. `単独実測`: 上に当てはまらず、許容内の観測値が 1 本の録画だけ。
  5. `推論`: それ以外。
     候補は `records:new -- claim --from` の `grade` に入り、`plan/verifications.md` にも出す。人が上書きできる。上書きしたときに検査で落とすのは、機械の候補より**上**の等級を人が書いたときだけ（機械が `単独実測` と見たものを `反復実測` にするには、`basis` に別の録画を書く必要がある）。
- **最小構成の警告**: 検証記録の録画の編成に、測りたい 1 体のほかに、`plan/skills.md` で「機構が確定」でないキャラが 1 体以上いれば、その検証記録に「未確定の要素が 2 つ以上。結論は作らない（AGENTS.md）」と出す。最初は警告だけで、落とさない（7 節の 5）。「機構が確定したキャラ」の判定は skills.md の対応状況（全効果・notes の結論が確定か範囲外）と、通常攻撃の条件（コア命中率・距離ボーナス・弾丸命中率）が的ごとに測られているか（`data/enemies.json` の表に値があるか）で機械的に出す。

### 3.6 結論と結果の下書き

- 結論は 3.1 節の `records:new -- claim --from V-NNNN`。`text`・`model` は人が書く。`state` は `仮説` で出す。人が `確定` に書き換えたとき、等級が 1〜3 でなければ `records:check` で落とす（いまは claims.md の冒頭に文で書かれているだけ）。
- 既存の結論を裏付けたとき（V-0073 の形）は、`records:new -- claim` ではなく、人が既存の結論の `basis` に観測値 ID と検証記録 ID を足す。等級の候補はこのときも出す（`basis` に新しい録画が入れば `反復実測`）。
- 検証記録の「結果」の節には、residuals.md と同じ生成ブロック（`replaceGeneratedSection`）で、予測と観測値の表を `records:check` が書き込む。表の下の散文（何が分かったか、数え直しの経緯）は人が書く。生成ブロックの外は検査で触らない。
- 「分かったこと・分からないこと」「次に撮るもの」は人の文のまま。

### 3.7 閉じる（`records:close`）

- `records:close -- V-NNNN` は、状態を `完了` にする前の検査を回す。
  - 冒頭の「結論」の各 ID が、この検証記録を `source` にする観測値を `basis` に持つか、`basis` にこの検証記録の ID を書いている。
  - 予測ファイルがあれば、その commit の日付が、録画の `date` と観測値の `readAt` のどれよりも前。無ければ「予測なし（探索）」と検証記録に書いてある。
  - 結論の `確定` の等級が 1〜3。
  - 「次に撮るもの」の節が空でない（「なし」でもよい）。
  - 最小構成の警告があるのに結論を作っている（7 節の 5 で落とすと決めたとき）。
- 通れば `npm run records:check` → `npm run format:check && npm run lint && npm run typecheck && npm test && npm run build` を回し、PR の題名の案（`<題名>（V-NNNN、C-NNNN）`）を出す。`roadmap.md` の更新と PR の作成は人（エージェント）が行う。

## 4. 自動化しないこと

- 問い・仮説・解釈を立てること。機械は予測値を出すだけ。
- モデルの値・定義・表を動かすこと。残差を見て自動で合わせるコマンドは作らない（「残差を係数で埋めない」）。
- 状態を `確定` にすること。機械は「確定にできる条件を満たす」と言うだけ。
- 目で数える読み取り。レシピは機械で決まる値だけを出す。
- 閉じた検証記録と観測値の書き換え。レシピで読み直して違えば、新しい記録で訂正する。
- roadmap.md の更新と PR の文。
- エージェント固有の手順（Claude Code のスキルで上の流れを順に案内するなど）は、この設計書の外。作るならエージェントのメモに手順と、ここへのポインタだけを置く（AGENTS.md「記録の置き場所」）。

## 6. 確かめ方

- A: 旧の観測値との一致（値が同じ。`method.tool` だけが違う）。違いが出たら、その箱は結論に使わず、別の検証記録で調べる。
- B〜D: 設計書の承認の後に始める新しい検証を 1 件、最初から最後までこの流れで通し、人が手で書いた部分と機械が出した部分を検証記録に分けて書く。流れの手戻りがあれば、この設計書の「経過」に書く。
- 既存の検査（`records:check`・`npm test`）は全件通ったまま。

## 7. 決めてほしいこと（推奨つき）

1. **予測の置き場所**: (a) `records/predictions/V-NNNN.json` を新しく作る / (b) 観測値のファイルに `use` を足して混ぜる。**推奨は (a)**。観測値は実測、予測はモデルの出力で、性質が違う。混ぜると照合と結論の根拠が濁る。
2. **予測の条件の書き方**: (a) 予測ファイルの手書きの部分（`hypotheses`・`targets`）に書き、同じファイルに機械が `predicted` を書き込む / (b) 検証記録の Markdown に埋める。**推奨は (a)**。1 ファイルで条件と値が揃い、Markdown の解析が要らない。検証記録からは ID で指す。
3. **中間出力のキャッシュの置き場所**: (a) `E:/nikke_project_captures/derived/`（追跡しない。Drive に同期） / (b) `records/derived/`（追跡する）。**推奨は (a)**。録画由来で公開しない。再現性はレシピの版と録画の sha256 で担保する。
4. **結論の状態**: 機械は常に `仮説` で出し、`確定` は人が書き換える。**推奨はこのとおり**。
5. **最小構成の検査の強さ**: (a) 警告だけ / (b) 警告のある検証記録が結論を作っていれば `records:check` で落とす。**推奨は (a) から始める**。旧の検証記録（多人数の録画で結論を作ったもの）に警告が出るので、まず数を見てから (b) に上げるかを決める。
6. **旧の観測値をレシピで読み直して違ったとき**: (a) 新しい検証記録で訂正し、旧の観測値に `invalid` を付ける / (b) レシピの側を旧の値に合わせる。**推奨は (a)**。レシピを合わせ込むと再現性の意味が無くなる。ただし違いの原因がレシピの誤りなら、レシピを直してから (a) を判断する。
