## Context

スペック固定 OFF の録画（迎撃戦の特殊個体・射撃場の実ビルド）を読むには、撮った時点のオーナーの育成（装備・OL・キューブ・コレクション・好感度・リサイクルルームの研究・スキル Lv）が要る。今はこれを、撮る日ごとに次の手作業で用意している（2026-10-24 の取得の時点）。

1. ShiftyPad を開いてオーナーがログインし、開発者ツールのコンソールに `scratch/blablalink/shiftypad-console.js` を貼る。ニケを 1 体開くと、ページが送るリクエストのヘッダを拾って 3 つの API を呼び、アカウントを特定できる値を除いた `shiftypad-raw-<日付>.json` をダウンロードさせる（2026-09-24 は Claude のブラウザペインとクリップボードで取った。11.1 節）。
2. `scratch/blablalink/convert.ts`（コミットしていない）で、`--build` の JSON（resourceId → `BuildInput` と `growth`）の `builds-all.json` に写す。前の取得の結果は上書きされる。
3. どの育成で読んだかは、録画の台帳の `conditionNote` に自由文で書く（例: 録画 0577「2026-10-24 に ShiftyPad から取った育成」）。

困ること:

- 取り方が毎回の手作業で（コンソールへの貼り付け・ページの `debugger` 文での一時停止の解除・ダウンロードの置き直し）、撮る日の手間が大きい。
- 写し方がコミットしたコードに無く、テストも無い。前の取得の結果が残らない。
- 前の取得との差が見えない。V-0462 は、企業の研究の Lv が古い育成データのまま 5 体を読み、防御力を誤った（V-0486 で棄却）。差が出ていれば、撮る前に気づけた。
- 録画とその育成の対応が自由文なので、ツール（読み取り・残差）が辿れない。
- クラウドと worktree のエージェントは所持を確かめられず、設計書ごとに「所持はオーナーに聞く」と書いている（[design-persona.md](design-persona.md)・[design-heal-vocabulary.md](design-heal-vocabulary.md) ほか）。

## 1. 目標

- 1 つのコマンドで「取る → アカウントの値を除く → `--build` の形に写す → 前回との差を出す」まで終わる。
- 写し方は core の純関数にし、テストで固定する（テストのデータは作った値。実データはコミットしない）。
- 録画の台帳が、読むのに使う育成のスナップショットを構造で指す。
- 守ること（11.1 節のまま）: パスワード・トークン・Cookie をツールが読まない・保存しない。API は読み取りだけ。アカウントのデータは公開リポジトリに入れない。

## 2. 取る（デスクトップ）

### 2.1 案

| 案          | 中身                                                                                                                                                                                                                                                          | 良い点                                                                                                     | 弱い点                                                                                                                    |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| A（推奨）   | `npm run build:fetch` が Playwright で、インストール済みの Chrome（`channel: 'chrome'`）を画面ありで開く。ユーザーデータのフォルダはリポジトリの外の専用のもの（パスは `private/`）。ログインが切れていれば、開いた窓でオーナーがログインするのをツールが待つ | 2 回目からはコマンド 1 つ。ファイルに直接書けるので、ページの CSP を避ける細工（クリップボード）が要らない | 依存（`playwright-core`）が増える。デスクトップで 1 回試すまで、ShiftyPad が自動操作のブラウザを拒まないかは分からない    |
| B           | ブックマークレット。ShiftyPad のページで押すと、ページの `fetch` を包んでヘッダを拾い、3 つの API を呼んで JSON をダウンロードさせる                                                                                                                          | 依存が増えない                                                                                             | ニケを 1 体開く操作が要る。受け取ったファイルを `npm run build:import` に渡す手順が残る。ページの作りが変わると壊れやすい |
| C（不採用） | クラウドの Routine で定期的に取る                                                                                                                                                                                                                             | 手が要らない                                                                                               | クラウドにログインの状態（Cookie かトークン）を置くことになり、1 節の「守ること」に反する                                 |

### 2.2 A の流れ

1. 専用のプロファイルで ShiftyPad を開く。ログインの画面なら、ログインし終わるまで待つ（ツールは入力に触れない）。
2. ページ自身が送る `GetUserCharacterDetails` などのリクエストを `page.on('request')` で拾い、同じヘッダを得る（11.1 節の手順と同じ。ヘッダは処理の間だけメモリに置き、書き出さない）。
3. ページの文脈（`page.evaluate`）で 3 つの API を呼ぶ: `Game/GetUserCharacters`・`Game/GetUserCharacterDetails`（20 体ずつ）・`Game/GetUserProfileOutpostInfo`。Cookie はブラウザが付けるので、ツールは値を見ない。
4. 応答から `intl_open_id` などアカウントを特定できる値を除いて、生のスナップショット（`private/builds/<YYYY-MM-DD>.raw.json`）に書く。生を残すのは、写し方の誤りが後で見つかったときに取り直さずに写し直すため。
5. 3 節の写し方を通し、4 節の差を出す。

- 同じ日に 2 回取ったら、`<YYYY-MM-DD>-2` のように枝番を付ける（撮影の合間に育成を変えた日のため）。

## 3. 写す（コミットするコード）

- `packages/core/src/shiftypad.ts`（純関数）の `toBuildSnapshot`: 生のデータとキャラの一覧（`data/characters/index.json`）から、スナップショットを作る。写し方は 11.1 節「写し方」を、次の 3 点を直してコードにした（13 節）。
  - キャラは `name_code` で引く。キャラのデータに CDN の `name_code` を `nameCode` として足した（`normalize.ts`）。
  - 装備の T9 / OL は、生のデータの `<部位>_equip_tier`（9 / 10）で決める。CDN の `ItemEquipTable` は引かない。
  - OL のオプション ID は 7 桁の `700GGLL`（11.1 節の `70GGLL` は書き誤り）。
- スナップショット（`private/builds/<名前>.json`）の形: `formatVersion`・`fetchedAt`・`synchroLevel`・`recycleRoom`（tid → Lv）・`characters`（resourceId → 1 体分）・`unmapped`。1 体分は `growth` と `BuildInput` の項目に `skillLevels`・`treasure` を足したもので、`--build` の 1 件と同じ形。
- `sim-run.ts` の `--build` は、スナップショットをそのまま読む（`buildEntriesOf`）。1 件の `skillLevels` をスキル Lv の既定にし、`--skill-levels` が指定されていればその枠はそちらを優先する。
- 宝物の段階: API の `favorite_item_lv` から決める（`treasurePhaseOfLevel`。Lv 1・2 = 段階 2・3。C-0744、2026-10-30 に追記）。Lv 0 は画面で見ていないので決めず `phase: null` とし、所持の一覧と `sim-run.ts` に「段階は未確定（`--treasure` で指定する）」と出す（AGENTS.md のプレースホルダーの規則）。`sim-run.ts --build` は、`--treasure` の無い枠にスナップショットの段階を使う（スキル Lv と同じく、スペック固定では使わない）。写し方を直す前のスナップショットは `npm run build:import -- --rebuild` で写し直す。
- 写せない値（データに無いキャラ、T9 / OL でない装備、知らないオプション ID、R / SR / 宝物でないコレクション）は、黙って捨てずに `unmapped` に出す。取り込みの道具は、育成入力として通らない値（`validateBuild`）も合わせて出す。
- テスト（`packages/core/src/__tests__/shiftypad.test.ts`）: 作った生のデータ（3 体。OL・オプションの空き・T9・企業装備・キューブ・R / SR のコレクション・宝物・好感度 0）で、写した結果・`validateBuild`・写せない値・アカウントの欄の除去・差・所持の一覧を固定する。

## 4. 前回との差

- 取り込むたびに、直前のスナップショットとの差を出す（標準出力と `private/builds/<名前>.diff.md`。`diffSnapshots`）。
  - アカウント全体: シンクロ Lv・リサイクルルームの研究の Lv
  - 所持の増減
  - キャラごと: 凸・コア・好感度・装備（OL の行を含む）・キューブ・コレクション・スキル Lv と、`computeCombatAttack` で出した戦闘中の攻撃力（バフ前）
  - アカウント全体の値の変化だけで攻撃力が変わったキャラは、まとめて別の一覧にする
- V-0486 の見落とし（研究の Lv）は、2026-10-06 → 10-24 の差の「アカウント全体」の行に出る（13 節）。

## 5. 置き場所

- `private/builds/`（AGENTS.md「記録の置き場所」で、育成状況は `private/`）。生のスナップショットは 1 回で数百 KB 以下の見込みで、クラウドの始めのフックが中身まで取る 1 ファイルの上限（`tools/drive/cloud-sync.ts` の 5MB）に収まる。クラウドのセッションも、始めのフックで降りてきたものを読める。`drive:sync` の `private` の対は 2026-10-29 まで `*.json` をすべて外していて、`builds/` のスナップショットが Drive に上がっていなかったので、外すのを直下の `*.json`（鍵と `build-fetch.json`）に絞った。
- 名前は取得の日（日本時間）。同じ日に別の取得があれば `<日付>-2`、`-3` …（撮影の合間に育成を変えた日のため。`tools/builds/import-lib.ts`）。同じ取得をもう一度取り込むと、同じ名前に書き直す。
- 今ある取得済みのデータ（`scratch/blablalink/` の 2026-09-24・10-06・10-24 の 3 回分）は、どれも生のデータの形のまま取り込める（13 節）。デスクトップで `npm run build:import` に 1 回ずつ渡して `private/builds/` に置く。`scratch/blablalink/` はそのまま残す。

## 6. 録画との結び付け

- 録画の台帳に `buildSnapshot`（`"2026-10-24"` か `"2026-10-24-2"`）を足す。スペック固定 OFF（`fixedSpec` が `true` でない）で、実ビルドの録画に書く。既存の録画は書き直さない（`conditionNote` の自由文のまま）。
- `tools/captures/intake.ts`: 取り込む録画の日付以前で最新のスナップショットを既定にして聞く。その日に取ったスナップショットが無ければ「撮った日の育成が無い（最新は YYYY-MM-DD）」と知らせる。
- `records:check`: `buildSnapshot` の形だけを確かめる（スナップショットの実体は `private/` にあり CI から見えないので、有無は確かめない）。
- 読み取りのレシピ・残差で使う育成は、この欄から引ける（使い方は、要る検証が出たときに足す）。

## 7. いつ取るか

時刻ではなく、出来事で取る（推奨）。育成データが要るのはスペック固定 OFF の録画を読むときと所持を確かめるときだけで、決まった間隔で取っても使われない。

- スペック固定 OFF の撮影の日に、撮る前に取って `npm run build:import` で取り込む（`protocol.md` に 1 行。段 2 の後は `npm run build:fetch`）。
- 育成を変えたとき（オーナーが任意で）。
- 取り忘れは、6 節の `intake.ts` の知らせで気づく。

代替: Windows のタスクスケジューラで週 1 回回す（ログインが切れていたら、取れなかったことだけ知らせる）。12 節 5。

## 8. 所持の一覧

- 取り込むたびに、いちばん新しいスナップショットから所持の一覧（`private/roster.md`。resourceId・キャラ名・凸・コア・スキル Lv・キューブ・コレクション / 宝物）を作り直す（`rosterMarkdown`）。
- 所持の一覧の正は `roster.md`（生成）にする。`private/owner.md` の所持の節は、オーナーがデスクトップで `roster.md` を指す形に直す（`private/` はエージェントからはオーナーに渡して足すもの。AGENTS.md「記録の置き場所」）。
- これで、クラウドと worktree のエージェントも、撮影の候補が所持キャラかを確かめられる（クラウドは始めのフックで `private/` が降りるので）。`protocol.md` の所持の一覧の行を `private/roster.md` に直した。

## 9. 規約とアカウント

- 読むのはオーナー自身のアカウントの、ShiftyPad の画面に出るのと同じデータで、頻度は撮影の日に 1 回程度。書き込む API は呼ばない。
- [references.md](references.md) の ExiaInvasion は、Blablalink の自動取得に規約違反の可能性があると README に書いている。今の手順（11.1 節）も同じ API を呼んでいるので、ルーティン化で増えるのは手間の削減だけで、呼ぶ API と頻度は変わらない。自動操作のブラウザを使うこと（案 A）は、12 節 1 でオーナーが決めた。

## 13. 段 1 の実装（2026-10-29）

- キャラのデータに `nameCode` を足した（`CharacterIndexEntry`。`npm run fetch-data` で取り直し、`fetch-data:diff` で `nameCode` のほかの差が無いことを確かめた）。
- 写し方（3 節）・差（4 節）・所持の一覧（8 節）は `packages/core/src/shiftypad.ts`、取り込みの道具は `tools/builds/import.ts`（`npm run build:import -- <生の JSON>`。写し方を直したときは `-- --rebuild` で `private/builds/` の生のデータを全部写し直す）。
- 今ある 3 回分の生のデータ（`scratch/blablalink/`）で確かめたこと:
  - 装備の `<部位>_equip_tier` は、3 回分の全所持キャラの全部位で CDN の `ItemEquipTable` の `item_rare` と一致し、部位（`item_sub_type`）とクラスも一致した。このため、写し方は装備の表を引かない。
  - 2026-10-24 の取得を写した結果は、`convert.ts` が作った `builds-all.json` と全所持キャラで一致した（スキル Lv と宝物は `builds-all.json` に無いので比べていない）。写せない値は 3 回分とも無かった。
  - 2026-10-24 のスナップショットを Lv200 にして出した A1 は、V-0486 に値が書いてある 4 体（ソルジャーE.G.・ココア・I-DOLL・フラワー・リター）で、そこに書いてある値と端数まで同じだった。`sim-run.ts --build` で出したリターの戦闘中の攻撃力も、V-0486 のキャラ画面の値と同じだった。
  - 2026-10-06 → 10-24 の差に、リサイクルルームの研究の Lv の上がりが出る（V-0486 の見落とし）。
- 道具がクラウドで書いた `private/builds/` は Drive に戻していない（このセッションは始めのフックで `private/` を取れておらず、応答の終わりの同期は動かない）。デスクトップで 5 節のとおり取り込み直す。

## 14. 段 2 の実装（2026-10-29）

- `npm run build:fetch`（`tools/builds/fetch.ts`）。案 A の流れ（2.2 節）のとおり。依存に `playwright-core` を足した（ブラウザは落とさない）。
  - 専用のユーザーデータのフォルダのパスは `private/build-fetch.json` の `userDataDir`。無ければ、ホームの下の既定のパスで作る。リポジトリの中のパスは拒む。
  - ヘッダは `context.on('request')` で拾う（ログインの窓や別のタブで送られても拾えるよう、ページでなくコンテキストで聞く）。`request.headers()` は Cookie などの security に関わるヘッダを返さないので、ツールは Cookie の値を見ない（`allHeaders()` は使わない）。ページの `fetch` / XHR は包まない。
  - 3 つの API は、リクエストを送ったページの文脈で `page.evaluate` から呼び、応答の JSON を戻り値で Node 側へ受け取る（`exposeBinding` は要らなかった）。応答の `code` が 0 でなければ失敗にする。
  - 生のデータの形はコンソールのスクリプトと同じ（`{ fetchedAt, source, outpost, characters, details, stateEffects }`）。応答から配列・オブジェクトを深さ優先で探す処理とヘッダの選び方は `tools/builds/fetch-lib.ts`（純関数。テストは `fetch-lib.test.ts`）。
  - 取り込み（名前・写す・差・所持の一覧）は `tools/builds/store.ts` に切り出し、`build:import` と共有した。
