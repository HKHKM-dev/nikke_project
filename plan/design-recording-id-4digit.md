## Context

録画の番号は、001〜063 の 2 桁の時代（ファイル名は `20260922-01_…`）と、064 からの 3 桁が混ざっている。番号が 1000 を超えると 4 桁も混ざる（1 本ずつの振り直しの道具は 4 桁まで扱える）。オーナーの指示（2026-10-25）で、番号を `0001` から `9999` までの 4 桁にそろえる。

数として同じ番号に変えるので、1 本ずつの振り直しと違い、**置き換え漏れがあっても別の録画を指すことはない**（`124` と `0124` は同じ録画と読める）。この性質を使って、置き換えの範囲と、人が見る所の扱いを決める（3・4 節）。

## 3. 置き換える形

1 本ずつの振り直し（[design-recording-renumber.md](design-recording-renumber.md) 4 節）の「確かさの高い形」を、全部の録画について一度に置き換える。番号は、`records/recordings/` にある録画の番号（数として 1〜612）だけを 4 桁にする。

| 形                                                                                   | 置き換え                                                                                       |
| ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| 「録画」の後の番号の並び（「録画 124・178」「録画（400〜402）」「録画: 046、055」）  | 並びの中の 2〜3 桁の録画の番号を 4 桁にする（「録画 41」→「録画 0041」）                       |
| バッククォートの番号の並び（`` `124` ``・`` `064`〜`066` ``）                        | 3 桁だけ（2 桁のバッククォートは観測値の略記 `` `046-03`〜`06` `` の `06` などで、録画でない） |
| 観測値の ID（`124-01`）                                                              | 頭を 4 桁に（観測値のファイルにある ID だけ）                                                  |
| ファイル名（`<YYYYMMDD>-124_`・`<YYYYMMDD>-41_`・`124_f<フレーム>`・`derived/124/`） | 番号の部分を 4 桁に                                                                            |
| `records/` の下の JSON の文字列 `"124"`                                              | `"0124"`                                                                                       |

- **範囲は展開しない**。全部の番号を同じ規則で 4 桁にするので、順が保たれる（`` `064`〜`066` `` → `` `0064`〜`0066` ``）。録画をまたぐ観測値の範囲（`` `174-06`〜`177-06` ``）も、両端を 4 桁にすれば意味は変わらない。1 本ずつの道具の、範囲の展開とまとめ直し・人が見る所はここでは要らない。
- `records/` にない番号（テストの例の 9 百番台・フレーム数「録画 2245」など）は変えない。
- 置き換えは何度回しても同じ結果になる（4 桁の番号は形に当たらない）。

## 4. 置き換えない所

- **素の番号**（「録画 124 と 178」の「178」・表の中の番号など）。数として同じ録画を指すので、残っても読める。21,623 か所を人が見るのは割に合わないので、場所も出さない。[captures/index.md](captures/index.md)「命名規約」に「2026-10-25 より前の文の 2〜3 桁の番号は、同じ数の 4 桁の録画」と 1 行書く。
- **テストのコード**（`__tests__/`・`*.test.ts`）。例の ID（`'101-01'` と `recording: '101'` の組など）の片方だけが置き換わると、テストの意味が変わる。実在の記録を読むテスト（`records/observations/057.json`・`obs('057-10')`・`recordingMap(file).get('287')` など）は、`npm test` で落ちる所を手で直す。
- `L-` の旧の録画（[design-recording-renumber.md](design-recording-renumber.md) 9 節と同じ）。

テスト以外のコード（コメント・スキル定義の notes）は置き換える。

## 5. リポジトリの外の名前の変え方

1 本ずつの道具の `planCaptureRenames`・`applyCaptureRenames`（`tools/captures/renumber-files.ts`）を、全部の録画について `NNN` → `0NNN` で回す。

- 先に全部の録画の計画を作り、止める理由（移す先が既にあるなど）が 1 つでもあれば、何も変えずに止める。
- E: で名前を変え、Drive では `rclone moveto` で Drive の中の改名にする（上げ直さない）。約 870 回の `rclone moveto` になるので、数十分かかる。
- 途中で失敗したら、そこで止めて、変えたものを出す。回し直すと、変えた後の名前を「もう変えてあった」として飛ばして続ける（1 本ずつの道具と同じ）。
- **Drive の同期（bisync）の削除の上限**: 双方向同期は、片側で半分を超えるファイルが消えると止まる（`--max-delete 50`。[design-cloud-environment.md](design-cloud-environment.md) 4 節）。両側で同じ名前に変えても、前回の一覧と比べると captures の対のほぼ全部が消えて新しくできたように見える。名前を変えた後に、captures の対だけ `npm run drive:sync -- --pair captures --resync` を回す（両側が同じなので、送るものは無い。先に `--dry-run` で確かめる）。
- `plan/captures/backup-log.md` に 1 段落を足す（いつ・何本・E: と Drive で変えた数）。

## 6. 道具

- `npm run records:renumber -- --pad-all [--dry-run]` を足す。1 本ずつの振り直しと同じスクリプトの中で、確かめ → E:・Drive の名前 → リポジトリの中の置き換え（`git mv` と文の置き換え）→ 報告、の順。
- 純粋な部分は `renumber.ts` に `padRecordingsInText(text, ids, opts)` を足す（3 節の形）。
- **これからの番号は 4 桁だけにする**:
  - `intake.ts` の `--id` は 4 桁の数字に限る。次の空き番号の案内も 4 桁。
  - どれかのブランチが足した番号との比べ（`recordingIdsInBranches`）は、数として比べる（ブランチの歴史には 3 桁の `124.json` が残るため）。`records:renumber` の新しい番号の確かめも同じ。
  - 1 本ずつの振り直しの新しい番号も 4 桁に限る。古い番号は 2〜4 桁を受ける（素の番号の残る古い文を読むため）。

## 7. 手順

1. ブランチで `records:renumber -- --pad-all --dry-run` を回し、件数と止める理由が無いことを見る（オーナーに出す）。
2. 承認の後、`npm run drive:sync` で E: と Drive をそろえてから、`--pad-all` を回す。
3. `npm run drive:sync -- --pair captures --resync --dry-run` で送るものが無いことを見て、`--resync` を回す。
4. `records:table`・`records:check`・`records:minimal` で生成物を作り直し、テストの落ちる所を手で直して、CI と同じ確認を通す。
5. 1 本の PR で main に入れる。**この PR が入るまで、ほかのブランチで録画・観測値・検証記録を足さない**（ほぼ全部の記録のファイルが変わるので、衝突する）。
6. 入った後に main から外れて残っているブランチは、取り込む前にそのブランチで `--pad-all` を回す（何度回しても同じなので、main と同じ変更になり、git が同じ変更としてまとめる。E: と Drive は「もう変えてあった」になる）。

## 11. 決めること

1. 置き換えの範囲を 3 節の形に限り、素の番号は置き換えず、場所も出さない（4 節）。**推奨: そうする**。理由: 数として同じなので読み違えが起きない。2 万か所の多くはフレーム数・値の誤検出で、見る手間に見合わない。
2. 2 桁の時代のファイル名も 4 桁にする（`20260922-01_SR_delta.mp4` → `20260922-0001_SR_delta.mp4`）。**推奨: そうする**（オーナーの指示の `0001`〜 のとおり。1 本ずつの振り直しの 10.1 節の 3 と同じ扱い）。
3. 凍結の文書（`plan/verification.md`・`plan/captures/legacy-usage.md`・`roadmap-archive.md` ほか）の中も置き換える。**推奨: そうする**（1 本ずつの振り直しの 10.1 節の 3 と同じ。参照がいまの名前を指すように）。
4. テストのコードは自動では置き換えず、落ちる所だけ手で直す（4 節）。**推奨: そうする**。
5. 道具が E: と Drive の名前を変え、その後に captures の対を `--resync` する（5 節）。**推奨: そうする**。
