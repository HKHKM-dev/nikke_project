## 1. 語彙

### 1.1 対象の絞り込み `targetClass`

- `targetClass: "Attacker" | "Defender" | "Supporter"`（火力型・防御型・支援型。`CharacterData.class`）。対象の枠のキャラのクラスで絞る。武器種（`targetWeapon`）・コード（`targetElement`）と同じ形で、書ける効果と対象もそれと同じにする（論点 2）。
- 自分もクラスが合えば対象に入る（「味方全体」は自分を含む。エヌ：ミラクルフェアリーは支援型なので、S1 の支援型への回復は自分にも付き、バーストの火力型への効果は自分に付かない）。
- 編成で決まる静的な絞り込みなので、発火のたびの文脈は要らない（`skills/targets.ts` の `matchesTargetFilter` に足す）。最小構成の検査も、武器種・コードと同じく「対象のクラスが観測した枠と違う」で外す。
- 画面: 効果の出どころに「（火力型の味方）」のように出す。

### 1.2 攻撃速度 `attackSpeed`

- 比率の stat。射撃に効く stat（`FIRING_STATS`）に入れ、1 パス目の射手が件を読む（`frame/firing.ts` の `FiringBuffs`）。
- 効かせる所: レートを蓄積して撃つ武器の、マガジンの中の発と発の間だけ（`cadence.ts` の `rateAfterShots` の rpm を、`frame/shooter.ts` の蓄積と `cadence.ts` の `simulateShotFrames` で読む）。リロード（`reloadChunkFrames`）・リロード明けの 1 発目の待ち（C-0148）・構え（C-0114）には効かせない（論点 6。撮影で、変わらないことも見る。V-0458）。
- 式は撮影で決める（V-0458）。候補は 2 つで、どちらも 1 フレーム 1 発（`MAX_RPM`）で頭打ち:
  - (a) レート × (1 + Σ)（発と発の間 ÷ (1 + Σ)）
  - (b) 発と発の間 × max(0, 1 − Σ)（レート ÷ (1 − Σ)。リロード速度・チャージ速度と同じ形。C-0013）
- 撮影の前は、リロード速度・チャージ速度の `SPEED_FORMULA` と同じく切り替えの定数で持ち、両方の予測を出す。撮影の後に、合った方に決める（合わない方の枝は消す）。
- 決まったこと（2026-10-20。V-0458 の録画 510〜512。C-0600）: (a)。撮影が実装より先に済んだので、切り替えの定数は作らず、(a) だけを入れた（`frame/firing.ts` の `FiringParams.rateScale` = 1 + Σ を `cadence.ts` の `rateAfterShots` で掛ける）。リロードとリロード明けの 1 発目までは変わらなかった。
- 書ける対象: `targetWeapon` が AR・SMG・SG の効果だけ。チャージ武器（チャージの秒の式）と MG（立ち上げのレート）への効き方は、使い手がいないので決めない（書けないようにする）。

### 1.3 状態の間だけ効く `while`（PR 2）

トーブ S2 の「自分が応急改造のフルスタック時のみ、味方全体に…「持続」」は、いまの語彙では書けない。条件の `selfState`（段 1 の 1.1 節・段 3 の 1.4 節）は発火の瞬間だけ見る（付いた後に外れても維持の終わりまで続く）。状態の中身（`contents`）は状態の持ち主にしか効かず、トーブ S2 は自分の状態を見て、味方全体に効く。分類の別紙 4.6 節の「続いている間の条件」で、「他人の状態・HP などは語彙なし」としていた所。形は [design-named-state.md](design-named-state.md) 8.4 節の「他人の状態の間だけ効く」（`while`）と、[design-stage11-modernia.md](design-stage11-modernia.md) 11.2 節の 6（`while?: { selfState }`。窓の積）で見込んでいた。

- **形**: `passive` に `"while": { "selfState": { "state": "<id>", "stacks": "full" } }`。中身は条件の `selfState` と同じ形（`stacks` は `'full'` か N、`stacksRef` も書ける。`present: false` は書けない）。説明文の「自分が〈名前〉（のフルスタック）状態の時のみ、…「持続」」の行に書く。
- **意味**: 効果を出した枠（自分）にその状態が付いていて、スタックの条件を満たすフレームの間だけ、対象に効く（窓の積）。条件が外れたら効かなくなり、また満たせばまた効く。
- **件**: 対象ごとに件の列を作る。件は、自分のその状態の段 1 の件（出どころは問わない。条件の `selfState` が見るものと同じ。家族の根なら家族のどの状態でも）から作る: `stacks` が N なら段 N 以上の件の和、`'full'` なら付与の上限の段の件の和、`stacks` が無ければ状態の件の和。状態の件が作り直されたら作り直す。段は 1.5（段 1 の件を読む）。
- **解決**: 状態の中身と同じく、状態の窓の間だけ効く件の効果にする（`whileState` を持つ形。名前の付いた状態の設計書 8.4 節の「中身と同じ `whileState` に解く」）。違いは、窓が効果を出した枠の状態の窓で、効く相手が効果の対象であること。常時の値（`resolvePassiveStates`）には入れない。
- **読む側**: 射撃に効く stat（攻撃速度）は 1 パス目の射手が件を読み（`firingBuffsAt`）、会心率▲などは区間（値の小片）が読む。
- **書けないもの**: 静的な状態（常時の効果で書く）・`timed`（使い手がいない）・条件 `selfHp` との組み合わせ・順位の対象（`topAttack` など）。
- **画面**: 効果の出どころに「（応急改造 フルスタックの間）」のように出す。

## 5. 論点

決定（2026-10-18、オーナー）: 論点 1〜4 は推奨どおり。論点の文は諮った時のまま。

1. **段 9 の範囲**（決定: 推奨どおり）
   - 推奨: 定義のあるキャラに使い手がいるクラスでの絞り込み（PR 1）と攻撃速度（PR 2）だけを段 9 で足す。ほかの家族は、使い手を定義する時にその PR で足す（確かめ方は 3 節）。
   - 代わりの案: 段 9 の中で、ほかの家族の使い手（ツバイ・エード：エージェントバニーなど）も 1 体ずつ新しく定義して撮る。
2. **クラスでの絞り込みを書ける範囲**（決定: 推奨どおり）
   - 推奨: 武器種・コードの絞り込みと同じ（自分のほかの対象の、常時・持続・付与・即時の効果）。キリ・ビスケット・D（未定義）の使い方もこの形で書ける。
   - 代わりの案: 使い手のいる `timed` と `heal` だけに書けるようにする。
3. **エヌ：ミラクルフェアリーの回復を PR 1 で定義するか**（決定: 推奨どおり）
   - 推奨: 定義する（説明文の読み）。回復を受けた時の効果を持つ味方がいない編成では値は変わらない。撮影でアスカ（火力型）にバーストの回復が付くかも見られれば一緒に確かめる。
   - 代わりの案: 攻撃力▲だけを定義し、回復は未対応の notes のまま（回復を受けた時の効果を持つ味方との撮影の時に足す）。
4. **PR の順**（決定: 推奨どおり）
   - 推奨: PR 1 → PR 2（PR 1 は段の最初の使い手。PR 2 は攻撃速度の式を撮って決めるので、撮影の計画が大きい）。
   - 代わりの案: 2 つの撮影を 1 回にまとめる（編成は別なので、録画は別）。

PR 2 の論点（2026-10-19 に起案。2026-10-20 にオーナーが論点 5〜7 を推奨どおりに決めた）:

5. **「フルスタック時のみ…「持続」」の書き方**（1.3 節）（決定: 推奨どおり）
   - 推奨: `passive` に `while` を足す（自分の状態の件との窓の積）。説明文の読みのまま書け、ほかの「〜の時に限り」「〜の時のみ」（自分の状態・スタック数を見て、ほかの味方に効く行）にもそのまま使える。
   - 代わりの案: いまの語彙で近似する（`timed`・`{ applied: "temporaryModification" }`・条件 `selfState` のフルスタック・維持 5 秒）。応急改造の付き直しと維持が同じ 5 秒で、スタックの数え直しが「全スタックを数え直す」なので、トーブではフルスタックの窓と同じ件になる見込み。ただし、維持の秒とスタックの数え方が同じことに頼った近似で、段 1〜3 で書き直してきた近似と同じ種類になる。
6. **攻撃速度が効く所**（1.2 節）（決定: 推奨どおり。式は撮影で (a) に決めた）
   - 推奨: マガジンの中の発と発の間（レートの蓄積）にだけ効かせ、式は撮影で (a)・(b) から決める。リロード・リロード明けの待ち・構えは変えない（撮影で変わらないかも見る。V-0458）。
   - 代わりの案: リロードの長さにも効かせる（説明文にも撮影にも根拠が無い）。
7. **基礎版の S2**（2.2 節）（決定: 推奨どおり）
   - 推奨: notes のまま（理由を「基礎版の応急改造は確率のきっかけの S1 から付き、モデルでは付かない」に書き換える）。基礎版を定義しても、モデルではどの編成でも効かない。
