# バーストの着弾の遅れと、同じ発動の中の効果の順

- 日付: 2026-10-01
- 状態: 承認（2026-10-02。オーナーが 6 節の 1〜5 を推奨どおりに決めた）
- 関連: [design-damage-taken.md](design-damage-taken.md) 4 節、[design-stage8.md](design-stage8.md)（バースト使用の回数トリガー・段階の読み）、[skills-guide.md](skills-guide.md) 1.4 節、[roadmap.md](roadmap.md) 今後の課題「バーストの効果の着弾の遅れと、同じ発動の中の効果の順」
- 検証記録: V-0075（イサベルの受けるダメージ▲。完了）、V-0078（イサベルの遅れの値。完了。C-0165）
- 結論: C-0160〜C-0163（イサベル）、C-0138（クルミの▲の窓）

## 0. 要約

- イサベル（231）のバーストは、モデルと実機で 2 つ合わない。どちらも、いまの語彙では書けない。
  - **着弾の遅れ**（C-0162）: バーストの効果（バーストスキルダメージ・▲・段階の追加ダメージ・S1 の段階のバフ）は、発動の瞬間ではなく、バーストスキルダメージの着弾から効く。モデルは発動フレームに置いている。
  - **同じ発動の中の順**（C-0163）: 段階 2・3 の追加ダメージには、同じ発動の段階 1 の▲が乗る。同じ発動の S1 のバフと、バーストスキルダメージへの▲は乗らない。モデルは、同じ発動の効果をどれも乗せない。
- 提案
  - **案 A**: バーストの発動から、バーストの倍率ダメージのヒットと、「バーストスキルを使用した時」の効果の発火を、それぞれキャラごとの遅れだけ後ろにずらす。遅れはヒットと効果で別に持ち（ヘルムは効果がヒットより先に出る。1.2 節）、キャラごとの実測値の表に置く。既定は 0（いまと同じ）。
  - **案 B**: バーストのスロットに「下位効果のスタック適用」を表す印 `sequential` を足す。印のあるスロットでは、同じ発動の効果を書いた順に当て、後の倍率ダメージは前の効果で付いた窓を見る。
- どちらも、書かない定義・表に無いキャラではいまの挙動のまま（4 節）。変わるのはイサベルだけ。

- 発動の直前のバフで計算する規則（`BURST_HIT_USES_PRE_ACTIVATION_BUFFS`）は、ラピ（録画 018）・ノワール（019）・ドレイク（037）・イサベル（038。C-0160）で合っている。ヒットの直前と読み替えても、この 4 体の値は変わらない見込み（どれも、自分のバーストで付くバフが乗らないことを見た例）。

  - 遅れはキャラによって違う（クルミはほぼ 0、イサベルはフルバーストの半ばまで遅れる）。全キャラ共通の定数にはできない。
  - ヒットと効果は、同じだけ遅れるとは限らない（ヘルムは効果が先）。1 つの「着弾」の時刻にまとめず、ヒットの遅れと効果の遅れを別に持つ。

## 2. 案 A: ヒットと効果の発火の遅れ

### 2.1 考え方

- バーストの 1 回の発動に、3 つの時刻を持たせる。
  - **発動**: いまの `BurstActivation.frame`。チェーンの段の進み・CT の始まり・フルバーストの始まり・「バースト N 段階突入時」・`burstUsers` はこちら。
  - **ヒット**: 発動 + ヒットの遅れ。バーストの倍率ダメージ（`burstDamage`）が出る。
  - **効果の発火**: 発動 + 効果の遅れ。そのキャラの「バーストスキルを使用した時」（トリガー `burstUse` と `{ count: burstUse }`）で発火する効果が出る。
- イサベルは、ヒットと効果の発火が同じフレーム（着弾）で、ヒットが先（2.2 節の順）。ヘルムは、効果の発火がヒットより先。
- 遅れが 0 のキャラは、3 つとも同じフレームで、いまと同じ。

### 2.2 何をずらすか

| もの                                                                  | 時刻       | 理由                                                                                                         |
| --------------------------------------------------------------------- | ---------- | ------------------------------------------------------------------------------------------------------------ |
| `burstDamage` のヒット                                                | ヒット     | `038-07`・`038-17`                                                                                           |
| 自分の `burstUse`・`{ count: burstUse }` で発火する効果（全スロット） | 効果の発火 | ▲（`038-15`）と S1 の段階のバフ（凍結した記録）。S1 は別スロットだが「バーストスキルを使用した時」で発火する |
| 回数の数え方（`atLeast`）                                             | 効果の発火 | 発火と同じ時刻で数える（段階は同じ発動で上がる前を見る。C-0160）                                             |
| チェーン・CT・フルバーストの窓・段階突入・`burstUsers`                | 発動       | フルバーストの長さ（C-0011）と段の間隔（C-0073）は発動で合っている                                           |
| ほかのキャラの `fullBurstStart` など                                  | 発動       | フルバーストの始まりはチェーンの出来事                                                                       |

- 「発動の直前のバフで計算する」（`BURST_HIT_USES_PRE_ACTIVATION_BUFFS`）は、「**ヒット**の直前のバフで計算する」と読み替える。ただし、同じ発動の効果がヒットより先に発火するキャラ（ヘルム）では、その効果がヒットに乗るかが決まっていない。表の行ごとに「同じ発動の効果をヒットに乗せない」を既定にし、乗ると分かったキャラだけ行に書く（論点 5）。
- イサベルは、ヒットと効果の発火が同じフレームで、そのフレームに付く窓（同じ発動の▲・S1 のバフ）は直前の区間に入らないので、`038-07`〜`038-10` はいまと同じ値になる。
- フルバースト補正（`SKILL_HIT_FULL_BURST_BONUS`）は、いまと同じく出たフレームがフルバースト中かで決める。イサベルの着弾はフルバーストの中なので、段階の追加ダメージの補正は変わらない。

### 2.3 遅れの値の置き場所

| 案                            | 中身                                                                                                                                                 | 長所                                                                                                                                   | 短所                                                                                |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| **A-1 実測値の表（推奨）**    | `burst/landing.ts` に `MEASURED_BURST_LANDING_DELAY`（resourceId → ヒットの遅れ・効果の遅れ（ゲーム内のフレーム数）・結論の ID）。表に無いキャラは 0 | skills-guide.md 1.5 節の「実測でしか決まらない値は、表の 1 行にして結論の ID を添える」と同じ形（紅蓮BS の `MEASURED_CHARGE_CADENCE`） | 表に無いキャラの 0 は「未測定」で、正しいとは限らない（6 節の論点 3）               |
| A-2 定義の burst スロットの欄 | `data/skills/231.json` の burst に `landingDelayFrames`                                                                                              | 定義とまとまる。ヘルムの `gaugeHits`（実測のフレーム数）の前例がある                                                                   | 定義は説明文の値を `ref` で指すのが原則。説明文に無い値を定義に増やす               |
| A-3 全キャラ共通の定数        | 1 つの値                                                                                                                                             | 小さい                                                                                                                                 | クルミの▲はバーストを使った瞬間から乗る（C-0138）ので、キャラによって違う。採れない |

- 単位はゲーム内の時間のフレーム（モデルのフレーム）。動画のフレームからの換算は、フルバーストの入りの止まり（C-0069。`videoFrameOf`）を差し引く。
- CDN のデータに演出の長さの値があれば、それを使う案もある。いまは見つかっていないので、実測で決める。

### 2.4 実装の場所（sim → calc の順。共通の部分が多い）

1. `burst/schedule.ts`: `BurstActivation` に `hitFrame`・`effectFrame`（発動 + それぞれの遅れ。戦闘時間を超えたら持たない）を足す。時刻表を作る `burst/controller.ts`（動的）と固定サイクルで埋める。
2. `skills/triggers.ts`: 出来事 `FrameEvents` に `burstEffects`（そのフレームに効果が発火した発動）を足し、`burstUse` の判定を `activations` から `burstEffects` に替える。`replayEvents` も同じ。
3. `frame/firstPass.ts`: 1 パス目のフレームループで、効果の発火のフレームの `burstEffects` を出す（回復の `pendingHeals`・ゲージの `pendingGauge` と同じく、先のフレームに積んでおく）。射撃に効く窓（装弾数・使用武器の変更など）と即時効果（CT 短縮）も、`burstUse` なら効果の発火から。
4. `sim/engine.ts`・`calc/model.ts`: バーストの倍率ダメージを、`hitFrame` で `burstSnapshotState(…, hitFrame, …)` を使って出す。
5. 画面: 表に載ったキャラのバーストに「ヒットは発動の X 秒後・効果は Y 秒後（実測。C-NNNN）」、表に無いキャラは何も出さない（6 節の論点 3）。

### 2.5 端の扱い

- ヒットや効果の発火が戦闘の終わりより後なら、それは出ない（実機と同じとみなす。確かめていない）。
- それより前に同じキャラが次に発動することは、CT（20 秒以上）からは起きない。起きたら時刻表を作るところで落とす。
- 遅れのあいだにフルバーストが終わることはありうる（遅れ > フルバーストの長さ）。そのときもフルバースト補正は出たフレームで決まる。
- ドレイクの 3 ヒットのような分かれたヒットは、この設計では扱わない（1 回の `burstDamage` のまま、ヒットの時刻に置く）。

## 3. 案 B: 同じ発動の中の効果の順

### 3.1 案

| 案                                        | 書き方                                                                                                                 | 長所                                                                                                            | 短所                                                                                                 |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **B-1 スロットの印 `sequential`（推奨）** | burst スロットに `"sequential": true`。同じ発動で発火する効果を書いた順に当て、後の `damage` は前の `timed` の窓を見る | 説明文の「下位効果のスタック適用」をそのまま写せる。印 1 つで足りる。別スロット（S1）は見ないので C-0163 と合う | 書く順に意味が出る（効果の並べ替えで値が変わる）。検証で、`burstDamage` が先頭にあることを求める     |
| B-2 効果ごとの `order`                    | 同じ発火の効果に整数の順を付け、`damage` は自分より小さい `order` の `timed` を見る                                    | 並べ替えに強い。スロットをまたいでも書ける                                                                      | 書く欄が増える。スロットをまたぐ順の根拠はまだ無い                                                   |
| B-3 stat で決める規則                     | 「同じ発動の `damageTaken` は、同じキャラの `damage` に乗る」を共通の規則にする                                        | 定義を変えない                                                                                                  | イサベル 1 体の観測から全キャラの規則を作る。▲を付けた枠と倍率ダメージの順が別のキャラで逆なら外れる |

### 3.2 B-1 の決まり

- 印は burst スロットだけに書ける（いまはイサベルの「ターゲットマーキング段階別の追加効果」だけ）。
- 同じ発動の効果の発火のフレームで発火した効果を、スロットに書いた順に当てる。
  - `burstDamage`: 先頭にあること（検証で落とす）。いまと同じく、ヒットの直前のバフで計算する（`038-07`〜`038-10`）。印を書けるのは、ヒットと効果の発火が同じフレームのキャラだけ（検証で落とす）。
  - `timed`: 窓は効果の発火のフレームから。
  - `damage`: 効果の発火の直前のバフに、同じスロットで前に書いた `timed` のうち、同じフレームに発火してこの枠を対象にするものの値を足して計算する（`skills/buffs.ts` の `applyResolvedEffect`）。
- 別のスロット（S1）で同じ発動に発火する効果は、印のあるスロットの効果より後に当てる（`038-14` の 3 回目に段階 3 の攻撃力が乗っていない）。
- 実装は `frame/plan.ts` の `planSkillHits` の 1 か所（sim と calc が共有する）。

### 3.3 イサベルの定義の形（B-1 のとき）

- burst の効果の並び（いまの `231.json` のまま）: `burstDamage` → ▲（`timed`・`damageTaken`）→ 段階 2 の `damage` → 段階 3 の `damage`。
- 足すのは `"sequential": true` だけ。段階 2・3 の `assumes` と notes の「未実装」を消し、C-0163 のモデル側を実装に直す。

## 4. 退化

- 遅れの表に無いキャラはヒット・効果の発火 = 発動で、`burstEffects` は `activations` と同じ列になる。`sequential` を書かない定義は、いまの計算のまま。
- 既存のテストの数値と、照合の結果（plan/residuals.md）は、イサベルを含む録画（`038`）の行のほかは変わらない見込み。実装の段ごとに確かめる（skills-guide.md 1.5 節の 3）。
- イサベルの `038` の行の見込み
  - `038-07`〜`038-10`（バーストスキルダメージ）: 変わらない（ヒットの直前のバフは、発動の直前と同じ。S1 の段階のバフは 45 秒で、前の発動から続いている）。
  - `038-11`〜`038-13`（▲の窓の中のラム・デルタの 1 発）: 比べるフレームが新しい窓の中にあるかを確かめ、外なら比べるフレームを直す。
  - `038-14`（追加ダメージ）: B を入れると `compare` にでき、許容内に入る見込み。
  - `038-15`・`038-16`（▲の窓の境目）: A を入れると比べられる。窓の始まりと終わりを返す指標を照合ランナーに足す。

## 5. 確かめ方（実装の前と後）

1. **遅れの値を決める検証記録**（撮影なし。録画 038 の読み直し）
   - 2〜5 回目のフルバーストの始まり（III の発動）を、`038-04` と同じ読み方で取る。着弾は `038-15` の着弾のフレーム。
   - 動画のフレームの差から、フルバーストの入りの止まり（C-0069）を引いて、ゲーム内のフレームに直す。5 回で揃うかを見る（揃えば反復実測）。
   - 予測は読む前に書く。
2. **ほかのキャラの遅れ**: 1.2 節のとおり、発動のフレームまで読んだ例はほとんど無い。表に入れるのは、発動・ヒット・効果の 3 つを読んだキャラだけにし、ほかは 0 のまま（未測定）。ヘルムは録画 079 の III の発動を読み直せば、ヒットと効果の遅れが両方出せる見込み。新しく撮るのは、遅れがダメージに大きく効くキャラ（短い窓のバフ・デバフを持つキャラ）から。
3. **実装の後**: `038-14` を `compare` にし、▲の窓の境目の指標を足して `038-15`・`038-16` を比べる。C-0162・C-0163 のモデル側を実装に直す。

## 6. 論点と決めたこと

2026-10-02 にオーナーが 1〜5 を推奨どおりに決めた（「１～５全て推奨通りでOK」）。覆すときは、この節を直してから実装を戻す。

1. **案 A の値の置き場所**: A-1（実測値の表）か A-2（定義の欄）か → **A-1 に決めた**。
2. **案 B の書き方**: B-1（スロットの印 `sequential`）か B-2（効果ごとの `order`）か B-3（stat の規則）か → **B-1 に決めた**。
3. **表に無いキャラの扱い**: 遅れ 0 のまま何も出さないか、画面に「バーストの着弾の遅れは未測定」と出すか（推奨は、表に載ったキャラにだけ値を出し、未測定は出さない。ほとんどのキャラが未測定になり、注記が目障りになるため）→ **表に載ったキャラにだけ出すに決めた**。
4. **進め方**: 5 節の 1（イサベルの遅れの値）を先に検証記録にしてから実装するか、実装と同じ PR にするか → **先に検証記録にすると決めた**。V-0078 で値を決めた（C-0165）。
5. **効果がヒットより先に出るキャラ（ヘルム）で、同じ発動の効果をヒットに乗せるか**: 既定は乗せない（いまの規則のまま。ラピ・ドレイクで、自分のバーストで付くバフは自分のバーストのダメージに乗らなかった）。ヘルムは録画 079 のヒットの値（`079-07`）が、いまのモデル（乗せない）で合っているかを 5 節の 2 で確かめる → **既定は乗せないに決めた**。

## 7. リスク

- 遅れはキャラの演出の長さで、ゲームの更新で変わりうる。表の行に結論の ID を添え、録画の日付で追えるようにする。
- 遅れは、バーストのヒットがゲージを溜めるか（いまは溜めない）や、ほかのキャラの「味方がバーストを使った時」のような未実装のトリガーにも関わりうる。いまの語彙に無いものは扱わない。
- `sequential` の書く順に意味が出るので、定義を書き直すときに順を崩すと値が変わる。検証で `burstDamage` が先頭かだけは落とすが、`timed` と `damage` の順は落とせない。編成のテスト（`isabelTeam.test.ts`）で値を固定する。
