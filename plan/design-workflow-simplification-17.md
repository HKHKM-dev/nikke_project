## 2. 結論の書き直し

**いま**

- `records:new claim` は、新しい結論の下書きを作る。根拠・等級の候補・状態は道具が出し、text と model は人が書く。
- 前からある仮説の結論（C-xxxx）を、新しい検証で確定にする課題が、撮影の検証 4 本の全部だった。やり方が 3 通りに分かれた。
  - その場で上書き（前例を探して約 6 分）。
  - 新しい結論を作り、古い結論を棄却にする。
  - `records:new claim` で下書きを作り、消してから node で書き直す。
- 新しい結論でも、下書きの後に model・basis・state・judgment（overrides・reason）を node で書き換えた（11 本中 8 本。1 回 1〜2 分）。
- 手で「確定」にした結論が、records:check か close の誤り（最小構成・Stage 18-C・20-A）で仮説に戻る往復が 2 本あった（1 回 2〜2.5 分）。確定にしない理由を見るためだけに `--no-push` で下書きを作って消した本もある。
- 結論の番号が決まる前に定義やテストを書き、仮の ID（C-XXXX）を後で書き換えた。2 つの番号を取り違えた本もある。

**案**

- `records:new claim --update C-NNNN --from V-NNNN [--observations ...]`: 前の結論の text・subject・model を残し、根拠の観測値を足して、等級の候補・状態・最小構成の検査を出し直して書き換える。確定にできなければ、欠けた条件を出して仮説のままにする。
- `--model "<モデルの扱い>"`・`--judgment "<理由>"`（人の判断で上書きする条件と理由。close の judgment と同じ形）を、新しい結論にも `--update` にも付けられるようにする。
- `--dry-run`: 書かずに、状態と確定にできない理由だけを出す。
- 決まり: 前の仮説を新しい検証で確定にするときは `--update` で上書きする。仮説の中身（式・値）が変わるときは、新しい結論を作って古い結論を棄却にする（AGENTS.md「結論を訂正するときは、古い結論を消さずに棄却にする」）。[verification-guide.md](verification-guide.md) の「結論」の段に 2 行足す。
- 仮の ID は、`records:new claim` を先に回して番号を取る、と同じ段に 1 行書く（道具は変えない）。

## 3. 観測値の直し・無効

**いま**

- 観測値は `records:new observation` で足す。直すときと無効にするときは手で書く。
  - 値・args・記述の直し（1183-14）、scope の直し、compare の setup の直し（3 回）。
  - 8 件を無効にし、それを根拠にしていた結論（C-1257）の根拠を付け替えた（約 6 分）。
- 無効は観測値の `invalid: { reason, date }`（`observations/types.ts`）。結論の根拠に無効の観測値だけが残ると records:check が止める。

**案**

- `records:new observation --replace <観測値 ID> (--json | --file)`: 同じ ID のまま欄を差し替え、観測値の検査を通ったら書く。
- `records:new observation --invalidate <観測値 ID>[,...] --reason "<理由>" [--by <新しい観測値 ID>]`: invalid を付け、`--by` があれば、それを根拠にしている結論の observations を新しい ID に付け替える。

## 4. 録画の下見の道具

**いま**

- `still.ts` は 1 フレームを 1 枚の画にする。範囲の並べ画は、[captures/guide.md](captures/guide.md) の手順（crop → drawtext → select → tile。フォントは Windows のパス）を手で組む。
- 録画を読んだ 7 本のうち 6 本が、ffmpeg で並べ画か切り出しを自作した。
  - `-ss` の頭出しのスクリプトを 17 回呼んだ（約 6 分）。`-ss` のずれで読み直しが約 7 分。
  - `select=eq(n,N)` で 1 フレームずつ切り出すループが遅く、約 10 分むだにした。`still.ts` で 5 枚を取るのに 4 分（1 枚ごとに頭からデコードする）。
  - 取り込む前の下見に、Drive から落とすだけのスクリプトを 2 回書いた。
- 領域の色や数字の変わり目をフレームごとに追うスクリプトも、3 本で書いた（CT の数字の切り替わり約 5 分、オート射撃のボタンの色約 12 分、コアの球の間隔約 10 分。HP のバーは第 15 回で hp-bars にした）。

**案**

- `still.ts --range A-B [--every N] [--crop ...] [--sheet COLSxROWS] --out <画>`: 範囲を 1 回のデコードで読み、フレーム番号を入れた並べ画を出す。フォントは道具がリポジトリの中か OS の既定から選ぶ（Windows のパスを書かない）。`--frames a,b,c` で飛び飛びの番号も 1 回で取る。
- 取り込む前の録画も、録画の名前（Drive の名前）で指せるようにする（`fetch.ts` で落としてから読む）。
- **案 B**: 領域の値をフレームごとに出すレシピ `region`（`--opt crop=...`・`--opt stat=mean|min|bright`・`--opt threshold=...`）。値の列を `derived/` にキャッシュし、変わり目のフレームを出す。1 つの用途に 1 回ずつなら自作のほうが速いこともあるので、A を先に入れ、次の回でまた自作が出たら B を作る、でもよい。

**取り寄せの上書き（実装の後に見つけた課題の決定）**

- 課題: `fetch.ts` は、sha256 を突き合わせないファイルを、手元の大きさが Drive と違えば落とし直していた。これが `frames/` などにも効くので、クラウドで `still.ts` が作り直した画（応答の終わりの push まで Drive に上がらない）を、その前に `fetch.ts frames/` を回すと Drive の古い版で上書きする。また、`Drive.connect` を引数の処理より前に呼んでいたので、鍵の無いデスクトップで `drive:<パス>` を指すと、手元のパスを出す分岐に届く前に止まった。
- 決定: 大きさが Drive と違うとき、証拠フレーム（`frames/`）だけは落とし直さず、手元を残して「あり」の行に添えて知らせる（`--force` で Drive の版にする）。ほかのファイルは今までどおり落とし直す。理由: 大きさの比べは、Drive for desktop が上げ終える前に落とした途中の版を使い続けないためのもの。手元で作って後から Drive へ上げるのは証拠フレームだけ（`still.ts` が作り、`frames-upload.ts` と応答の終わりの push が上げる）なので、違っても手元が新しいことがあるのはそこだけ。課題に挙げた「録画に限る」は、手元で作らない参照資料などの途中の版を残してしまうので採らなかった。全部で「知らせて止める」は、録画の途中の版も手で `--force` し直すことになるので採らなかった。
- 決定: Drive への接続は、Drive を引く所で初めて行う（取り寄せの本体を `fetch-lib.ts` に移し、接続を渡す形にしてテストで差し替える）。

## 9. 小さな直し

- **取り込みのフックの誤り**: ブランチを `git checkout -B <ブランチ> origin/main` で作り直すと、追跡先が origin/main になる。main が進むと、`catch-up.ts` は「origin の <ブランチ> に手元に無い commit がある」と誤って判断し、main を取り込まない（このセッションで毎回出た）。追跡先が origin/main のときは、追跡先の無いブランチと同じに扱う。
- **pr:prep を裏で待つ**: Bash の既定の 120 秒で pr:prep が裏に回り、`pgrep -f` と `sleep` のループで待つか、応答を終えようとして Stop フック（未コミットの変更と review-flow）が止めた（11 本中 4 本）。Stop フックの知らせに、pr:prep が動いているとき（ロックがあるとき）は「pr:prep の終わりを待つ。前で回すときは Bash の timeout を 600000 にする」と出す。
- **見直しの段の取り違え**: medium で見直した後に `frame/` に触れていたと気づき、high で見直し直した（約 5 分）。review-flow のフックが、`/code-review` を呼んだときの差分が `frame/`・`sim/`・`tools/git/` に触れていて段が high でなければ知らせる。
- **intake**: `--rid` が全部の録画に同じ値で入り、6 本が別のキャラの録画で台帳を node で直した（2 回）。`--rid` を `;` で区切って録画ごとに書けるようにし、`--level` を足す。
- **fetch.ts**: Drive の利用上限（403）で再試行しない（約 1.5 分）。少し待って 2 回まで再試行する。
- **課題のファイル**: 起票のたびにひな形と既存のファイルを読み、section と order を手で決めた（3 本、0.5〜1.5 分）。`records:new backlog --section <節> --name <名前> --text "<本文>"` で、order と 2 節の番号を振る。
- **sim の手で撃つバースト**: `records:model` の manualBursts と同じものを `npm run sim -- --manual-bursts <f,...>` で指定できるようにする。
- **PR のテンプレート**: 毎回探して `ls` が失敗した（3 本）。リポジトリには置かない。メモリ `pr-workflow` に「テンプレートは無い」と書く。

**案**

- `npm run code:survey`: 長い関数（行数の上位）・重なり（構文木で同じ形の塊）・使われない export・循環の import を出す。一緒に変わるファイルは git の履歴から出す。
