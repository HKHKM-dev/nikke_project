## 1. 何が困っているか

- クイーン（真）の定義（`data/skills/870.json`）には、未対応（`unimplemented`）の notes が 2 つ残っている。
  - S1「追撃が適用された時、敵全体に最終攻撃力の X% の分配ダメージ」: きっかけが説明文と CDN から分からない、とした。
  - S2「1more が適用された時、自分を除く基本バースト段階が 3 のペルソナ状態の味方全体に、バトンタッチ: スキル発動者基準で攻撃力 X%▲（N スタック・持続）」: 対象の語彙が無い、とした。

  2. 対象の絞り込み: 「ペルソナ状態の」「基本バースト段階が 3 の」「自分を除く（味方全体）」

## 3. 語彙の案

### 3.1 ペルソナ状態: 定義の `states`

```json
{
  "formatVersion": 1,
  "resourceId": 870,
  "states": ["persona"],
  "skills": { "...": "..." }
}
```

- 定義の最上位に、その枠が持つ**状態の名前の列** `states` を足す。いまの名前は `persona` だけ。
- 3 体の S1 はどれも「戦闘開始時、自分に…（持続・解除不可）」なので、味方が倒れない前提では**戦闘の始まりから終わりまでの静的な状態**になる（[design-true-damage-element.md](design-true-damage-element.md) 6 節の論点 2 の `withCharacter` と同じ考え方）。窓は持たせない。
- 効果ではないので、スロットの対応状況（`support`）には数えない。状態を与える行（「ペルソナ - ヨハンナ」の付与そのもの）は、S1 の notes（`modeling`）に「ペルソナ状態は定義の `states` で持つ」と書く。根拠の結論は、その notes の `claims` で指す（`states` 自体には `claims` を持たせない。根拠の突き合わせ（`records/skills.ts`）が効果と notes だけを見るので、その仕組みを変えずに済む。9 節）。
- 置き場所の代案は 8 節の論点 1（キャラのデータから導く・コードの表）。

### 3.2 対象の絞り込み

| 言い回し                | 欄                           | 意味                                                                                                        |
| ----------------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------- |
| ペルソナ状態の          | 新: `targetState: "persona"` | 対象の枠の定義の `states` にその名前がある枠だけ                                                            |
| 基本バースト段階が N の | 新: `targetBurstStep`        | 対象の枠の `CharacterData.burstStep` が N（`Step1`〜`Step3`。`BasicBurstStep`。AllStep は数えない）の枠だけ |
| 自分を除く（味方全体）  | `excludeSelf: "always"`      | いまは `topAttack` だけに書ける。`allies` にも開く（8 節の論点 3）                                          |

- 3 つとも `targetWeapon`・`targetElement`・`targetSquad` と同じ、**編成で決まる静的な絞り込み**。発火の文脈は要らない（`skills/targets.ts` の `matchesTargetFilter` に足す）。
- `targetBurstStep` は `burstStepMix`（自分を除く編成に段階 N のキャラがいるかの**条件**）とは別物。条件は効果を持つか持たないか、絞り込みは誰に付くか。型の注釈と画面の文言で分ける。
- 書ける対象は `allies`（と `burstUsers`）。`self` には意味が無いので落とす。
- `excludeSelf` を `allies` に開くと、[design-target-vocab.md](design-target-vocab.md) 1.1 節の「自分を除く味方全体」の 6 体（ティアのバーストなど）にも使える形になる。ただしこの設計ではその 6 体は定義しない。

### 3.3 きっかけ: 名前の付いた効果と `{ "applied": 名前 }`

```json
{ "kind": "timed", "trigger": "burstUse", "enemyElement": "Wind", "target": "allies", "...": "...", "name": "followUp" }
```

```json
{ "kind": "damage", "trigger": { "applied": "followUp" }, "ref": 4, "damageType": "distributed" }
```

- `timed` の効果に、説明文の効果名を表す任意の欄 `name` を足す（いまの名前は `followUp`（追撃）だけ。`batonTouch` は付けてよいが、それを数えるきっかけは無い）。
- 新しいトリガー `{ "applied": "<名前>" }`: 編成のどの枠のどの効果でも、`name` がその名前の効果が**この効果を持つ枠に付いたフレーム**で発火する。付いたフレームは、名前の付いた効果の発火のフレームのうち、この枠が対象に入るもの。
  - 名前の付いた効果のトリガーは、いまの語彙の文字列のトリガー（`burstUse` など）か回数トリガーに限る。`{ "applied" }` で付く効果に名前を付けて連鎖させることは落とす（使うキャラがいない。循環を作らない）。
  - 書ける効果は `damage`（クイーン（真）S1）。`timed` にも意味はあるが、使うキャラがいないので落とす。
  - `enemyElement` は名前の付いた効果の側で判定する（雪子の追撃が付かない的では、クイーン（真）の S1 も発火しない）。きっかけの側にもう一度書かない。
- 1 回の発火で何回数えるか（付いている間にまた付いたら数えるか）は説明文から決まらない（4 節の 3）。案は「付くたびに 1 回」（1more の分配ダメージ C-0310 の「バーストを撃つたびに 1 回」と同じ読み）。
- **1more は名前で書き直さない**。クイーン（真）S1 の 1more の分配ダメージ（C-0310）と S2 の▲（C-0307）、バーストの攻撃力▲（C-0308）は、いまの `burstUse` + `enemyElement: Wind` のまま。1more は自分に付く効果で、きっかけと同じフレームなので、名前の付いた効果にしても値は変わらない（確定の結論の定義を、語彙の都合だけで書き換えない）。
- 代案は 8 節の論点 2（雪子のバーストをクイーン（真）の側に直に書く）。

### 3.4 持続のスタック: `durationUntil: "battleEnd"`

```json
{
  "kind": "timed",
  "trigger": "burstUse",
  "enemyElement": "Wind",
  "target": "allies",
  "excludeSelf": "always",
  "targetState": "persona",
  "targetBurstStep": "Step3",
  "stat": "attack",
  "scaling": "casterAttack",
  "ref": 6,
  "maxStacksRef": 7,
  "durationUntil": "battleEnd",
  "name": "batonTouch"
}
```

- バトンタッチは「N スタック」「持続」。いまの `timed` は維持の欄（`durationRef`・`durationSeconds`・`durationShots`・`durationShotsRef`・`durationUntil`）をちょうど 1 つ要り、トリガー付きで戦闘の終わりまで続く書き方が無い。
- `DurationUntil` に `battleEnd` を足す: 付いたフレームから戦闘の終わりまで。スタックは発火のたびに 1 足し、上限（`maxStacksRef`）で止まる。終わりが無いので `STACK_REFRESH` の違い（`all`・`each`）は効かない。
- いまの `durationUntil: 'fullBurstEnd'` は、1 パス目で窓を追う stat（攻撃力など）とスタックに書けない（窓が `planBuffTimeline` でだけ決まるため）。`battleEnd` は窓の終わりが常に戦闘の終わりなので、1 パス目でも窓が作れる。攻撃力とスタックに書けるようにする（8 節の論点 4）。
- 「スキル発動者基準で攻撃力 X%▲」は既存の `scaling: "casterAttack"`（発動者のバフ前攻撃力 × 比率の固定加算）。スタックと組み合わせた定義はまだ無いので、1 スタックあたりの固定加算 × スタック数と読む（4 節の 5）。

## 5. 退化の見込み

- 足す欄（`states`・`targetState`・`targetBurstStep`・`name`・トリガー `{ applied }`・`durationUntil: battleEnd`、`excludeSelf` を `allies` に開く）はどれも省略できる。書かない定義の計算は変わらない。
- クイーン（真）の定義を 3.5 節の形にしても、**雪子がいない編成では数値が変わらない**（追撃が付かず、バトンタッチの対象がいない）。いまあるクイーン（真）の録画（[captures/recordings.md](captures/recordings.md)）に雪子はいないので、照合の結果は変わらない見込み。
- 1more の 3 つの効果（C-0307・C-0308・C-0310）は書き換えない（3.3 節）。

## 6. 根拠と検証（効果を有効にする道）

この設計で効果を**有効にするのは、根拠の結論があるものだけ**にする（AGENTS.md）。いまはどれにも結論が無いので、語彙を足しただけではクイーン（真）の 2 つの notes は残る（理由を「語彙が無い」から「雪子の定義と撮影が無い」に直す）。
