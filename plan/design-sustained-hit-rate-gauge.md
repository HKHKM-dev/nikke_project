### 0.3 根拠のつながり

「持続の▲で上がった弾丸命中率のぶん、1 パス目のゲージと命中の回数も増える」は、次の結論をつないだもの。これを 1 つの文にした結論は無い。

1. 的に 1 回当たるごとに `target_burst_energy_pershot` が溜まる（C-0083、確定・厳密一致。確かめたのは AR・MG・SR）。何にも当たらない弾は溜めない（C-0139、確定）。
2. 命中率▲は弾丸命中率を H2 の形で上げる（C-0192、確定・反復実測）。根拠の録画の▲は、ミサト S1 の**持続の**スタックの▲（自分）。
3. 味方に配られた持続の▲も常時の▲と同じ式で効く（C-0170、仮説。コア命中率で確かめた）。
4. 常時の▲の上がりは、今も 1 パス目のゲージに入っている（`planLandings` の計画の値）。持続の▲だけを外す理由は、根拠ではなく作りの都合（1 パス目が窓を追っていない）だった（design-bullet-hit-rate-frame-coverage.md 4.3 節）。

- 弱い所: C-0083 は SMG を確かめていない。外れた弾のうちコンテナに当たった分（C-0139 の半分のゲージ）はモデルに入っていない（常時の▲と同じ扱い）。

## 1. 何を決めるか

1 パス目が持続の `hitRate` の窓を追い、条件が自動の枠の弾丸命中率とコア命中率を、2 パス目と同じ N（常時 + その時点の持続の▲）で出し直して、ゲージ（`energyAt`）と命中の期待値（`hitsAt`）に掛ける。

- **N** = 計画の常時の N（`LandingPlan.hitRateUp`）+ フレーム f に効いている持続の `hitRate` の和（スタックは効いている段の数だけ）。2 パス目の区間の `buffs.hitRate` と同じ値になるようにする。
- **式**は 2 パス目と同じ `landingPartsWith`（コアは C-0036・C-0170、弾丸は C-0192 の H2。N ≥ 1 は 1）。式は足さない。
- **効く範囲は今の 2 パス目と同じ**: 条件が自動の枠で、的の表から取った値（`tableBulletHitRate`・`tableCoreHitRate`）だけ。SG・手入力・表が null の項目は今のまま（`landingPartsWith` がそのまま返す）。
- `TeamInput.sustainedHitRateUp` が false（V-0165 の対照の切り替え）なら、1 パス目も持続の▲を足さない（2 パス目と揃える）。

## 2. 語彙

### 2.1 定義（JSON）には語彙を足さない（論点 1）

- 足すものは定義の書き方ではなく、1 パス目が「どの stat の窓を追うか」の分け方。`hitRate` の効果は今の定義のまま（`timed`・`stat: hitRate`）で書けている。
- 効果ごとに「ゲージにも効かせる」旗（例 `gauge: true`）を足す案は採らない。どの持続の▲も同じ根拠のつながり（0.3 節）に乗り、効くかどうかは受け手の武器種と条件の出どころ（自動か手入力か）で決まる。旗にすると、同じ事実を定義ごとに書き写すことになる（1 つの事実を 1 か所に）。

### 2.2 stat の分け方（`skills/types.ts`）

今の分け方:

| 分け       | stat                                                          | 1 パス目                                             | 2 パス目                                        |
| ---------- | ------------------------------------------------------------- | ---------------------------------------------------- | ----------------------------------------------- |
| 射撃に効く | `FIRING_STATS`（最大装弾数・リロード速度・チャージ速度 ほか） | 窓を追い、射手に渡す                                 | 区間の鍵                                        |
| 状態だけ   | `STATE_STATS`（`hitRate`）                                    | 条件「自分が〈stat〉増加状態なら」に要るときだけ追う | `stateWindows`。自動の枠だけ区間の `buffs` と鍵 |
| フラグ     | `FLAG_STATS`（`infiniteAmmo`）                                | （射撃に効く）                                       | —                                               |

案: `STATE_STATS` の中に「当たりに効く状態の stat」を置き、1 パス目が常に追う印にする。

```ts
/**
 * 当たり（弾丸命中率・コア命中率）を変える状態の stat。1 パス目（frame/firstPass.ts）が窓を追い、条件が自動の枠の
 * ゲージと命中の期待値に、2 パス目と同じ N で掛ける（plan/design-sustained-hit-rate-gauge.md）
 */
export const HIT_STATE_STATS = ['hitRate'] as const satisfies readonly (typeof STATE_STATS)[number][];
export function isHitStateStat(stat: BuffStat | 'weapon'): boolean;
```

- 名前は既存の `isFiringStat`・`isStateStat`・`isFlagStat` にならう。`hitRate` 1 つだけの今は、`STATE_STATS` の説明を書き換えるだけで済ませる案もある（論点 2）。
- `types.ts` の `BuffStat` の説明の「全弾命中の前提なので射撃にも弾丸命中率にも効かない」は、C-0192 の後の古い記述。この PR で「弾丸命中率とコア命中率の N（1 パス目のゲージと命中の期待値、2 パス目の与ダメージ）に使う」に直す。

### 2.3 notes の種類（design-skill-note-kinds.md 2.1 節）

- アスカのバーストの notes[2]（`unimplemented`）は消す。1 パス目が窓を追えば、モデルの中で扱っている（結果が 0 なのは 0.1 節のとおりで、近似ではない）。バーストの `support` は `partial` から `supported` に変わる。
- notes[1]（`modeling`）の文に「ゲージにも同じ N で効かせる（ただしアスカの▲はフルバーストの窓に収まり、ゲージの溜まる時間と重ならない）」を足すかは論点 3。
- ミサト S1・ミランダ S1・モダニア S2・ドレイク S1 は、今は notes にずれを書いていない（書き漏れ）。この設計を入れれば書く必要が無くなるので、足さない。入れずに止めるなら、4 つに `unimplemented` を足す（論点 4 の案 C）。
- ノワールのバーストは SG で、弾丸命中率に▲を効かせていない（C-0157）。ゲージも同じ扱いで変わらない。notes は今のまま。

## 3. 入れ方（core）

1. **窓を追う**（`frame/firstPass.ts`）: `plainTimed`（条件・順位の無い timed）のうち `isHitStateStat` の効果を `hitTrack: FiringSource[]` にし、今の `stateTrack` と同じ `register`（和集合・スタックは `stackWindows`）で登録する。手順 3 の順番は 回復 → 状態の窓 → **当たりの窓** → 攻撃力の窓 → 射撃に効く窓 → 即時効果。戦闘開始時の窓はループの前に登録する（今の 3 種と同じ）。
   - 追うのは、条件が自動の枠に掛かりうる効果があるときだけ（`options.hitRates` が null でない枠を `canTarget` が含む）。無ければループは今と 1 フレームも違わない。
2. **N を引く**: `hitUpAt(i, f)` = 計画の常時の N + 「f − 1 までに登録済み」かつ「start ≤ f < end」の窓の値の和（スタックは段の数）。射撃の実効値と同じ規則（design-stage10.md 1.1 節）。
   - 2 パス目の窓との食い違い: 同じフレーム f に付いた窓は、1 パス目では f の発に効かない。回数トリガーは f + 1 から（両方とも）なので食い違わない。`burstUse`・`fullBurstStart` は、付くフレームがフルバーストかチェーンの中（ゲージを足さない）なので、ゲージは食い違わない。`hitsAt` は f の 1 発ぶんだけ食い違いうる（テストで端を固定する）。
3. **区間の値を出し直す**: `LandingHitRateSpan` に着地点の鍵（`landing`）を持たせ、`plan.ts` が `(slotIndex, landing, n) => { hitRate, coreHits }` の関数（中で `landingPartsWith` → `mixedHitRate`・`mixedCoreHits`。キャッシュは `landingPartsWith` のもの）を `FirstPassOptions.hitRateWith` で渡す。`energyAt`・`hitsAt` は、`hitUpAt(i, f)` が計画の N と違うときだけこれを呼ぶ。
4. **窓の一致**: 当たりの窓は `planBuffTimeline` の `stateWindows` と同じ TriggerTracker から作るので一致するはず。射撃に効く窓と同じく、テストで `stateWindows` と突き合わせる。
5. **注記と表示**: `landing.ts` の `auto-condition` の文、`hitRateSpansOf` の説明、`NotesSummary.tsx`・README の「持続の▲の上がりは 1 パス目のゲージには入れていない」を消す。条件欄（`SlotCard.tsx`）の値は 2 パス目のままで変わらない。
6. **データ**: アスカのバーストの notes[2] を消す（2.3 節）。
7. **結論のモデル側**: C-0192 の `model` の「持続の▲による上がりは 1 パス目のゲージに入れていない」を「入れた」に直す。C-0170・C-0183・C-0186 の `model` に 1 パス目を足す。結論の文は変えない。

## 4. 確かめ方

- テスト:
  - ミサト単騎（自動の枠・SMG の遠に固定した的）: 3 段の間の 1 発のゲージが `bulletHitRateWithHitRateUp(p, 0.1512)` の比で上がる。▲の無いリター単騎は変わらない。
  - アスカ入りの編成: 1 パス目の時刻表が、入れる前と 1 フレームも違わない（0.1 節。違えば作りの誤り）。
  - モダニア（10 秒のフルバーストを作る III と組む）: S2 の▲の後ろ 5 秒だけ、AR・SMG・MG の味方のゲージが上がる。SG の味方・手入力の枠は変わらない。
  - `sustainedHitRateUp: false` で、入れる前と同じ。
  - 当たりの窓と `stateWindows` の一致。
- 照合: 入れる前後で `npm run records:check` を回し、動いた観測値を PR に書く。比べている観測値に満タンのフレームがある録画のうち、自動の枠に AR・SMG・MG の受け手がいて、ミサト・ミランダ・モダニア・ドレイクの▲が `charging` の間に掛かるものだけが動くはず。遠ざかったら原因を調べる（係数で埋めない）。
- 撮影は要らない（入れ方の根拠は 0.3 節の結論）。持続の▲のゲージを 1 本で確かめる最小構成は、ミサト単騎（スペック固定 ON・オートバースト OFF）の 1 回目の満タン（BURST バーが消えるフレーム）。既存の録画（V-0118・V-0148 のミサトとリター）から読めるかは、入れた後に予測（入れる前と後の差）を出して、差が読みの分解能より大きいときだけ起案する（論点 5）。

- コンテナに当たった弾のゲージ（C-0139 の未反映）。
- アスカの `burstUse` の効果の遅れの測定（0.1 節の例外）。
- `burstGaugeSpeed` を timed に書けるようにすること（同じ 1 パス目の作りで書けるようになるが、使う定義が無い）。

## 6. 論点（オーナーに決めてほしいこと）

1. **定義に語彙を足さず、stat の分けで効かせる**（2.1 節）。推奨はこの案。代案は効果ごとの旗（`gauge: true` など。根拠の結論 ID を効果ごとに持てるが、同じ事実を書き写す）。
2. **stat の分けの名前**（2.2 節）。推奨は `HIT_STATE_STATS`・`isHitStateStat` を足す（`hitRate` 以外の当たりの stat が来たときに 1 か所で済む）。代案は `STATE_STATS` の説明を書き換えるだけ（今は `hitRate` しか無いので同じ結果）。
3. **アスカのバーストの notes**（2.3 節）。推奨は notes[2]（`unimplemented`）を消し、notes[1]（`modeling`）に「▲の窓はフルバーストに収まり、ゲージに効く時間が無い（きっかけの遅れは未測定で 0）」を足す。ただし「フルバースト中はゲージが溜まらない」に結論の ID が無い（design-stage7.md の録画 19）。この行の根拠に足すため、凍結の記録から結論を起こすか（等級は反復実測か、録画 19 の 1 本なら単独実測）。代案は notes[1] に足さず、消すだけ。
4. **入れる範囲**。
   - 案 A（推奨）: 1 節のとおり、2 パス目で弾丸命中率・コア命中率に効かせているすべての持続の▲（ミサト・ミランダ・モダニア・ドレイク・アスカ）を、1 パス目のゲージと命中の期待値にも効かせる。2 パス目と 1 パス目で N が揃う。根拠は 0.3 節。仮説の結論（C-0170・C-0186）に乗るものは、2 パス目と同じく仮説として入る。
   - 案 B: 確定の結論だけのつながりに絞る（自分に乗せる▲ = ミサト S1 とアスカのバースト）。配られた▲（C-0170 は仮説）は、2 パス目では効かせ、1 パス目では効かせない（今の食い違いが残る）。
   - 案 C: 入れずに、ミサト S1・ミランダ S1・モダニア S2・ドレイク S1 の notes に `unimplemented` を足し、backlog の対象を直すだけ。
5. **「持続の▲の上がりもゲージに効く」を結論として起こすか**（0.3 節）。推奨は、入れる PR で仮説（推論）の結論として起こし、C-0083・C-0139・C-0192 をつないだものと書く。ミサト単騎の満タンのフレームで確かめるのは、入れた後の予測の差が読める大きさのときだけ（4 節）。代案は結論を起こさず、C-0192 のモデル側に書くだけ（常時の▲のゲージと同じ扱い）。
