## 1. 何が困っているか

- マナ（290）のバーストと、レイヴン（851）のバーストの A.N.モードは「自分に持続ダメージ X%▲・10 秒間維持」を持つ。語彙に持続ダメージ▲の stat が無いので、どちらも `unimplemented` の notes にしてある。
  - マナのバーストは、持続ダメージ（`dot` で書ける）も合わせて未定義。スロットは `unsupported` で、マナのバーストのダメージは 0。
  - レイヴンは S1 の持続ダメージ（定義済み。C-0181・C-0182）にバーストの▲が乗るはずで、フルバーストの後の tick が過小になる（notes に書いてある）。
- 持続ダメージ▲が式のどこに入るかは、まだどの録画でも確かめていない（2 節）。

全キャラの説明文から「持続ダメージ … ▲」を拾った。どれも `passive`・`timed` と既存の対象（自分・味方全体・武器種と属性の絞り込み）で書ける。パーツの破壊・状態（イントロ・ブランチングなど）のきっかけは、この設計の外。

| キャラ                         | 言い回し                                                                                 |
| ------------------------------ | ---------------------------------------------------------------------------------------- |
| ロザンナ：シックオーシャン     | バーストで味方全体に▲                                                                    |
| モリー                         | バーストで味方全体に▲、S2 はパーツの破壊で味方全体にスタックの▲                          |
| アークレンジャー・ブラック     | 通常攻撃 N 回で自分に▲、フルバースト時に風圧コードの AR の味方全体に▲、バーストで自分に▲ |
| ディーゼル：ウィンタースイーツ | フルチャージの攻撃で自分にスタックの▲、フルバースト時に状態つきの▲、パーツの破壊で▲      |
| ミハラ：ボンディングチェーン   | バースト 3 段階突入時に自分に▲                                                           |
| クラスト                       | 状態つきで味方全体に▲                                                                    |
| サクラ：ブルーム・イン・サマー | パーツの破壊で自分に▲                                                                    |

キューブ・コレクションには持続ダメージ▲は無い（`buildEffects.ts`）。

## 2. 分かっていること・分かっていないこと

分かっていること（どれも確定）:

- 持続ダメージの 1 tick は倍率ダメージと同じ式（(最終攻撃力 − 防御) × X%。会心は乗り、コア・距離は乗らない）（C-0100・C-0131）。
- フルバースト中の tick には、倍率グループに 0.5 を足す形でフルバースト補正が乗る。tick ごとにその時点で決まる（C-0111）。
- 攻撃ダメージ▲は、tick ごとにその時点の▲が別枠の乗数（1 + Σ）で乗る（C-0112）。
- レイヴンの S1 の tick は、全スタックの和が 1 つのダメージ（C-0182）。

分かっていないこと（結論が無い）:

- **a. 持続ダメージ▲の式の中の置き場所**（3.3 節の H1〜H3）。
- **b. 乗るかを決める時点**: tick の時点の▲か、持続ダメージを付けた時点の▲か（3.4 節の T1・T2）。
- **c. マナのバーストの持続ダメージの tick の時刻と数**（5.1 節の D1〜D3）。ニヒリスターの火傷（C-0101: 付いた瞬間と、その 1.5 秒後から 1 秒ごと）と、クルミのバースト使用時のハッキング（C-0132: 付いた 1 秒後から 1 秒ごと）で形が違う。
- d. 持続ダメージ▲が持続ダメージのほか（通常攻撃・倍率ダメージ）に乗らないこと。名前からの推測で、確かめていない。

## 3. 語彙の案

### 3.1 stat `sustainedDamage`（持続ダメージ▲）

- `BuffStat` に `sustainedDamage` を足す。値は割合（`ratio`。X/100）。`passive`・`timed` で書け、対象の語彙（`self`・`allies`・武器種・属性の絞り込み）は既存のものをそのまま使う。
- `BuffTotals` に `sustainedDamage` を足す（ほかの stat と同じく和）。
- 状態の stat・射撃に効く stat・フラグの stat ではない（区間を割る乗数の stat。`distributedDamage` と同じ扱い）。
- 画面のラベルは「持続ダメージ」（英語 Sustained Damage）。ゲーム内の言い回しに合わせる。

### 3.2 掛かる先

- **`dot` の tick にだけ掛ける**。`autoAttack`（アニス：スター。内部は `dot` と同じ道）には掛けない（説明文が「持続ダメージ」でない。[design-anis-star-s2-burst.md](design-anis-star-s2-burst.md) 論点 3 で分けた理由そのもの）。通常攻撃・`damage`・`burstDamage`・`cycle` の段にも掛けない（2 節の d。5 節の録画で、▲の窓の中の通常攻撃の値が変わらないことを見る）。
- 誰の▲か: tick を出す枠（持続ダメージを付けた射手）の▲。味方全体に配る▲（ロザンナなど）は、受けた各枠が自分の持続ダメージに使う。
- 実装の場所: `computeBurstHit` で、効果が `dot` を持ち `autoAttack` でないときだけ乗数を掛ける（`distributed` に `distributedDamageMultiplier` を掛けるのと同じ形）。`computeSkillHit` が `buffs.sustainedDamage` を渡す。calc は 1 パス目の `skillHits` を使うので、同じ値が入る。

### 3.3 式の中の置き場所（未確定。5 節で決める）

| 仮説 | 形                                                                   | 似た既存の stat                                                 |
| ---- | -------------------------------------------------------------------- | --------------------------------------------------------------- |
| H1   | 別枠の乗数 (1 + Σ sustainedDamage)                                   | 分配ダメージ▲（`distributedDamage`）・受けるダメージ▲（C-0138） |
| H2   | 攻撃ダメージ▲と同じ群 (1 + Σ attackDamage + Σ sustainedDamage)       | なし                                                            |
| H3   | 倍率グループに足す (1 + 会心 + フルバースト補正 + Σ sustainedDamage) | フルバースト補正（C-0111）・コア・距離                          |

- 見分けの大きさ（Lv10 の説明文の値。tick 1 回の会心なしの値の、▲なしに対する比）:
  - マナ（▲ 52.8%、S2 の攻撃ダメージ▲ 21.12% が同時、フルバースト中）: H1 ×1.528、H2 ×1.436、H3 ×1.352。どの 2 つも 6% 以上違う。
  - レイヴン（▲ 89.44%、攻撃ダメージ▲なし、フルバースト中）: H1・H2 ×1.894（同じ値）、H3 ×1.596。**レイヴンでは H1 と H2 を見分けられない**。H1 と H2 を分けるのは、攻撃ダメージ▲を同時に持つマナ。
- 実装では置き場所を 1 つの表の値（定数）にし、根拠の結論の ID を添える（skills-guide 1.5 節「キャラ固有の分岐をコアに置かない」）。予測のために、照合の `CompareSetup` に仮説の切り替え（`sustainedDamagePlacement`）を足し、予測ファイルの仮説の `override` で H1〜H3 を回す（V-0165 の `sustainedHitRateUp` と同じ形）。

### 3.4 乗るかを決める時点（未確定）

- T1（tick の時点。C-0112 の攻撃ダメージ▲と同じ）と T2（持続ダメージを付けた時点）。
- 既定は T1（今の tick の計算は、tick のフレームのバフで値を出す。`frame/plan.ts` の `planSkillHits`）。T2 にするには、付けた時点のバフを tick まで持ち回る仕組みが要る。
- マナでは見分けられない（▲と持続ダメージが同じバーストで同時に付く）。見分けられるのはレイヴン（▲の前に付けたスタックの tick が▲の窓の中に出る。▲の窓の後も、窓の中で付けたスタックの tick が出る）。

### 3.5 退化と画面

- 定義に `sustainedDamage` を書かない限り、どの数値も変わらない（既存のテストが数値を変えずに通ることを確かめる）。
- 画面: スキル欄の stat のラベル（`skillLabels.ts`）、内訳の乗数の表示（`distributedDamage` と同じ並び）。CLI（`sim-run.ts`）の内訳。

## 4. 定義（承認と検証の後）

効果を有効にするのは、根拠の結論ができたものだけ（[skills-guide.md](skills-guide.md) 1.6 節の流れで、予測を出すときに解釈の結論（仮説・推論）を作って効果に結び付け、撮影の結果で確定か棄却にする。main に入るのは検証が済んでから。論点 2）。

- マナ（`290.json`）の burst:
  - `timed`・`burstUse`・`self`・`sustainedDamage`・`ref: 1`・`durationRef: 2`。
  - `dot`・`burstUse`・`ref: 4`・`intervalSeconds: 1`・`durationRef: 5`・`firstTick` は 5.1 節の結果。
  - notes の「持続ダメージと自分の持続ダメージ▲は未対応」を消す。
  - マナの S1（`attack`）・S2（`attackDamage`・`attack`）の効果に根拠の結論を付ける（backlog 5-2。S1 は録画 010 の観測値 `010-01`〜`010-04`、S2 は 5.1 節の録画のフルバースト中の通常攻撃。論点 3）。
- レイヴン（`851.json`）の burst:
  - `timed`・`burstUse`・`self`・`sustainedDamage`・`ref: 2`・`durationRef: 3`。
  - 一点集中の解除は書かない（一点集中が起きないので何もしない）。notes の未対応の行は、`modeling`（一点集中の解除は、一点集中が前提の外なので扱わない）に替える。
- 録画で決まらなかった部分（例: T1・T2）は、効果の `assumes` か `unimplemented` の notes に「未確定」と書く。

## 6. リスク

- マナの tick とマナの通常攻撃が同じフレームに出ると、増分が足し合わさる。値で分けられないフレームは数えない。
- マナのバーストの効果の遅れが分からないので、窓の端の tick がフルバースト・S2 の▲・持続ダメージ▲の窓の内か外かの予測がずれる。端の tick は H の判定に使わず、c（tick の時刻）の判定にだけ使う。
- 置き場所の判定は 1 キャラ（マナ）の録画に立つ。配る▲（ロザンナなど）が同じ置き場所かは、そのキャラを定義するときに確かめる。

## 7. 論点

1. **stat の名前と掛かる先**。推奨は `sustainedDamage`・`dot` の tick にだけ（`autoAttack` には掛けない）（3.1・3.2 節）。代案は `dotDamage`（コードの `dot` に合わせた名前。画面のラベルは同じ）。
2. **効果を有効にする時期**。推奨は skills-guide 1.6 節の流れ: 実装のブランチで解釈の結論（仮説・推論）に結び付けて予測を出し、撮影の結果で確定・棄却してから 1 本の PR で main に入れる（main には根拠の結論のある効果だけが入る）。代案は、予測のときだけ効果を足す切り替えを照合に作り、定義は検証の後に書く（コードが増える）。
3. **同じ録画の中で、未確定の要素を順に決めてよいか**。マナの S2（根拠の結論が無い。backlog 5-2）とレイヴンの S1 の攻撃力▲（C-0185。仮説）は、どちらもフルバーストの開始で付くので、▲と切り離して撮れない。推奨は、▲の乗らない通常攻撃の値で先にそれを決め（予測は撮る前・読む前に commit）、tick の値では▲だけを未確定の要素として比べる。両方が端数まで合ったときだけ確定にする。代案は、こうした録画からの▲の結論は仮説までにする（AGENTS.md「未確定の要素が 2 つ以上混ざる録画」をそのまま当てる）。
4. **レイヴンを録画 173 の読み直しにするか、撮り直すか**。推奨は読み直し（5.2 節。tick を読んでいないので比べられる。撮影が要らない）。代案は同じ編成で新しく撮る。
5. **進める順番と優先度**。推奨は、承認の後に 5.1 の検証記録を起こして予測を固定し、撮影を待つ（撮影の後に 5.2）。backlog のほかの課題との順番はオーナーが決める。
