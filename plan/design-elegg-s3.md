## 1. 何を足すか

エレグ（500。Supporter・MG・バースト II）の、ブームインストール状態の敵への命中の回数で起きる 2 つの効果。

| スロット | 行（説明文）                                                                                                                    | いま                                       |
| -------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| S1       | 通常攻撃が 100 回命中した時、対象がブームインストール状態なら、対象と周囲の敵 2 機に最終攻撃力の 158.65% の分配ダメージ（Lv10） | `500.json` の skill1 の notes[1]（未対応） |
| S2       | 通常攻撃が 60 回命中した時、対象がブームインストール状態なら、味方全体にスキル発動者基準で攻撃力 13.09%▲（5 秒。Lv10）          | `500.json` の skill2 の notes[0]（未対応） |

どちらも、エレグのバーストが敵に付けるブームインストールの間だけ起きる。ブームインストールの状態（付与・10 秒・中身の防御力▼）は段 2 が定義する。段 3 はそれを条件として見るだけで、状態を定義しない。

- **状態の名前**: `boomInstall`（英語版の状態名 BOOM Install の lowerCamelCase。[design-named-state.md](design-named-state.md) 5.1 節の付け方）。段 2 の設計（`design-elegg.md` 8.2 節の案 A）も同じ名前で目録に足す。段 2 の実装で別の名前になれば、それに合わせる（7 節の論点 5）。

## 2. 段 2 に頼ること

段 3 は、段 2 の実装で 1 と 3 が揃っていることを前提にする。2 は段 2 の設計（`design-elegg.md` 8.2 節）で段 3 に回されたので、段 3 の実装の PR で足す。1 が案 B（`timed` で書く）になったら、状態の付与への書き換えも段 3 で行う。

1. ブームインストールが、敵が持つ名前の付いた状態（目録の `holder: 'enemy'`）として付与で付く（[design-named-state.md](design-named-state.md) 8.3 節の `kind: 'state'`・`target: 'enemy'`）。
2. 条件 `enemyState` が、付与で付いた敵の状態も見る。いまの `enemyState` が見るのは持続ダメージの付ける状態（`skills/holders.ts` の段 C の `enemyStateSources`）だけで、`frame/plan.ts` の `enemySpans` も `origin.kind === 'enemyState'` の件だけを拾う。8.3 節の見込みどおり「dot が付ける状態と同じ列にまとめる」が要る（**段 3 で足す**）。
3. 状態の付き始め（バーストの使用か、バーストのヒットか）と終わり（10 秒）の結論。段 3 の回数の判定（3 節）はこの区間から数えるので、区間の端が数フレームずれても見分けには効かない（MG はおよそ 1 フレームに 1 発で、仮説の差は数十発。4.2 節）が、付き始めの遅れは段 2 の結論を使う。

## 3. 語彙

### 3.1 S1: 今の語彙で書ける（回数の数え方が K1 なら）

```json
{
  "kind": "damage",
  "trigger": { "count": "normalHit", "everyRef": 2 },
  "condition": { "enemyState": "boomInstall" },
  "ref": 4,
  "damageType": "distributed",
  "assumes": {
    "ja": "敵 1 体。周囲の敵はいないので、分配ダメージは対象に全額入る",
    "en": "One enemy. With no surrounding enemies, the distributed damage goes entirely to the target"
  },
  "claims": []
}
```

- 回数の数え方が K2・K3（4.1 節）なら、`trigger` に窓を足す語彙が要る（3.3 節）。
- 「周囲の敵 2 機」の値（`description_value_03`）は、敵 1 体の前提で使わない。

### 3.2 S2: `timed` の条件に `enemyState` を開く

```json
{
  "kind": "timed",
  "trigger": { "count": "normalHit", "everyRef": 1 },
  "condition": { "enemyState": "boomInstall" },
  "target": "allies",
  "stat": "attack",
  "scaling": "casterAttack",
  "ref": 2,
  "durationRef": 3,
  "claims": []
}
```

- 「スキル発動者基準で攻撃力 X%▲」は既存の `scaling: 'casterAttack'`（発動者のバフ前攻撃力 × 比率の固定加算。`skills/types.ts` の `BuffScaling`）。
- **語彙の変更**: `CONDITION_KEYS_OF.timed` に `enemyState` を足す（いまは `selfBuffed`・`inFullBurst`・`selfState`・`usedBurst`）。`enemyState` は件を見る鍵なので、`conditionReadsItems` で効果の段が上がる（いまの関数のまま）。判定の場所は `selfState` と同じ段 1.5（`skills/holders.ts`）で、発火のフレーム f に敵がその状態の窓 [start, end) の中にいれば発火する。
- **同じフレームの境界**: 状態が付いたフレームの命中で数えが届いたとき、発火するか。`damage` の `enemyState`（`frame/plan.ts` の `damageConditionHolds`）は `start <= frame` で同じフレームを入れている。`selfState` の `damage` は同じフレームを入れない（C-0160 と同じ読み）。推奨は `damage` の `enemyState` にそろえる（同じ鍵の判定を効果の種類で分けない）。境界の 1 発は確かめられない（4 節）ので、`assumes` に書く。
- **付き直し**: 窓の中で 60 回目が来るたびに付き直す（MG ではほぼ 1 秒ごと）。いまの `timed` の付き直し（同じ効果は重ねずに窓を延ばす）のまま書き、U4（4.3 節）で確かめる。
- 使い手は S2 の 1 つだけだが、条件の型は `timed`・付与・`damage` で 1 つ（[design-named-state.md](design-named-state.md) 10 節の論点 8）で、鍵を受ける効果の種類を広げるだけなので、新しい語彙ではない（同 3.6 節の「使い手のいない語彙」には当たらない）。

### 3.3 K2・K3 のときに足す語彙（結果しだい。いまは入れない）

回数を状態の間だけ数える（K2・K3）と分かったら、`ShotCountTrigger` の窓（`during`）に敵の状態を足す。

```json
{ "count": "normalHit", "everyRef": 2, "during": { "enemyState": "boomInstall" }, "reset": "windowStart" }
```

- いまの `during` は `'fullBurst'` だけ、`reset` は `'fullBurstStart'`・`'never'` だけ（`SHOT_COUNT_WINDOWS`・`SHOT_COUNT_RESETS`）。`during` をオブジェクトの形にも開き、`reset` の `windowStart`（窓の始まりで 0 に戻す。`fullBurstStart` を窓の種類に依らずに言い直したもの）を足す。K3 は `reset: "never"`。
- 数える側（`skills/triggers.ts`）は、発ごとに敵の状態の窓の中かを見る。ブームインストールはバーストの使用（時刻表で決まる）で付くので、状態の窓は回数のトリガーより前の段で決まり、循環しない。
- K2・K3 で `during` を書いたら、`condition.enemyState` は要らない（窓の中でしか届かない）。S1 と S2 で数え方が違えば、それぞれの結論のとおりに書く（4.1 節の注）。
- 使い手が S1・S2 だけでも、結論が出てから足すので、根拠のある語彙になる。

## 4. 確かめること

### 4.1 回数の数え方（U1。論点 1）

| 仮説                                   | 中身                                                                                                    | 書き方                                         | 前例                                                 |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------- | ---------------------------------------------------- |
| **K1**: 常に数え、届いた時に状態を見る | 命中を戦闘中ずっと通算で数え、100（60）の倍数に届いた命中の時に対象がブームインストール状態なら発火する | 3.1・3.2 節のまま（`condition.enemyState`）    | ソーダ：TB S1（`firesDuring`。V-0443）               |
| **K2**: 状態の間だけ数え、付くたびに 0 | ブームインストール状態の対象への命中だけを数え、状態が付く（付き直す）たびに 0 に戻す                   | `during: { enemyState }`・`reset: windowStart` | クルミ S2（`during: 'fullBurst'`・`fullBurstStart`） |
| **K3**: 状態の間だけ数え、持ち越す     | 同じく状態の間だけ数えるが、状態が切れても残りを持ち越す                                                | `during: { enemyState }`・`reset: never`       | クルミ S2 の `never`                                 |

- 説明文: 日本語は S1・S2 とも「通常攻撃が N 回命中した時、対象がブームインストール状態なら」で K1 に読める。英語は S1 が「after landing 100 normal attacks … if the target is in BOOM Install」（K1 に読める）、S2 が「after landing 60 normal attacks on a target in the BOOM Install state」（K2・K3 に読める）で、S1 と S2 で書き方が違う。文面は根拠にしない（AGENTS.md「事実と記録」）が、S1 と S2 で数え方が違うこともありうるので、**S1 と S2 は別々に判定する**。
- **見分ける量**: 状態が付いてから最初に発火するまでの命中の数 n₁（窓ごと）。
  - K1: n₁ = 100 −（状態が付いた時の通算の命中 c を 100 で割った余り）。窓ごとにばらつき、c から当てられる。
  - K2: n₁ = 100。どの窓でも同じ。
  - K3: n₁ = 100 −（前の窓までの状態の間の命中を 100 で割った余り）。1 回目の窓は 100。
  - S2 は 100 を 60 に読み替える。
- 命中の数は照準の横の残弾（最大 300）とリロードの回数から、撃った数として数える。MG の弾丸命中率は 0.99 以上（C-0543）で、3 分で外れは数発の見込み。K1 の予測は c の外れの分だけ数発ずれるが、仮説の差（数十発）より小さい。窓ごとに予測を固定してから読む。
- 2 回目以降の窓で K1 と K3 が分かれる（1 回目の窓は c が小さく、K1 と K2・K3 の差が小さいことがある）。

### 4.2 発火のフレーム（U2・U3。論点 2）

- **U2（S1 の分配ダメージ）**: 届いた命中のフレームから、分配ダメージのヒットまでの遅れ。いまのモデルは射撃の回数の `damage` を発のフレームに出す。当たった対象への追加ダメージは遅れない（ネオン：VE・シンデレラ・クルミ。C-0410・C-0583・C-0276）。一方、敵に向けたスキルの効果は約 6〜10f 遅れるものがある（[design-shot-count-trigger-frame.md](design-shot-count-trigger-frame.md) 2.2 節の H-enemy。確かめていない読み）。「対象と周囲の敵」は当たった対象を含むので、どちらとも言えない。測った遅れがあれば `delayFrames`（同 6.2 節の案 A）で書く。
- **U3（S2 の攻撃力▲）**: 届いた命中のフレームから、▲がエレグ自身の発に乗るまでの遅れ。味方全体の効果は遅れない読み（H-enemy。マナ S1 の回復 C-0628・ルドミラ：WO S1 C-0645）で、モデルは次のフレームから（`startOfFire`）。遅れが測れたら同じく `delayFrames` で書く。
- MG はおよそ 1 フレームに 1 発なので、6f の遅れは約 6 発分で、U1 の仮説の差（数十発）とは混ざらない。U1 の n₁ は「遅れを引いた発火のフレーム」で数える。

## 5. 撮影の前提（論点 3・4）

### 5.1 エレグの通常攻撃の条件

エレグを撃たせる（命中が要る）ので、通常攻撃の条件がその的で測られているかを確かめた。

- コア命中率・弾丸命中率: 射撃場の的の MG の表（C-0543。確定・反復実測）。値を決めた旧の録画 L-AN はエレグ単騎・AUTO そのもので、更新（2026-10-08）の後はクラウン（MG）の単騎で再現した（V-0423）。
- 距離ボーナス: エレグの範囲（35〜55）と着地点の距離（C-0031・C-0032・C-0044）で決まる。
- 射撃の間隔・リロード: MG の連射の上がり方とリロード明けの 1 発目（C-0115 にエレグの L-AN を含む）。

推奨は、エレグの単騎の段を別に撮らないこと。どれも確定の結論があり、エレグの値はその根拠に入っている。更新の後のエレグ自身の射撃の録画は無いので、段 3 の録画の、最初のバーストより前の区間を読み、表と食い違わないかを見る（根拠にはしない。食い違えば単騎を撮る）。

### 5.2 編成（推奨）

> **2026-10-26 に替えた（検証記録 V-0524 を起こすとき）**: 下の 2 人の編成をやめ、V-0521 の編成 C（鈴原サクラ 1 枠目・I-DOLL・サン 2 枠目・◎エレグ 3 枠目）でエレグを撃たせる形にした。モデルは枠を詰めて並べ、撃たない枠も無い（[design-elegg.md](design-elegg.md) 8.4 節）ので、2 人の編成ではモデルで鈴原サクラが撃ち、実機に無い S1 の受けるダメージ▲が入って、U5・U6 の値をモデルと比べられない。3 人とも撃つ形なら実機とモデルの編成がそろい、操作枠のエレグの発は照準の左の残弾で数えられる。その代わり、総ダメージの跳びにはほかの 2 人のヒットも入る（V-0521 と同じく値で分ける）。下の表は承認したときの形として残す。

| 枠     | キャラ     | 設定                             | 役                                            |
| ------ | ---------- | -------------------------------- | --------------------------------------------- |
| 1 枠目 | エレグ     | AI（撃つ）                       | II。ブームインストールを付け、S1・S2 を起こす |
| 3 枠目 | 鈴原サクラ | 操作・オート射撃 OFF（撃たない） | I。オートバーストで I を撃つだけ              |

- 共通: 射撃場・3 分モード・スペック固定 ON・オートバースト ON。2 枠目は空き。
- 撃つのはエレグだけにする。HUD の総ダメージの跳びがエレグの発・S1・エレグのバーストだけになり、S1 のヒットと▲の前後の 1 発の値が読みやすい。
- 鈴原サクラは撃たないので、S1（命中 120 回の受けるダメージ▲）・S2（攻撃 60 回の回復量▲・受けるダメージ▼）は起きない。バーストは持続回復だけで、ダメージに効かない（C-0590）。III がいないのでフルバーストは無く、フルバーストの補正も入らない。効きうる未確定の要素は、エレグの S1・S2 と段 2 の効果だけになる。
- 操作枠を 3 枠目にするのは、戦闘開始の操作枠が 3 枠目になるから（[captures/protocol.md](captures/protocol.md)「編成と条件の選び方」）。撃たない操作枠は 3 枠目に置く。
- エレグの S2 で戦闘開始の直後にゲージが満タンになり（C-0662）、1 回目のチェーンはすぐに来る。1 回目の窓は c（通算の命中）が小さく U1 の見分けが弱いので、2 回目以降の窓で判定する。2 回目からのゲージはエレグ（AI。フルチャージ倍率は乗らない。C-0007）の発だけで溜まる。3 分で何回の窓が入るかは、撮影計画で `records:predict` で確かめる。
- U0 で II が撃たれなければ、V-0504 の編成（鈴原サクラ・ソルジャーF.A.・エレグ・I-DOLL・サン）からソルジャーF.A. を外し、エレグを II にする（I-DOLL・サンも撃つので読みにくくなる）。
- 本数: 2 本（U1 の判定は窓ごと。2 本で 2 回目以降の窓が数回ずつ入る見込み）。

### 5.3 最小構成と段 2 の関係（論点 4）

- **段 2 の効果が確定してから撮る**（推奨。段 2 の実装の後に撮影を頼むという段取りとも同じ）。S1 の値（U6）には、同じバーストの防御力▼・分配ダメージ▲が必ず乗る（S1 はブームインストールの 10 秒の間だけ起き、分配ダメージ▲も同じ発動の 10 秒）。段 2 が未確定のままだと U6 は未確定の要素が 3 つになる。
- 回数とフレーム（U1〜U4・U8）は値を読まないので、段 2 の値には依らない。依るのは状態の区間（2 節の 3）だけ。
- **同じ録画の中の S1 と S2**: S2 の▲（U5）はエレグの 1 発の値で読み、S1 のヒットの跳びは除けるので、S1 に依らない。S1 の値（U6）には S2 の▲が乗る（最終攻撃力に入る）。推奨は、先に S2（U3〜U5）を確定にし、その後に同じ録画を読み直して S1 の値を判定すること（過去の録画の読み直しでも確定にできる。AGENTS.md「事実と記録」）。U6 の結論の `decidedOn` に、S2 の値を決めるのに使った録画であることを書く。

## 6. 定義の変更（承認・結論の後）

- `packages/core/data/skills/500.json`: skill1 の notes[1] を 3.1 節の `damage` に、skill2 の notes[0] を 3.2 節の `timed` に替える。数え方が K2・K3 なら 3.3 節の形にする。`claims` に結論を書く。
