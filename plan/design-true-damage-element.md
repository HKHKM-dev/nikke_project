## 1. 何が困っているか

- 3 キャラの説明文には、いまの語彙で書けない効果がまとまって残っている。中心は 2 つ。
  - **防御力無視ダメージ**: 「通常攻撃が防御力無視ダメージに変化」「防御力無視ダメージ X%▲」「最終攻撃力の X% の防御力無視ダメージ（使用武器変更）」。モデルの 1 発の式は max(1, 攻撃力 − 防御力) で、防御力を引かない発も、防御力無視ダメージだけに乗る▲も持てない。
  - **有利コードの攻撃ダメージ▲**（スキル由来）: stat `elementDamage` は Stage 13 に OL・キューブの効果層のために足した（C-0119）。スキルの DSL にも書けるが、スキルの効果に使った定義はまだ無く、OL・キューブと同じ群に入るかの根拠も無い。
- ほかに、同じスロットの中で次が足りない（「等」の中身）。
  - フォーメーション（エマ：TU と ウンファ：TU が両方いるときの追加効果）の条件。
  - 「フルバーストタイムなら」（フルチャージの発の条件）。
  - 「解除条件：フルバーストタイムが終了した時」（維持の終わりが出来事で決まる）。
  - 「1more が適用された時」「追撃が適用された時」のきっかけ。
  - 環境コントロールの再発動周期（戦闘開始と、その後の一定間隔）と、その強化（バースト）。
- 語彙の外に残すもの: カモフラージュの被弾での解除と単一攻撃対象からの除外は `outOfScope`、エマ S1 の陽動とエマ S2 の陽動発動不可は `noDamage`、エマ S1 の持続回復は `unimplemented`（7 節）。

## 3. 語彙の案

どれも、書かない定義では計算が今と同じになる（退化しない）。値は説明文の `ref` で指し、実測値は書かない。

### 3.1 防御力無視ダメージ

```json
{ "kind": "timed", "trigger": "burstUse", "target": "self", "stat": "trueDamageConversion", "durationRef": 1 }
{ "kind": "timed", "trigger": "burstUse", "target": "self", "stat": "trueDamage", "ref": 2, "durationRef": 1 }
{ "kind": "weaponChange", "damageRef": 1, "trueDamage": true, "durationSeconds": … }
```

- `trueDamageConversion`（フラグの stat。`infiniteAmmo` と同じく `ref` を書かない。`timed` の `self` だけ）: 窓のあいだ、自分の通常攻撃の 1 発の基礎を max(1, 攻撃力 − 防御力) から max(1, 攻撃力) にする。射撃ごとの倍率ダメージ・スキルの倍率ダメージは変えない（説明文は「通常攻撃が」）。
- `weaponChange` の `trueDamage: true`: 変更後の武器の 1 発を防御力無視ダメージにする（基礎は max(1, 攻撃力)）。
- `trueDamage`（防御力無視ダメージ X%▲）: 防御力無視ダメージの発（上の 2 つ）にだけ乗る。ほかの発には乗らない。
  - 式の中の置き場所は、表の 1 行（`damage.ts` の `TRUE_DAMAGE_BUCKET`）にして検証で決める（論点 1）。候補: (a) ほかのどの群とも別の乗数 (1 + Σ)、(b) 攻撃ダメージ▲の群 (1 + Σ攻撃ダメージ + Σ防御力無視ダメージ) に足す。(b) に決まった（10.1 節）。
- 射撃場の的の防御力は 100。防御力を引かない差は 1 発の (防御力 100 ÷ 攻撃力) ほどで小さいが、1 発の値は端数まで読めるので、変化そのものは見分けられる。

### 3.2 維持の終わりを出来事で決める `durationUntil`

```json
{
  "kind": "timed",
  "trigger": "burstUse",
  "target": "self",
  "stat": "elementDamage",
  "ref": 1,
  "durationUntil": "fullBurstEnd"
}
```

- 「解除条件：フルバーストタイムが終了した時」。付いたフレームから、次のフルバースト終了のフレームまで続く。`durationRef`・`durationSeconds`・`durationShots` とちょうど 1 つ。
- 値は `fullBurstEnd` だけにする（いま要るのはこれだけ）。フルバーストを開かずに終わることは、バーストを撃てばフルバーストが開くモデルでは起きない。

### 3.3 編成に特定のキャラがいる条件 `withCharacter`

```json
{
  "kind": "passive",
  "target": "allies",
  "stat": "trueDamage",
  "ref": 4,
  "withCharacter": { "rid": 93, "present": true }
}
```

- 自分を除く編成の枠に、`rid` のキャラが 1 体以上いる（`present: true`）/ いない（`false`）ときだけ効果を持つ。`squad`・`burstStepMix` と同じく編成で決まる静的な条件で、満たさない効果は最上位で外す（`skills/composition.ts`）。
- 「自分にフォーメーションLT 適用中」を「編成にエマ：TU がいる」と読む（論点 2）。フォーメーションLT は「自分が生存している限り」の効果で、味方が倒れない前提では戦闘中ずっと続く。LT がウンファ：TU に「適用」されるかは説明文から一意には読めない（LT の効果 1 は同じ部隊の味方全体、効果 2 は味方全体。2 人とも部隊 Absolute なのでどちらでも対象に入る）。

### 3.4 フルバーストタイムの条件 `inFullBurst`

- 2026-10-09: ウンファ：TU のカモフラージュは、中身を 2 つのきっかけで直接付ける書き方（6 節の論点 3 の (a)）から、状態の付与 2 件（中身は 1 件目）に移した（[design-named-state.md](design-named-state.md) 7.1 節）。2 つのきっかけの窓が重なる間に▲が 2 回足されていたのが 1 回になった（同 2.2 節の 2）。条件 `inFullBurst` は付与にもそのまま書く。

```json
{
  "kind": "timed",
  "trigger": { "count": "fullChargeShot" },
  "condition": { "inFullBurst": true },
  "target": "self",
  "stat": "trueDamageConversion",
  "durationRef": 1
}
```

- 発火の瞬間がフルバーストタイムの中のときだけ発火する。いまの `condition`（`selfBuffed`）の並びに足す。カウンタは条件に関係なく数える（`selfBuffed` と同じ）。満たさない発火は `conditionSkips` に出る。
- カモフラージュは「バースト使用時」と「フルバースト中のフルチャージ時」の 2 つのきっかけで付く同じ状態。中身（`trueDamageConversion`・`trueDamage`）を 2 つのきっかけそれぞれで付け、窓は和集合（`timed` の上書き延長）にする。カモフラージュという名前の状態は持たない（被弾で解除されないので、中身の窓と同じ）。

### 3.5 環境コントロールの周期と強化

```json
{ "kind": "timed", "trigger": { "everySeconds": 30, "atStart": true }, "target": "allies", "stat": "damageTaken", "ref": 1, "durationRef": 2, "withCharacter": { "rid": 95, "present": false } }
{ "kind": "timed", "trigger": { "everySeconds": 10, "atStart": true }, "target": "allies", "stat": "damageTaken", "ref": 1, "durationRef": 2, "withCharacter": { "rid": 95, "present": true } }
```

- 周期のトリガー `{ everySeconds }`（ニヒリスター編）に `atStart: true` を足す: 戦闘開始時に 1 回と、その後 k × everySeconds 秒に発火する。`timed` には、射撃に効かない stat（`damageTaken` など、1 パス目で窓を追わない stat）に限って書けるようにする。
- 再発動周期 20 秒▼（エマ S2 のフォーメーションAS の追加効果）は、周期を書き換える語彙を作らず、`withCharacter` で 30 秒と 10 秒の 2 通りに書き分ける（条件が静的なので同じ結果になる）。
- 再発動周期の起点は発動から数える（C-0305）。
- 環境コントロール強化（バースト。「環境コントロール効果によるダメージの増加倍率が 100% 効果量に対し増加」・10 秒）は、S1 の結論 C-0305 の後に、論点 6 の推奨どおり窓の切り取りの語彙 `amplifies` で書いた（8.1 節）。

```json
{
  "kind": "timed",
  "trigger": "burstUse",
  "target": "allies",
  "stat": "damageTaken",
  "durationSeconds": 10,
  "amplifies": { "skill": "skill1", "percent": 100 }
}
```

- 参照するのは、同じ枠の `skill` スロットの、同じ stat の `timed` 効果の窓（エマなら S1 の環境コントロールの 2 通り。編成の条件で外れた方は窓が無い）。
- 発火の瞬間に、自分（発動した枠）に参照する窓が効いていなければ発火しない（「自分が環境コントロール状態なら」。C-0335）。外れた発火は `conditionSkips` に出る。
- 窓は発動から 10 秒（和集合）。参照する窓が効いている所は参照する値 × percent ÷ 100 を、切れた所は発動の瞬間の参照の値 × (1 + percent ÷ 100) を同じ stat に足す（C-0336。仮説）。最初の読み（参照する窓との重なりだけ。C-0338）は V-0230 で棄却した（8.2 節）。

### 3.6 1more と追撃

```json
{ "kind": "damage", "trigger": "burstUse", "ref": 3, "damageType": "distributed", "enemyElement": "Wind" }
```

- 「1more が適用された時」は、クイーン（真）のバースト（「対象が風圧コードなら自分に 1more」）が風圧の敵に撃たれた時。新: 敵の属性の条件 `enemyElement`（敵 1 体の前提で、敵のプリセットの属性で決まる静的な条件）。満たさない効果は最上位で外す。敵の属性は `TeamInput.enemy.element`。
  - バーストの 1more の攻撃力▲も、`assumes`（「対象が風圧コード」）から `enemyElement: 'Wind'` に置き換えた（論点 4）。
- 「追撃が適用された時」は、ほかのペルソナのキャラが起こすもので、説明文と CDN からはきっかけが分からない（論点 5）。

## 4. 退化の見込み

- 足す stat・条件・欄はどれも省略できる。書かない定義の計算は変わらない（既存のテストと照合の結果も変わらない）。
- `trueDamage`・`trueDamageConversion` はバフの区間の鍵（`skills/timeline.ts` の `BUFF_FIELDS`）に入れ、calc も同じ値を使う。
- 周期のトリガーを `timed` に開いても、1 パス目は変わらない（射撃に効く stat には書けない）。

## 6. 論点（2026-10-05 にオーナーがすべて推奨どおりと決めた）

1. **防御力無視ダメージ▲の置き場所**: (a) 別の乗数 (1 + Σ)、(b) 攻撃ダメージ▲の群に足す。
   - 決定: 置き場所を表の 1 行にして語彙を作り、値は検証で決める。最初の検証（5 節の 3）は攻撃ダメージ▲の乗らない編成で撮り、(a)・(b) は区別しない。区別は、攻撃ダメージ▲を持つ機構が確定したキャラを足した 2 本目で行う。
   - 2026-10-09: 炸裂弾で防御力無視ダメージ▲と発射体爆発ダメージ▲（攻撃ダメージ▲の群。C-0205）が 1 つの和で掛かっていた（C-0376）ので、(a) を外し、`TRUE_DAMAGE_BUCKET` を `attackDamage` にした（10.1 節）。
   - 2026-10-10: ヘルムの攻撃ダメージ▲を足した撮影（V-0409）で、防御力無視ダメージ▲は攻撃ダメージ▲と 1 つの和だった（C-0525）。(b) で決まり、モデルは変えない（10.1 節）。
2. **フォーメーションの条件の読み**: (a) 「編成に相手のキャラがいる」の静的な条件 `withCharacter`（3.3 節）、(b) フォーメーションという名前の状態を持つ仕組みを作る。
   - 決定: (a)。味方が倒れない前提では、生存している限りの効果は戦闘中ずっと続き、(b) と同じ結果になる。読みは `assumes` に書き、5 節の 6 で確かめる。
3. **カモフラージュの書き方**: (a) 中身を 2 つのきっかけで直接付ける（3.4 節。新しいのは条件 `inFullBurst` だけ）、(b) 名前の付いた状態の語彙を作る。
   - 決定: (a)。被弾で解除されない前提では窓が同じになる。（2026-10-09 に状態の付与へ移した。3.4 節）
4. **`durationUntil` と `enemyElement`**: 3.2・3.6 節の形でよいか。`enemyElement` を足すなら、クイーン（真）のバーストの 1more の `assumes` も置き換えるか。
   - 決定: どちらも足す。`assumes` の置き換えは、灼熱の的の録画の残差が動くかを確かめてから同じ PR で行う（残差は動かなかった）。
5. **追撃とバトンタッチ**: ほかのペルソナのキャラ（コラボ）がいないと起きない。(a) 今のまま `unimplemented`（理由を「ペルソナのキャラがいる編成のきっかけが分からない」に直す）、(b) `outOfScope` にする。
   - 決定: (a)。編成次第でモデルの前提の中で起きうるので、前提の外ではない。
6. **環境コントロールの周期と強化**: 周期は 3.5 節の形（`atStart` と `withCharacter` の書き分け）でよいか。強化（バースト）は、(a) 環境コントロールの窓に重なる部分だけ同じ値の `damageTaken` を足す語彙（窓の切り取り）を作る、(b) エマ：TU S1 の結論が出るまで作らない。
   - 決定: 周期は 3.5 節の形。強化は (b)。周期の起点と窓の長さが確かまってから、切り取りの要る範囲を決める（C-0305 の後に `amplifies` を足した。8.1 節）。
7. **進める順（課題の優先順位）**: 5 節の表の順。

## 8. 実装の記録（2026-10-05）

- `durationUntil`・`inFullBurst`・周期のトリガーは、1 パス目で窓を追わない stat にだけ書ける（`isFirstPassTrackedStat`。攻撃力・射撃に効く stat・状態の stat は不可）。`durationUntil` はスタックと組み合わせられない。1 パス目は変えていない。
- 静的な条件 `withCharacter`・`enemyElement` は `passive`・`timed`・`damage` に書ける。
- 1 発の式（`damage.ts`）: `isTrueDamageShot`（`trueDamageConversion` の窓か、`trueDamage` の使用武器の変更）なら、通常攻撃の基礎を max(1, 攻撃力) にし、`trueDamageMultiplier` を掛ける。射撃ごとの倍率ダメージの基礎は変えない。

### 8.1 環境コントロール強化の語彙（2026-10-06）

- `timed` の `amplifies: { skill, percent }`。値は参照する効果から取るので `ref`・`scaling`・`decrease` は書かない。スタック・条件・発数や出来事の維持・順位の対象とは組み合わせない。1 パス目で窓を追う stat には書けない。
- 窓は `planBuffTimeline` の 2.5 段目で、1〜2 段目の窓から同じ枠・参照するスロット・同じ stat の窓を拾い、発動の瞬間の状態を見て足す。1 パス目では追わない。
- 定義: エマ：TU（93）の burst の effects[1]。

### 8.2 V-0230 の結果と直し（2026-10-06）

- 録画 0263 で、強化は環境コントロールの窓が切れても発動から 10 秒続き、発動の瞬間に窓の外なら付かなかった。値は 2 倍の読みよりわずかに大きい。
- 同日、オーナーが V-0230 の論点をすべて推奨どおりと決めた: 1 (a) `amplifies` の窓を切り取らない、2 (a) 値は 2 倍の読みのままでずれは残差に残す、3 C-0338 を棄却して置き換える。
- 結論: C-0335（条件。確定）、C-0336（窓と値。仮説）、C-0337（同じバーストの攻撃力▲。確定）。C-0338 は棄却。

## 9. 使用武器変更の武器のパラメータ（2026-10-06 起案・承認・実装）

[backlog.md](backlog.md) 6 節の「使用武器変更の武器のパラメータの語彙」の行。5 節の 4 の残り（ウンファ：TU のバーストの徹甲炸裂弾の 1 発。値は C-0313）。

### 9.1 何が足りないか

- 説明文（`data/characters/95.json` の burst）: 「使用武器変更：チャージ時間：0.3秒・ダメージ：最終攻撃力の {01}％の防御力無視ダメージ・フルチャージダメージ：300％・最大装弾数：{02}発」。**維持時間が無い**（モダニアの殲滅モードは「{NN}秒間維持」）。
- それまでの `weaponChange` は、変更後の武器に基礎の武器のチャージ時間・フルチャージ倍率・最大装弾数を写し（`skills/resolve.ts` の `changedWeaponShot`）、維持は秒（`durationRef`・`durationSeconds` のどちらかが必須）で終わる。
- C-0313 で確定していること: 1 発だけ撃つ、その 1 発の値、倍率グループは基礎の SR と同じ、撃った後は基礎の SR に戻る。
- 決めることは、**変更がいつ終わるか**（維持時間の無い変更）と、**戻るフレームと戻った後の基礎の武器**。

### 9.2 語彙の案

```json
{
  "kind": "weaponChange",
  "trigger": "burstUse",
  "damageRef": 1,
  "trueDamage": true,
  "chargeTimeSeconds": 0.3,
  "fullChargeDamage": 300,
  "maxAmmoRef": 2
}
```

- `chargeTimeSeconds`（即値・秒）・`fullChargeDamage`（即値・%）: 説明文に `description_value` でなく数字で書かれている（Lv で変わらない）ので即値にする（データ明記）。`maxAmmoRef` は `description_value_NN`。
- どれも省略できる。省略した欄は今のまま基礎の武器を写す（モダニアの定義と計算は変わらない）。チャージの欄は基礎の武器がチャージ武器のときだけ書ける（ほかは解決で拒否）。
- 1 発の式（`damage.ts`）は変えない。武器倍率・フルチャージ倍率・コア倍率を `buffs.weapon.shot` から取るので、写した値を差し替えれば C-0313 の式になる（コア・会心・距離ボーナスは基礎の SR と同じ = `WEAPON_CHANGE_CORE` の `base`）。
- calc は、射撃に効く stat（`weapon` を含む）の窓を持つグループの発を 1 パス目の射撃の列で数える（`calc/model.ts` の `hasFiringWindow`）ので、1 パス目が炸裂弾の 1 発を撃てば calc と sim の両方に入る。

### 9.3 論点（2026-10-06 にオーナーがすべて推奨どおりと決めた）

8. **維持時間の無い変更の終わり方**
   - (a) **撃ち切りで終わる**（決定）: `maxAmmoRef` を書き、維持の欄（`durationRef`・`durationSeconds`）を書かない `weaponChange` は、変更後の武器をリロードせず、最後の 1 発を撃ったフレームの次のフレームに基礎の武器に戻す。窓の終わりは 1 パス目の射手が決め、`planBuffTimeline` の `weapon` の窓は 1 パス目の切り替えのフレームを使う（1 パス目で窓を閉じる新しい仕組み）。C-0313 の「1 発だけ撃ち、撃った後は基礎の SR に戻る」をそのまま書け、装弾数と終わりが同じ値（`maxAmmoRef`）から決まる。
   - (b) `timed` の `durationShots`（発数の維持）を `weaponChange` に開く: `weapon` に限って 1 パス目でも追う必要があり、(a) と同じ仕組みが要るうえ、装弾数と別に同じ 1 を 2 か所に書く。採らない。
   - (c) 秒で書く: 根拠が無い。採らない。
   - 維持の欄と `maxAmmoRef` を両方書いた変更（秒の途中で撃ち切る）は、いま要る定義が無いので検証で弾く。
9. **戻るフレームと戻った後の基礎の武器**: どちらも根拠の結論が無い（録画 0232 の発の時刻は `0232-01`・`0232-02`・`0232-04`・`0232-12`）。
   - (a) **いまの戻し方（`frame/shooter.ts` の `resumeShooter`。満タンのマガジンで、リロードの後の 1 発目と同じ待ち）のまま**（決定）: モダニア由来の決まりで、リロードまでの発数は録画と同じ並びになる見込み。1 発目の待ちは録画より短くなる見込みで、そのずれは残差として残す（係数で埋めない）。定義の `assumes` に「戻りの待ちは未確定」と書く。
   - (b) 戻り方を確かめる検証を先に起こし、語彙の実装は検証の後にする。採らない。
   - どちらでも、カモフラージュの窓に入る基礎の SR の発の数がモデルと録画で違いうる（`0232-11`）。これは 1 発の値でなく発の時刻の差で、C-0311 の結論は変わらない。
10. **炸裂弾の発の時刻**: 持ち替えの次のフレームから、チャージ武器の 1 発目の待ち（`cadence.ts` の `firstShotFrames`。構え + チャージ 0.3 秒 + 満ちてから撃つまで）で撃つ（`weaponChangeShooter`）。録画の着弾との差（C-0312 の `assumes`）は新しいパラメータで埋めず、残差として残す。
11. **炸裂弾の発のバーストゲージ**: 根拠が無い。(a) いまの決まりのまま基礎の SR の 1 発の量を写し、`assumes` に未確定と書く（決定。モダニアと同じ決まりで、ゲージの量は撮影で確かめる）、(b) 0 にする（根拠が無い点は同じ）。

### 9.5 実装の記録（2026-10-06）

- 撃ち切りで終わる変更は、解決後に `durationFrames` 0・`durationUntil: 'ammoSpent'`（解決後だけの値。`ResolvedDurationUntil`）を持つ。
- 1 パス目（`frame/firstPass.ts`）: `ammoSpent` の変更は窓を戦闘の終わりまで開け、変更後の射手が最後の弾丸を撃ったら `closeWeaponChange` で次のフレームに閉じ、`ShotLog.weaponChangeEnds` に書く。基礎の武器への戻しは `resumeShooter`（論点 9）。
- 区間（`skills/timeline.ts`）: `untilWeaponChangeEndWindows` が、持ち替えるフレームから `weaponChangeEnds` までの窓を作る。1 パス目の窓と一致する（`__tests__/eunhwaTuWeaponChange.test.ts`）。

### 9.6 論点 12（2026-10-06 にオーナーが推奨 (a) と決めた）: 徹甲炸裂弾の受けるダメージ▲が炸裂弾自身に乗る

- 起きていたこと（9.5 節の実装の時点）: 定義の受けるダメージ▲（burst の effects[0]。C-0312）は、バースト使用のフレームから 10 秒の窓で付く。炸裂弾はその後に撃つので、モデルの炸裂弾の 1 発に受けるダメージ▲が乗り、`0232-10` の値のちょうどその倍率になった。確定の C-0312 の「炸裂弾自身には乗らない」と矛盾する。論点 10 で窓の起点の移しはこの変更に含めないとしたが、炸裂弾をモデルに入れると、起点のずれが炸裂弾の値そのものに効く。
- 選択肢:
  - (a) **起点を炸裂弾の発にする語彙を足す**（決定）: 射撃の回数トリガーの種類に `weaponChangeShot`（自分の使用武器の変更で撃った発。`ShotLog` に発のフレームを書く）を足し、受けるダメージ▲を `{ "count": "weaponChangeShot" }` で付ける。射撃の回数トリガーの窓は発の次のフレームから（Stage 8 の規則）なので、炸裂弾自身には乗らず、次の発から乗る（C-0312 の結論と同じ）。窓の終わりは録画の終わりの幅（`0232-12`）の中にある。受けるダメージ▲は 1 パス目で窓を追わない stat なので、1 パス目は変わらない。新しいのはトリガーの種類 1 つで、C-0312・C-0313 の両方の結論どおりになる。
  - (b) 炸裂弾の定義を入れたまま、受けるダメージ▲の窓をバースト使用時のままにする: C-0312 と矛盾する。採らない。
  - (c) 炸裂弾の定義を戻し、語彙だけを入れる: 炸裂弾の値は入らないが、矛盾はしない。(a) が決まるまでの退避。

### 9.7 論点 12 の実装の記録（2026-10-06）

## 10. 炸裂弾の発射体爆発ダメージ▲と、2 つの▲の置き場所（2026-10-09 実装）

[backlog.md](backlog.md) 6 節の「語彙を足す」の行。確定の C-0376（V-0249。炸裂弾に発射体爆発ダメージ▲が乗り、防御力無視ダメージ▲と 1 つの和で掛かる）をモデルに入れた。6 節の論点 1 の進め方（置き場所を表の 1 行にして検証で決める）に沿う。

### 10.1 置き場所の決め方

- 候補は 6 節の論点 1 の (a) 別の乗数・(b) 攻撃ダメージ▲の群。発射体爆発ダメージ▲は攻撃ダメージ▲の群（`PROJECTILE_EXPLOSION_BUCKET` が `attackDamage`。C-0205）なので、(a) では炸裂弾は (1 + Σ防御力無視ダメージ) × (1 + Σ発射体爆発ダメージ) の積になり、C-0376 の和と合わない。(b) なら 3 つの▲が 1 つの和 (1 + Σ攻撃ダメージ + Σ発射体爆発ダメージ + Σ防御力無視ダメージ) になり、攻撃ダメージ▲の無い録画 0287 では C-0376 の和そのものになる。`TRUE_DAMAGE_BUCKET` を `attackDamage` にした。
- C-0311・C-0375 は攻撃ダメージ▲の無い録画の結論なので、(a)・(b) のどちらでも同じ値で、変わらない。
- 「攻撃ダメージ▲を含まず、防御力無視ダメージ▲と発射体爆発ダメージ▲だけの和」(c) は、攻撃ダメージ▲の無い録画では (b) と同じ値になる。2026-10-10 に V-0409（フラワー + ウンファ：TU + ヘルム（宝物版。III・撃たない））で分けた。フルバーストの中のカモフラージュの発（ヘルムの攻撃ダメージ▲の中）は (b) と端数まで合い、(c) と、攻撃ダメージ▲が乗らない読みの値は出なかった（C-0525）。3 つの▲は 1 つの和で、`TRUE_DAMAGE_BUCKET` は `attackDamage` のまま。

### 10.2 語彙

```json
{ "kind": "weaponChange", "trigger": "burstUse", "damageRef": 1, "trueDamage": true, "projectileExplosion": true, … }
```

- `weaponChange` の `projectileExplosion: true`（`skills/types.ts`。`true` だけ）: 変更後の武器の発が発射体の爆発を持つ。解決で `ChangedWeapon.projectileExplosion` に写し（`skills/resolve.ts`）、`damage.ts` の `hasProjectileExplosion(shot, buffs)` が、基礎の武器の発射体（RL の `explosionRange`）か、この印で真になる。基礎の武器の発射体（着弾の範囲など。`frame/landing.ts`）は変えない。
- 1 発の式（`damage.ts`）: `trueDamageMultiplier(shot, buffs)` は、`attackDamage` の枠のとき、同じ枠に入る発射体爆発ダメージ▲（爆発を持つ発だけ）を分母に含める。`projectileExplosionMultiplier` との積が (1 + ΣAD + ΣPE + ΣTD) ÷ (1 + ΣAD) になる。
- calc と sim: どちらも `computeTriggerDamage` を通るので、両方に効く。

### 10.3 定義と照合

- 定義（`data/skills/95.json` の burst の effects[1]）: `projectileExplosion: true` と `claims` に C-0376。burst のスロットは supported。
