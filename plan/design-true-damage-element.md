## 1. 何が困っているか

- 3 キャラの説明文には、いまの語彙で書けない効果がまとまって残っている。中心は 2 つ。
  - **防御力無視ダメージ**: 「通常攻撃が防御力無視ダメージに変化」「防御力無視ダメージ X%▲」「最終攻撃力の X% の防御力無視ダメージ（使用武器変更）」。モデルの 1 発の式は max(1, 攻撃力 − 防御力) で、防御力を引かない発も、防御力無視ダメージだけに乗る▲も持てない。
  - **有利コードの攻撃ダメージ▲**（スキル由来）: stat `elementDamage` は Stage 13 に OL・キューブの効果層のために足した（C-0119）。スキルの DSL にも書けるが、スキルの効果に使った定義はまだ無く、OL・キューブと同じ群に入るかの根拠も無い。
- ほかに、同じスロットの中で次が足りない（「等」の中身）。
  - フォーメーション（エマ：TU と ウンファ：TU が両方いるときの追加効果）の条件。
  - 「フルバーストタイムなら」（フルチャージの発の条件）。
  - 「解除条件：フルバーストタイムが終了した時」（維持の終わりが出来事で決まる）。
  - 「1more が適用された時」「追撃が適用された時」のきっかけ。
  - 環境コントロールの再発動周期（戦闘開始と、その後の一定間隔）と、その強化（バースト）。

## 3. 語彙の案

どれも、書かない定義では計算が今と同じになる（退化しない）。値は説明文の `ref` で指し、実測値は書かない。

### 3.1 防御力無視ダメージ

```json
{ "kind": "timed", "trigger": "burstUse", "target": "self", "stat": "trueDamageConversion", "durationRef": 1 }
{ "kind": "timed", "trigger": "burstUse", "target": "self", "stat": "trueDamage", "ref": 2, "durationRef": 1 }
{ "kind": "weaponChange", "damageRef": 1, "trueDamage": true, "durationSeconds": … }
```

- `trueDamageConversion`（フラグの stat。`infiniteAmmo` と同じく `ref` を書かない。`timed` の `self` だけ）: 窓のあいだ、自分の通常攻撃の 1 発の基礎を max(1, 攻撃力 − 防御力) から max(1, 攻撃力) にする。射撃ごとの倍率ダメージ・スキルの倍率ダメージは変えない（説明文は「通常攻撃が」）。
- `weaponChange` の `trueDamage: true`: 変更後の武器の 1 発を防御力無視ダメージにする（基礎は max(1, 攻撃力)）。
- `trueDamage`（防御力無視ダメージ X%▲）: 防御力無視ダメージの発（上の 2 つ）にだけ乗る。ほかの発には乗らない。
  - **式の中の置き場所は根拠が無い**（論点 1）。発射体爆発ダメージ▲と同じく、置き場所を表の 1 行（`damage.ts` の `TRUE_DAMAGE_BUCKET`）にして、検証で決める。
  - 候補: (a) ほかのどの群とも別の乗数 (1 + Σ)、(b) 攻撃ダメージ▲の群 (1 + Σ攻撃ダメージ + Σ防御力無視ダメージ) に足す。
- 射撃場の的の防御力は 100（`range-bigarms-*`）。防御力を引かない差は 1 発の (防御力 100 ÷ 攻撃力) ほどで小さいが、1 発の値は端数まで読める（012 の 1 ペレットは許容 ±1 で合う）ので、変化そのものは見分けられる。

### 3.2 維持の終わりを出来事で決める `durationUntil`

```json
{
  "kind": "timed",
  "trigger": "burstUse",
  "target": "self",
  "stat": "elementDamage",
  "ref": 1,
  "durationUntil": "fullBurstEnd"
}
```

- 「解除条件：フルバーストタイムが終了した時」。付いたフレームから、次のフルバースト終了のフレームまで続く。`durationRef`・`durationSeconds`・`durationShots` とちょうど 1 つ。
- 値は `fullBurstEnd` だけにする（いま要るのはこれだけ）。フルバーストを開かずに終わることは、バーストを撃てばフルバーストが開くモデルでは起きない。

### 3.3 編成に特定のキャラがいる条件 `withCharacter`

```json
{
  "kind": "passive",
  "target": "allies",
  "stat": "trueDamage",
  "ref": 4,
  "withCharacter": { "rid": 93, "present": true }
}
```

- 自分を除く編成の枠に、`rid` のキャラが 1 体以上いる（`present: true`）/ いない（`false`）ときだけ効果を持つ。`squad`・`burstStepMix` と同じく編成で決まる静的な条件で、満たさない効果は最上位で外す（`skills/composition.ts`）。
- 「自分にフォーメーションLT 適用中」を「編成にエマ：TU がいる」と読む（論点 2）。フォーメーションLT は「自分が生存している限り」の効果で、味方が倒れない前提では戦闘中ずっと続く。LT がウンファ：TU に「適用」されるかは説明文から一意には読めない（LT の効果 1 は同じ部隊の味方全体、効果 2 は味方全体。2 人とも部隊 Absolute なのでどちらでも対象に入る）。

### 3.4 フルバーストタイムの条件 `inFullBurst`

```json
{
  "kind": "timed",
  "trigger": { "count": "fullChargeShot" },
  "condition": { "inFullBurst": true },
  "target": "self",
  "stat": "trueDamageConversion",
  "durationRef": 1
}
```

- 発火の瞬間がフルバーストタイムの中のときだけ発火する。いまの `condition`（`selfBuffed`）の並びに足す。カウンタは条件に関係なく数える（`selfBuffed` と同じ）。
- カモフラージュは「バースト使用時」と「フルバースト中のフルチャージ時」の 2 つのきっかけで付く同じ状態。中身（`trueDamageConversion`・`trueDamage`）を 2 つのきっかけそれぞれで付け、窓は和集合（`timed` の上書き延長）にする。カモフラージュという名前の状態は持たない（被弾で解除されないので、中身の窓と同じ）。

### 3.5 環境コントロールの周期と強化

```json
{ "kind": "timed", "trigger": { "everySeconds": 30, "atStart": true }, "target": "allies", "stat": "damageTaken", "ref": 1, "durationRef": 2, "withCharacter": { "rid": 95, "present": false } }
{ "kind": "timed", "trigger": { "everySeconds": 10, "atStart": true }, "target": "allies", "stat": "damageTaken", "ref": 1, "durationRef": 2, "withCharacter": { "rid": 95, "present": true } }
```

- 周期のトリガー `{ everySeconds }`（ニヒリスター編）に `atStart: true` を足す: 戦闘開始時に 1 回と、その後 k × everySeconds 秒に発火する。いまは `damage`・`dot` にだけ書ける（1 パス目の出来事の列にタイマーのフレームが無いため）。`timed` には、射撃に効かない stat（`damageTaken` など、1 パス目で窓を追わない stat）に限って書けるようにする。
- 再発動周期 20 秒▼（エマ S2 のフォーメーションAS の追加効果）は、周期を書き換える語彙を作らず、`withCharacter` で 30 秒と 10 秒の 2 通りに書き分ける（条件が静的なので同じ結果になる）。
- 再発動周期の起点（効果が切れてからか、発動からか）は説明文から一意に読めない。上の案は発動から数える読み（論点 6 の撮影で確かめる）。
- 環境コントロール強化（バースト。「環境コントロール効果によるダメージの増加倍率が 100% 効果量に対し増加」・10 秒）は、環境コントロールの窓の中だけ、その▲を 2 倍にする効果。書き方は論点 6。
- 2026-10-06（S1 の結論 C-0305 の後。論点 6 の推奨どおり）: 窓の切り取りの語彙 `amplifies` を足した（8.1 節）。

```json
{
  "kind": "timed",
  "trigger": "burstUse",
  "target": "allies",
  "stat": "damageTaken",
  "durationSeconds": 10,
  "amplifies": { "skill": "skill1", "percent": 100 }
}
```

- 参照するのは、同じ枠の `skill` スロットの、同じ stat の `timed` 効果の窓（エマなら S1 の環境コントロールの 2 通り。編成の条件で外れた方は窓が無い）。
- 発火の瞬間に、自分（発動した枠）に参照する窓が効いていなければ発火しない（「自分が環境コントロール状態なら」）。外れた発火は `conditionSkips` に出る。
- ~~窓は、発動から 10 秒（和集合）と参照する窓の重なり~~（V-0230 の `263-03` で外れた。8.2 節）。窓は発動から 10 秒（和集合）。参照する窓が効いている所は参照する値 × percent ÷ 100 を、切れた所は発動の瞬間の参照の値 × (1 + percent ÷ 100) を同じ stat に足す（受けるダメージ▲なら同じ群の中で合計 3.9% → 7.8% を 10 秒保つ）。
- 最初の読み（重なりだけ）は仮説の結論 C-0338 にし、V-0230 で撮って棄却した。いまは条件が C-0335（確定）、窓と値が C-0336（仮説。2 倍より 1 ヒットで +1.7 大きい）。再発動周期の起点は C-0305 で確定（発動から数える）なので、それで窓を作る。

### 3.6 1more と追撃

```json
{ "kind": "damage", "trigger": "burstUse", "ref": 3, "damageType": "distributed", "enemyElement": "Wind" }
```

- 「1more が適用された時」は、クイーン（真）のバースト（「対象が風圧コードなら自分に 1more」）が風圧の敵に撃たれた時。新: 敵の属性の条件 `enemyElement`（敵 1 体の前提で、敵のプリセットの属性で決まる静的な条件）。満たさない効果は最上位で外す。
  - いまバーストの 1more の攻撃力▲は `assumes`（「対象が風圧コード」）で書いている。`enemyElement` を足すなら、こちらもそれに置き換えられる（灼熱の的の録画 021・040 では、1more の攻撃力▲は付かないのが正しい。置き換えで残差が動くかは実装のときに確かめる）。
- 「追撃が適用された時」は、ほかのペルソナのキャラが起こすもので、説明文と CDN からはきっかけが分からない（論点 5）。

## 4. 退化の見込み

- 足す stat・条件・欄はどれも省略できる。書かない定義の計算は変わらない（既存のテストと照合の結果も変わらない）。
- `trueDamage`・`trueDamageConversion` はバフの区間の鍵（`skills/timeline.ts` の `BUFF_FIELDS`）に入れ、calc も同じ値を使う。
- 周期のトリガーを `timed` に開くと、1 パス目は変わらない（射撃に効く stat には書けない）。

## 9. 使用武器変更の武器のパラメータ（2026-10-06 起案・承認・実装）

[backlog.md](backlog.md) 6 節の「使用武器変更の武器のパラメータの語彙」の行。5 節の 4 の残り（ウンファ：TU のバーストの徹甲炸裂弾の 1 発。値は C-0313）。

### 9.1 何が足りないか

- 説明文（`data/characters/95.json` の burst）: 「使用武器変更：チャージ時間：0.3秒・ダメージ：最終攻撃力の {01}％の防御力無視ダメージ・フルチャージダメージ：300％・最大装弾数：{02}発」。**維持時間が無い**（モダニアの殲滅モードは「{NN}秒間維持」）。
- いまの `weaponChange` は、変更後の武器に基礎の武器のチャージ時間・フルチャージ倍率・最大装弾数を写し（`skills/resolve.ts` の `changedWeaponShot`）、維持は秒（`durationRef`・`durationSeconds` のどちらかが必須）で終わる。
- C-0313 で確定していること: 1 発だけ撃つ、その 1 発の値（max(1, 攻撃力) × 105.6% × (300% + チャージダメージ▲) × (1 + 防御力無視ダメージ▲)）、倍率グループは基礎の SR と同じ、撃った後は基礎の SR に戻る。
- 5 節の表は「語彙（変更後の武器のチャージ時間・フルチャージ倍率・装弾数）を足せば定義に書ける」までで、**変更がいつ終わるか**（維持時間の無い変更）と、**戻るフレームと戻った後の基礎の武器**は決めていない。

### 9.2 語彙の案

```json
{
  "kind": "weaponChange",
  "trigger": "burstUse",
  "damageRef": 1,
  "trueDamage": true,
  "chargeTimeSeconds": 0.3,
  "fullChargeDamage": 300,
  "maxAmmoRef": 2
}
```

- `chargeTimeSeconds`（即値・秒）・`fullChargeDamage`（即値・%）: 説明文に `description_value` でなく数字で書かれている（Lv で変わらない）ので即値にする（データ明記）。`maxAmmoRef` は `description_value_NN`。
- どれも省略できる。省略した欄は今のまま基礎の武器を写す（モダニアの定義と計算は変わらない）。
- 1 発の式（`damage.ts`）は変えない。いまも武器倍率・フルチャージ倍率・コア倍率を `buffs.weapon.shot` から取るので、写した値を差し替えれば C-0313 の式になる（コア・会心・距離ボーナスは基礎の SR と同じ = `WEAPON_CHANGE_CORE` の `base`）。
- calc は、射撃に効く stat（`weapon` を含む）の窓を持つグループの発を 1 パス目の射撃の列で数える（`calc/model.ts` の `hasFiringWindow`）ので、1 パス目が炸裂弾の 1 発を撃てば calc と sim の両方に入る。

### 9.3 論点（2026-10-06 にオーナーがすべて推奨どおりと決めた）

8. **維持時間の無い変更の終わり方**
   - (a) **撃ち切りで終わる**（推奨）: `maxAmmoRef` を書き、維持の欄（`durationRef`・`durationSeconds`）を書かない `weaponChange` は、変更後の武器をリロードせず、最後の 1 発を撃ったフレームの次のフレームに基礎の武器に戻す。窓の終わりは 1 パス目の射手が決め、`planBuffTimeline` の `weapon` の窓は 1 パス目の切り替えのフレームを使う（1 パス目で窓を閉じる新しい仕組み）。C-0313 の「1 発だけ撃ち、撃った後は基礎の SR に戻る」をそのまま書け、装弾数と終わりが同じ値（`maxAmmoRef`）から決まる。
   - (b) `timed` の `durationShots`（発数の維持）を `weaponChange` に開く: `durationShots` はいま 1 パス目のループでは追わない（`planBuffTimeline` が射撃の列から作る）ので、`weapon` に限って 1 パス目でも追う必要があり、(a) と同じ仕組みが要る。装弾数と別に同じ 1 を 2 か所に書く。
   - (c) 秒で書く: 根拠が無い。採らない。
   - 維持の欄と `maxAmmoRef` を両方書いた変更（秒の途中で撃ち切る）は、いま要る定義が無いので検証で弾く（推奨）。
9. **戻るフレームと戻った後の基礎の武器**: どちらも根拠の結論が無い。録画 232 では、炸裂弾の着弾（f2704）の後の基礎の SR の 1 発目が f2841（+137f）で、そこから 82f ごとに 6 発（`232-02`・`232-01`・`232-04`）撃ってリロードした（4 回のバーストとも、外の最初の発はリロードの後。`232-12`）。
   - (a) **いまの戻し方（`frame/shooter.ts` の `resumeShooter`。満タンのマガジンで、リロードの後の 1 発目と同じ待ち）のまま**（推奨）: モダニア由来の決まりで、6 発でリロードは録画と同じ並びになる見込み。1 発目の待ちは録画より短くなる見込みで、そのずれは残差として残す（係数で埋めない）。定義の `assumes` に「戻りの待ちは未確定」と書き、実装のときに `records:check` の差を検証記録に残す。
   - (b) 戻り方を確かめる検証を先に起こす（録画 232・233 の発の時刻で読めるかを見る。撮影は要らない見込み）。語彙の実装は検証の後。

### 10.1 置き場所の決め方

- 候補は 6 節の論点 1 の (a) 別の乗数・(b) 攻撃ダメージ▲の群。発射体爆発ダメージ▲は攻撃ダメージ▲の群（`PROJECTILE_EXPLOSION_BUCKET` が `attackDamage`。C-0205）なので、(a) では炸裂弾は (1 + Σ防御力無視ダメージ) × (1 + Σ発射体爆発ダメージ) の積になり、C-0376 の和と合わない。(b) なら 3 つの▲が 1 つの和 (1 + Σ攻撃ダメージ + Σ発射体爆発ダメージ + Σ防御力無視ダメージ) になり、攻撃ダメージ▲の無い録画 287 では C-0376 の和そのものになる。`TRUE_DAMAGE_BUCKET` を `attackDamage` にした。
- C-0311・C-0375 は攻撃ダメージ▲の無い録画の結論なので、(a)・(b) のどちらでも同じ値で、変わらない。
