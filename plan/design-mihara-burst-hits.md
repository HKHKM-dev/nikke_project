## 0. 要約

- ミハラ（161）のバーストスキルダメージは 3 等分の 3 ヒットに分かれ、フルバースト補正が乗らない（C-0564）。追加ダメージ（`burst.effects[1]`）は 3 ヒットのそれぞれと同じフレームに出て、フルバースト補正が乗る（C-0565）。モデルは、バーストスキルダメージを 00.00 の 1 ヒット、追加ダメージを発動のフレームに 1 回（補正なし）出している。
- 提案
  - **III の発動から 1 ヒット目までの遅れを録画 0469・0470 で読んだ**（2 節）: III のタイマーの 00.00 から動画で 39f（止まり 22f を含む）。表の値は 17f。
  - **分かれたヒットの表にミハラの行を足す**（3.1 節）: `hitFrames: 17`・`effectFrames: 0`・`hitOffsets: [0, 10, 22]`。バーストスキルダメージにフルバースト補正が乗らないのは、いまのモデルの規則のまま（`BURST_SKILL_FULL_BURST_BONUS = false`）で足りる。
  - **damage に「分かれたヒットごとに出る」印を足す**（3.2 節の案 P-1）: `perBurstHit: true`。burstUse の damage を、発動のヒットのフレームの列（`hitFramesOf`）のそれぞれに、等分しない倍率で出す。条件は効果の発火のフレームで 1 回だけ判定し（C-0566 を保つ）、撃つ側のバフは発動の直前で固定、フルバースト補正はヒットのフレームで決める。

## 3. 案

### 3.1 バーストスキルダメージ（論点 1）

- `MEASURED_BURST_DELAYS` に `{ resourceIds: [161], delays: { hitFrames: 17, effectFrames: 0, hitOffsets: [0, 10, 22] }, claim: <2 節の結論>・C-0564 }` を足す。倍率は等分（design-burst-split-hits.md の D-1）。
- フルバースト補正は、いまの規則（バーストの倍率ダメージには乗せない）のまま。新しい分岐は要らない。ヒットごとの撃つ側のバフは発動の時点、敵の側のデバフはヒットの時点（design-burst-split-hits.md 4.2 節のまま）。
- 会心が 3 ヒットでそろうことは、期待値のモデルでは値に効かない（notes に書く）。

### 3.2 追加ダメージの語彙（論点 2）

| 案                                        | 中身                                                                                                                                                        | 長所                                                                                                | 短所                                                                                                                                           |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| **P-1 damage の印 `perBurstHit`（推奨）** | trigger が `burstUse` の damage だけに書ける `perBurstHit: true`。発火（効果のフレーム）ごとに、その発動の `hitFramesOf` のそれぞれへ、倍率を等分せずに出す | 条件の判定は今の発火のフレームのまま（C-0566 を変えない）。トリガーの仕組み（出来事の列）を触らない | damage の欄が 1 つ増える                                                                                                                       |
| P-2 新しいトリガー `burstHit`             | 「自分のバーストの倍率ダメージが当たった時」を出来事の列に足す                                                                                              | ほかの効果（timed など）にも使える                                                                  | 条件がヒットのフレームで判定されるので、2 回目のバーストで同じ発動のペインロード 2 を見てしまう（C-0566 と食い違う）。出来事の列の変更が大きい |

- P-1 の決まり:
  - 時刻: 発火のフレーム f（`effectFrameOf`）の発動の `hitFramesOf`。戦闘の終わりを越えるヒットは出さない。表に行の無い・1 ヒットのキャラなら `hitFrameOf` の 1 回（III は 00.00）。
  - 条件（`condition`）: f で 1 回判定し、成り立てば全部のヒットに出す。
  - バフ: burstUse の damage のいまの規則（発動の直前で固定。`burstHitBuffs` に発動のフレームとヒットのフレームを渡し、敵の側のデバフだけヒットの時点）。追加ダメージの値（438,441）はペインロード 1 が前の回から付いている回だけなので、どちらの時点でも同じで、録画では見分けられない。
  - フルバースト補正: ヒットのフレームがフルバースト中なら乗る（いまの `isInFullBurst(schedule, frame)` をヒットのフレームで見る）。
  - 倍率: 等分しない（1 ヒットごとに 266.4%。`0469-05` の値）。
  - 書ける組み合わせ: trigger が `burstUse`、`delayFrames` と併用しない、sequential のバーストでは書けない（分かれたヒットと同じ理由）。
- 定義: `161.json` の `burst.effects[1]` に `"perBurstHit": true` と `claims: ["C-0566", "C-0565"]`。

### 3.3 結論と notes（論点 3）

- C-0564: 反復実測のまま確定に上げる（`0469-07`・`0470-07` が許容内になる。decidedOn は 469）。モデルの欄を表の行に書き直す。
- C-0565: 1 ヒットの値が式と 1 の位まで合う（438,441.12）ので、等級を **厳密一致** に上げて確定にする。ヒットの数（9）は 2 本で同じ。モデルの欄を `perBurstHit` に書き直す。
- 2 節の遅れ: 新しい結論 C-0575（反復実測・確定）。
- `161.json` の `burst.notes`: notes[1]（分かれたヒットの modeling）は「会心は 3 ヒットでそろう（期待値のモデルでは値に効かない）」に書き直す。notes[2]（unimplemented）はモデルに入ったので消す。
- minimal: C-0563・C-0566 の印（`ミハラ burst.notes[2]`）は、消す notes を指すので外す。`npm run records:minimal` で、新しい要素の警告が出ないか見る。

## 4. 退化

- `perBurstHit` を書かない damage と、表に行の無いキャラは、いまの挙動のまま。ミハラ以外の値は変わらない見込み（`npm run records:check` の差分で確かめる）。

## 6. 論点

1. 遅れ 17f（動画 39f の最も多い値）を表の値にし、新しい結論（反復実測で確定）にしてよいか。
2. 追加ダメージの語彙は P-1（damage の `perBurstHit`）でよいか。バフは発動の直前で固定（いまの burstUse の damage の規則）でよいか。
3. C-0565 の等級を単独実測から厳密一致に上げて確定にしてよいか。notes[2] を消し、minimal の印を外してよいか。

- 2026-10-17 のオーナーの決定: 論点 1〜3 は推奨どおり（遅れ 17f を C-0575 に、語彙は P-1、C-0565 は厳密一致で確定、notes[2] を消して minimal の印を外す）。

## 7. 実装（2026-10-17）

- `skills/types.ts`・`skills/burstDamage.ts`: damage の `perBurstHit`（burstUse のときだけ・delayFrames と併用しない）。`frame/plan.ts` の planSkillHits が、発火のフレームで条件を判定し、その発動の `hitFramesOf` のそれぞれに出す（撃つ側のバフは発動のフレームで固定。sequential のバーストでは拒否）。
- `burst/landing.ts`: ミハラの行（17f・[0, 10, 22]。C-0575）。`data/skills/161.json`: burst の effects[1] に `perBurstHit`、notes[1] を会心の modeling に書き直し、notes[2] を消した。
- 観測値 `0469-08`・`0470-08` を足した。`0469-01`〜`0469-08`・`0470-01`〜`0470-08` がすべて許容内。ほかの観測値の予測は変わらない。
- C-0564 の根拠の `0469-03`・`0469-04`（会心）には、未確定の S1 のクリティカルダメージ▲が効くので、最小構成の印を付けた（会心の 1 ヒットの値にだけ効き、3 ヒットがそろうことと等分には効かない）。`0469-02`・`0469-05`・`0469-07`・`0470-02`・`0470-05`・`0470-07` は、確定の結論の根拠にするため手入力の条件で比べる形にした（自動の条件で比べた観測値は結論に結び付けない。design-stage18.md 12.4 節）。手入力でも許容内

## 8. 追加ダメージの撃つ側のバフの時点（2026-10-27）

- PR #724（C-0657。シンデレラ）で、planSkillHits は perBurstHit の全部で撃つ側のバフをヒットの時点で取るようになり、ミハラ（161）も 7 節の「発動のフレームで固定」から変わった。161 には根拠が無い（2026-10-27 のデイリーレビュー）。オーナーの指示で根拠を調べる。
- 既存の録画では決まらない: 161 の録画は 0469・0470 だけで、追加ダメージが出る 3〜5 回目は、発動からヒットまでの間に撃つ側のバフが変わらない（ペインロードは前の回から、S1 のクリティカルダメージ▲もリロードの周期より長く付いたまま。ラム・デルタはミハラの与ダメージに効かない）。161 だけを発動の時点に戻した版でも、比べる観測値（`0469-01`〜`0469-08`・`0470-01`〜`0470-08`）のモデルの値は 1 つも変わらない。読んでいない数字を読み直しても見分けられない。
- 撮り方の案（最小構成）: アニス：スター・デルタ・ミハラ（操作）、射撃場 BigArms（風圧）、スペック固定、オートバースト、2 本（1 本目で決め、2 本目で再現）。V-0479（録画 0543・0544）の III をミハラに替えた編成。アニス：スターがフルバーストの始まりに付ける攻撃力▲・攻撃ダメージ▲は、発動からヒットまでの間に付き、ソーダ：トゥインクルバニーのバーストスキルダメージには乗らない（C-0615）。ミハラのバーストスキルダメージも発動の直前のバフで出る（C-0563）ので、3 回目以降の追加ダメージ（会心なし）に乗るかで 2 つの規則が分かれる（モデルでは発動の時点 438,441・ヒットの時点 738,394）。2 回目のバーストスキルダメージの 1 ヒットを実測し、3 回目以降の増分から引いて追加ダメージを出す（バーストスキルダメージ側の規則が外れていても見分けられる）。会心のヒットは未確定の S1 の▲が乗るので判定に使わない。
- 撮るまでは、いまの main（ヒットの時点）のままにする。撮影の依頼と予測は、検証記録を起こすときにその記録と records/predictions/ に置く。
