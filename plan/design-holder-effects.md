## 0. 目的と方針

- 目的: 実機と同じく、効果を受けるキャラ（持ち主）ごとに「いま受けている効果の一覧」を持ち、フレームごとに起きた出来事で一覧を変える形に組み直す。2 段目の語彙（消去・解除・切り替え・スタックの操作・状態の出来事・バリアなど。[design-skill-catalog.md](design-skill-catalog.md) 9 節の段の候補 1〜4）を、段を足さずに一覧の操作として書けるようにする。
- 方針:
  1. **値を変えない**。各段で、いまの出力と並びまで一致することを確かめる（4 節）。モデルの値を変えないので、結論は作らず、変えない。
  2. **出力の形を残す**。窓（`BuffWindow` など）・区間・記録は、一覧の履歴から書き出す。読む側（ダメージの式・calc・sim・観測値の指標・画面）は変えない。
  3. **段の制約は再現する**。いまの段（1・1.5・2・2.5 段目）が判定に入れる窓の範囲を、一覧の件に付けた段の印で再現する。制約を外すのはモデルの変更なので、根拠ができてから 1 つずつ（論点 2）。
  4. **定義と語彙は変えない**。スキル定義の JSON と DSL の型は触らない。[design-named-state.md](design-named-state.md) 8 節の後の拡張の語彙の形（`selfState`・`removeOn`・`group`・`{ ended }`・`while`・敵に付く状態）はそのまま使い、実装の置き場所（段の位置と「解除で切る」段。同 8.5 節）だけを一覧の操作に置き換える。

## 1. いまの作り

### 1.2 2 パス目の窓の作り方

`planBuffTimeline`（`skills/timeline.ts`）は、1 パス目が確定した射撃の列と時刻表から出来事の列を流し直し（`replayEvents`）、効果ごとに「発火 → 受け手（`isEffectTarget`）→ 窓」を作る。効果どうしが見合う所は、次の段の順に閉じる。

| 段  | 作る窓                                                                                           | 判定に使う窓                                    |
| --- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------- |
| 1   | 条件・順位の対象・強化のどれでもない効果（確率のきっかけは期待値の小片）と、この段で確定する状態 | —                                               |
| 1.5 | 条件（`selfBuffed`・`inFullBurst`）つきの効果と付与                                              | 常時の値と、段 1 の窓（`inFullBurst` は時刻表） |
| 2   | 順位の対象（`topAttack`）の効果と付与                                                            | 常時の値と、段 1・1.5 の攻撃力の窓              |
| 2.5 | 強化（`amplifies`）                                                                              | 同じ出どころ・スロット・stat の段 1〜2 の窓     |

- 同じ出どころ・同じ効果・同じ受け手の再発火は和集合（上書き延長。[design-stage6.md](design-stage6.md) 8 節の 2）。終わりのフレームちょうどの再発火も続きとみなす。スタックする効果は段ごとの窓（`skills/stacks.ts`）。
- 状態は、出どころ × 状態ごとに状態の窓を作り、その状態の付与のいちばん後の段で確定する（[design-named-state.md](design-named-state.md) 5.2 節）。
- 後の段の窓は、前の段の判定に入らない。この制約は段の作りに合わせて決めたもので（[design-stage11-modernia.md](design-stage11-modernia.md) 2.4・3.3 節、[design-named-state.md](design-named-state.md) 8.5 節）、実機で確かめた規則ではない。

### 1.3 1 パス目のループ

`runFirstPass`（`frame/firstPass.ts`）は、射手・ゲージ・バーストの状態機械と一緒に、射撃に効く stat・当たりの stat（持続の命中率▲）・順位に要る攻撃力・条件に要る stat の窓だけを追う（[design-stage10.md](design-stage10.md) 1 節）。

- 手順 3 の順は、回復 → 条件なしの付与 → 状態の窓 → 条件つきの付与 → 当たりの窓 → 攻撃力の窓 → 順位の対象の付与 → 射撃に効く窓 → 即時効果。
- 射手はフレーム f に、f − 1 までに登録した窓のうち f を含むものを見る。
- ループの後で、2 パス目がすべての窓を作り直す。追った窓が作り直した窓と一致することは、テストで保っている。
- 1 パス目で窓を追う stat（攻撃力・射撃に効く stat・状態だけの stat）には、`amplifies`・条件 `inFullBurst`・維持 `fullBurstEnd`・発数の維持を書けない（`skills/types.ts` の `isFirstPassTrackedStat` などの検証）。

### 1.4 いまも受け手ごと

窓は受け手ごとに作り、持続時間も受け手ごとに決まる。

- N 発間維持は、受け手自身の射撃の数で切る（`shotCountWindows`）。
- 対象が発火ごとに変わる効果（直前にバーストを使った味方・攻撃力の順位）は、受け手ごとに和集合を取る。
- 吸収回復は効果ごと・受け手ごとに持ち、出どころが違えば別に扱う（C-0082・C-0087）。

そのため、いまの語彙の範囲では、キャラごとに効果を持つ実機と同じ値になる。組み直しで変わるのは作り方で、値ではない。

### 1.5 作り方の違いと、困る所

1. **後からまとめて作る**。実機はフレームごとに起きた順で、持ち主の効果を変える。いまは戦闘を回し終えた後に、効果ごとに作る。
2. **段で閉じる**。効果どうしが見合う種類が増えるたびに、段の位置と循環の禁止を決める必要がある（[design-named-state.md](design-named-state.md) 8.5 節）。2 段目の語彙は、効果が付いていることで別の効果が付いたり外れたりするものが多く、段と制約が増え続ける。
3. **二重の実装**。1 パス目と 2 パス目が、同じ窓を別のコードで作る（状態の付与のまとめ方は、`frame/firstPass.ts` と `skills/timeline.ts` の両方に `stateGroupsOf` がある）。語彙を足すたびに両方に書き、一致をテストで保っている。
4. **敵が持ち主でない**。敵の受けるダメージ▲は味方全員の窓で、敵の状態は出どころを持たない。敵の防御力▼など、敵が持つ効果の置き場所が無い。

## 2. 組み直した形

### 2.1 用語

- **持ち主**: 効果を持つ側。味方の枠と、敵（1 体の前提）。目録の `StateHolder`（`ally`・`enemy`）と同じ語。
- **件**: 一覧の 1 行。いまの窓の和集合の単位にあたる（出どころ × 効果 × 持ち主。状態は出どころ × 状態 × 持ち主）。付き直しは同じ件を延ばし、外れた後に付けば新しい件になる。
- **一覧**: 持ち主ごとの、いま持っている件（付いた順）。
- **履歴**: 件の一生（付いた・延びた・スタックが増えた・外れた）の記録。窓・区間・記録はここから書き出す。件は外れても消さずに履歴に残し、一覧はいま効いている件への索引にする。

### 2.2 件の形（案。名前は仮）

```ts
/** 持ち主。味方の枠と、敵（1 体の前提） */
type Holder = { kind: 'ally'; slotIndex: number } | { kind: 'enemy' };

/** 一覧の 1 件 */
type HeldEffect = {
  holder: Holder;
  /** 付けた枠 */
  sourceSlotIndex: number;
  /** 何の件か。同じ持ち主で、出どころとこれが同じなら同じ件（付き直し） */
  item:
    | { kind: 'timed'; effect: ResolvedTimedEffect }
    | { kind: 'state'; state: NamedStateId; contents: ResolvedStateContent[] }
    | { kind: 'healWindow'; effect: ResolvedInstantEffect }
    | { kind: 'cycleEvery'; effect: ResolvedCycleEvery }
    | { kind: 'enemyState'; state: NamedStateId };
  /** 付いたフレーム（付き直しでは変えない） */
  start: number;
  /** 終わり方: フレーム（秒・持続・戦闘の終わり）、持ち主の発数、出来事 */
  until: { frame: number } | { shots: number; counted: number } | { event: 'fullBurstEnd' | 'ammoSpent' };
  /** スタックする件の、段 k の始まり（k − 1 番目）。スタックしない件はキーごと無い */
  stackStarts?: number[];
  /** 段の印（2.5 節） */
  stage: 1 | 1.5 | 2 | 2.5;
};
```

- 値は件に持たせない（解決済みの効果の値を読む）。確率のきっかけの件は機会の列を持ち、強化の件は付いた瞬間の参照の値を持つ（いまと同じ式で値を出すため。2.6 節）。
- 書き出しに要る印も件に持つ（状態の件に、射撃の回数のトリガーの付与が発火を足したか。いまの `NamedStateWindow.shotCount`）。
- 解除不可の印など、2 段目の語彙が要る欄は、その語彙を足す時に足す（使い手のいない欄は入れない）。

### 2.3 一覧の操作

1. **付ける**: 発火 1 つを、対象の持ち主ごとに一覧へ入れる。同じ件があれば延ばす（終わりを、その発火からの終わりと比べて遅い方にする。発数の維持は数え直す）。スタックする件は段を 1 つ足し、全段の終わりを数え直す（いまの `STACK_REFRESH` の `all`）。同じ件が無ければ新しい件を作る。
2. **続きとみなす境目**は、件の種類ごとにいまの規則のまま。
   - 持続バフ・状態・循環の間隔の変更・スタック: 終わりのフレームちょうどの付き直しも続き（いまの和集合の `f ≤ end`）。
   - 吸収回復: 終わりのフレームちょうどに付けば、新しく付いた（`healed` を起こす。`createHealWindow` の `f < end`）。
3. **外す**: 終わりに達した件は、そのフレームの付与を済ませた後に一覧から外す（終わりのフレームちょうどの付き直しを続きにするため）。出来事で終わる件は、その出来事のフレームで閉じる。
   - 発数: 持ち主の N 発目の射撃の次のフレーム。付いたフレームの持ち主の射撃も数える（いまの `shotCountWindows` が `f ≥ s` の射撃を数えるため。ループでは手順 1 の射撃が先に済んでいるので、付ける時に同じフレームの射撃を数えに入れる）。
   - フルバーストの終わり: 付いた後に来る最初の終わり。
   - 撃ち切り: 1 パス目が基礎の武器に戻すフレーム（`weaponChangeEnds`）。
4. **値を出す**: 持ち主のフレーム f の値は、常時の値に `start ≤ f < end` の件の値を足したもの（スタックは効いている段の数だけ）。足す順は書き出しの並び（2.6 節）。
5. **見る**: 条件・順位・強化の参照は、段の印で見える件だけを見る（2.5 節）。
6. **書き出す**: 履歴から、いまの形の窓・区間・記録を作る（2.6 節）。

### 2.4 フレームの中の順番

1 パス目の手順 1・2（射手、ゲージと状態機械）はいまのまま。手順 3 は、いまの順を段で並べ直し、段 1 にすべての stat を入れる。

回復 → 段 1 の件（条件なし・順位の対象でない効果と付与）→ 段 1.5 の件（条件つき）→ 段 2 の件（順位の対象）→ 段 2.5 の件（強化）→ 即時効果

- いまの順（1.3 節）と同じ結果になる。手順 3 の中の順が効くのは、同じフレームに付いた件が判定に入るかと、弾丸チャージが同じフレームに付いた最大装弾数▲を見るかだけで、どちらも段の順で決まる（条件は段 1、順位は段 1・1.5 の同じフレームの件を見る。即時効果はすべての件の後）。射手は f − 1 までに付いた件しか見ないので、手順 3 の中の順に依らない。

### 2.5 段の印（いまの見え方の再現）

| 見る側                                                                 | 見える件                                                                                     | いまの出どころ      |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------- |
| 射手（最大装弾数・リロード・チャージ・装弾数無限・使用武器の変更など） | 射撃に効く stat の件。f − 1 までに付いたもの                                                 | 1 パス目の手順 1    |
| 当たり（ゲージ・命中の期待値）                                         | 当たりの stat の件（条件なし・順位の対象でない効果と、状態の中身）。f − 1 までに付いたもの   | 1 パス目の手順 1    |
| 条件 `selfBuffed`                                                      | 常時の値と、段 1 の件（同じフレームに付いたものを含む）                                      | 2 パス目の 1.5 段目 |
| 順位（最終攻撃力）                                                     | 常時の値と、段 1・1.5 の攻撃力の件（同じフレームに付いたものを含む。確率のきっかけは期待値） | 2 パス目の 2 段目   |
| 強化の参照                                                             | 同じ出どころ・スロット・stat の、段 1〜2 の件（同じフレームに付いたものを含む）              | 2 パス目の 2.5 段目 |
| 区間（ダメージの式）                                                   | すべての件（状態だけの stat は、着地点の計画があり持続の命中率▲を使う時だけ命中率に足す）    | 2 パス目の区間      |

- 状態の件の段は、その状態の付与のいちばん後の段（いまと同じ）。
- 表の細部はいまのコードが正で、新旧の比べ（4 節）で確かめる。

### 2.6 書き出し

- 書き出すもの: `BuffTimeline` の各欄（`windows`・`stateWindows`・`namedStateWindows`・`applications`・`conditionSkips`・`rankings`・`heals`・`cycleWindows`・`segments`）と、`FirstPassResult` の窓の欄（`firingWindows`・`rankAttackWindows`・`hitWindows`・`namedStateWindows`）。形と意味はいまのまま。
- 件 1 つからの書き出し:
  - 和集合の件: 窓 1 つ。
  - スタックする件: 段ごとの窓（いまの `stackWindows` と同じ）。
  - 確率のきっかけの件: 期待値の小片（いまの `chancePieces`）。
  - 強化の件: 参照する件が効いている所と、切れた所の小片（いまの 2.5 段目の作り方）。
  - 状態の件: 状態の窓と、中身ごとの窓。
- **並び**: いまの作る順に合わせる（段ごとに、効果の窓（出どころの枠 → 定義の順 → 受け手 → 時刻）の後に状態の窓と中身の窓。強化の小片は、効いている所 → 切れた所）。区間の値は窓の並びの順に足すので（[design-stage6.md](design-stage6.md) 9 節の浮動小数の加算順）、並びが同じなら値はビット単位で同じになる（論点 5）。記録（`conditionSkips`・`rankings` など）の並びも、いまの作る順に合わせる。細部はいまのコードが正。

### 2.7 1 パス目と 2 パス目（段 B の後）

- 1 パス目のループが、すべての件を一覧で持つ（射撃に効く stat などだけを追うのをやめる）。射手・当たり・順位・弾丸チャージは、一覧から値を読む。
- `planTeamRun`（`frame/plan.ts`）は、1 パス目の履歴から書き出す。2 パス目での作り直しはしない。
- `planBuffTimeline` の入口は残す（論点 4）。中身は、確定した射撃の列と時刻表から出来事の列を流し直し、同じ一覧の操作で履歴を作って書き出す。
- 窓を作るコードが 1 つになるので、1 パス目で窓を追う stat に書けない語彙の制限（1.3 節）は要らなくなる。制限を外すのは、使うキャラの定義の時（使い手のいない語彙は入れない）。

### 2.8 敵を持ち主にする（段 C）

- 敵の受けるダメージ▲（`damageTaken`）を敵の件にする。値は、いまと同じく味方の各枠の区間の値に足す（敵 1 体の前提で、敵が受ける全ダメージに掛かる。C-0138）。書き出しも、いまと同じく味方の各枠の窓にする（[design-named-state.md](design-named-state.md) 8.3 節の「味方全体の窓に写す」と同じ）。
- バーストのヒットが、ヒットのフレームの敵の側のデバフを見る規則（`burstHitBuffs`。C-0163・C-0167）は、敵の件をヒットのフレームで読む形になる。値は変わらない。
- 敵の状態（持続ダメージが付けるハッキングなど）を敵の件にし、出どころを持たせる。始まりと終わりは、いまの `dotActiveSpans`（最初の発火から最後の tick まで）のまま。条件 `enemyState` は敵の一覧を見る（どの出どころの件でもよい。いまと同じ）。
- 検証を広げる: 敵の件になる効果には、持ち主ごとに違いうる絞り込みと維持（自分を除く・状態・バースト段階・発数の維持など）を書けないようにする。いまの定義の `damageTaken` は、どれも対象が味方全体で絞り込みが無い（2026-10-15 に確かめた）ので、値は変わらない。

### 2.9 範囲の外

- 段の制約を外すこと（論点 2）。
- 2 段目の語彙。組み直しの後に、一覧の操作として足す（6 節）。
- スキル定義の JSON と DSL の型。
- 常時の値・即時効果・持続ダメージと自動攻撃の tick（論点 3・8）。
- 射手・バーストの状態機械・ダメージの式・calc・sim・画面。読む形が変わらないので触らない。

## 3. 進め方（段と PR）

各段を 1 つの PR にする（AGENTS.md の「実装・検証が完了した時点」）。この設計書は段 A の PR に含める。2026-10-15 の会話で示した手順の 1（一覧の型と操作）と 2（2 パス目の置き換え）は、1 だけでは使い手がいないので段 A にまとめた。

- **段 A: 一覧の型と操作、2 パス目の置き換え**
  1. 一覧の型と操作（2.2・2.3 節）を純関数で置く（`skills/holders.ts`。名前は仮）。件の種類ごとの単体テスト（付き直しの境目・スタック・発数・出来事の終わり・段の見え方）。
  2. `planBuffTimeline` の中身を、出来事の列を流し直して一覧を進める形に置き換える。出力の形と並びはいまのまま。
  3. 新旧の比べ（論点 6）を置く。旧の実装は比べのためだけに残す。
- **段 B: 1 パス目の置き換え**
  1. ループの窓（射撃に効く窓・当たりの窓・攻撃力の窓・状態の付与・吸収回復の窓・段の循環の窓）を一覧に置き換え、すべての件を追う。
  2. `planTeamRun` は 1 パス目の履歴から書き出す（2.7 節）。
  3. 段 B を閉じる時に、旧の実装と比べの仕掛けを消す。
- **段 C: 敵を持ち主にする**（2.8 節）。
- **その後**: 2 段目の語彙を、[design-skill-catalog.md](design-skill-catalog.md) 9 節の段の候補 1 から足す。段 A を始めてから段 B を閉じるまでは、語彙を足さない（その間は、1 パス目の窓（いまのまま）と 2 パス目（一覧）が別のコードのままなので）。

## 4. 確かめ方（各段の完了の条件）

1. `npm test` が、テストの期待値を変えずに通る（窓と区間の形を見るテストが、そのまま退化の確かめになる）。
2. 新旧の比べ（論点 6）で、`BuffTimeline` と `FirstPassResult` が並びまで一致する。
3. `npm run records:check` で、生成物（`plan/residuals.md`・`plan/claims.md`・`plan/skills.md`・`plan/minimal.md` など）に差分が出ない。
4. `npm run records:minimal` で、感度（`records/minimal/sensitivity.json`）に差分が出ない。
5. 速さ（論点 7）を測って経過に書く。
6. CI と同じ確認（AGENTS.md のコミット手順の 2）が通る。

比べで差が出たら、新しいコードの誤りとして直す。ただし、差の出どころがいまの 1 パス目と 2 パス目の食い違いだと分かった時は、どちらに合わせるかがモデルの変更になるので、直さずにオーナーに諮る。

## 5. 危険と対策

- **境目の規則の取り違え**（付き直しの `f ≤ end` と吸収回復の `f < end`、発数の数え始め、射撃の回数のトリガーの f + 1、使用武器の変更の頭の 1 フレーム（`weaponStartTrim`））: 件の種類ごとの単体テストと、新旧の比べで拾う。
- **足し算の順**: 書き出しの並び（2.6 節）。比べは並びまで見る。
- **段の見え方の取り違え**: 2.5 節の表を単体テストにする（見る側ごとに、同じフレームに付いた件と、後の段の件が見えるか）。
- **1 パス目が重くなる**: すべての件を毎フレーム追う。一方で、2 パス目の作り直しは無くなる。前後を測る（論点 7）。

## 6. 組み直しの後にできること（2 段目へのつながり）

[design-skill-catalog.md](design-skill-catalog.md) 9 節の段の候補 1〜4 と、効果解除・敵が持つ効果は、一覧の操作で書ける。語彙の形は [design-named-state.md](design-named-state.md) 8 節のまま。

## 7. 論点

決定（2026-10-15、オーナー）: 論点 1・2 と、段の構成（3 節）は推奨どおり。論点 3〜8 は未決。

1. **組み直す時期**（決定: 推奨どおり）
   - 推奨: 2 段目の段の候補 1（自分の状態の条件と外れ方）より前。段の候補 1〜4 の語彙はどれも一覧の操作なので、先に組み直せば、二重の実装と段の追加を避けられる。
   - 代わりの案: 2 段目の語彙を足しながら、要る所から組み直す。
2. **段の制約**（決定: 推奨どおり）
   - 推奨: 当面は件の段の印でいまの見え方を再現する。外すのはモデルの変更なので、根拠（検証）ができてから 1 つずつ。
   - 代わりの案: 組み直しと同時に外し、実機と同じく起きた順に見る。値が変わりうる。
3. **一覧に入れる範囲**
   - 推奨: いま窓を持つもの（持続バフ・デバフ、状態、吸収回復の維持、循環の間隔の変更）と、敵の受けるダメージ▲・敵の状態（段 C）。常時の値（常時パッシブ・静的な状態の中身・育成の効果層）は件にしない（変わらないので件にする利点が無く、着地点の計画など 1 パス目より前に読む所もある）。即時効果も件にしない（その瞬間に CT・弾数・ゲージを変えるだけ）。
   - 代わりの案: 常時の値も件にする。効果解除・消去の相手になる時に揃うが、読む所が増えて段 A が大きくなる。常時の効果を外す語彙を足す時に件にすれば足りる。
4. **2 パス目の入口（`planBuffTimeline`）**
   - 推奨: 残し、中身を一覧の流し直しにする。テストが射撃の列と時刻表を手で与えて窓を確かめているため。本番（`planTeamRun`）は 1 パス目の履歴を使う。
   - 代わりの案: 消して、テストも 1 パス目から作る。テストの書き直しが大きい。
5. **書き出しの並び**
   - 推奨: いまの並びを再現し、値をビット単位で同じにする。新旧の比べを等価で見られる。
   - 代わりの案: 時刻の順にする（読みやすい）。浮動小数の末尾が変わりうるので、比べと一部のテストを許容つきにする。
6. **新旧の比べ方**
   - 推奨: 段 A・B の間だけ旧の実装を残し、比べの仕掛け（`planTeamRun` と `planBuffTimeline` の中で新旧を両方回し、食い違えば例外にする）を置く。仕掛けは、テストの準備と記録の道具からだけ入れるスイッチにする（画面の計算には入れない）。仕掛けを入れて `npm test`・`records:check`・`records:minimal` を回せば、テストの全編成・録画ごとの条件・感度の変種で比べられる。段 B を閉じる時に旧の実装ごと消す。
   - 代わりの案: 比べを、録画ごとの条件の編成だけを流す固定のテストにする。仕掛けは要らないが、テストの編成と感度の変種を比べない。
7. **速さ**
   - 推奨: 目安は置かず、各段の前後で `npm test` と `records:minimal` の時間を測って経過に書く。遅くなった時は、原因を調べてから諮る。
   - 代わりの案: 目安（例: 1.5 倍以内）を完了の条件にする。
8. **持続ダメージ・自動攻撃**
   - 推奨: この組み直しでは件にしない（tick の刻みとゲージの予約は `frame/dot.ts` の追跡のまま）。敵の状態だけを敵の件にする（段 C）。持続ダメージを外す語彙などが要る時に、件にするかを決める。
   - 代わりの案: 持続ダメージを敵の件にし、tick を件から出す。段 C が大きくなる。
