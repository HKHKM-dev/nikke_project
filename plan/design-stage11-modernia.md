### 0.3 いまのモデルとの差

- **1 トリガーの値が武器と通常攻撃のダメージだけ**: `computeTriggerDamage`（`damage.ts`）の `perTrigger` は `(攻撃力 − 防御) × 武器倍率 × … ` の 1 本。毎回の追加ダメージは Stage 8 の倍率ダメージ（`planSkillHits` が発火ごとに 1 件ずつ作る）の形なので、1 発ごとに作ると 180 秒で約 6,000 件になる。
- **スタックが無い**: `planBuffTimeline` は同じ効果の再発火を**和集合**（上書き延長）にするだけ。何回重なったかは数えない。
- **状態を見る条件が無い**: トリガーは出来事（射撃・発動・フルバースト・回復）だけで決まり、「その瞬間に何のバフが付いているか」は見ない。順位（アリス編）はバフの窓を見るが、見るのは対象の決め方で、発火するかどうかではない。
- **武器が 1 つ**: 射手（`sim/shooter.ts`）もダメージの式も `character.shot` を読む。射撃に効くバフ（Stage 10）が変えられるのは最大装弾数・リロード時間・チャージ時間の 3 つだけ。

## 2. DSL の追加（`skills/types.ts`）

### 2.1 毎回の倍率ダメージ（「通常攻撃が命中した時、最終攻撃力の X% の追加ダメージ」）

`damage` の検証（`parseDamageEffect`）で、射撃の回数トリガーの**毎回**（`every` 省略か 1、`everyRef` 無し）を許す。対象は `normalShot` / `normalHit` / `fullChargeShot`（どれも「その枠の射撃 1 回ごと」。`lastShot` の毎回は今までどおりマガジンに 1 回の `SkillHit`）。

```json
{ "kind": "damage", "trigger": { "count": "normalHit" }, "damageType": "additional", "ref": 1 }
```

- **1 トリガーの値に畳み込む**（3.1 節、10 節 2）。`planSkillHits` には入れない（発火が射撃と 1 対 1 で、同じ区間の中では毎回同じ値なので、区間の 1 トリガーの値に足せば sim と calc の両方でそのまま数えられる）。
- 式は Stage 8 の倍率ダメージと同じ（`computeSkillHit`）: `max(1, 最終攻撃力 − 防御) × X × (1 + 会心期待値 + フルバースト補正) × (1 + Σ攻撃ダメージ) × 属性`。**コア・距離は乗らない**（Stage 8 の実測: 倍率ダメージに距離は乗らない、フルバースト補正と攻撃ダメージは乗る、会心する）。コアが乗るかは未確認なので定数 `PER_SHOT_DAMAGE_CORE = false` に置き、録画 44 で確かめる（7.5 節の 1）。
- **SG は解決時に拒否する**（「命中した時」がペレットごとかトリガーごとか分からない。使うキャラが出たときに決める）。
- `everyRef` の値が Lv で 1 になる場合も同じ扱いにする（今は解決時に RangeError。毎回として畳み込む側に回す）。

### 2.2 効果のあるスタック

```ts
// timed に足す
/** 最大スタック数の description_value_NN。有れば、発火のたびに 1 スタック足す（上限で止める）。値は 1 スタックあたり */
maxStacksRef?: number;
/** 最大スタック数の即値。maxStacksRef と片方まで */
maxStacks?: number;
```

- **スタックの規則（推奨・10 節 3）**: 発火のたびに 1 スタック足し（上限で止める）、**全スタックの維持時間を発火の時点から数え直す**。維持時間が切れたら全スタックが一度に消える。上限に達した後の発火は維持時間の更新だけ。
- **窓の作り方**: スタックの段ごとの窓にほどく。同じ効果の発火を「維持時間の中で続いている一続き（チェーン）」に分け、**段 k の窓 = そのチェーンの k 回目の発火から、チェーンの終わり（最後の発火 + 維持時間）まで**。区間では段ごとの窓を 1 つずつ足すので、k スタックのときの合計は `k × 値` になる（`applyResolvedEffect` はそのまま）。
- `BuffWindow` に `stack?: number`（1 始まりの段）を足す（UI の「× 3 スタック」とテスト用）。
- スタックの無い効果は今までどおり（1 段だけの窓 = 和集合。退化）。
- 代替（スタックごとに独立の維持時間）は、段 k の窓 = 「直近の維持時間の中に k 回以上発火している区間」になる。どちらも窓の作り方だけの違いなので、定数 `STACK_REFRESH: 'all' | 'each'` で切り替えられるようにし、録画 44 の最大装弾数で確かめる（7.5 節の 2）。
- クラウンの `ShotCountTrigger.stacksRef`（数えるだけのスタックが満ちたら発火）とは別物。名前が近いので、型のコメントで区別する。

### 2.3 「▼」（`decrease`）

```ts
// passive / timed に足す
/** 「▼」。値の符号を反転する（最大装弾数 5.04%▼ → −0.0504） */
decrease?: true;
```

- `scaling` が `ratio` / `flat` のときだけ（`casterAttack` / `casterChargeTime` は拒否）。
- 最大装弾数の実効値は Stage 10 の `effectiveMaxAmmo`（比率は加算、四捨五入、下限 1）のまま: 5 スタックで 300 × (1 − 0.252) = 224.4 → **224**。最大が減って残弾を上回ったら削る（`MAX_AMMO_CLAMP_ON_DECREASE`、録画 39 で確定）。
- ほかの stat の「▼」（敵へのデバフではなく味方の stat が下がるもの）も同じ形で書ける。

### 2.4 stat「命中率」と条件「自分が 〈stat〉 増加状態なら」

```ts
export type BuffStat = /* 既存 10 */ | 'hitRate' | 'infiniteAmmo';

// timed に足す
/** 発火の瞬間に、自分（効果を持つ枠）がその stat の増加状態（常時パッシブか、効いている窓で合計 > 0）なら発火する */
condition?: { selfBuffed: BuffStat };
```

- `hitRate`（命中率）はダメージの式も射手も読まない（全弾命中の前提）。**区間の鍵（`keyOf`）にも入れない**ので、命中率だけが違う区間は同じグループのまま（calc のグループの数も値も変わらない）。`BuffTotals.hitRate` に足して、UI の「受けているバフ」と条件の判定にだけ使う。
- **カウンタは状態に関係なく通算で数え、発火の瞬間（200 発目の射撃のフレーム）に状態を見る**（10 節 4）。説明文の「200 回命中した時、自分が命中率増加状態なら」をそのまま読んだ形。代替の読み（状態の間だけ数える）とは、フルバースト開始から最初の攻撃力▲までの発数で見分けられる（7.5 節の 3）。
- 状態の判定は「`start ≤ f < end` の窓」で、**同じフレームに付いた窓も入れる**（アリス編の順位と同じ）。フルバースト開始と同じフレームの 200 発目でも発火する。
- 条件に使える stat は、条件付きの効果が出す窓の外から来るもの（1 段目の窓）だけにする（3.3 節）。`condition` を持つ効果の `stat` は `condition` に使われる stat と同じにできない（連鎖させない。検証エラー）。
- 書けるのは `timed` だけ（`passive` は常時なので条件の意味がない。即時効果・`damage` は使うキャラが出たら広げる）。
- 型は `condition?: EffectCondition`、`type EffectCondition = { selfBuffed: BuffStat }` とユニオンの形で置く。後で固有の名前の状態（`{ selfState: '<id>' }`）を足すときに、判定の段（1.5 段目）・同じフレームの規則・`conditionSkips` をそのまま使えるようにするため（11 節）。今回の JSON と挙動は変わらない。
- **既存の定義に命中率▲を足す**（4 節）: ドレイク（101）S1「フルバースト時 味方全体 命中率 10 秒」（基礎版・宝物版）、ノワール（271）バースト「SG の味方 命中率」。どちらも notes で「ダメージに効かない」としていたが、モダニアの S2 の状態を作るので定義に入れる。数値は変わらない（区間の鍵に入らないので退化）。

### 2.5 stat「装弾数無限」

- `infiniteAmmo` は射撃に効く stat（`FIRING_STATS` に足す）。値を持たないフラグなので、**`ref` を書かない**（`ref` 無しを許すのはこの stat だけ。解決後の値は 1）。`timed` だけに書ける。
- 射手はこの窓の中では残弾を減らさない（リロードが起きず、「最後の弾丸」も出ない）。窓に入った時点でリロード中なら、そのリロードは続ける（仮。3.4 節）。
- 区間の鍵に入る（射撃が変わるので、calc では Stage 10 のハイブリッドの「実数」のグループになる）。

### 2.6 使用武器の変更（`weaponChange`）とデータ

```ts
/** 「殲滅モード」「使用武器変更」: 維持時間のあいだ、自分の通常攻撃を別の武器にする */
export type WeaponChangeEffect = {
  kind: 'weaponChange';
  trigger: EffectTrigger;
  /** 変更後の 1 発のダメージ（%）の description_value_NN */
  damageRef: number;
  durationRef?: number;
  durationSeconds?: number;
  assumes?: LocalizedText;
};
```

- 対象は常に自分。どのスロットにも書ける（K・シンデレラなどは S1・S2 で武器が変わる）が、今回はバーストだけで使う。
- **武器のデータ**（10 節 5）: `normalize.ts` でバーストの `skill_type` が `ChangeWeapon` のキャラに `CharacterData.burstSkill.changeWeapon = { rateOfFire, shotId }` を足す（`skill_value_data` の [1]・[2]。数値は CDN から取り、手で書かない）。取り込みは `.cache` の roledata から作り直すだけで、他キャラのデータは変わらない（`ChangeWeapon` の 12 体に 1 フィールド増えるだけ）。
- **変更後の武器の組み立て**: 基礎の `shot` を写し、`damage` を `damageRef` の値（× 100。2.24% → 224）、`rateOfFire` と `endRateOfFire` を `changeWeapon.rateOfFire`（4200）に差し替える。**CDN に無いパラメータは仮の定数**で置く（3.4 節の表）: コア倍率は基礎の武器と同じ（200%）、スピンアップ無し（最初から 4200 rpm。モデルでは 1 フレーム 1 発 = 毎秒 60 発）、1 発目の遅延なし、ゲージの量は基礎の武器と同じ（フルバースト中はゲージが溜まらないので効かない）。
- `BuffTotals` に `weapon: ResolvedWeaponChange | null` を足し、区間の鍵に武器の識別子を入れる。同じ区間に 2 つの武器の変更が重なることは無い（1 体に 1 つ。後から付いたほうを使う）。

## 3. 計算の変更

### 3.1 1 トリガーの式（`damage.ts`）

```ts
export type TriggerDamageInput = {
  // 既存 …
  /** Stage 11 モダニア: その枠の毎回の倍率ダメージ（resolvePerShotDamage の結果）。省略は無し */
  perShot?: readonly ResolvedSkillDamage[];
};

export type TriggerDamage = {
  // 既存 …
  /** 通常攻撃の分（今までの perTrigger） */
  normal: number;
  /** 毎回の追加ダメージの分（computeSkillHit。無ければ 0） */
  perShot: number;
  /** normal + perShot */
  perTrigger: number;
};
```

- 武器は `buffs.weapon?.shot ?? character.shot`。武器倍率・コア倍率・チャージの有無はこの武器から取る。
- `perShot` は `computeSkillHit(perShot, character, enemy, { attack, attackDamageMultiplier }, buffs, SKILL_HIT_FULL_BURST_BONUS && fullBurst)`。攻撃力・会心・攻撃ダメージは同じ区間の通常攻撃と同じバフ後の値。
- sim（`engine.ts`）は射撃ごとに `perTrigger` を足し、calc（`team.ts`）はグループのトリガー数 × `perTrigger`。**どちらも今の式の呼び出しに `perShot` を渡すだけ**で、sim と calc の厳密一致・離散化誤差の基準はそのまま使える。
- `perShot` が無ければ `perTrigger = normal` で、今と 1 ビットも変わらない（退化）。

### 3.2 スタックの窓（`skills/timeline.ts`・`sim/firstPass.ts`）

- `planBuffTimeline` の 1 段目で、`maxStacks` のある効果は `unionWindows` の代わりに `stackWindows(fires, 維持, frames, 上限)` で段ごとの窓を作る（2.2 節）。対象が発火ごとに変わる効果（`burstUsers` / `topAttack`）では、対象の枠ごとに「その枠が受けた発火」で数える（クラウン編の「上書き延長はその枠が受けた発火どうしでだけ」と同じ）。
- **1 パス目のループ**: 最大装弾数▼は射撃に効くので、ループでも段ごとの窓を登録する。`FiringSource.windows` の各枠に「今のチェーンの終わり・スタック数」を持たせ、発火のたびに「チェーンが続いていればスタック + 1（上限まで）、切れていれば 1 から」とし、段 1〜スタック数の窓の終わりを新しいチェーンの終わりまで延ばし、新しい段の窓を発火のフレーム（射撃の回数起点なので次のフレーム）から始める。
- **ループの窓 = `planBuffTimeline` の窓**をテストで固定する（Stage 10 以来の一致テスト。段ごと）。

### 3.3 状態の条件（1.5 段目）

`planBuffTimeline` の段を 1 つ増やす。

1. **1 段目（今のまま）**: 条件も順位も要らない効果の窓（スタックの段を含む）。
2. **1.5 段目（新設）**: `condition` のある効果について、発火ごとに発動者の「その stat の状態」（常時パッシブ + 1 段目の窓の合計 > 0）を見て、満たす発火だけで窓を作る。
3. **2 段目（アリス編）**: 順位の要る効果。順位の材料の攻撃力の窓に **1.5 段目の攻撃力の窓も入れる**（モダニアの S2 の攻撃力▲は最終攻撃力に入るため）。

- 1 パス目のループでは、条件付きの効果が射撃に効く stat を持つか、`topAttack` の効果がある（攻撃力の窓を順位のために追っている）ときだけ、条件の stat（命中率）の窓も追う。手順 3 の順番は **回復 → 状態の窓（命中率）→ 攻撃力の窓（条件なし → 条件付き）→ 射撃に効く窓 → 即時効果**。モダニアの定義だけなら条件付きの効果は攻撃力なので、ループは今のまま（退化）。
- 発火を間引いた記録を `BuffTimeline.conditionSkips`（`{ frame, sourceSlotIndex, effect }`）に残す（UI・テスト用。「命中率増加状態でないので発動せず」が何回あったか）。

## 9. リスク・留意点

- **殲滅モードの武器のパラメータが CDN に無い**: コア倍率・スピンアップ・レートの上限・ゲージの量はすべて仮の定数。録画 44 の 5 で読めなければ、UI に「仮定」として残す。とくに「1 発 2.24%」が別プロジェクトの指摘どおり実機と合わない（ダメージが下がらない）なら、1 発の読み（ヒット数・倍率）から見直す。
- **MG の毎秒 60 発の上限**: 基礎の MG では録画 35・41 で確かめた（`plan/design-mg-fire-rate.md`）。殲滅モードの 4200 rpm が上限を超えて撃つ（1 フレームに 2 発）なら、射手に「1 フレームに複数発」を足す必要がある。その場合は S1 の 200 回の進みも速くなる。
- **スタックの規則**: 付与のたびに更新（推奨）と独立の維持時間で、最大装弾数（224 か 285 / 270 か）と会心のスタック数が大きく変わる。モダニアの DPS に直結するので、録画 44 の 2 で必ず確かめる。
- **カウンタの数え方**: S1 と S2 の 200 回は別々のスキルなので、実機ではカウンタが別かもしれない（どちらも射撃ごとに 1 足すなら同じ発で発火する）。モデルでは同じ射撃の列を通算で数えるので同じ発になる。
- **1 トリガーの値に畳み込む前提**: 追加ダメージが「命中した時」の効果なので、全弾命中の前提に乗っている（Stage 8 の `normalHit` と同じ）。命中率を扱う日に分岐させる。
- **状態の条件の範囲**: 今回は「自分が 〈stat〉 増加状態なら」だけ。固有の名前の状態（殲滅態勢・過熱など、111 スキル）は別の語彙で、使うキャラの Stage で足す（方針は 11 節）。
- **3 分モードの的の停止**: 射撃の列の予測は数秒ずれる。スタックやカウンタは残弾・ポップアップから数えて合わせる。

### 11.2 取り入れること

**考え方（状態を名前で追い、付与と要求で結ぶ）は採る。ただし実装は、固有の名前の状態で数値が変わる所持キャラを定義する Stage まで待つ**（Stage 11 の「そのキャラに要る語彙だけ足す」方針。いま足すと実機で確かめられる効果が無い）。そのときの形の見込み:

1. **状態は窓で表す**: `kind: 'timed'` と同じ発火・維持・上書き延長・スタック（2.2 節の段ごとの窓）で「状態 `id` の窓」を作る。値は持たず、`BuffTotals` にも区間の鍵にも入らない（命中率と同じ扱い）。
2. **状態の宣言は定義ファイルに置く**: `SkillDefinition.states?: { id: string; name: LocalizedText; maxStacks?: number }[]`。`id` はそのキャラの定義の中で一意、付与・要求は同じ定義の `id` だけを参照できる（他キャラの状態を見る効果が出たら広げる）。
3. **付与**: 効果の種類 `kind: 'state'`（`trigger`・`state`・維持秒数）を足す。既存の `timed` に `grantTag` を生やすのではなく別の種類にするのは、「状態だけ付いて数値は無い」効果が多いため。
4. **解除**: 維持時間のほかに `removeOn?: EffectTrigger`（フルバースト開始など）と `exclusiveWith?: string[]`（切り替え式の状態）を書けるようにする。フルスタックでの解除はクラウンの `stacksRef` を状態のスタックに寄せられるかをそのとき決める。
5. **要求（発火の瞬間）**: 2.4 節の `EffectCondition` に `{ selfState: string; minStacks?: number }` を足す。判定は 1.5 段目（3.3 節）で、同じフレームの窓を入れる規則もそのまま。
6. **要求（状態の間だけ効く）**: 説明文と実機で「状態の間だけ」と確かめられたキャラが出たら、`timed` / `passive` に `while?: { selfState }` を足し、窓を状態の窓で切る。これは発火の判定ではなく窓の積なので、1.5 段目の後ろに置く。
7. **循環の禁止**: 状態を付ける効果が、同じ状態を要求しない（連鎖させない）。状態を要求する効果が付ける状態は、ほかの要求の材料にしない（1.5 段目を 1 回で閉じる）。今の `condition` の規則（2.4 節）と同じ。
8. **`assumes` の置き換え**: マナのマターシグマ（3 件）は、状態の仕組みが入った Stage で `assumes` から状態の要求に書き換え、数値が変わらないこと（毎サイクル再付与で常に満たす）を退化テストにする。状態でない `assumes` はそのまま残す。

### 12.1 設計からの差分

1. **使用武器の変更の窓は「頭を 1 フレーム削る」**（`skills/timeline.ts` の `weaponStartTrim`）。3.4 節では「発火の次のフレームから」としか決めていなかった。発火を 1 フレーム後ろにずらすと、窓の終わりも 1 フレーム後ろになり、同じ発動の装弾数無限（`[f, f + 900)`）より 1 フレーム長く残る（その 1 フレームだけ「殲滅モードなのに残弾が減る」状態になる）。そこで窓は `[f + 1, f + 900)` とし、終わりを装弾数無限とそろえた。射撃の回数トリガー（窓がもともと `f + 1` から）と戦闘開始時は削らない。
2. **命中率の窓は区間に入れず `BuffTimeline.stateWindows` に置く**（2.4 節の「区間の鍵に入れない」を一歩進めた）。区間の境界にも `timedEffects` にも入らないので、ドレイク・ノワールに命中率▲を足しても既存の編成の区間は 1 つも変わらない。ドレイク・ノワールの命中率▲は効果の**末尾に足した**（`effectIndex` を変えないため）。ノワールの「同じ部隊の味方がいれば」の命中率▲は部隊の条件が語彙外なので notes のまま。
3. **条件付きの効果の制限を足した**: 対象 `topAttack` と一緒に書けない（順位の段と条件の段が絡むため）。状態だけの stat（命中率）と、自分の条件と同じ stat は出せない（2.4 節どおり）。条件の判定に使うのは 1 段目の窓と状態の窓だけで、条件付きの効果どうしは連鎖させない。
4. **`SKILL_HIT_FULL_BURST_BONUS` を `damage.ts` に移した**（`skills/burstDamage.ts` からも export）。1 トリガーの式が射撃ごとの倍率ダメージに同じ規則を使うため、循環 import を避けた。
5. **1 トリガーの値の内訳**: `TriggerDamage` に `normal`（通常攻撃の分）と `perShot`（射撃ごとの倍率ダメージの分）を足し、`perTrigger = normal + perShot`。射撃ごとの倍率ダメージの無いキャラは `perShot = 0` で、今までと 1 ビットも変わらない。
6. **`TeamSlotResult` に `stateWindows` と `conditionSkips`** を足した（UI の「命中率 +8.56%」「状態でなく発動せず 17 回」）。
7. **射手**: `FiringParams` に `infiniteAmmo` と `weapon` を足し、1 パス目のループが武器ごとに別の射手の状態を持つ（持ち替えたら変更後の武器を新しい状態で始め、戻ったら `resumeShooter` で基礎の武器の状態を戻す）。
8. **スタックの窓**は `skills/stacks.ts` の `stackWindows`。ループは対象の枠ごとの窓の始まりの列から段ごとの窓を作り直す（発火は 180 秒で 30 回程度なので軽い）。`STACK_REFRESH = 'each'`（スタックごとの維持時間）の窓も同じ関数で作れる。
9. **データ**: `normalize.ts` の `changeWeaponOf` が `ChangeWeapon` の 12 体に `burstSkill.changeWeapon = { rateOfFire, shotId }` を足した（`.cache` から作り直し、差分はこの 12 ファイルの 1 フィールドだけ）。
10. **定義**: `260.json` の `checkedAt` は、定義の検証テストが UTC の日付で見るので 2026-09-23 にした（アリス編と同じ）。
11. **仮の定数の置き場所**: `PER_SHOT_DAMAGE_CORE = false`（`damage.ts`）、`STACK_REFRESH = 'all'`（`skills/stacks.ts`）、`WEAPON_CHANGE_CORE = 'base'`（`skills/resolve.ts`）、`WEAPON_CHANGE_RESTORE = 'resume'`（`sim/shooter.ts`）。
12. **テスト**: `skills/__tests__/stage11Modernia.test.ts`（DSL・解決・1 トリガーの式・スタックの窓・条件）、`__tests__/stage11ModerniaTeam.test.ts`（録画 44 の予測、ループと `planBuffTimeline` の窓の一致、射手、2 編成の sim / calc 整合）、`scripts/normalize.test.ts`（`changeWeapon`）。テストは **581 件**（アリス編の完了時点の 539 件から 42 件増）。既存の 539 件は、射撃ごとの倍率ダメージを拒否していた 2 件の期待を「書ける」に変えたほかは数値を変えずに通った。
