## Context

Stage 11 の 4 体目。モダニア（PR #18）がマージされたので、ロードマップの順どおり **紅蓮：ブラックシャドウ（225。以下 紅蓮BS）** に進む。紅蓮BS は III・RL の Attacker で、火力の大半が **S1 の「攻撃回数別の効果」（3 発ごとに 283.03% → 565% → 848.03% を循環）** から出る。バーストはこの循環を「1 発ごと」に速め、攻撃力とチャージダメージを上げる。

S2 とバーストの数値の効果（最大装弾数▲・弾丸チャージ・攻撃力▲・チャージダメージ▲）は、どれも **Stage 10 までの語彙でそのまま書ける**。語彙の外にあるのは次の 2 つだけ。

| 仕組み                                                                        | どこ     | いまのモデル                                                                                   |
| ----------------------------------------------------------------------------- | -------- | ---------------------------------------------------------------------------------------------- |
| 「攻撃回数別の効果」「各段階の効果のみ適用」（**段を順に循環**する）          | S1       | 回数トリガーは「N 回ごとに同じ効果」だけ。段は発動の回数の段階（イサベル。上がったら戻らない） |
| 「スキル 1 のフルチャージ攻撃回数の条件が 1 回 / 2 回 / 3 回に変更」（10 秒） | バースト | 別のスキルのトリガーを書き換える効果が無い                                                     |

**設計の芯は「循環を 1 本の通算カウンタで表す」こと。** 先行撮影の録画 47 を読み直すと、S1 の回数は**戦闘開始からの通算のフルチャージ攻撃回数**で、窓の外では通算が 3 の倍数の射撃で次の段、窓の中では毎回次の段になり、**窓の中の毎回の段は 3 の倍数の位置をずらさない**と読むと、未解決だった「FB 明けの次の段が 1 発目か 2 発目か」が 5 回のフルバーストすべてで説明できる（0.3 節）。これを `planSkillHits`（Stage 8）の射撃の列の上の 1 本のループにし、窓は モダニア編の状態の窓（区間に入れない）に置く。射手・区間・1 トリガーの値は変えない。

あわせて、紅蓮BS の**射撃間隔が実機 43f・モデル 40f**（リロードをまたぐと 172f・160f）とずれていて、フルバーストの 10 秒に入る発数（実機 13 発）が変わるので、較正値を足す（3.3 節）。

### 0.3 S1 の回数の数え方（録画 47 の読み直し）

先行の読み取りでは「FB 明けに次の段が出るのが FB2 は 1 発目、FB1・FB3 は 2 発目」が未解決だった。射撃の列を 43f の刻みで見直すと、HUD の増分の中に他のキャラのヒットと重なって見落としていた紅蓮BS の射撃が 3 発あった（f3468・3553・5978。どれも前の射撃のちょうど 43f 後で、増分の合計から 207,265 がちょうど 1 回分引ける）。それを入れた FB ごとの流れ:

| FB  | 窓の前（最後の段の後に撃った段なしの発数 p）          | 窓の中の段（13 発） | 窓の後で次の段が出たのは               | 通算で数える（推奨）の予測: p + 13 + k ≡ 0 (mod 3) | 段ごとに数え直すの予測 |
| --- | ----------------------------------------------------- | ------------------- | -------------------------------------- | -------------------------------------------------- | ---------------------- |
| 1   | f1250 で C、その後すぐ FB（p = 0）                    | A → … → A           | **2 発目**（f2142 で B）               | k = 2 ✓                                            | 3 発目 ✗               |
| 2   | f3553 で A、f3596 の 1 発（p = 1）                    | B → … → B           | **1 発目**（f4346 で C）               | k = 1 ✓                                            | 3 発目 ✗               |
| 3   | f5892 で B、f5935・5978 の 2 発、f6225 で C（p = 0）※ | A → … → A           | **2 発目**（f6994 で B）               | k = 2 ✓                                            | 3 発目 ✗               |
| 4   | f8403 で A、f8447 の 1 発（p = 1）                    | B → … → B           | **1 発目**（f9186 で C）               | k = 1 ✓                                            | 3 発目 ✗               |
| 5   | f10857 で C、その後すぐ FB（p = 0）                   | A → … → A           | 録画の終わり（1 発目 f11569 は段なし） | k = 2（1 発目は段なし ✓）                          | —                      |

※ f6225 の射撃はバーストのカットイン中（HUD が 29 フレーム止まっていた）で、通常攻撃はバフなし・段 C はバフありだった。通算では 3 の倍数（p = 2 の次）なので、窓に関係なく段が出る。

- **読み**: S1 のカウンタは戦闘開始からの通算のフルチャージ攻撃回数。窓の外では**通算が 3 の倍数**の射撃で次の段、窓の中では**毎回**次の段。窓の中の段はカウンタを 0 に戻さないので、窓が終わった後の最初の段は「通算の 3 の倍数」の射撃に戻る。段のポインタ（A → B → C → A …）はカウンタと別に 1 つだけ持つ。
- 「段が出るたびに数え直す」読みは 4 回とも外れる（窓の後の最初の段が 3 発目になるはず）。「窓の中の射撃は数えない」読みも FB1 で 3 発目になり外れる。
- 説明文の「3 回 / 6 回 / 9 回」→「1 回 / 2 回 / 3 回」は、この読みでは「段の間隔 3 → 1」と同じ。
- 見落としていた 3 発は刻みと増分の合計からの推定。実装後に sim の射撃の列と録画の残弾表示（照準横の N/9・N/14）で裏を取る（7.5 節の 2）。

### 0.5 いまのモデルとの差

- **回数トリガーに順番が無い**: `ShotCountTrigger` の `every: 3` は「通算 3・6・9 … 回目ごとに**同じ**効果」。段を順に替えるには、効果の側に「何段目か」を持たせる必要がある。イサベル（231）の段階は発動の回数（`EventCountTrigger.atLeast`）で、上がったら戻らない。
- **別の効果の数え方を変える効果が無い**: 窓（`timed`）が変えられるのは stat の値だけで、トリガーの間隔は変えられない。
- **射撃間隔**: 0.1 節のとおり紅蓮BS だけ実機と 3f ずれる。起案時の sim（定義なし）は単騎 180 秒で 203 発（実機の刻みなら約 188 発）、録画 47 の編成では FB の 10 秒に 14 発入る（実機 13 発）。

起案時の sim（定義なし、`npm run sim -- --ids 822,20,225 --fixed-spec --controlled 3`）: FB 5 回（7.83 秒から 40.00 秒ごと、チェーン切れ 0）で実機の周期（39.7〜41.0 秒）と合う。紅蓮BS の 180 秒は 46,502,473（実機 284,726,954。差のほとんどが S1 とバーストのバフ）。

### 0.6 検証に使うキャラ

録画 46・47 と同じ。ラム（822・I・SR）とデルタ（20・II・SR）はどちらも**攻撃力▲・会心▲・チャージ系を配らない**ので、紅蓮BS の数値の変化は紅蓮BS 自身のスキルだけで説明できる。紅蓮BS の 1 発（20 万〜400 万台）と、ラム・デルタの 1 発（20 万台の決まった値）は HUD の増分で分けられる（録画 47 で分けた）。

## 2. DSL の追加（`skills/types.ts`）

### 2.1 段の循環（`cycle`）

```ts
/**
 * Stage 11 紅蓮BS: 「攻撃回数別の効果」「各段階の効果のみ適用」の循環。
 * trigger の回数（射撃の通算カウンタの every の倍数）ごとに steps を 1 段ずつ順に発動し、最後の次は最初に戻る。
 * 段のポインタはカウンタと別に 1 つだけ持ち、戦闘中ずっと続く（リロードでもフルバーストでも戻さない）
 */
export type CycleEffect = {
  kind: 'cycle';
  /** 1 段進むきっかけ。射撃の回数トリガーだけ（every = 段の間隔。「3 回 / 6 回 / 9 回」なら 3。stacksRef・lastShot は不可） */
  trigger: ShotCountTrigger;
  /** 段の中身（2 つ以上）。今は倍率ダメージだけ */
  steps: CycleStep[];
  assumes?: LocalizedText;
};

/** 段の中身。DamageEffect から trigger を除いた形 */
export type CycleStep = { kind: 'damage'; ref: number; damageType: SkillDamageType; assumes?: LocalizedText };
```

- 段の中身を `damage` だけにするのは、紅蓮BS に要るのがそれだけだから（1 節の方針）。アルカナ（弾丸チャージ・スタック）が来たら `ammoRefill` / `timed` を段に足せる形にしておく。
- 各段の倍率ダメージは Stage 8 の `damage` と同じ式（`computeSkillHit`: 会心・FB 補正・攻撃ダメージあり、コア・距離なし）。分配ダメージは「単体ボスでは全額」の今の仮定のまま。
- **段 B の 3 ティックは 1 ヒットにまとめる**（10 節 4）。合計は全額で同じ。ティックごとの会心は期待値では 1 ヒットと同じ。ずれるのは「最後のティックが窓の境目をまたぐ」ときだけ（30f 以内）。
- 1 つの定義に `cycle` は 1 スロットに 1 つまで（2.2 節の `cycleEvery` がどの循環を指すかを曖昧にしないため）。

### 2.2 循環の間隔の変更（`cycleEvery`）

```ts
/**
 * Stage 11 紅蓮BS: 「スキル N の（フルチャージ）攻撃回数の条件が … に変更」。維持時間のあいだ、自分のスロット slot の cycle を
 * every 回ごとに進める（通算カウンタの every の倍数。1 なら毎回）。カウンタは変えない（0.3 節）
 */
export type CycleEveryEffect = {
  kind: 'cycleEvery';
  trigger: EffectTrigger;
  /** 対象の cycle を持つ自分のスロット */
  slot: SkillSlot;
  /** 変更後の段の間隔（即値。説明文の「1 回 / 2 回 / 3 回」は 1） */
  every: number;
  durationRef?: number;
  durationSeconds?: number;
  assumes?: LocalizedText;
};
```

- 対象は常に自分（説明文が「自分に」だけで、他キャラの循環を変える効果は無い）。
- 検証: `slot` にちょうど 1 つの `cycle` があること、`every` は 1 以上でその `cycle` の `every` 未満、トリガーは射撃の回数トリガー以外（自分の射撃で自分の循環を速めると判定が循環するため。今は `burstUse` だけ使う）。
- 窓の作り方は `timed` と同じ（発火・維持・上書き延長）。**区間には入れない**（ダメージの式も射手も読まない）。モダニア編の状態の窓（`BuffTimeline.stateWindows`）に置き、UI とテストで見えるようにする（10 節 3）。
- 「1 回 / 2 回 / 3 回」を `every: 1` と読むのは 0.3 節の実測による（窓の中は毎回段が出る）。説明文どおり「窓の中だけ別の閾値 1・2・3 で数え直す」読みは 0.3 節の表で外れる。

### 2.3 既存の語彙で書くもの

## 3. 計算の変更

### 3.1 循環の発動（`team.ts` の `planSkillHits`）

`planSkillHits` に、`damage` の発動と並べて `cycle` の発動を足す。射撃の列（`shots[slotIndex]`、1 パス目で確定済み）の上を 1 回なめるだけ。

```text
n = 0（通算のフルチャージ攻撃回数）、step = 0（段のポインタ）
各射撃 s（昇順）について:
  n += 1
  e = s が cycleEvery の窓 [start, end) に入るなら その every、入らないなら cycle.every
  n % e == 0 なら steps[step] を s で発動し、step = (step + 1) % steps.length
```

- 発動のフレームは射撃のフレーム（Stage 8 の射撃の回数トリガーと同じ）。値はその射撃と同じバフ（その射撃で付くバフは次のフレームから）、FB 補正はそのフレームが FB 中なら乗る（`SKILL_HIT_FULL_BURST_BONUS`）。
- 窓の判定も射撃のフレームで行う（10 節 3）。実機の RL は着弾が数フレーム遅れ、0.3 節の f6225 のようにカットイン中の 1 発で「射撃はバフなし・段はバフあり」がありうるが、1 回の FB で高々 1 発なので扱わない（9 節）。
- 数えるのは `fullChargeShot`（チャージ武器の全射撃。AI の射撃もフルチャージに数える、Stage 10 で確定）。
- sim と calc は同じ `planSkillHits` を使うので、倍率ダメージは今までどおり厳密一致（`skill hits (sim=calc)`）。
- `SkillHitEvent` に `cycleStep?: number`（0 始まりの段）を足す（UI の「A × 41 / B × 40 / C × 40」とテスト用）。

### 3.2 窓（`skills/timeline.ts`）

- `cycleEvery` は `planBuffTimeline` の 1 段目で `timed` と同じく窓にし、`stateWindows` に置く（`stat` の代わりに `'cycleEvery'` と `slot` を持つ窓）。区間の境界にも `timedEffects` にも入らないので、既存の編成の区間は 1 つも変わらない。
- 射撃に効かないので、1 パス目のループ（`firstPass.ts`）では追わない。

### 3.3 射撃間隔の較正（`weapons.ts`・`sim/shooter.ts`・`cadence.ts`）

紅蓮BS の射撃は、チャージ 18f に対して間隔 43f（モデル 18 + 22 = 40f）、リロードをまたぐと 172f（モデル リロード 120 + 40 = 160f）。このままだと単騎 180 秒で約 8% 多く撃ち、FB の 10 秒に 14 発入る（実機 13 発）。**S1 の段の位置は通算の発数で決まるので、1 発の差が段の列を丸ごとずらす**。

```ts
/**
 * Stage 11 紅蓮BS: 射撃の刻みを実測で較正する武器（resourceId で引く）。202 体で射撃のパラメータ
 * （チャージ 0.3 秒・maintainFireStance 23・uptypeFireTiming 1）が紅蓮BS だけ違い、1 秒チャージの較正（82f）が当てはまらない
 */
export const MEASURED_CHARGE_CADENCE: Readonly<
  Record<number, { chargeReleaseFrames: number; reloadExtraFrames: number }>
> = {
  225: { chargeReleaseFrames: 25, reloadExtraFrames: 9 }, // 録画 46・47: 間隔 43f = 18 + 25、最後 → 次 172f = 120 + 9 + 43
};
```

- キャラデータを読むとき（`load.ts`）に `ShotParams` に載せ、射手（`firstShotFrames`・リロード明け）と `simulateShotFrames`・`computeCadence` が `DEFAULT_WEAPON_MODEL.chargeReleaseFrames` の代わりに使う。チャージ速度▲はチャージの 18f の側にだけ効く（Stage 10 の式のまま）。
- CDN の値ではなく実測の較正値なので、`CharacterData` の JSON には書かない（`chargeReleaseFrames` と同じ扱い）。表に無いキャラは今までと 1 ビットも変わらない。
- 規則（`uptypeFireTiming` や `maintainFireStance` からの式）にしないのは、同じパラメータのキャラが他にいなくて 1 点では式が決まらないため（10 節 5）。
- FB 開始から 1 発目までの実機 55〜62f（モデル 43f）は、バーストのカットインで射撃が止まる分とみられる。13 発目が窓に入り 14 発目が窓の外になるのはどちらでも同じなので、この Stage では扱わない（9 節）。

### 3.4 退化

新しい語彙（`cycle`・`cycleEvery`）と較正表を使わない編成で、射撃の列・時刻表・区間・バフ・倍率ダメージ・1 トリガーの値が**モダニア編の完了時点と厳密一致**（既存の 584 件が数値を変えずに通る）。

## 9. リスク・留意点

- **0.3 節の読みは見落とした 3 発の推定に乗っている**。3 発とも 43f の刻みにぴったり乗り、増分の合計からも 207,265 が 1 回分ずつ引けるので確度は高いが、7.5 の 2 で残弾から裏を取る。
- **較正値は 1 キャラ 1 点**: 43f・172f は操作キャラの録画 2 本から。AI のときも同じかは確かめていない（録画 47 の紅蓮BS も操作）。表の値は操作・AI 共通として置く。
- **窓の判定は射撃のフレーム**: 実機は着弾（RL）で判定しているかもしれない。カットイン中の 1 発（0.3 節の f6225）のように、窓の境目の 1 発で段のバフの有無が変わりうる（1 回の FB で高々 1 発、差は 1 段ぶん × 約 3 倍）。
- **段 B の 3 ティック**を 1 ヒットにまとめるので、B が窓の終わりをまたぐと最後のティックの FB 補正・攻撃力▲の有無がずれる（窓の最後の射撃が B のときだけ）。
- **FB 開始から 1 発目の遅れ**（実機 55〜62f、モデル 43f）: 窓の中の発数（13）は変わらないが、FB の中の射撃のフレームが 12〜19f 早い。Stage 7 の演出時間と同じく範囲外にする。
- **3 分モードの的の停止**（約 36 秒ごとに約 2 秒）: 射撃の列の予測は数秒ずれる。7.5 の 3 は FB の時刻ではなく型（端数と段の並び）で比べる。
- **複数の敵**: S1 の段の対象（最も防御の低い敵・攻撃範囲内・敵全体）と分配ダメージの割り方は、単体ボスの前提で全部同じ敵・全額にしている。

## 12. 実装時の差分と知見（2026-09-24）

### 12.1 設計からの差分

1. **較正表の引き方**（3.3 節）: resourceId の表を読み込み時に `ShotParams` に載せる案をやめ、**射撃のパラメータの組**（チャージ 0.3 秒・`maintainFireStance` 23・`uptypeFireTiming` 1）で `firingParams` の中で引くようにした（`sim/firing.ts` の `MEASURED_CHARGE_CADENCE` と `measuredChargeCadence`）。`ShotParams` に resourceId が無く、キャラの読み込みの経路（アプリの fetch・テスト・CLI の直読み）が 3 つあって、読み込み時に載せると取りこぼすため。組は 202 体で紅蓮BS だけ（テストで固定）。`resourceIds` は出どころの記録として残した。
2. **較正値の持ち方**: 「解放 25f」ではなく、チャージのフレームに **+3f**（`chargeExtraFrames`）、リロード 1 回分に **+9f**（`reloadExtraFrames`）を足す形にした。射手・`simulateShotFrames`・`computeCadence` はどれも `FiringParams.chargeFrames` と `reloadChunkFrames` を読むので、呼び出し側を変えずに済む。チャージ速度▲は元のチャージ時間の側にだけ効く（+3f は縮まない）。
3. **間隔の変更の窓は `stateWindows` ではなく `BuffTimeline.cycleWindows`**（3.2 節）: 状態の窓は命中率の条件の判定（`statTotal`）が stat ごとに読むので、stat でない窓を混ぜると解決後の stat の型（`EffectStat`）と条件の判定に手を入れることになる。専用の窓の列にして、`resolveTimed` にも 1 パス目のループにも入らないようにした。窓の作り方（発火のフレームから、上書き延長は和集合）は `timed` と同じ。`TeamSlotResult.cycleWindows` で UI にも出す。
4. **段の番号は `ResolvedDamageEffect.cycle`**（3.1 節の `SkillHitEvent.cycleStep` の代わり）: 段ごとの倍率ダメージを `ResolvedDamageEffect` として作り、`{ step, steps }` を持たせた。`planSkillHits` は Stage 8 の倍率ダメージと同じ計算（その射撃と同じバフ・FB 中なら補正 +0.5）をそのまま使う。
5. **新しいモジュール `skills/cycles.ts`**: `resolveCycles`・`resolveCycleEvery`・`cycleShotFrames`・`cycleFires`（0.3 節の規則）。`cycleFires` は窓が重なったら小さいほうの間隔を使う。
6. **検証の追加**: `cycleEvery` の `every` が対象の循環の間隔以上なら、定義の検証（即値どうし）と解決時（`everyRef` の場合）の両方でエラー。宝物版の定義にも同じ検証を掛ける。
7. **注記**: 射撃姿勢維持型（`maintainFireStance` ≠ 0）の武器に出していた「未対応」の注記を、較正表の武器では「近似（射撃場の実測で較正）」に変えた（`damage.ts` の `modelNotes`）。
8. **定義**: `225.json` の `checkedAt` は、定義の検証テストが UTC の日付で見るので 2026-09-23 にした（モダニア編と同じ）。バーストの攻撃力 115.12%・チャージダメージ 169.63% が「バフは 100% 以下」の検査に掛かるので、`attack` / `chargeDamage` の `timed` だけ上限を 200% にした。
9. **CLI**: `sim-run.ts` に循環の段ごとの回数・合計と、間隔の変更の窓ごとの並び（窓の前の最後の段・端数 p・窓の中の段・窓の後の最初の段）を足した。
10. **テスト**: `skills/__tests__/stage11ScarletBs.test.ts`（DSL・解決・循環の規則）、`__tests__/stage11ScarletBsTeam.test.ts`（射撃の刻み・録画 47 の予測・1 発の値・3 編成の sim / calc 整合）。テストは **619 件**（モダニア編の 584 件から 35 件増）。既存の 584 件で期待を変えたのは 2 件（全キャラの射撃の列が Stage 9 と同じかのテストで 225 だけが違うこと、上の 8 の上限）。
