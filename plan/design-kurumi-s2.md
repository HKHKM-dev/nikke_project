## 1. 何が足りないか

クルミ（862）の S2 の説明文（`data/characters/862.json` の skill2）:

> フルバーストタイムの持続中に通常攻撃が{description_value_01}回命中した時、対象がハッキング状態なら、対象に「最終攻撃力の{description_value_02}％の追加ダメージ」

| 部分                                     | いまの語彙                                                                                            | 足りないもの                                                                                     |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 通常攻撃が N 回命中した時                | `{ count: normalHit, everyRef }`（S1 で使用中。C-0130）                                               | なし                                                                                             |
| フルバーストタイムの持続中に             | 無い。回数トリガーのカウンタは戦闘開始から通算で、状態によらず数える                                  | フルバースト中の命中だけを数える数え方か、発火の瞬間がフルバースト中かの条件（どちらかは未確定） |
| 対象がハッキング状態なら                 | 無い。条件は `timed` の `selfBuffed`（自分の stat の増加状態）だけ                                    | 敵に付いた持続ダメージ（`dot` の `status`）の状態の条件                                          |
| 最終攻撃力の X% の追加ダメージ（対象に） | `damage`・`damageType: additional`（1 ヒットの式は倍率ダメージと同じ。C-0131 の tick と同じ式を仮定） | なし                                                                                             |

「フルバーストタイムの持続中に N 回命中した時」には、少なくとも次の 3 つの読みがあり、説明文からは決まらない。

- **H1（フルバーストごとに数え直す）**: フルバースト中の命中だけを数え、フルバーストが始まるたびに 0 に戻す。各フルバーストの N・2N … 回目の命中で発火する。
- **H2（フルバースト中だけ数え、持ち越す）**: フルバースト中の命中だけを数え、フルバーストをまたいで続ける。
- **H3（通算の N の倍数の命中がフルバースト中なら）**: 戦闘開始から通算で数え（S1 と同じ列）、N の倍数の命中がフルバースト中なら発火する。S1 の N と同じ 36 なので、S1 のハッキングが付く命中と同じ命中で発火する。

同じ形の説明文はほかのキャラにもある（語彙の一般性を見るためだけに挙げる。どれも定義は無い）。

- フルバースト中の回数: ミハラ：ボンディングチェーン（162）の S2（対象の状態の条件つき。効果はスタックで、語彙に無い）、ソーダ：トゥインクルバニー（314）の S1（「通常攻撃で N 回攻撃した時」）。
- 対象の状態の条件: マルチャーナ：マリンスタディ（322）・エレグ（500）・レイ（仮称）（834）・リトルマーメイド（513）・プリバティ（170）・ファントム（580）・ベスティー：タクティカル・アップ（94）。状態の多くは持続ダメージではない（気絶・予告状・徹甲炸裂弾など）ので、この案の `targetStatus`（`dot` の `status` を見る）では書けない。持続ダメージでない状態は、そのキャラを定義するときに状態の付け外しの語彙を別に足す。

## 2. 案

### 2.1 回数トリガーの `during`（フルバースト中だけ数える）

`ShotCountTrigger` に次を足す。

```jsonc
{ "count": "normalHit", "everyRef": 1, "during": "fullBurst", "reset": "fullBurstStart" }
```

- **`during: 'fullBurst'`**: フルバーストの窓（`isInFullBurst` と同じ `[start, end)`）の中の射撃だけをカウンタに足す。窓の外の射撃は数えない（足す量 0）。
- **`reset`**（`during` を書くときは必須）:
  - `'fullBurstStart'`: フルバーストが始まるフレームでカウンタを 0 に戻す（H1）。
  - `'never'`: 戻さない（H2）。
  - 既定を持たせない（論点 4）。どちらを書くかは、根拠の結論で決める。
- 判定は `skills/triggers.ts` の `createTriggerTracker` に置く。`FrameEvents` の `fullBurstStart`・`fullBurstEnd` でフルバースト中かを閉包に持ち、同じフレームの射撃は開始なら数える・終了なら数えない（`isInFullBurst` と同じ境界）。1 パス目と `triggerFrames` の流し直しが同じコードを通るので、食い違わない。
- `every`・`everyRef` と組み合わせる。`stacksRef`・`lastShot` とは組み合わせない（使うキャラが無い）。
- 書ける効果: `damage` だけ（2.4 節）。

### 2.2 条件 `condition` の `fullBurst`（発火の瞬間がフルバースト中なら）

- 2026-10-09: `fullBurst` は `timed` と同じ `inFullBurst` に、2.3 節の `targetStatus` は目録の id を指す `enemyState` に、dot の `status` は `state` に改めた（[design-named-state.md](design-named-state.md) 5.5・5.6 節。ハッキングの id は `hacked`。付いている区間は [最初の発火, 最後の tick + 1) の半開区間で、含むフレームは同じ）。以下は当時の語彙として残す。

H3 を書くための条件。

```jsonc
{ "trigger": { "count": "normalHit", "everyRef": 1 }, "condition": { "fullBurst": true } }
```

- 発火のフレームがフルバーストの窓（`[start, end)`）の中のときだけ発火する。カウンタは窓によらず数える（`selfBuffed` と同じ。「カウンタは状態に関係なく数える」）。
- 2.1 節の `during` とは別物。`during` は数える射撃を絞り、`fullBurst` は発火を絞る。

### 2.3 条件 `condition` の `targetStatus`（対象が 〈状態〉 なら）

```jsonc
{ "condition": { "targetStatus": "hacking" } }
```

- 発火のフレームに、敵（1 体の前提）に `status` がその名前の持続ダメージが付いているときだけ発火する。
- 「付いている」は、同じ status のまとまり（`frame/dot.ts` の `dotTickTracker` が作る、維持の途中の付け直しでつながった発火の列）の **最初の発火のフレームから、最後の tick のフレームまで**（両端を含む）。
  - クルミのハッキングでは、最後の tick は最後に付いてから 5 秒の刻み（C-0133）なので、「最後に付いてから 5 秒」と同じ。
  - 同じフレームに付いたものも入れる（`selfBuffed` の「同じフレームに付いた窓も入れる」と同じ。論点 5）。
- 見る持続ダメージは、編成のどの枠のものでもよい（状態は敵に付くので）。`status` の名前はキャラの定義の中の名前で、別のキャラの同じ名前は同じ状態とみなす（いまは `hacking` を持つのはクルミだけ）。
- 名前の `status` を持つ `dot` が編成のどこにも無ければ、決して満たさない（定義の検証では落とさない。編成で決まるので）。

### 2.4 条件の型と、書ける場所

- damage の条件は `DamageCondition`（`skills/types.ts`）。キーを 1 つ以上持ち、キーが複数あれば、すべてを満たすときだけ発火する（AND）。

```ts
export type DamageCondition = {
  fullBurst?: true; // 2.2 節
  targetStatus?: string; // 2.3 節
};
```

- 実装では、`timed` の条件（`EffectCondition` の `selfBuffed`）とは型を分けた（2026-10-05）。書ける場所も判定する所（1 パス目のループの中か、後か）も違うので、1 つの型にすると既存の `selfBuffed` の読み手が欠けうる値を扱うことになる。
- `selfBuffed` の既存の定義（モダニア）は変わらない。
- `fullBurst`・`targetStatus` と `during` は、**`damage` にだけ** 書ける。
  - `damage` の発動は 1 パス目の後（`frame/plan.ts` の `planSkillHits`）で積むので、持続ダメージのまとまりとフルバーストの窓が出そろってから判定できる。
  - `timed`（攻撃力・射撃に効く stat）に書くと、1 パス目のループの中で敵の状態を追う必要が出る。使うキャラが無いので、いまは書けないことにする（検証で落とす）。
  - `damage` の `gaugeHits` とは組み合わせない（ゲージは 1 パス目で溜めるので、同じ理由）。クルミの S2 の追加ダメージがゲージを溜めるかの根拠も無い。
  - 射撃ごと（every = 1）の畳み込み（`damage.ts` の `perShot`）は、条件つきでは使わない（`during` の無い every = 1 に条件を書いたら、解決で落とす（`resolveDamageEffects` の RangeError）。`during` つきの every = 1 は畳み込まず、射撃ごとに 1 件ずつ発動を作る）。

### 2.5 実装の場所（承認後）

[skills-guide.md](skills-guide.md) 1.5 節の順。

1. `skills/types.ts`: `ShotCountTrigger` の `during`・`reset`、`EffectCondition` の `fullBurst`・`targetStatus`、`DamageEffect` の `condition` と、`parseSkillDefinition` の検証。単体テスト。
2. `skills/resolve.ts`: 解決したトリガーと条件を運ぶ。
3. `skills/triggers.ts`: `createTriggerTracker` で `during` と `reset` を数える。
4. `frame/plan.ts` の `planSkillHits`: 枠のループの前に、編成の全枠の持続ダメージのまとまりから status ごとの「付いている」区間の列を出しておき、`damage` の発火を `fullBurst`（`isInFullBurst`）と `targetStatus` で絞る。`frame/dot.ts` に、まとまりの区間（最初の発火・最後の tick）を返す関数を足す。ヒットを積む順（damage → dot → cycle）は変えない。
5. calc は `planTeamRun` の `skillHits` を使うので、別の変更は要らない。
6. 画面（`apps/web/src/components/SkillSection.tsx`）と CLI（`packages/core/scripts/sim-run.ts`）のラベル: 「フルバースト中の N 回命中（各フルバーストで数え直す / 持ち越す）」「フルバースト中なら」「対象が 〈状態〉 なら」。

### 2.6 退化

- 新しい項目を使う定義は無い（クルミの S2 は notes のまま）。既存のテストの数値、照合の結果（plan/residuals.md）は 1 行も変わらない見込み。
- 区間の列を先に出すだけで、ヒットを積む順は変えないので、`SkillHitEvent` の並び（同じフレームは枠順・定義順）も変わらない。

## 3. 根拠ができたときの定義の形

5 節の検証で読みが 1 つに決まったら、skill2 に次のどれか 1 つを書き、notes を消す（`claims` に結論の ID）。対象の状態の条件はどの読みでも同じ。

```jsonc
// H1
{ "kind": "damage", "trigger": { "count": "normalHit", "everyRef": 1, "during": "fullBurst", "reset": "fullBurstStart" },
  "condition": { "targetStatus": "hacking" }, "ref": 2, "damageType": "additional" }
// H2: reset を "never" に
// H3
{ "kind": "damage", "trigger": { "count": "normalHit", "everyRef": 1 },
  "condition": { "fullBurst": true, "targetStatus": "hacking" }, "ref": 2, "damageType": "additional" }
```

- `assumes`: 撃った弾はすべて命中する（S1 と同じ）。対象は敵 1 体。ハッキング状態の境界（付いたフレーム・最後の tick のフレーム）は 2.3 節の読み。
- フルバースト補正は、フルバースト中に出た倍率ダメージに乗る既存の扱い（`SKILL_HIT_FULL_BURST_BONUS`）がそのまま効く。クルミのバーストの受けるダメージ▲（C-0138）も既存の扱いで乗る。

## 4. 対象の状態の条件の根拠

- 「対象がハッキング状態なら」という条件があることは説明文に書かれている。境界（付いたフレーム・切れるフレーム）は書かれていない。
- クルミが撃ち続けている間は、S1 のハッキングが 36 回ごとに付き直り（C-0129）、バースト使用時にも付く（C-0136）ので、フルバースト中にハッキングが切れていることはほとんど無い。既存の録画からは境界を見分けられない見込みで、境界は `assumes` に書く仮定にとどめる。
- 条件を外すと（いつも満たすとすると）、ハッキングが切れているフルバースト（的のジャンプでクルミが撃てない間など）で追加ダメージを出しすぎる。説明文にある条件なので、外さずに書く。

## 5. 数え方の根拠の道筋（検証。承認後に起こす）

- **単騎では撮れない**。単騎ではフルバーストが起きない（C-0024）。クルミの単騎の録画（V-0051・V-0054 ほか）に S2 は出ない。II と III が要る。
- **既存の録画にフルバースト中のクルミがある**: クルミ（AI）+ デルタ（AI）+ III（操作・撃たない）の録画 125・196（III は I-DOLL・サン）と 132・133・195・197（III はドレイク。宝物 3 段階）。どれもフルバーストが 4 回ずつある（`125-02`・`132-02` など）。V-0103・V-0109・V-0165 は、クルミの 1 ヒットをコア命中率のために分けたが、S2 の追加ダメージの増分は数えていない（V-0103「読み方」で「分解できなければ落とす」とした）。
- **見分け方**: S2 の追加ダメージは、ハッキングの tick と同じ式（C-0131）なら、倍率の比（description_value_02 の 86.17 と S1 の 52.24）で tick と別の値の格子になる。各フルバーストで、追加ダメージの増分が出た命中が、
  - H1: フルバーストの入りから数えて N・2N … 回目の命中、
  - H2: 前のフルバーストからの続きで数えて N の倍数の命中、
  - H3: S1 のハッキングが付く命中（その 1 秒後から tick が始まる命中。C-0130）と同じ命中、
    のどれに当たるかで分ける。1 本に 4 回のフルバーストがあるので、H1 と H2 は 2 回目以降のフルバーストで分かれる。
- **最小構成**: 125・196 の未確定の要素は、問いの S2 のほかに I-DOLL・サン（308）の枠。I-DOLL・サンの説明文の効果は、S1 が自分の防御力▲（撃たないので起きない）、S2 が被弾時（前提の外）、バーストが自分の最大装弾数▲（撃たないので効かない）で、クルミの S2 に効く道は無い。ただし 308 は定義が無く、AGENTS.md の「機構が確定したキャラ」に当たらない（論点 3）。ドレイクの 4 本は、ドレイクの定義の効果がどれも根拠なしなので、使わない（ドレイクの S1 の攻撃力▲は追加ダメージの値の格子に乗る）。
- 予測は、読む前に固定する（[design-reread-prediction.md](design-reread-prediction.md)）。仮説は定義（トリガーと条件）を切り替えるものなので、予測ファイルの範囲外の部分は検証記録に手で書く（records/predictions/README.md）。語彙を実装した後なら、仮説ごとの定義でモデルを回して、フルバーストごとの追加ダメージの回数とフレームを出せる。

## 6. 論点

1. **語彙の形**
   - A（推奨）: 2.1〜2.3 節の 3 つ（`during` + `reset`、`fullBurst`、`targetStatus`）を足す。3 つの読みをどれも定義で書け、検証の仮説を定義の差し替えで出せる。ミハラ：ボンディングチェーン・ソーダ：トゥインクルバニーにもそのまま使える。
   - B: 検証で読みが決まってから、その読みの分だけ足す。語彙は小さいが、予測をモデルで出せず、手で数えることになる。
   - C: クルミ専用の効果の種類を作る。ほかのキャラに使えない。
2. **進め方**
   - a（推奨）: 語彙を実装し（クルミの S2 は notes のまま。退化なし）、次に検証記録を起こして、既存の録画 125・196 の読み直しで数え方を見分ける。撮影は要らない。
   - b: 新しく撮る（最小構成の III を探し、自動バースト ON で 180 秒）。
   - c: 語彙も検証も後回しにする（課題の優先順位）。
3. **I-DOLL・サン（308）の枠を最小構成に数えるか**（2 の a を選ぶとき）
   - i（推奨）: 308 の定義を notes だけで起こし（S1・バースト: 自分だけに付く効果で、撃たない操作枠では起きない、S2: 被弾は前提の外）、その根拠の結論を、125・196 の戦闘履歴のパネル（I-DOLL・サンの与ダメージ）と説明文から作ってから読み直す。
   - ii: 308 はクルミの S2 に効く道が無いので、オーナーの判断で読み直しの根拠に使ってよいとする（最小構成の警告は出たまま）。
   - iii: 読み直しは仮説の出どころにとどめ、結論は新しい録画（2 の b）で作る。
4. **`reset` に既定を持たせるか**
   - 推奨: 持たせない（`during` を書くときは必須）。H1 と H2 のどちらが多いかの根拠が無いので、書いた人が選ぶ形にする。
   - 代わり: H1 を既定にする（説明文の「フルバーストタイムの持続中に」を 1 回のフルバーストの中と読む）。
5. **`targetStatus` の境界**
   - 推奨: 2.3 節のとおり、まとまりの最初の発火のフレームから最後の tick のフレームまで（両端を含む）。同じフレームに付いたものも入れる（`selfBuffed` と同じ）。H3 では S2 と S1 が同じ命中で発火するが、その前の付き直しのハッキングが続いているので、ほとんどの場合は結果が変わらない。
   - 代わり: 同じフレームに付いたものは入れない（S2 の判定が S1 の付与より先）。根拠が無いので、推奨と同じく `assumes` に書く仮定になる。
