# 設計書: 戦闘力による一覧の並び替え

- 対象: 戦闘力の計算（`packages/core/src/combatPower.ts`）、育成のマスタの戦闘力の値（`packages/core/data/masters/` の `cubes.json`・`collections.json`・`overload.json`）、オーナーの育成データでの突き合わせ（`tools/builds/combat-power.ts`）
- 状態: 一部完了（段 1・育成状況の JSON の入出力・一覧の並び替えは実装済み（3・5・6 節）。戦闘力が同じキャラの順は調べ終えた（7 節。名前順のまま）。会心の項の形は未起案（4 節））
- 関連: C-0981・C-0982（式。根拠は V-0685）、[design-build-snapshot.md](design-build-snapshot.md)（育成データのスナップショット）、[design-cdn-refresh.md](design-cdn-refresh.md)（CDN の取り直し）
- 作成日: 2026-11-07

## 1. 背景

- キャラの一覧を戦闘力の降順で並べたい。実機の一覧の既定の並びが戦闘力の降順で、利用者が画面を直感的に扱える。
- 戦闘力の式は C-0981 で確定した（攻撃力・HP・防御力・会心・スキル Lv と、OL の行・キューブ・コレクション（宝物）の値）。

## 2. 決めたこと（2026-11-07、オーナー）

1. 個人の育成状況をコードに組み込まない。
2. 育成状況は、JSON で入出力できる機能にする。どのような機能にするかは未定。
3. ひとまず、オーナーの JSON を取り込み、実際の並びと合っているかを確かめる（段 1）。

## 3. 段 1: 計算と突き合わせ（実装済み）

### 3.1 データ

- キューブ・コレクション・宝物の値は CDN にある（`powers`）。`fetch-data` が正規化して `CubeData.powers`（index = Lv − 1）・`CollectionData.powers`（index = Lv）・`CollectionMaster.treasurePower`（段階 1〜3 で同じ値でなければ止める）に書く。
- OL の行の値（ゲームの `function_battlepower`）は CDN に無いので、`overload.json` に手書きする（`OverloadOptionData.powers`。index = Lv − 1）。ShiftyPad の `state_effects` に出た点はテストで固定し、出ていない Lv は C-0982 の規則の値。

### 3.2 計算

- `computeCombatPower(character, { growth, build, skillLevels, treasure }, masters)`。入力は `--build` の 1 件と同じ形（`BuildInput` と育成・スキル Lv）で、オーナーの育成は持たない。
- 攻撃力・HP・防御力は `computeCombatStat`（キャラ画面の値）。宝物は `treasure`（解放しているか）だけを見て、ステータスと値を足す（V-0685: ShiftyPad の Lv 0 も同じ。段階は戦闘力に効かないので、スナップショットの段階が未確定（`phase: null`）でも出せる）。
- アリーナの戦闘力は、`build.cube` をアリーナ用の欄のキューブにして同じ関数を呼ぶ。スナップショットはアリーナ用の欄を持たないので、段 1 では扱わない。

### 3.3 突き合わせ

- `npm run build:combat-power -- [<スナップショット>] [--actual <生の JSON>] [--list]`。育成データのスナップショット（`npm run build:import` が書く JSON）から戦闘力を出し、ShiftyPad の生のデータの `combat` と、値・降順の並び（高低が食い違う 2 体の組の数）を比べる。結果は画面に出すだけで、ファイルには書かない（オーナーのデータは `private/` から出さない）。
- 結果（2026-11-07）: 2026-09-24〜10-29 の 4 回の取得とも、全キャラの値が一致し、並びの食い違いは 0。ゲームの戦闘力が同じキャラの組があり、その組の一覧での順は式では決まらない（4 節）。

## 4. 残り

- 育成状況の JSON の入出力（2 節の 2）。形と画面は未定。スナップショット（`BuildSnapshot`）の形がそのまま使えるかも含めて、起案するときに決める。
- 一覧の画面の並び替え。
- 戦闘力が同じキャラの、実機の一覧での順（並べる 2 つ目の鍵）。実機の一覧のスクショと突き合わせれば分かる。
- 会心の項の形・取得に出ていない Lv（V-0685「分からないこと」）。次の育成データの取得で、`npm run build:combat-power` を回して確かめる。

## 5. 育成状況の JSON の入出力

4 節の 1 項目目。調べた時点は main の 69494cc。

### 5.1 いまの形

- 育成状況の JSON は、スナップショット（`BuildSnapshot`。`packages/core/src/shiftypad.ts`）が 1 つだけある。`npm run build:import`・`build:fetch` が ShiftyPad の生のデータから作り、`private/builds/` に書く（[design-build-snapshot.md](design-build-snapshot.md) 3 節）。
  - 形: `formatVersion: 1`・`fetchedAt`・`synchroLevel`・`recycleRoom`（tid → Lv）・`characters`（resourceId → 1 体分）・`unmapped`。1 体分は `growth`（Lv・凸・コア）と `BuildInput`（好感度・装備・キューブ・コレクション・リサイクルルーム・その他攻撃加算）に、`skillLevels`・`treasure`（tid・Lv・段階。段階は未確定なら `null`）を足したもの。
  - 読むのは CLI だけ: `sim-run.ts --build`（`buildEntriesOf`）と `build:combat-power`。どちらも形を確かめず、型を付けて読む（おかしな値は計算の途中で落ちる）。
- 画面（`apps/web`）は、育成をスロットごとに持つ（`SlotState` の `growth`・`build`・`skillLevels`・`treasurePhase`。キャラを替えても残る）。シンクロ Lv とリサイクルルーム（コンソール）は編成で共通。キャラごとの育成の置き場は無い。
- 画面のファイルの入出力は無い。スロット 1 つ分の育成の JSON の読み書き（`serializeSlotBuild`・`readSlotBuildJson`）は、画面の欄を #704 で消し、関数も [design-ui-rebuild.md](design-ui-rebuild.md) 3 節で消すと決めた。今回の育成状況は、スロットでなくアカウントの全キャラの育成で、別の機能。
- 戦闘力（段 1）は、スナップショットの 1 体分を `computeCombatPower` に渡して出す（`tools/builds/combat-power.ts`）。一覧の並び替え（4 節の 2 項目目）には、画面がキャラごとの育成を持つことが要る。

### 5.2 論点と案

#### 論点 1: JSON の形

| 案        | 中身                                                                                        | 良い点                                                                                                                                | 弱い点                                                                                                                              |
| --------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| A（推奨） | スナップショット（`BuildSnapshot` の版 1）をそのまま使う。画面も CLI も同じ形を読み書きする | 形が 1 つ。オーナーの `private/builds/` のファイルを、そのまま画面に読ませられる。CLI の `--build` と戦闘力の道具も同じファイルを読む | 1 体分の `recycleRoom` は上の `recycleRoom` と重なり、`extraAttack` は常に 0（`--build` の 1 件と同じ形にした名残）。画面は使わない |
| B         | 画面の用の新しい形を作り、スナップショットから写す                                          | 画面に要る項目だけにできる                                                                                                            | 形が 2 つになり、写す処理と検査が 2 組要る                                                                                          |

- 版: `formatVersion` は 1 のまま（前の版は無い）。読み込みは 1 だけを通し、ほかの値は「この版は読めない」で止める。これから形を変えるときは版を上げ、core の読み込みに前の版からの写しを足す（画面の編成の保存（`TEAM_FORMAT_VERSION`）と同じ流儀）。
- 読み込みで欠けてよい欄: `unmapped`（無ければ空）。ほかの欄は要る。

#### 論点 2: 入出力の入口

| 案        | 中身                                                                                                                                                                                                                                                                                                                                | 良い点                                                                                                                                                   | 弱い点                                       |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| A（推奨） | 画面と CLI の両方。画面は設定のメニュー（右上）に「育成状況」の欄を足し、「読み込む」（ファイルを選ぶ）・「書き出す」（ファイルを保存させる）・「消す」を置く。読み込んだものはブラウザ（localStorage）に保存する。CLI は今の道具（`build:import` が書き、`sim-run.ts --build`・`build:combat-power` が読む）に、5.3 節の検査を通す | 一覧の並び替え（次の項目）に、画面がキャラごとの育成を持てる。個人の育成状況は利用者のブラウザの中だけにあり、コードにもサーバーにも入らない（2 節の 1） | 画面の作りが増える                           |
| B         | CLI だけ。画面は並び替えの項目でまとめて作る                                                                                                                                                                                                                                                                                        | 今回の差分が小さい                                                                                                                                       | 画面から使えない。並び替えの項目が大きくなる |

- 設定のメニューは `apps/web/src/components/SettingsMenu.tsx` にあり、クラシック・モダンで同じ。モダン UI のブランチが直している `ModernView.tsx`・`styles.css` は触らない（見た目は今のメニューの部品を使う）。
- ShiftyPad の生のデータを画面で直接読むことはしない。生のデータを取るにはログインが要り、アカウント連携は範囲の外（[requirements.md](requirements.md) 4 節）。生のデータからスナップショットへの写しは、これまでどおり CLI（`build:import`・`build:fetch`）で行う。

#### 論点 3: 画面で読み込んだ育成状況をどう使うか

| 案        | 中身                                                                                                                                                                                                                                                                                                                                                                                                                                                | 良い点                                                                                                                           | 弱い点                                                                                                                                                                       |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A（推奨） | 読み込んだ育成状況は書き換えない。育成状況にいるキャラをスロットに入れたときに、そのキャラの育成（凸・コア・好感度・装備・キューブ・コレクション・スキル Lv・宝物の段階）をスロットへ写す。読み込んだときは、シンクロ Lv とコンソールも写し、全部の編成のスロットのうち育成状況にいるキャラにも写す（スロットで変えた育成を上書きするので、読み込む前に確かめる）。書き出しは、保存してある育成状況をそのまま書く（別のブラウザへ移す・控えにする） | 育成状況は取った時点の実際の育成のまま残り、スロットでの試し（装備を替えたら、など）がそれを壊さない。並び替えは実際の育成で並ぶ | 画面で育成状況を作る・直すことはできない。育成状況を作れるのは、今は CLI（ShiftyPad から）だけ                                                                               |
| B         | A に加え、スロットで変えた育成を育成状況に書き戻す。書き出しはそれを含む                                                                                                                                                                                                                                                                                                                                                                            | ShiftyPad を使わない利用者も、スロットで入れた育成を育成状況として残せる                                                         | 試しの値で実際の育成が上書きされる。宝物は段階しか画面に無く、tid と Lv に戻せない（段階 1 の Lv が未確定）。同じキャラを入れた編成が 2 つあると、どちらを残すかが決まらない |
| C         | 持つだけ。スロットには写さない（並び替えだけに使う）                                                                                                                                                                                                                                                                                                                                                                                                | 今のスロットの動きが変わらない                                                                                                   | 今回の項目では画面に何も起きない。並べた一覧から入れたキャラの育成を、手で入れ直すことになる                                                                                 |

- A で写さないもの: キャラごとの Lv（`growth.level`）。画面は編成で共通のシンクロ Lv で計算する（[design-ui-rebuild.md](design-ui-rebuild.md) 3 節）ので、シンクロデバイスの元の 5 体の Lv は写らない。戦闘力（並び替え）はキャラごとの Lv で出す。
- 宝物の段階が未確定（Lv 0。`phase: null`）のキャラは、宝物なし（段階 0）でスロットに写し、読み込みの結果に「宝物の段階が未確定の N 体は宝物なしにした（スロットで選ぶ）」と出す（CLI の `sim-run.ts --build` と同じ扱い。AGENTS.md のプレースホルダーの規則）。戦闘力は段階によらない（3.2 節）ので、並び替えには効かない。
- スペック固定の間は、計算が固定の育成を使う（今のまま）。写したスロットの値は、固定を外すと効く。

### 5.3 読み込みの検査とエラーの見せ方

- 検査は core の 1 つの関数（`readBuildSnapshot(json, index)`）にし、画面と CLI で同じものを使う。値の範囲は、画面の編成の保存の読み込み（`apps/web/src/team.ts` の `parseBuild` ほか）と同じもの（凸・コアはレアリティの上限、好感度 1〜40、装備の Lv 0〜5、OL の行 3 つまで・Lv 1〜15、キューブの Lv 1〜15、コレクションの Lv 0〜15、スキル Lv 1〜10、宝物の段階 2・3・`null`）を core に置き、両方から使う（同じ範囲を 2 か所に書かない）。キューブの種類・OL の項目のマスタとの照合は、今までどおり計算の時（`validateBuild`）。
- 止める（何も変えない）もの: JSON として読めない・スナップショットの形でない・知らない版・範囲の外の値。理由は欄の場所つきで、最初の 5 件まで出す（例: `characters.5001.gear.arm.level: 0〜5 の整数でない（7）`）。
- 進めて知らせるもの: キャラのデータに無い resourceId（CDN の取り直しの前のデータ。飛ばす）・宝物の段階が未確定・`unmapped` が空でない。
- 画面: 結果をメニューの「育成状況」の欄の中に文で出す（成功は「2026-10-29 の育成・N 体を読み込んだ」と知らせの行、失敗は理由）。保存してある育成状況は、欄に取得の日と体数を出す。
- CLI: `build:combat-power` と `sim-run.ts --build`（スナップショットを渡したとき。`formatVersion` の無い今の `--build` の JSON は今のまま）が同じ検査を通し、止めるものは理由を出して終わる。

### 5.4 戦闘力の計算（段 1）とのつながり

- スナップショットの 1 体分から戦闘力を出す処理を core の 1 つの関数にし（`computeCombatPower` に `growth`・`build`・`skillLevels`・宝物の有無を渡す）、`build:combat-power` と、次の項目の画面の並び替えの両方で使う。
- 今回の項目では、画面に戦闘力を出さない（一覧の並び替えは 4 節の 2 項目目）。

### 5.5 決めてほしいこと

1. JSON の形 — 推奨: **論点 1 の案 A（スナップショットの版 1 をそのまま使う）**。代替: 案 B（画面の用の形）。
2. 入出力の入口 — 推奨: **論点 2 の案 A（画面の設定のメニューと CLI の両方）**。代替: 案 B（CLI だけ）。
3. 画面での使い方 — 推奨: **論点 3 の案 A（書き換えない・スロットに入れたときと読み込んだときに写す・書き出しは保存したまま）**。代替: 案 B（スロットの変更を書き戻す）、案 C（持つだけ）。
4. 読み込みの検査 — 推奨: **5.3 節のとおり（core の 1 つの関数で、止めるものと知らせるものを分ける）**。

- 決定（2026-11-07、オーナー）: 1〜4 とも推奨のとおり。

### 5.6 実装（2026-11-07）

- core: 形・読み込みの検査・戦闘力は `packages/core/src/buildSnapshot.ts`（`readBuildSnapshot`・`snapshotCombatPower`。型は `shiftypad.ts` から移した）。値の範囲の検査は `packages/core/src/buildJson.ts` に置き、画面の編成の保存の読み込み（`apps/web/src/team.ts`）もそれを使う。使われなくなった `buildEntriesOf` は消した。
- CLI: `build:combat-power` と `sim-run.ts --build`（`formatVersion` を持つ JSON のとき）が同じ検査を通す。
- 画面: 設定のメニューの「育成状況」（`components/RosterSettings.tsx`・`useRoster.ts`）。写し方と保存は `apps/web/src/roster.ts`（保存のキーは `nikke-calc.roster.v1`）。キャラをスロットに入れる操作は、育成状況の育成を付けて reducer に渡す（`selectCharacter` の `fields`。別のニケに変えたときだけ写す）。
- 確かめたこと: オーナーの 2026-10-29 のスナップショットを、`build:combat-power`（全キャラが一致・並びの食い違い 0）・`sim-run.ts --build`・画面（読み込み・スロットへの写し・書き出し・再読み込みの後の保存）で読んだ。範囲の外の値は、CLI と画面の両方で欄の場所つきで止まった。

## 6. 一覧の並び替え

4 節の 2 項目目。5 節の育成状況（画面に読み込んだスナップショット）を使う。調べた時点は main の 98d5a8d と、5 節の PR のブランチ。

### 6.1 いまの形

- キャラを選ぶ一覧は 2 つある。どちらも、受け取ったキャラの一覧（`index`）を、その中で名前順（`localeCompare(…, 'ja')`）に並べ直している。
  - モダン: ニケ一覧のトレイ（`apps/web/src/components/modern/CharacterTray.tsx`）。名前の検索・バッジの絞り込み・「完全対応のみ」がある。
  - クラシック: スロットごとのニケの選択肢（`apps/web/src/components/CharacterPicker.tsx`。`<select>`）。
- 所持の区別は無い（全キャラが並ぶ）。
- 戦闘力の計算（`snapshotCombatPower`）には、1 体ごとにキャラのデータ（`data/characters/<id>.json`）の `rarity`・`class`・`corporation`・`weaponType`・`levelCurve`・`statEnhance`・`treasure`・`crit` が要る。画面は今、スロットにいるキャラのデータだけを読む（`useCharacterCache`）。
  - キャラのデータは 206 体で 8.4MB、gzip で 1 体およそ 17KB。そのうち 6.1MB が `levelCurve`（Lv 1〜1400 の基礎ステータス）で、中身は 37 通りしかない。
- モダン UI のブランチ（`claude/nikke-damage-styling-lrz7em`）が、`CharacterTray.tsx` の見出しの部分と `ModernView.tsx`・`styles.css` を直している。

### 6.2 論点と案

#### 論点 1: 並びを切り替えるか、どこで切り替えるか

| 案        | 中身                                                                                                                                                             | 良い点                                                                                                         | 弱い点                                                                                    |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| A（推奨） | 「名前順」と「戦闘力順」を切り替える。欄は設定のメニューの「育成状況」の欄に置く。既定は、育成状況があれば戦闘力順、無ければ名前順。選んだ並びはブラウザに覚える | 2 つの画面で同じ欄。モダン UI のブランチが直しているトレイの見出しに触れない。育成状況の無い利用者には今のまま | 並びを変えるのにメニューを開く                                                            |
| B         | A と同じ切り替えを、トレイの絞り込みの並び（検索の横）に置く。クラシックは設定のメニュー                                                                         | 一覧のそばで切り替えられる                                                                                     | モダン UI のブランチと同じ所を直すので、そのブランチのマージを待つ。欄が 2 か所に分かれる |
| C         | 切り替えない。育成状況があれば常に戦闘力順                                                                                                                       | 欄が要らない                                                                                                   | クラシックの選択肢（200 体の `<select>`）で、名前から探しにくくなる                       |

#### 論点 2: 育成状況にいないキャラ（所持していないキャラ）

| 案        | 中身                                                                                             | 良い点                                             | 弱い点                                           |
| --------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------- | ------------------------------------------------ |
| A（推奨） | 戦闘力順では、育成状況にいるキャラを戦闘力の降順で先に並べ、いないキャラをその後に名前順で並べる | 所持していないキャラでも試算できる今の使い方が残る | 実機の一覧（所持キャラだけ）と、後ろの部分が違う |
| B         | 戦闘力順では、育成状況にいるキャラだけを出す                                                     | 実機の一覧と同じ                                   | 所持していないキャラを入れるには、名前順に戻す   |

- 所持だけに絞る欄（バッジの絞り込みの「所持のみ」）は、要る場面が出たら足す（トレイの見出しはモダン UI のブランチが直している）。

#### 論点 3: 計算に要るキャラのデータの読み方

| 案        | 中身                                                                                                                                                                                                                                                                             | 良い点                                                                                                  | 弱い点                                                                                    |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| A（推奨） | 戦闘力の計算に要る値だけの表（`data/characters/combat.json`）を作る。1 体分は `levelCurve` を除く 7 項目と、37 通りの `levelCurve` の番号。`levelCurve` は表の中に 1 回ずつ置く。`npm run fetch-data` が `index.json` と一緒に書き、今のキャラのデータからも作り直せるようにする | 1 回の読み込み（今のキャラのデータで作ると 1.2MB、gzip で 400KB）。並びが読み込みの途中で入れ替わらない | データの道具に手が入る。キャラのデータと表の食い違いを、テストで見る必要がある            |
| B         | 育成状況にいるキャラのデータ（`<id>.json`）を全部読む（`useCharacterCache` を使う）                                                                                                                                                                                              | データの道具を変えない                                                                                  | 読み込みが 200 回・gzip で 3MB 前後。読み終わるまで並びが決まらず、読むにつれて入れ替わる |

#### 論点 4: 戦闘力の値を一覧に出すか

| 案        | 中身                                                                                                                            | 良い点                                                   | 弱い点                                                 |
| --------- | ------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------ |
| A（推奨） | 戦闘力順のときに出す。トレイは項目の `title`（マウスを重ねたときの文）に、クラシックは選択肢の名前の後ろに「（戦闘力 12,345）」 | 実機の値と見比べられる。見た目（`styles.css`）を変えない | トレイでは、マウスを重ねないと見えない                 |
| B         | トレイの項目の名前の下に出す                                                                                                    | いつも見える                                             | 見た目の変更が要り、モダン UI のブランチのマージを待つ |
| C         | 出さない                                                                                                                        | 変更が小さい                                             | 並びが正しいかを、画面では確かめられない               |

### 6.3 決めずに置くもの

- 戦闘力が同じキャラの順（4 節の 3 項目目）は分かっていない。それまでは名前順で並べ、未対応・近似・仮定の一覧に「戦闘力が同じキャラの、一覧での順は実機と違うことがある」と出す（戦闘力順のときだけ）。
- 戦闘力が出せないキャラ（育成状況の値がキャラのデータと合わず、計算が止まるもの）は、育成状況にいないキャラと同じ所に並べ、その数を設定のメニューの「育成状況」の欄に出す。

### 6.4 作り

- 並べる処理は純関数（`apps/web/src/listOrder.ts` など）にして、テストで固定する。App が並べたキャラの一覧を作って画面に渡し、`CharacterTray.tsx`・`CharacterPicker.tsx` の名前順の並べ直しをやめる。`ModernView.tsx` は、受け取った一覧をそのままトレイへ渡しているので触らない。
- 戦闘力は、育成状況とマスタと表（論点 3）が変わったときだけ計算し直す。

### 6.5 決めてほしいこと

1. 並びの切り替え — 推奨: **論点 1 の案 A（設定のメニューで切り替える。育成状況があれば戦闘力順が既定）**。代替: 案 B（トレイに置く）、案 C（切り替えない）。
2. 育成状況にいないキャラ — 推奨: **論点 2 の案 A（後ろに名前順で並べる）**。代替: 案 B（出さない）。
3. キャラのデータの読み方 — 推奨: **論点 3 の案 A（戦闘力の計算に要る値だけの表を作る）**。代替: 案 B（キャラのデータを全部読む）。
4. 戦闘力の値 — 推奨: **論点 4 の案 A（戦闘力順のときに、トレイは `title`、クラシックは選択肢の名前の後ろに出す）**。代替: 案 B（トレイの項目に出す）、案 C（出さない）。

- 決定（2026-11-07、オーナー）: 1〜4 とも推奨のとおり。

### 6.6 実装（2026-11-07）

- 戦闘力の表: `packages/core/src/combatTable.ts`（`buildCombatPowerTable`・`combatCharacterOf`・`loadCombatPowerTable`）と `packages/core/data/characters/combat.json`。`npm run fetch-data` がキャラのデータと一緒に書き、`npm run combat-table` が手元のキャラのデータから作り直す。基礎ステータスの曲線は前の Lv との差で持ち、37 通りを 1 回ずつ置く（今のデータで 0.9MB、gzip で 55KB）。表から出す戦闘力がキャラのデータから出すものと全キャラで同じことを、テストで確かめる。
- 戦闘力の計算（`computeCombatStat`）は、宝物の中身を見ず有無だけを見るので、キャラの `treasure` の型を `unknown`（null なら無い）に広げた。
- 育成状況の全キャラの戦闘力は core の `snapshotCombatPowers`（出せないキャラは理由つきで分ける）。画面と `build:combat-power` が使う。
- 画面: 並べる処理は `apps/web/src/listOrder.ts`、状態は `useListOrder.ts`（並びはブラウザに覚える。表は育成状況があるときだけ読む）、切り替えは設定のメニューの「一覧の並び」（`components/ListOrderSettings.tsx`）。App が並べた一覧を画面に渡し、トレイと選択肢は名前順の並べ直しをやめた。戦闘力の添え書きと、未対応の一覧の「一覧の並び」の 1 行は、React の context（`ListOrderContext`）で渡す（モダン UI のブランチが直している `ModernView.tsx` を通さないため。そのブランチのマージの後に props にしてよい）。
- 確かめたこと: オーナーの 2026-10-29 の育成状況を画面に読み込み、クラシックの選択肢の並びをゲームの戦闘力（生のデータの `combat`）と比べた。育成状況にいるキャラが先に並び、隣どうしの高低の逆転は 0。所持していないキャラはその後に名前順。トレイの `title`・選択肢の名前の後ろの値・設定の切り替えと再読み込みの後の保存・未対応の一覧の 1 行も出た。

## 7. 戦闘力が同じキャラの順

4 節の 3 項目目。6 節の一覧の戦闘力順で、戦闘力が同じキャラを今は仮に名前順に並べ、未対応の一覧に「実機と違うことがある」と出している（6.3 節）。

### 7.1 分かっていること

- 2026-10-24・10-29 の取得に、戦闘力が同じ組がある（2〜4 体）。組の中のキャラは、凸・コア・Lv が同じで、キャラの番号（`nameCode`）・`resourceId`・名前・属性・企業・武器・バーストの段階が違う。
- 取得の API が返すキャラの順は、番号の順ではなく、取得の回によって組の中の順が入れ替わる（入手の順のような固定の順でもない）。
- 実機の一覧での順は、まだ見ていない。仮説と見分け方は V-0688。

### 7.2 論点と案

#### 論点 1: 確かめ方
