# 自動マージを待つ PR の衝突を GitHub Actions が直す（2026-11-21）

- 何のための文書か: 自動マージを予約した PR が、main が進んで衝突になったときに、セッションが気づくまで止まる時間をなくす案と論点を出す。2026-11-21 にオーナーが案 A を承認し、実装した（7 節）。
- 関連: 生成物の衝突をなくした回（[design-pr-conflicts.md](design-pr-conflicts.md)。1 節の頻度・5 節のデプロイキー）、`pr:prep`（`tools/git/pr-prep.ts`）、番号の振り直し（`packages/core/scripts/records-renumber.ts`）、PR の見張りを既定の動きに任せた回（[design-workflow-simplification-17.md](design-workflow-simplification-17.md) 12 節）。

## 1. いま起きていること

- 生成物は PR に入らないので（design-pr-conflicts.md 5 節）、PR を作った後に残る衝突は次の 2 つ。
  1. 並行するスキルの PR どうしで、足した結論・録画の ID が重なるもの（同じファイル名を足すので Git の衝突になる）。例: 開いている PR #1309（claude/leona）とマージ済みの #1305（ノベル）が、どちらも C-1449 を足した。
  2. 手で直すファイルを両方が直したもの。
- 2026-11-21 の時点で、自動マージを予約した PR #1299 が衝突（`mergeable_state: dirty`）のまま止まっている。
- main が進んで PR が衝突になっても、GitHub は PR にイベント（コメント・CI・レビュー）を出さない。そのため、PR の見張りの既定の確認（最後の動きから約 50 分後）か、デスクトップの Auto-fix の確認まで、だれも気づかない。作成の後に衝突した PR の開いている時間の中央値は 30 分、衝突しなかったものは 5 分（design-pr-conflicts.md 1 節。#701〜）。
- 衝突の直し方は、ほとんどが決まった手順で済む。`pr:prep` が生成物の衝突と「両方が行を足しただけ」の衝突を解き、ID の重なりは `records:renumber` のコマンドを出す。人が考える必要があるのは、生成物でない手で直すファイルの中身の衝突だけ。

## 2. 案

### 案 A（推奨）: main への push で動くワークフローが、衝突した PR を直して push する

新しいワークフロー `.github/workflows/auto-rebase.yml` と、道具 `tools/git/auto-rebase.ts`（判断の部分は `auto-rebase-lib.ts` に分けてテストする）を足す。

1. **起動**: main への push（`push: branches: [main]`）。スカッシュマージ（人の操作なので Actions が起きる）と、CI の生成物の commit（デプロイキーの push なので起きる）の両方で動く。`concurrency` は 1 つのグループにし、走っている古い実行は止める（後の実行が全部を見直す）。
2. **対象を集める**: 開いている PR のうち、自動マージを予約していて、head が同じリポジトリのブランチのもの。それぞれ `mergeable` を問う。GitHub は main の push の後に非同期で計算するので、`null` の間は数秒おきに問い直す（上限 2 分）。
   - `mergeable: false`（衝突）の PR を直す。
   - `mergeable: true` でも、ブランチで足した ID が main と重なる PR は直す。検証記録はファイル名に名前が付くので、番号が重なっても Git の衝突にならず、そのままマージされうる（design-stage20.md の 223 行目の論点。いまは一覧の `plan/verifications.md` が生成物なので、一覧の行の衝突でも止まらない）。
3. **直す**（PR ごと。head の sha を覚えておく）:
   1. ブランチを取り出し、`pr:prep` と同じ判定（`collisions`）で、足した ID が main と重なっていないかを見る。重なった検証記録・結論は `records:renumber` で、道具の出した番号に振り直して commit する（「番号の振り直し（自動）」）。録画と課題の番号は振り直さない（録画は E: と Drive の名前も変えるのでオーナーの手元でしか回せない。課題の番号は道具で振り直さない決まり。design-backlog-files.md 2.2 節）。この 2 つは 4. のコメントに回す。
   2. `npm run pr:prep -- --no-ci --allow-progress` を回す（リベース・生成物と「両方が行を足しただけ」の衝突の解消・records:check の書き換えの commit・バッジの書き出し・生成物を main の版に戻す）。型・テスト・ビルドは、push で起きる PR の CI に任せる。進み具合の書き写しは、PR を出す前の `pr:prep` が見ているので省く。
   3. デプロイキー（secret の `GENERATED_DEPLOY_KEY`）で、覚えておいた head の sha を期待値にして `git push --force-with-lease=refs/heads/<ブランチ>:<sha>` する。セッションが先に直して push していたら、push が断られるので何もしない。
   4. 振り直したら、PR の題名・本文の古い ID を新しい ID に書き換え、何を振り直したかを PR にコメントする。
   5. push の後に自動マージが外れていたら、PR にコメントして、セッションに予約し直しを頼む（4 節の論点 4。Actions は予約し直さない）。
4. **直せないとき**: 生成物でないファイルの中身が衝突した・録画か課題の番号が重なった・`pr:prep` が別の理由で止まった・lease で断られた以外の理由で push が落ちた、のどれかなら、push せずに PR にコメントする。コメントには止まった理由と `pr:prep` の出力の末尾と「セッションで `npm run pr:prep -- --push` を回す」を書く。コメントは PR の見張りのイベントとして届き、セッションを起こす（届くかは 6 節で確かめる）。同じ head の sha に同じコメントを 2 回書かない（コメントに sha の印を入れて見分ける）。
5. **セッションの側**: `pr:prep` に、fetch の後で origin の同じ名前のブランチに手元に無い commit があれば止める確かめを足す（4 節の論点 3）。止まったら、`git reset --hard origin/<ブランチ>` で取ってから回し直す、と出す。

### 案 B: 衝突を見つけて知らせるだけ

1・2 は案 A と同じで、直さずに PR にコメントしてセッションを起こす。直すのはセッション。

- 良い点: PR のブランチに Actions が push しない。振り直しを自動でしない。
- 悪い点: セッションが起きて `pr:prep` を回すまで、数分から十数分止まる（セッションがほかの作業の途中なら、その後）。ID の重なりの振り直しのような決まった手順も、毎回セッションが行う。

### 採らない案

- **PR の見張りの確認を短くする**: 確認は空振りが多く、オーナーの依頼で既定に任せた（design-workflow-simplification-17.md 12 節）。どの PR でも同じ間隔で起きるので、衝突のときだけ早く起きることはできない。
- **ruleset で「最新の main に合わせる」を求める（strict）**: 衝突でない PR まで、main が進むたびに CI を回し直す必要が出る。並行が多い日には、後の PR ほど長く待つ。

## 3. 費用

- 衝突した PR 1 本あたり、`npm ci` と `pr:prep --no-ci`（records:minimal とバッジの書き出し。このクラウドの環境で約 1 分半）。その後の PR の CI は、セッションが直しても同じだけ回る。
- 衝突が無いときは、PR の一覧と `mergeable` を問うだけで終わる（`npm ci` も回さない）。

## 4. 論点

1. **デプロイキーで PR のブランチに push してよいか**: ruleset「automerge」は既定のブランチ（main）だけに掛かる（2026-11-21 に API で確かめた）。書き込みのできるデプロイキーは、ほかのブランチにも push できる。デプロイキーの push は、GITHUB_TOKEN の push と違って PR の CI（`pull_request` の `synchronize`）を起こすので、直した版が必須チェックを通ってからマージされる。対象は同じリポジトリの `claude/`・`antigrav/` のブランチに限る（フォークの PR と、ほかの名前のブランチには触らない）。
2. **振り直しを自動でしてよいか**: 対象は、自動マージを予約した PR、つまり仕上がって見直しも済んだもの。振り直しは検証記録・予測・結論のファイルと、リポジトリの中の参照（`records:renumber` が全部のテキストのファイルで置き換える）をまとめて動かすので、リポジトリの中の参照は壊れない。リポジトリの外（チャットの撮影の依頼・オーナーの覚え）の古い ID は残るが、PR にコメントで新旧の対応を残すので引ける。範囲の書き方（「C-NNNN〜C-MMMM」）の中に古い ID があると、`records:renumber` は ID だけ置き換えて場所を出す（人が直す）。この場合は push せず、コメントに回す（範囲が崩れたまま入れない）。
3. **セッションの手元のブランチが古くなる**: Actions が push すると、セッションの手元のブランチは origin より古くなる。
   - 取り込みのフック（`catch-up.ts`）は、PR を出したブランチと、origin に手元に無い commit があるブランチを取り込まないので、上書きはしない。
   - マージの後は、フック（`sync-after-merge.ts`）がマージ済みのブランチを origin/main に揃えるので、手元の古さは消える。
   - 危ないのは、セッションがマージの前に `pr:prep -- --push` を回したとき。`pr:prep` は `git fetch origin` の後に `--force-with-lease`（期待値を書かない形）で push するので、fetch で追跡先が Actions の版に進み、Actions の直しを黙って上書きする。そこで 2. の 5 の確かめを足す。
4. **自動マージが外れたときに Actions が予約し直さない理由**: GITHUB_TOKEN で予約すると、マージの操作が github-actions[bot] のものになり、マージの commit の push で main の CI（生成物の作り直し）と Pages が起きない（GITHUB_TOKEN の操作は Actions を起こさない）。書き込みのできる人の push では自動マージは外れない（GitHub の仕様）ので、デプロイキーの push で外れるかは 6 節で確かめる。外れるなら、コメントでセッションに予約し直しを頼む。
5. **メモリ `pr-workflow` の手順**: 「衝突を直して push し直したら、自動マージを予約し直す」は残す（セッションが直したとき）。Actions のコメントを受けたときの手順（直せなかった → `pr:prep -- --push` と予約し直し、振り直した → 手元を `git reset --hard origin/<ブランチ>` で揃える、は要らない。マージの後のフックが揃える）を足す。
6. **PR のマージの直前の競り合い**: main が進んで Git の衝突にならない ID の重なり（検証記録）は、PR の CI が先に通っていれば、ワークフローが見る前に自動マージされうる（必須チェックは最新の main に合わせることを求めていない）。案 A はこの隙を狭めるが、なくしはしない。main に重なった ID が入ったら、main の CI（`records:check`）が落ちて分かる。

## 5. 推奨

案 A。案 B より止まる時間が短く（main の push の後、数分で直った版が PR の CI に入る）、直せないときの動きは案 B と同じ。新しい secret・鍵・ruleset の設定は要らない（デプロイキーは CI の生成物の commit と同じものを使う）。

## 6. マージの後に GitHub の上で確かめること

GitHub の上でしか試せないので、この PR のマージの後に次を確かめ、経過に書く。

1. main の push でワークフローが動き、衝突の無いときは `npm ci` を回さずに終わる。
2. 衝突している PR（そのとき開いていれば #1299 か #1309。無ければ使い捨ての 2 本の PR で同じ行を変えて作る）を直して push し、PR の CI が回り、自動マージが残るか。
3. 直せない衝突で書いたコメントが、`subscribe_pr_activity` の見張りのイベントとしてセッションに届くか（github-actions[bot] のコメント）。届かないなら、コメントの代わりの起こし方を別に考える（この設計の範囲の外。課題に起票する）。

## 7. 決定と実施

- 決定（2026-11-21、オーナー）: 案 A。デプロイキーで PR のブランチ（このリポジトリの `claude/`・`antigrav/`）に push してよい。検証記録・結論の ID は自動で振り直してよい（範囲の書き方の中にあるものは振り直さずコメントする）。
- 実装: `.github/workflows/auto-rebase.yml` と `tools/git/auto-rebase.ts`（判断は `auto-rebase-lib.ts`）。`records:renumber` に `--fail-on-ranges`（人が直す範囲の書き方があれば終了コード 3）、`pr:prep` に 2 節の 5 の確かめ（`fixedByAutoRebase`）、ID の重なりの判定の共有（`branchCollisions`）、デプロイキーの ssh の共有（`tools/git/deploy-key.ts`）を足した。
- 案からの変更:
  - 振り直しの後、ブランチを 1 つの commit にまとめてから `pr:prep` を回す。PR #1309 の写しで試すと、振り直しを別の commit にしても、リベースは振り直す前の C-1449 のファイルを足した commit から当て直すので、main の C-1449 と衝突して止まった。まとめると、取り込みは通った（`states.ts` は「両方が行を足しただけ」で解けた）。PR はスカッシュでマージするので、途中の commit は要らない。衝突の有無にかかわらずまとめる（途中の commit だけの衝突も無くなる）。セッションの `pr:prep` の手順にも同じ問題がある（課題 `pr-prep-renumber-rebase.json`）。
  - Actions の中の `pr:prep` は、環境変数 `NIKKE_AUTO_REBASE=1` で 2 節の 5 の確かめを省く（2 回目の直しで、自分の前の直しに当たって止まるので）。
  - `--find` は GitHub の API だけで決め（npm ci の前）、衝突か、決まらなかったか、ID の重なりうる記録（検証記録・結論・録画・課題の番号）を足した PR を `--fix` に渡す。ID の重なりは `--fix` が git で確かめる。直せなかった head は、コメントの印を見て次から飛ばす。
  - 見直し（バグ）で分かったこと: 4 節の 3 の「マージの後はフックがマージ済みのブランチを origin/main に揃えるので、手元の古さは消える」は当たらない。フック（`sync-after-merge.ts`）は、マージした PR の head と手元の HEAD が同じときだけ揃える。そこで、振り直さなかったときも直して push したら PR にコメントし、セッションに `git reset --hard origin/<ブランチ>` で揃えてもらう（揃えればマージの後にフックが働く）。まとめた commit のメッセージには、元の commit のメッセージ（帰属の行を含む）を残す。通信の失敗（fetch・push）はコメントせず、次の実行で直し直す。
- 制約: `--fix` は PR のブランチを取り出してから、そのブランチの版の `records:renumber`・`pr:prep` を回す（道具は自分のいる作業ツリーを書き換えるため）。この PR より前に main から分かれたブランチでは `--fail-on-ranges` が無いので、振り直しが要るときは止まってコメントになる。
- 確かめたこと: 道具の判断の部分のテスト（`auto-rebase-lib.test.ts`・`pr-prep-lib.test.ts`）。PR #1309 の写しで、`branchCollisions` が C-1449 の重なりと空いた番号を出し、振り直し → 1 つにまとめる → `pr:prep --no-ci --allow-progress` が通ること。`records:renumber --dry-run --fail-on-ranges` が範囲の書き方のある結論で 3 で終わること（見直しの後は --dry-run を付けずに 1 回だけ回し、3 なら置き換えを捨てる形にした）。なお #1309 は `plan/design-leona.md` に C-1449 を含む範囲の書き方があるので、実際にはコメントになる。GitHub の上の動き（6 節）はマージの後に確かめる。

## 8. セッションの `pr:prep` の振り直しの後のリベース

### 8.1 問題

- `pr:prep` は、ブランチで足した ID が main と重なると、リベースの前に止めて `records:renumber` のコマンドを出す。その手順どおりに振り直して commit し、もう一度回しても、リベースは振り直す前の ID のファイルを足した commit から当て直すので、main の同じ ID のファイルと衝突して止まる（add/add）。7 節の写しの試しで見つけ、課題 `pr-prep-renumber-rebase.json` に起票した。
- 一時の git リポジトリで確かめた（`tools/git/squash-branch.test.ts`。C-0001 を足す commit → C-0002 に振り直す commit のブランチを、C-0001 を足した main にリベースすると、C-0001 が add/add で衝突する）。
- 同じことは、撮影待ちのトピックブランチでも起きる。ほかのブランチと番号が重なって振り直した（verification-guide.md 3 節）後に、そのブランチが先に main に入ると、取り込みのフック（`catch-up.ts`）のリベースが衝突して戻し、`pr:prep` で直すよう知らせる。

### 8.2 案

- **案 1（採る）**: `pr:prep` が、リベースの前に「ブランチの途中の commit で足して HEAD には無く、main にはあるパス」を探し（`branchStaleAdds`）、あればブランチを 1 つの commit にまとめてからリベースする。まとめる処理は `auto-rebase.ts` のものを共通の関数（`pr-prep-lib.ts` の `squashBranch`）にし、両方が使う。
- **案 2**: 案内だけ直し、振り直しの後に手で `git reset --soft` してまとめてもらう。手順が増え、撮影待ちのブランチで取り込みのフックが止まったときにも同じ手順が要る。
- **案 3**: `pr:prep` がいつもまとめる（`auto-rebase.ts` と同じ）。

### 8.3 決定と理由

案 1。

- まとめるのは、そのままではリベースが必ず衝突するときだけにする（案 3 にしない）。`pr:prep` は PR を出すときのほか、撮影待ちのトピックブランチで取り込みのフックが衝突したときにも回す（AGENTS.md「コミット手順」）。いつもまとめると、撮影計画・予測の commit が毎回 1 つに潰れる。案 1 なら、潰れるのは振り直した後の 1 回だけで、ほかのときは今までどおり。
- まとめてもオーナーの手元の作業は壊れない。
  - PR はスカッシュでマージするので、main に入る形は変わらない。
  - 撮る前の予測は確定の条件にしない（verification-guide.md 2.2 節）ので、予測の commit の時刻を根拠に使っていない。
  - リベースはもともと commit を作り直し、`pr:prep -- --push` は `--force-with-lease` で push する。まとめても、origin の書き換え方は同じ。
- まとめた commit の題名は、ブランチの最初の commit の題名にする（PR の題名はまだ無い）。本文に、まとめたわけと元の commit のメッセージ（帰属の行を含む）を残す。
- `squashBranch` は作業ツリーを add しない（見直しで分かったこと: `pr:prep` の作業中の変更の確かめは追跡していないファイルを見ないので、`git add --all` だと下書きなどが PR に入る。`auto-rebase.ts` は、振り直しで名前の変わったファイルを入れるために、呼ぶ前に自分で add する）。差分が無くなっても commit を作る（commit が落ちると、ブランチが分かれ目に残る）。
- `branchStaleAdds` は記録のファイルに限らず、どのパスでも見る（途中で足して消したファイルを main も足せば、記録でなくても同じ衝突になる）。
- 止めたときの案内は、手で振り直して commit し、もう一度回すまま（AGENTS.md「コミット手順」の 1 の文は変えない）。もう一度回すとまとめることを、案内の文に足した。
