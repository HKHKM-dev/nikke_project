# 最小構成の検査: 効きうる未確定の要素だけに警告を出す

- 関連: [design-minimal-check.md](design-minimal-check.md) 8 節（警告の単位と数え方の決定・試算）、[design-records-automation.md](design-records-automation.md) 3.5〜3.7 節、[design-skill-note-kinds.md](design-skill-note-kinds.md)、AGENTS.md「事実と記録」
- 作成日: 2026-10-07
- 状態: 承認（2026-10-07。9 節）。オーナーが選んだ策（1a・2a・3b・4a・5a・6c・7a・8a。design-minimal-check.md 8 節の後の対話）の組み合わせ。実装は 7 節の段取りで進める

## 1. 目的と、決まっていること

- 目的: **効きうる未確定の要素には警告を出し、効かない未確定の要素には出さない**。
- 決まっていること（[design-minimal-check.md](design-minimal-check.md) 8.3 節）:
  - 警告の単位は「結論 × 根拠の観測値」の組。
  - 出す結論は、確定の結論と、確定にしようとしている結論（`records:new -- claim` の下書き・`records:close`）。
  - 未確定は効果・notes の単位で数える。対象（観測したい事象）のほかに、効きうる未確定の要素が 1 つでもあれば、その組に警告を出す。
- この設計で使う策:

| 策  | 障害                         | 中身（この設計での形）                                                                                 |
| --- | ---------------------------- | ------------------------------------------------------------------------------------------------------ |
| 1a  | 観測量が特定できない         | 観測値に `scope`（枠・ヒットの出どころ・時刻の範囲）を持たせる（3.1 節）                               |
| 2a  | 対象が特定できない           | 結論に `subject`（定義の場所か、機構の名前）を持たせる（3.2 節）                                       |
| 3b  | 未確定の要素の中身が読めない | 未対応・前提の外の notes に、計算に使わない効果の形 `effect` を持たせる（3.3 節）                      |
| 4a  | 録画で何が起きたかが無い     | 台帳の枠に `fires`（撃ったか）・`bursts`（バーストを使ったか）を持たせる（3.4 節）                     |
| 5a  | 仮説の及ぶ範囲が読めない     | 仮説の結論に `when`（効く条件）を持たせる（3.5 節）                                                    |
| 6c  | 循環                         | モデルの窓（きっかけ・維持時間）は確定の要素にだけ使う。未確定の要素は、モデルの窓を信じない（4.1 節） |
| 7a  | 間接の経路                   | 未確定の要素を 1 つずつ変えて sim を回し直し、観測値の予測が動くかを見る（感度。4.1 節）               |
| 8a  | 0 / 1 では足りない           | 予測の動きを観測値の許容（`compare.tolerance`）と比べ、許容の中なら効かないとする（4.1 節）            |

## 2. 判定の流れ

結論 C と、その根拠の観測値 O の組ごとに:

1. **対象を決める**: C の `subject`（3.2 節）。対象の効果・notes は数えない。
2. **要素を並べる**: O の録画の編成の全枠について、効果・notes（3.3 節の `effect` を含む）、定義の無いキャラ（1 つの要素）、的の表に値の無い通常攻撃の条件（1 つの要素）。計算に無関係（`noDamage`）の notes は数えない（design-minimal-check.md 8.4 節の段 1）。
3. **未確定かを決める**: 要素の `claims` が、すべて確定（か範囲外）なら確定。仮説の結論は、`when`（3.5 節）がその録画で成り立つときだけ未確定に数える。`when` の無い仮説は常に数える。
4. **録画で起きうるかを決める**: 台帳の `fires`・`bursts`（3.4 節）と、単騎の録画（バースト・フルバーストは起きない。C-0024）で、起きないきっかけの要素を外す。的の属性の空は、射撃場の的の表を引く（design-minimal-check.md 5 節の D1）。
5. **効きうるかを決める**:
   - O が sim の `compare` を持ち、要素がモデルにある（定義の効果）とき: 感度（4.1 節）。
   - それ以外（O に `compare` が無い、または要素がモデルに無い）: 静的な判定（4.2 節）。
6. **残った要素**が 1 つでもあれば、その組に警告。人が理由を印に書けば通す（4.3 節）。

## 3. データの足し算

### 3.1 観測値の範囲 `scope`（1a）

```json
"scope": { "slot": 2, "source": "normal", "frames": [1892, 2309] }
```

- `slot`: 観測量がどの枠のものか（1 始まり。複数なら配列。編成の全体なら `"all"`）。
- `source`: 観測量の出どころ。`normal`（通常攻撃のヒット）・`skill`（倍率ダメージ・追加ダメージ）・`burst`（バーストのヒット）・`dot`（持続ダメージ）・`gauge`（ゲージ）・`burstChain`（バーストの段・CT）・`clock`（時計・止まり）・`target`（的の動き・大きさ）・`firing`（射撃の刻み・リロード）。
- `frames`: 読んだ範囲（動画のフレーム）。省略可。人が読む範囲の記録で、6c により未確定の要素の判定には使わない（確定の要素の判定と、人の確かめに使う）。
- `compare` があれば、`args` の `slot`（と `frame`）から `slot` を埋められる。`source` は指標から決まる（`hitDamage` は `normal`、`burstHitDamage` は `burst` など）。
- 必須にする範囲は 9 節の 2。

### 3.2 結論の対象 `subject`（2a）

```json
"subject": { "places": ["data/skills/17.json の skill2 の effects[0]"] }
"subject": { "mechanism": "clock" }
```

- `places`: 定義の場所（`model` の欄と同じ書き方）。2 体の組の結論は 2 つ以上書く。書いた場所の `claims` がこの結論を含むことを検査する（`validateSkillClaims` と同じ読み方）。
- `mechanism`: 定義に結び付かない結論の機構の名前。語彙は 3.1 節の `source` と同じ（`firing`・`gauge`・`burstChain`・`clock`・`target`）に、`damageFormula`（1 ヒットの式）・`targetTable`（的の表のコア命中率・弾丸命中率）を足す。機構は定義の要素ではないので、外す要素は無い。
- `records:new -- claim` は、定義の `claims` にこの結論を持つ場所を `places` の候補に出す。人が確かめて書く。
- 既存の確定の結論は、定義の `claims` から機械で埋められるものは埋め、残り（定義に結び付かない結論）は人が `mechanism` を書く。

### 3.3 notes の効く先 `effect`（3b）

```json
{
  "kind": "unimplemented",
  "ja": "…",
  "en": "…",
  "effect": { "kind": "timed", "stat": "critDamage", "target": "allies", "trigger": "unknown" }
}
```

- 未対応（`unimplemented`）と前提の外（`outOfScope`）の notes に、定義の効果と同じ語彙で `effect` を書く。計算（calc・sim）は読まない。対応状況（`support`）の決め方も変えない。
- 語彙で書けない欄は `"unknown"`（きっかけ・対象・stat）。`unknown` の欄は「何にでも当たる」として判定する（4.2 節）。
- 前提の外の notes も書く。射撃場の 3 分モードでは的が反撃するので、被弾をきっかけにする効果は起きうる（ラピの S1、ウンファ：タクティカル・アップのカモフラージュの解除。V-0249）。被弾のきっかけは語彙に `damaged` を足す。
- 補足（`modeling`）の notes は、指す効果を `refers`（`"effects[0]"` など）に書き、その効果と同じ要素として扱う。指す効果が無い補足は、`effect` を書く。
- 対象は、いまの定義で約 60 件（[skills.md](skills.md) の冒頭の notes の種類の件数）。

### 3.4 録画の枠の事実 `fires`・`bursts`（4a）

```json
"team": [{ "slot": 2, "rid": 160, "name": "ユニ", "controlled": true, "fires": false, "bursts": false }]
```

- `fires`: 戦闘中に通常攻撃を 1 発でも撃ったか。`false` なら、その枠の通常攻撃と、命中・射撃・フルチャージ・コア命中・最終弾をきっかけにする効果は起きない。
- `bursts`: バーストを 1 回でも使ったか。`false` なら、その枠のバーストのスロットの効果と、自分のバースト使用をきっかけにする効果は起きない。
- 省略は「分からない」で、起きうるとみなす。単騎の録画は `bursts: false` とみなす（C-0024）。
- 確かめ方: 戦闘履歴の与ダメージ（0 なら撃っていない）と、右のバースト欄の段の並び。取り込み（`intake.ts`）で聞く。既存の多人数の録画は、確定の結論の根拠にある録画から足す。
- sim でも同じ事実を使う（撃たない枠は射撃の列を空にし、バーストを使わない枠はバーストの順に入れない）。`buildTeamInput` に、台帳の事実から入力を作る分岐を足す。

### 3.5 仮説の効く条件 `when`（5a）

```json
"when": { "teamHas": { "burstStage": "AllStep" } }
"when": { "sameStatSources": { "stat": "damageTaken", "atLeast": 2 } }
```

- 仮説の結論にだけ書ける。その仮説が、どの条件の録画で効く話かを書く。
- 語彙: `teamHas`（編成に〈バースト段階・武器種・部隊の味方・キャラ〉がいる）、`sameStatSources`（同じ stat の効果の出どころが N 以上）、`enemyElement`（的の属性）。足りなければ足す。
- 例: C-0203（AllStep のキャラの扱い）は `teamHas.burstStage`、C-0153（受けるダメージ▲が重なるときの式）は `sameStatSources`。
- 書けない仮説は `when` を省く（常に未確定に数える）。

## 4. 判定

### 4.1 感度（7a・8a・6c）

O が sim の `compare` を持ち、要素 E がモデルにある（定義の効果）とき。

1. **基準の予測** P0: O の `compare.setup` で sim を回した予測（3.4 節の事実を入れる）。
2. **E を変えた予測**:
   - **外す**（P−）: E を定義から除いて回す。すべての種類の効果に当てる。
   - **常に効かせる**（P+）: 持続の効果（timed）だけ。E のきっかけと維持時間を信じず（6c）、戦闘の始めから終わりまで E の対象に効いている形（きっかけ `battleStart`・維持を戦闘の長さ）に置き換えて回す。
3. **効きうる**: P− か P+ の予測と P0 の差が、O の許容（`compare.tolerance`）を超える。配列の指標は、どれか 1 つの値が超えれば効きうる。
4. ほかの要素（確定の要素と、ほかの未確定の要素）は、モデルの窓のまま回す。6c で信じないのは、変えている E の窓だけ。

- 1 つずつ変える。未確定の要素どうしが重なって初めて効く形は見ない（8 節の限界）。
- 時刻を変える効果（CT▼・弾丸チャージ・ゲージ）や別のヒットの効果も P− で見る。時刻を通した間接の効き（障害 7）は、sim の中を伝わる分がそのまま予測の差に出る。
- 計算の量: 確定の結論の根拠で sim の `compare` を持つ観測値は、録画 × 設定で百数十通り。sim 1 回は数十 ms なので、要素ごとに 2 通り回しても数分。結果は、録画・設定・定義と結論の状態の内容から作る鍵でキャッシュする（追跡しない）。

### 4.2 静的な判定

O に `compare` が無いとき（`scope` を使う）と、E がモデルに無いとき（3.3 節の `effect`・定義の無いキャラ・通常攻撃の条件）。上から順に当てて、最初に「効かない」になれば外す。どれにも当たらなければ効きうる。

1. **定義の無いキャラ**: 効きうる（何をするか分からない）。
2. **出どころ**: O の `scope.source` が `normal` で、E が別のヒットを出す効果（倍率ダメージ・バーストのダメージ・持続ダメージ・自動攻撃）なら、O が 1 ヒットの値（`kind: hit`）のとき効かない。
3. **対象**: O が 1 ヒットの値か率（`kind: hit`・`rate`）で、E の対象が `scope.slot` を含みえない（ほかの枠の自分だけ・合わない武器種）なら効かない。時刻・回数・ゲージ・合計の観測値では、対象では外さない（間接に効く）。
4. **stat の分類**: design-minimal-check.md 8.4 節の段 3 の表（観測値の `kind` ごとに効きうる効果の分類）で、効きうる分類に入らなければ効かない。
5. **`unknown` の欄**がある E は、その欄では外さない。

### 4.3 人の判断の印

```json
"minimal": [
  {
    "observations": ["162-17"],
    "element": "イサベル skill2.notes[0]",
    "reason": "S2 のゲージは満タンを最大 1 刻み（約 15f）早めるが、仮説どうしの差（184f）より十分小さい",
    "decided": "2026-10-NN"
  }
]
```

- 結論の JSON に書く。`observations` は `"*"` で全部の組。`element` は 2 節の要素の名前。
- 印のある要素は、その組の警告から外す。印を書くのはオーナーの判断（AGENTS.md: 結論と矛盾する変更はオーナーに確認する）。
- 閉じた検証記録は書き換えないので、印は結論の側に置く。

## 5. 出力

- **生成物** `plan/minimal.md`（新設）: 結論ごとに、組と、効きうる要素と、その理由（感度の差か、静的な判定の段）と、印を並べる。件数は冒頭に出す。
- [claims.md](claims.md): 確定の結論の行に、警告のある組の数を出す。
- [verifications.md](verifications.md): 検証記録 × 録画の今の警告の行は、この検査に置き換えて消す。
- `records:new -- claim`: 状態の決め方（design-records-automation.md 3.6 節）の「最小構成の警告が無い」を、下書きの結論の組に警告が無いことに置き換える。
- `records:close`: その検証記録の結論について同じ判定を回し、警告を出す。
- コマンド: 感度は数分かかるので、`records:minimal` を新設し、`plan/minimal.md` を作り直す。`records:check` は、データの形の検査（3 節）と静的な判定だけを回す（9 節の 5 で決定）。

## 8. 限界

- **モデルの外**: 定義にも notes にも挙がっていない要素（的のジャンプ・障害物・AI の動き・説明文に無い効果）には警告を出せない。
- **1 つずつ変える**: 未確定の要素どうしが重なって初めて効く形は見ない。
- **P+ は持続の効果だけ**: 即時の効果（CT▼・弾丸チャージ）と別のヒットの効果は、外す（P−）だけで見る。回数やきっかけの時刻がモデルと違う場合の効きは、外したときの差の範囲でしか見ない。
- **値の大きさ**: 仮説の値がモデルより大きい側の不確かさは見ない（外すと常に効かせるの 2 通りだけ）。
- **静的な判定は粗い**: `compare` の無い観測値は、stat の分類と対象と出どころでしか分けない。時刻・回数・ゲージの観測値は、ほとんど外れない。
- **`fires`・`bursts` の省略**は保守的（起きうる）なので、台帳を埋めない録画では警告が減らない。

## 9. 決めたこと（2026-10-07、オーナー決定）

1. **既存の確定の結論にも全部当てる**。PR 3・4 の後、既存の確定の結論の警告の組を `plan/minimal.md` に出し、組ごとに、印を付ける（4.3 節）か、結論を見直すかをオーナーが決める。
2. **`scope` は必須**: 新しく確定にする結論の根拠の観測値のうち、`compare` を持たないものには `scope` を必須にする（`records:new -- claim`・`records:close` で検査）。
3. **前提の外の notes にも `effect` を書く**（3.3 節のとおり）。
4. **計算に無関係（`noDamage`）の notes は数えない**を、検査の規則として確定する。AGENTS.md「事実と記録」の「機構が確定したキャラ」の文に「計算に無関係の notes は除く」を足す（実装の PR に入れる）。
5. **感度は別コマンド `records:minimal`** にする。`records:check` は、データの形の検査と静的な判定だけを回す。

- 落とすか（`records:check` か `records:close` で止めるか）は、PR 5 で、既存の結論の警告の組を見てから決める（[design-minimal-check.md](design-minimal-check.md) 8.5 節の 5）。
