# 比べる設定の拡張: 遅れの表の上書き・手で撃ったバースト・予測の複数の編成・表示の時刻の指標

- 関連: [backlog.md](backlog.md) 5 節の 5-11、[design-investigation-review.md](design-investigation-review.md) 2.2 節・8 節、[design-burst-landing.md](design-burst-landing.md)（遅れの表）、[design-burst-hit-origin.md](design-burst-hit-origin.md) 8 節（発動の印と III の起点）、[design-records-automation.md](design-records-automation.md) 3.2 節（予測ファイル）、[design-minimal-relevance.md](design-minimal-relevance.md) 11.7 節（比べる指標の無い観測値）
- 作成日: 2026-10-17
- 状態: 起案（オーナーの判断待ち。7 節の論点）

## 1. 何が困っているか

design-investigation-review.md 2.2 節で挙げた、観測値の比べる設定（`CompareSetup`）と指標（`METRICS`）で書けないもの。

| 書けないもの                                        | 出た検証記録                                    | いまの扱い                                                                                                                                                                  |
| --------------------------------------------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 遅れの表（`MEASURED_BURST_DELAYS`）で切り替わる仮説 | V-0388・V-0392・V-0393                          | 予測ファイルの範囲外として、検証記録に手で書いた（遅れ 0 の H0、遅れ d の E1・E2、フルバーストより早く付く E3）。表はコードの定数なので、仮説の override で替えられない     |
| 手で撃ったバーストの時刻                            | V-0385（ほかに V-0230・V-0376 の録画 263・293） | モデルはオートバースト（満タンの 23f 後に撃つ）しか無い。手で撃った録画は、モデルの発動が録画とずれたまま比べるか、手計算の予測にした                                       |
| 予測で編成を 1 つしか書けない                       | V-0382・V-0391                                  | 予測ファイルの `team` はファイルに 1 つ。ほかの録画の編成の H0 は、その日の main のモデルを回して検証記録に手で書いた                                                       |
| 画面の表示の時刻                                    | V-0394〜V-0398                                  | 値は use: record の観測値にした。モデルの指標が無いので道具が等級の候補を出さず、C-0512・C-0515・C-0517 はオーナーの判断で確定にした（`judgment.overrides` が「指標なし」） |

- モデルの側は、いまは表示の時刻を持っている。I・II の六角形の替わり目は本当の発動の `HEXAGON_AFTER_ACTIVATION_FRAMES` 後、III のタイマーの 00.00 は `FULL_BURST_AFTER_ACTIVATION_FRAMES` 後（`burst/schedule.ts` の `hexagonFrameOf`。C-0512・C-0515 を反映した 2026-10-10 の案 C'）。足りないのは、それを録画の値と比べる指標だけ。
- 遅れの表は `burst/landing.ts` のモジュールの定数で、`measuredBurstDelayRow(character)` がキャラから引く。引く側（`burstDelaysOf`・`burstDelaysFieldOf`・`burstWindowTrimOf`・`sameActivationBuffsOnHit`）はどれもキャラ（`CharacterData`）だけを受け取る。
- 遅れは `withBurstDelays` が正の値だけを書く（0 と負は発動の印に足さない）。V-0392 の E3（フルバーストより早く付く）と、ヘルムの行の注記（効果は表示より前に付くが、発動より前に置けないので 0）は、負の遅れが書けないことによる。

## 2. 遅れの表の上書き（`CompareSetup.burstDelays`）

### 2.1 形

```ts
burstDelays?: {
  rid: number;
  /** 表の treasure と同じ。true なら宝物版の burst のときだけ当てる */
  treasure?: boolean;
  /** null は表の行を外す（遅れ 0。表に無いキャラと同じ）。行を書けば、表の行を置き換える（表に無いキャラには足す） */
  row: null | {
    hitFrames: number;
    effectFrames: number;
    hitOffsets?: number[];
    windowFromActivation?: true;
    sameActivationBuffsOnHit?: true;
    /** 遅れの起点。'mark'（省略）は発動の印（hexagonFrameOf）、'activation' は本当の発動 */
    origin?: 'mark' | 'activation';
  };
}[];
```

- 結論の ID（表の `claim`）は書かない。仮説の override と、録画の条件の違いを試す観測値にだけ使う（`addEffects` と同じ立場）。
- 例: V-0388 の H0 は `{ "rid": 172, "row": null }`。V-0392 の E1 は `{ "rid": 194, "row": { "hitFrames": 0, "effectFrames": d } }`、E2 は同じに `windowFromActivation: true`、E3 は `effectFrames: -d`（2.3 節）。

### 2.2 組み込み方

- `CharacterData` に任意の欄 `burstDelayRow?: MeasuredBurstDelayRow | null` を足し、`measuredBurstDelayRow` は欄があればそれを返す（無ければ今までどおり表から引く）。`buildTeamInput` が上書きのある枠のキャラにだけ欄を付ける。引く側の 4 つの関数は変えない。
- アプリ（`apps/web`）とスキル定義の読み込みは欄を付けないので、計算の結果は変わらない。

### 2.3 負の遅れ

- `withBurstDelays` は 0 でない遅れを書く（今は正だけ）。遅れを足した後のフレームが本当の発動より前になるときは、モデルを回すときに RangeError（「発動より前には置けない」）。I・II の印は本当の発動の 5f 後、III の 00.00 は 6f 後なので、`origin: 'mark'` の負の遅れは −5・−6 まで書ける。
- 表の行の遅れ 0 の意味は変えない（0 の欄は書かず、効果は本当の発動・III のヒットは 00.00）。上書きの行で `origin: 'activation'` と 0 を書くと、ヒットも本当の発動に置く。
- 効果の発火が発動より前に来る仮説（ヘルムの 2〜35f 前）は、この設計でも書けない（発動の時刻表の作り方が変わるので範囲外。6 節）。

## 3. 手で撃ったバーストの時刻（`CompareSetup.manualBursts`）

### 3.1 形

```ts
/** 手で撃ったチェーンの始まり（I の本当の発動）のゲーム内のフレームの並びを持つ観測値の id（同じ録画・use が input） */
manualBursts?: string;
```

- 値は、録画で読んだ各チェーンの I の本当の発動の**ゲーム内のフレーム**（戦闘開始から。動画のフレームから戦闘開始と、それより前の止まり（入り 22f・I・II の発動 1f）を引いた値）。`263-01`・`293-01` がこの形（フルバーストの無い単騎なので、止まりは I の発動の 1f だけ）。
- 観測値の id で持つのは `jumpWindows`・`obstacles` と同じ（値は観測値に 1 か所。比べる設定には書き写さない）。

### 3.2 モデルの動き

- `TeamInput.manualBursts?: number[]` を足し、動的サイクルの制御（`burst/controller.ts`）は、満タンの後の I を、満タンの 23f 後と、並びの次のフレームの遅い方で撃つ。並びが尽きたら、満タンのまま撃たない（録画でそれ以上撃っていない）。
- II・III は今までどおり（前の段の 28f 後と CT の明けの遅い方。オートと同じ）。手で撃つと I・II の止まりが 2f になる回が多い（C-0500）が、モデルは 1f 一律のまま（動画のフレームに直すときだけの差）。
- 的を狙えない間（`blocked`）でも、並びのフレームで撃つ（録画で撃った時刻を書いているので）。
- 並びのフレームに満タンでなければ、満タンになった 23f 後に撃つ（エラーにしない）。モデルのゲージが録画より遅いことは、比べる値の残差として出る。
- `manualBursts` があれば `burst` は true として扱う（`burst: false` と一緒に書けばエラー）。

## 4. 予測の複数の編成（`PredictionTarget.recording`・`team`）

- 予測ファイルの指標（`targets` の 1 件）に、任意の `recording`（録画の id）か `team`・`fixedSpec`（ファイルの `team`・`fixedSpec` と同じ形）を足す。`recording` はその録画の台帳の編成・スペック固定・育成で組み、`team` は撮る前の編成を書く。どちらも無ければファイルの `team`（今までどおり）。
- `recording` のある指標は、`jumpWindows`・`manualBursts` などの観測値の参照もその録画のものを使える（ファイルの `team` では録画が無いので使えない）。
- V-0382 なら、223 の指標はファイルの `team`、077・134・081 の指標は `recording` で書ける。

## 5. 表示の時刻の指標（`METRICS`）

どちらも動画のフレームで、モデルの値は `hexagonFrameOf`・`videoFrameOf` から出す。

| 指標                    | 引数        | 値                                                                                                                                                                                                               | 比べる観測値                                                 |
| ----------------------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `ctEndToFullBurstStart` | `slot`・`n` | 枠の n 回目（0 始まり。カンマ区切りの並びも書ける）の発動（III）の、その枠の CT の明けから III のタイマーの 00.00 までの動画のフレーム数の列。モデルでその回が CT の明けで撃っていなければ比べられない（エラー） | C-0512 の根拠（`222-21` など 9 件。いまは use: record）      |
| `chainStepIntervals`    | `n`         | n 回目（0 始まり）のフルバーストを開いたチェーンの、I → II・II → III の本当の発動どうしの動画のフレーム数 `[a, b]`（I・II の止まりを含む）                                                                       | C-0515 の根拠（`192-17`・`192-18`。12 本をまとめた値。6 節） |

- CT の明けは、前の発動のフレーム + CT − その間に縮んだ分（`cooldownReductions` の `applied`）。
- モデルの値はどちらも定数に近い（`ctEndToFullBurstStart` は 6、`chainStepIntervals` は 29）。それでも指標にするのは、録画ごとの回の並び（どの回が CT 律速か）をモデルと突き合わせ、道具が等級の候補を出せるようにするため（design-investigation-review.md 2.2 節）。
- C-0517（クルミの効果の付き始め）は、既存の `burstEffectDelay`（印から効果の発火まで）で比べられる。根拠の `113-05` は値が `{ activation, lastAbsent, firstPresent }` のオブジェクトで、比べる観測値にするには回ごとの数の観測値に分ける要がある（6 節）。

## 6. この設計の範囲外

- 発動より前に付く効果（2.3 節）。
- 複数の録画をまとめた観測値（`192-17`・`192-18`・C-0495 の根拠）。比べるには録画ごとの観測値に分ける。分けるかは結論ごとに決める（この PR ではしない）。
- 観測値の値の形（`113-05`・`244-06`・`366-09` のオブジェクト）。5-7（格子のレシピ）の出力の形と合わせて決める。
- 指標の形の残り（design-investigation-review.md 2.2 節の「回ごとの指標の多くが実測なし」）。予測の指標の n をモデルと録画の回でそろえる話で、予測ファイルの書き方の問題（4 節の範囲の外）。
- 5-10（予測の後のモデルの変更の注意）と 5-12（時刻で限る語彙）。どちらも `records:check` を触るが、この設計が触るのは `observations.ts` の比べる設定・指標と `predictions.ts` の組み方で、重ならない。

## 7. 論点（オーナーの判断）

1. **遅れの表の上書きの形**: 2.1 節（行ごと置き換え・null で外す・`origin` で起点を選ぶ）でよいか。推奨: このまま。
2. **負の遅れ**: 2.3 節（本当の発動まで。それより前はエラー）でよいか。推奨: このまま。
3. **手で撃ったバーストの値**: (a) I の本当の発動のゲーム内のフレーム（推奨。`263-01`・`293-01` がこの形。読む人が止まりを引く）、(b) 六角形の替わり目の動画のフレーム（5-6 のレシピがそのまま出せるが、戦闘開始と止まりの換算を道具が持つ）。
4. **手で撃つ段**: (a) チェーンの始まり（I）だけ（推奨。II・III はオートと同じ間隔）、(b) 段ごとに書く。
5. **予測の複数の編成**: 4 節（指標ごとに `recording` か `team`）でよいか。推奨: このまま。
6. **表示の時刻の指標**: 5 節の 2 つでよいか。推奨: このまま。
7. **例（完了の条件）**: 次でよいか。
   - `ctEndToFullBurstStart`: C-0512 の根拠の 9 件（`222-21`・`224-07`・`225-13`・`248-17`・`249-10`・`258-19`・`260-11`・`280-08`・`281-09`。`192-16` を含め 10 件）を use: compare（許容 `abs: 2`）にする。モデルで CT 律速でない回が出たら、その観測値は「比べられない」と残す。C-0512 は道具が等級の候補を出せるようになる（等級は変えない）。後付けの `192-16`・`258-19` も比べるが、根拠に数えない扱いは今までどおり（`decidedOn`）。
   - `manualBursts`: `263-01`・`293-01` を use: input にし、`263-02`〜`263-07`・`293-02`〜`293-07` の比べる設定に足す。モデルの発動が録画の時刻に動くので、窓の中・外の指定（`frame`）が録画の時刻とそろう。
   - 遅れの表の上書き・予測の複数の編成: 単体テストで確かめ、既存の観測値・予測ファイルは変えない（閉じた検証記録の予測を出し直さない）。
