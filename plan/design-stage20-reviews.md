## 8. 起案後のレビュー（2026-09-26、Antigravity）

指摘 7 点と段取りの注意 2 点を、コードとデータで確かめてから取り入れた。

- **1. 録画 ID の誤検知**
  - 確かめたこと: 設計はバッククォートつきだけを拾う。`plan/` と AGENTS.md のバッククォートつきの 3 桁は 5 件で、どれも実在の録画だった（誤検知 0）。「7,385 件」は、囲んでいない数字まで数えたものと思われる（囲んでいない 3 桁は 2,356 件）。ただし、桁を広げた形（3 桁以上-2 桁以上、4 桁以上）で散文から拾うと、`20260922-01`・`200801` などを誤って拾う（3 件）
  - 判断: 件数の前提は当たらないが、方向は取り入れる（案 1-A）。記号の付かない ID は散文から拾わない
  - 反映先: 3.6 節
- **2. 通し番号の衝突**
  - 確かめたこと: 結論は、同じ番号なら同じファイル名になり、Git の衝突で止まる。一方、検証記録を `V-NNNN-<名前>.md` にすると、名前が違えばファイル名も違うので、**Git の衝突にならずに同じ番号が main に入りうる**（必須チェックは最新の main に合わせることを求めていない。ruleset の `strict_required_status_checks_policy` は false）。振り直しで直す参照は、自分のブランチの中だけで済む
  - 判断: 取り入れる。ファイル名を ID だけにして衝突を必ず Git で止め、振り直しの手順を書く。番号帯の予約はしない
  - 反映先: 3.1・3.2・3.6 節、7 節の 5
- **3. 双方向の参照**
  - 確かめたこと: 起案では、検証記録の「結論」と結論の「検証記録」、検証記録の「観測値」と観測値の `source` の 2 組が両向きになっていた。1 節の方針 1 と食い違う
  - 判断: 取り入れる。片側だけ書き、逆は生成で引く
  - 反映先: 3.2・3.3 節、7 節の 11
- **4. 冒頭の書式**

  - 反映先: 3.2 節、7 節の 10
- **5. 複数の録画の観測値**

## 9. 再レビュー（2026-09-27、Antigravity）

8 節の反映を受けての再レビュー。指摘 5 点を確かめてから取り入れた。あわせて、同じ観点で自分でも 1 点見つけて直した。

- **1. 検証記録のファイル名に名前を戻す（重複は CI で止める）**
  - 確かめたこと: 名前が無いと、一覧のファイル名から中身が分からないのはそのとおり。ただし「CI で確実に止まる」は当たらない。PR の CI は push した時点の main と合わせて走り、ruleset は最新の main に合わせることを求めていない（`strict_required_status_checks_policy` は false）。そのため、同じ番号を足した 2 本の PR が互いのマージ前に CI を通すと、両方とも自動マージされ、main で初めて重複に気づく。一方、ID 順に 1 件ずつ並べる一覧を生成物としてコミットすると、2 本は同じ場所に行を足すので Git の衝突になり、後の方は自動マージされない
  - 判断: 取り入れる。止め方は、テストと一覧の衝突の 2 段にする
  - 反映先: 3.1・3.2・3.6 節、7 節の 5
- **2. 状態の 4 分類（調査中・保留・完了・未解決）**
  - 確かめたこと: 起案では状態の語彙を決めていなかった
  - 判断: 取り入れる。「未解決」は「まだ開いている」とも読めるので「打ち切り」と呼ぶ。状態ごとに冒頭の「結論」を書くかどうかを決め、テストで確かめる
  - 反映先: 3.2.1 節、7 節の 13
- **3. 開いている検証を `wip/` に分ける**
  - 確かめたこと: 状態を冒頭と置き場所の 2 か所に持つことになり、1 節の方針 1 と食い違う。一致はテストで確かめられるが、閉じるたびに `git mv` が要り、パスで張ったリンクが切れる。目的の「開いている検証が一目で分かる」は、一覧の冒頭の節で満たせる
  - 判断: 目的は取り入れる。置き場所の分離は別案に回す
  - 反映先: 3.2.1 節、7 節の 12
- **4. 依存・派生元**
  - 確かめたこと: 取り入れても、書くのは依存する側・派生した側だけにすれば、方針 1 と食い違わない
  - 判断: 取り入れる。逆向きと「再開できる保留」は一覧で引く。依存先の実在と循環をテストで確かめる。ID で指せない待ち（撮影・育成）は「待ち」に書く
  - 反映先: 3.2・3.2.1 節
- **5. 答えが出ない検証の出口**
  - 確かめたこと: claims の状態の語彙には、モデルで扱わないことを表す `範囲外` がある（今は 0 件）
  - 判断: 取り入れる。ただし「結論は作らない」は、モデルで扱わないと決めたときの範囲外の結論を除く
  - 反映先: 3.2.1 節
- **（自分で見つけた点）訂正の書き方**
  - 確かめたこと: 起案では、新しい記録から古い記録を指し、古い記録にも「訂正: V-NNNN」を足す両向きだった
  - 判断: 訂正する側にだけ書き、「訂正された」は一覧で引く
  - 反映先: 3.2 節

## 10. ほかの実装の調べ（2026-09-27）

オーナーの指示で、類似の OSS 3 つ（Jgaram/nikke-calc、それを移植した Moris-kr/nikke-calc、Infernal-Crack-LED/nikke-sim）と旧プロジェクトについて、検証の仕方と記録の持ち方を調べた。中身は [references.md](references.md)「検証の記録の仕方」にある。主な事実は元の資料で確かめた（旧プロジェクトの根拠の等級、nikke-sim の ID の重複、Jgaram の「変化の検知と正しさの検証は別」）。

**どこも同じ所で詰まっていた。** 旧プロジェクト・nikke-sim・Moris-kr は、どれも数か月のうちに次の 3 つを抱えている。

- 150KB を超える文書

旧プロジェクトは、運用の規則が 74KB、機械検査が 26 種、hook が 11 本まで増え、規則の保守が本来の作業を上回った。nikke-sim には「番号は生涯固定」の規則があるが、未解決と解決済みの問いで同じ番号（U37・U40・U41）が別の問いに使われている。

## 11. 再々レビュー（2026-09-27、Antigravity）

破綻のシナリオ 4 点と、儀式化への警告 1 点。確かめてから取り入れた。

- **1. 失効した観測値が、確定の結論の直しを強いる**
  - 確かめたこと: 起案の規則（失効した根拠が 1 件でもあれば落とす）では、失効を付けた PR で、その観測値を根拠にする確定の結論を必ず直すことになる（根拠から外すか、状態を変える）。結論のファイルは現状型なので git の履歴には残るが、「失効した根拠に頼っていた」ことが一覧から見えなくなる
  - 判断: 取り入れる。落とすのは有効な根拠が 1 件も残らない確定の結論だけにし、失効した根拠は消さずに印を付けて出す。棄却の結論は問わない
  - 反映先: 本体 3.4 節、7 節の 16
- **2. リベースで生成物が衝突すると、生成のスクリプトがこける**
  - 確かめたこと: 今の生成（`records-table.ts`・`records-check.ts`）は生成先を読み、印で区切った節だけを差し替える（`replaceGeneratedSection`）。節の中の衝突の印は差し替えで消えるので、そこではこけない。危ないのはむしろ、節の外に衝突の印が残ったまま気づかないこと。「クラッシュする」は当たらないが、手順が要るのはそのとおり
  - 判断: 手順を書く（main の版に戻す → 振り直す → 作り直す → 続ける）。丸ごと生成する新しい生成物は、前の中身を読まない
  - 反映先: 本体 3.6 節
- **3. 依存先が打ち切りの保留に「再開できる」が付く**
  - 確かめたこと: 起案の条件「依存先がすべて閉じた（完了か打ち切り）」では、前提の答えが出なかった保留にも「再開できる」が付く
  - 判断: 取り入れる。「再開できる」は依存先がすべて完了したときだけにし、打ち切りを含むものには「前提を見直す」の印を付ける
  - 反映先: 本体 3.2.1 節
- **4. 「パスのリンクが切れる」は ID で指す方針と矛盾する**
  - 確かめたこと: この理由は、検証記録へのリンクを ID で書く規則が無かったから成り立っていた。規則を足せば、どちらの案でもリンクは切れない。ただし、主な理由（状態を冒頭と置き場所の 2 か所に持つ）と、閉じるときの手間（移動と冒頭の書き換えの 2 つ）は残る。件数が増えたときに開いているものを見分ける目的は、一覧の「開いている検証」で満たせる
  - 判断: 理由を直し、検証記録へは ID で指す規則を足す。推奨（移動しない）は変えず、`wip/` と `wip-` は、手間と利点を並べた別案として残す。ここは見やすさの好みの問題なので、オーナーが決める
  - 反映先: 本体 3.2.1 節、7 節の 12
- **5. 根拠の等級と撮る前の予測の形骸化**
  - 確かめたこと: 起案の「確定にしてよいのは厳密一致と反復実測だけ」は、テストで見るかどうかを書いていなかった（方針 5 の検査の一覧には入れていない）。既存の結論では、C-0009（録画 22 の目視で「約 600f」）は条件に合わない。C-0011（録画 38 で 5 回とも 300f）と C-0027（丸めの有無で値が合う）は合う。「多数」が合わないかどうかは、20-B で等級を付けるまで分からない
  - 判断: 取り入れる。等級はテストで見ず、新しく確定にするときの条件として PR で確かめる。予測の影響の大きさは分かる範囲でよく、探索の撮影は定性的な見込みでよい
  - 反映先: 本体 3.2・3.3 節、7 節の 14・15
