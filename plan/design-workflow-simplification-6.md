## 1. クラウドの始めの取得を上限の内に収める

**いま**

- 始めのフックの `cloud-sync.ts --pull` は、Drive の `nikke_sync/` の `private`・`scratch`・`claude` を、受け口の `snapshot` で中身ごと順に取る。フックの上限は 120 秒（`.claude/settings.json`）。
- 今日のセッションで測った時間（受け口の `snapshot`、中身つき）:

| 取る対 | ファイル | 大きさ | 時間 |
| --- | --- | --- | --- |
| `private` | 15 | 1.9MB | 23 秒 |
| `claude`（メモリと全体の CLAUDE.md） | 17 | 35KB | 44 秒 |
| `scratch` | 445 | 22.7MB | 300 秒を超え、fetch の待ちが切れた（`UND_ERR_HEADERS_TIMEOUT`） |

- `scratch` の 22.7MB のうち 21.1MB は `scratch/official-news/`（373 件。いちばん新しいものが 2026-10-26 15:27）。これが増えてから、取得が 120 秒に収まらず、フックが途中で止められているとみられる。止められると、手元のファイルは VM の初めの版のままになる（`cloud-sync.ts` は全部を取ってから書くので、何も上書きしない）。
- その結果、今日のセッションで見えたもの:
  - メモリ・`private/`・`scratch/`・`~/.claude/CLAUDE.md` は、どれも 2026-10-26 21:10 の版（VM の作られた時刻）。Drive の `pr-workflow.md`・`records-layout.md`・`MEMORY.md` は 2026-10-27 の新しい版なのに、手元は古い版。
  - `private/` に、育成のスナップショット（`private/builds/`）と所持の一覧（`private/roster.md`）が無い。クラウドでは `intake.ts` のスナップショットの既定（#764）も効かない（`snapshotNames()` が無しを返す）。
  - Drive のメモリのフォルダに、衝突の別名が 7 件ある（`MEMORY.conflict-*` 3 件、`pr-workflow.conflict-cloud*`・`records-layout.conflict-cloud*` 各 2 件。2026-10-27・10-28）。古い版から直したメモリを応答の終わりに戻すと、Drive 側が新しいので衝突になる。第 3 回・第 5 回でクラウドから入れたメモリの直し（第 5 回 5 節）は、この別名のどれかに入ったままとみられる。

**案**

- **(a) 始めに `scratch/` を取らない**: 始めの取得は `private` と `claude` だけにする。`scratch/` は要るときに `node tools/drive/cloud-sync.ts --pull-scratch [<パス>]` で取る（一覧は 9 秒、中身は指したものだけ）。応答の終わりの戻しは、そのセッションで取ったものだけを見る（取っていない `scratch/` の VM の古い版を、新しいファイルとして戻さない）。
- **(b) 3 つを並べて取る**: `snapshot` を `Promise.all` で呼ぶ。(a) の後は `private` と `claude` の長いほう（今日は 44 秒）で済む。受け口の時間はばらつくので、上限の 120 秒は今のまま。
- **(c) 取れなかったら知らせる**: 取り始める前に、`~/.claude/CLAUDE.md` の「メモリ（クラウド）」の節を「Drive から取れなかった。メモリと `private/` は古い版かもしれない（`node tools/drive/cloud-sync.ts --pull` を回し直す）」と書いておき、取れたら今の中身で上書きする。フックが止められても、エージェントが古い版だと気づける。
- **(d) 溜まった衝突を一度だけ合わせる**: Drive の 7 件の別名は、デスクトップで `npm run drive:conflicts` で見て、オーナーかデスクトップのセッションが合わせる（クラウドから合わせると、(a)〜(c) の前はまた衝突になる）。
- **(e) `scratch/official-news/` の置き場所**: 21MB の写しが `scratch/` の往復に要らなければ、`E:/nikke_project_captures/reference/`（参照資料の置き場所。[storage.md](captures/storage.md)）に移すと、`drive:sync` の `scratch` の対も軽くなる。オーナーの判断。

**効果**: クラウドのセッションが、毎回いまの Drive の版のメモリ・`private/`（育成のスナップショットを含む）で始まる。クラウドで直したメモリが衝突にならずにデスクトップへ届き、別名を手で合わせる手間が無くなる。

**気をつけること**: 受け口（`tools/drive/gateway/Code.gs`）は変えない。変えるのは `cloud-sync.ts`・`cloud-lib.ts` とそのテスト、[cloud-guide.md](cloud-guide.md) の 2 行（始めに置かれるもの・`scratch/` の取り方）。

## 3. 宝物の段階を、育成のスナップショットから埋める

**いま**

- 宝物ありの枠の録画は、取り込みに `--treasure <枠>:<段階>` を付ける。段階は「画面から読まず、オーナーに確かめる」（[protocol.md](captures/protocol.md)「撮った後」・[guide.md](captures/guide.md)「原則」）。付け忘れると、モデルは黙って基礎版で回る（V-0231）。
- 台帳の 716 本のうち 74 本に `treasurePhase` があり、直近の 0700 番台でも 43 本のうち 7 本。
- 2026-10-30 に、育成の取得の `favorite_item_lv` の Lv 1・2 が段階 2・3 であることを確定にした（C-0744）。スナップショットは 1 体ごとに `treasure.phase` を持ち（Lv 0 は `null`）、`sim-run.ts --build` はもう `--treasure` の無い枠にこれを使う。取り込みの道具だけがまだオーナーに確かめた値を求めている（`intake.ts` の冒頭の説明）。

**案**

- `intake.ts` は、撮った日以前でいちばん新しいスナップショット（#764 の `--build-snapshot` の既定と同じ選び方）から、宝物を持つ枠の段階を既定で埋め、埋めた段階を取り込みの知らせに出す。スペック固定の ON・OFF によらない（宝物はスペック固定でも反映される。[guide.md](captures/guide.md)「原則」）。
- `--treasure` を付けた枠はその値を使う（スナップショットと違えば知らせる）。スナップショットが無い・そのキャラが無い・`phase` が `null`（Lv 0）の枠だけ、今のとおりオーナーに確かめて `--treasure` で書く（足りなければ止める）。
- protocol.md と guide.md の「段階は画面から読まず、オーナーに確かめる」を、「段階は取り込みがスナップショットから埋める。Lv 0 とスナップショットに無い枠だけオーナーに確かめる（C-0744）」に直す。

**効果**: 宝物ありの枠の録画ごとの確かめの往復が、Lv 0 の枠を除いて無くなる。付け忘れで基礎版のまま読む誤りを道具が止める。

**気をつけること**: スナップショットは取った時点の段階なので、撮る日より後に宝物を上げたときは、その日のスナップショットが要る（撮る前に `npm run build:fetch` を回す決まりは、スペック固定 OFF の日だけ。[protocol.md](captures/protocol.md)）。宝物を上げた日は撮る前に取り直す、を protocol.md の同じ行に足す。クラウドでは 1 の (a)〜(c) が入るまでスナップショットが見えないので、1 の後に実施する。
