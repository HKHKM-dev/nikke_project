- 作成日: 2026-10-09。同日、拡張性・読みやすさ・ほかの語彙との整合の観点で組み直した（11 節）
- 対象: 説明文の「名前の付いた状態」（「〈名前〉」：機能…効果 1…、〜状態なら、〜状態の味方、〜が適用された時、〜適用中）を定義に書く語彙。いま定義に入っているもの（ペルソナ・追撃・バトンタッチ・ハッキング・カモフラージュ）の書き方を 1 つの形にそろえる

## 0. 要約

- 名前の付いた状態を、**値を持たない持続効果**として 1 つの形にする。付与（`kind: 'state'`）が `timed` と同じ規則で状態の窓を作り、中身（状態の間だけ効く▲▼）と見る側（きっかけ・対象の絞り込み・条件）がその窓を参照する（3 節）。
- 状態の名前は core の 1 つの目録に置き、定義は目録の id で指す。いまの 3 つの置き場（`SkillState`・`EffectName`・dot の `status`）はこれに置き換える（5.1 節）。
- 中身は、同じ stat の `timed` とどこでも同じに扱う（区間・1 パス目・条件・順位・calc の数え方）。検証も `timed` の規則をそのまま通す（3.2 節）。
- 今回入れるのは、いまの 4 体（クイーン（真）・雪子・クルミ・ウンファ：TU）の書き方を移す分と表示だけで、値は変えない（7 節）。
- 「自分が〈名前〉状態なら」・解除・切り替え・敵への付与などは、どの家族に入り、時刻表のどの段で決まるかだけを決め、使うキャラの設計で足す（8 節）。

## 1. 用語

| 用語             | 意味                                                                                                            |
| ---------------- | --------------------------------------------------------------------------------------------------------------- |
| 状態             | 名前の付いた状態。説明文で名前で呼ばれ、ほかの効果から参照されるもの。stat の増加状態（`selfBuffed`）は含めない |
| id・目録         | 状態を指す名前（`persona` など）と、id・画面の名前・持ち主の側を並べた core の表（5.1 節）                      |
| 付与             | 状態を付ける効果（`kind: 'state'`）                                                                             |
| 持ち主・出どころ | 状態が付いている枠（か敵）と、付与を持つ枠                                                                      |
| 状態の窓         | 持ち主に状態が付いているフレームの区間 [start, end)。持ち主 × 状態 × 出どころごとに作る                         |
| 中身             | 状態の窓の間だけ持ち主に効く効果（付与の `contents`）                                                           |
| 見る側           | 状態の窓を参照する欄（きっかけ `{ applied }`・対象の絞り込み `targetState`・条件 `enemyState` など）            |
| 静的な状態       | 戦闘の始まりから終わりまで付いている状態。編成の段（`skills/composition.ts`）で決まる                           |
| 時刻表の段       | `planBuffTimeline` の 1 段目（条件なし）・1.5 段目（条件つき）・2 段目（順位）・2.5 段目（`amplifies`）         |
| 今回・後の拡張   | この設計で入れるもの・形だけ決めて後で足すもの（組み直しの前の「1 段目・2 段目」。時刻表の段と紛れる）          |

## 2. 何が困っているか

### 2.1 いまの表し方

名前の付いた状態は、定義を足すたびにそのキャラに要る形で入ってきた（定義ごとの表は 7 節）。

- ペルソナ: 定義の最上位の `states`（型の列挙 `SkillState`）。効果 1 は別の `passive`、付与は notes（`modeling`）。「ペルソナ状態の味方」は `timed` の `targetState`。
- 追撃・バトンタッチ: `timed` の `name`（型の列挙 `EffectName`。状態と中身が融合）。「追撃が適用された時」は `damage` のトリガー `{ "applied": "followUp" }`。
- ハッキング: dot の `status: "hacking"`（自由な文字列）。「対象がハッキング状態なら」は `damage` の `condition.targetStatus`。
- カモフラージュ: 中身 2 つ × きっかけ 2 つの `timed` 4 件に書き写す。
- 名前を持たない読み: フォーメーションは `withCharacter`（C-0306）、「環境コントロール状態なら」（強化）は `amplifies`、「命中率増加状態なら」は `selfBuffed`、「マターシグマ状態なら」は `assumes`。

### 2.2 問題

1. **名前の置き場が 3 つある**。検証も表示も別々で、`status` は検証されず、画面には「対象が hacking 状態」と内部名のまま出る（`apps/web/src/skillLabels.ts`）。名前を 1 つ足すのに、型の列挙・画面のラベル表（`EFFECT_NAME_LABEL`）・`targetState === 'persona'` の分岐・CLI を別々に直す。
2. **状態と中身の関係が定義に出ない**。ペルソナの効果 1（核熱ブースタ。C-0296）は状態と無関係な `passive` に見え、付与は notes の文にある（根拠 C-0354 も notes の `claims`）。追撃・バトンタッチの形は中身が 2 つ以上の状態に使えない。カモフラージュは書き写した中身が**別々の効果**なので、2 つのきっかけの窓が重なると▲が 2 回足される。いまの時刻表では重ならない（2026-10-09 に、録画 232 の編成と、エマ：TU を足した編成で窓を出して確かめた）ので値は合っているが、重なれば黙って値がずれる。
3. **見る側の形がばらばら**。対象の絞り込みは静的な状態だけ、きっかけと条件は `damage` だけ（条件は敵だけ）。「自分が〈状態〉なら」の一般の条件は無く、環境コントロールだけを `amplifies` で特別に扱っている。
4. **ほかの語彙と規則がずれている**。
   - 名前の付いた効果は、条件・順位の対象と組めず（適用の記録を時刻表の 1 段目でしか作らないため）、周期のトリガーも使い手がいないので絞った。同じ欄の `timed` との違いが、語彙の都合で生まれている。
   - 条件の型が 2 つある。`timed` の `condition` は鍵が 1 つ（`selfBuffed` か `inFullBurst`）、`damage` の `condition` は鍵の AND（`fullBurst`・`targetStatus`）で、同じ「フルバーストタイムなら」に 2 つの名前がある。
   - 「付いている」区間の端が違う。`timed` の窓は [start, end) だが、dot の `status` は最後の tick のフレームを含む（`frame/plan.ts` の `damageConditionHolds`）。
5. **これから要る形の置き場が決まっていない**。時間で付いて外れる状態・解除・切り替え・フルスタック・敵に付く状態が説明文に多い（4.1 節）。いまの流れでは、1 体ごとに新しい欄が足されていく。

### 2.3 前の見込みとの関係

[design-stage11-modernia.md](design-stage11-modernia.md) 11.2 節（2026-09-24）は、「状態を名前で追い、付与と要求で結ぶ」考え方を採り、実装は使う所持キャラが出るまで待つとした。その後、使う定義が 4 体になったので、今の語彙に合わせて決め直す。違いは、名前を定義ごと（`states: [{ id, name }]`）ではなく 1 か所の目録で持つこと（他のキャラが付けた状態を見る組がある。4.2 節）と、付与に中身（`contents`）を入れ子で持たせること（説明文の「〈名前〉：…効果 1…効果 2」の形のまま書け、きっかけが複数でも中身を 1 回だけ書ける）。11.2 節の残り（窓で表し区間の鍵に入れない・解除と切り替え・`selfState`・`while`・循環の禁止・`assumes` の置き換え）は 3 節と 8 節に引き継ぐ。

## 3. 設計の原則

語彙を足すときの判断は、この節に照らして決める。

### 3.1 状態は値を持たない持続効果

- 付与は、`timed` から値の欄（`stat`・`ref`・`scaling`・`decrease`）を除き、目録の id（`state`）を足したもの。窓の作り方は `timed` と同じ: 発火のフレーム（射撃の回数起点は次のフレームから）・対象と絞り込み・維持（秒・発数・出来事）・上書き延長（和集合）・スタック（段ごとの窓。`skills/stacks.ts`）・条件（1.5 段目）・順位の対象（2 段目）・バーストの効果の窓の終わり（`burstWindowTrimOf`）。
- 「同じ効果の再発火は上書き延長」の「同じ効果」は、付与では「同じ定義の同じ状態」と読む。きっかけの違う付与が 2 つあっても、状態は 1 つ（カモフラージュ）。
- `timed` と違うのは、名前を持つことと、その窓を中身と見る側が参照することだけ。`timed` に足した規則が付与にもそのまま効き、状態のためだけの規則の系を育てずに済む。

### 3.2 中身は同じ stat の timed と同じに扱う

- 中身は、窓の決め方（自分のトリガーではなく状態の窓を使う）のほかは、同じ stat・同じ窓の `timed` と区別しない。区間と鍵、`stateWindows`（命中率）への振り分け、1 パス目の列、条件 `selfBuffed` の判定、順位（攻撃力の窓）、強化 `amplifies` の参照、下位効果のスタック適用（`sequential`）、calc の射撃の数え方、観測値の指標（窓の始まり・終わり）のどれでも同じ。
- 検証も同じ: 付与の欄と中身の項目を合わせた 1 つの `timed` として、今の stat ごとの規則（`trueDamageConversion` は自分だけ・`fixedChargeTime` はスタックと条件なし・`burstGaugeSpeed` は `passive` だけ・1 パス目で追う stat は発数や `fullBurstEnd` の維持と条件 `inFullBurst` を書けない など）を通す。stat や規則を足せば、中身にも自動で効く。
- 付与 1 つ・中身 1 つの状態（追撃）は、名前の付いた `timed` と同じ値になる。移し替えの退化の見込みは、この対応に立つ。

### 3.3 見る側は今の語彙の家族に入る

| 見る形                 | 欄                                                   | 同じ家族の今の語彙                                       | 決まる所                                                   |
| ---------------------- | ---------------------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------------- |
| きっかけ（付いた時）   | トリガー `{ "applied": id }`                         | `healed`（回復効果が適用された時。持ち主に起きる出来事） | 時刻表の後（`frame/plan.ts`）                              |
| 対象の絞り込み         | `targetState: id`                                    | `targetWeapon`・`targetElement`・`targetSquad`           | 静的な状態は編成の段。時間で変わる状態は後の拡張（2 段目） |
| 発火の条件             | `condition.enemyState: id`（後の拡張で `selfState`） | `selfBuffed`・`inFullBurst`（`damage` は `fullBurst`）   | 1.5 段目（`timed`）・`frame/plan.ts`（`damage`）           |
| 窓の積（状態の間だけ） | 中身（自分の状態）。後の拡張で `while`（他人の状態） | `amplifies`（参照する窓との重なり）                      | 時刻表の段                                                 |

- 見る形を足すときは、まずどの家族に入るかを決め、その家族の規則（判定のフレーム・同じフレームの窓の扱い・段）に合わせる。たとえば「〈名前〉が終了した時」（後の拡張の `{ "ended": id }`）はきっかけの家族で、`fullBurstStart` に対する `fullBurstEnd` と同じ関係。同じフレームの扱いは今のまま（条件と順位は、同じフレームに付いた窓も入れる）。

### 3.4 静的な状態と時間で変わる状態の分け方は今と同じ

- 静的な状態（付与が戦闘開始時・戦闘の終わりまで・自分・条件なし）は、`withCharacter`・`targetSquad` と同じく編成の段で決める。中身は常時パッシブとして解く（いまのペルソナの効果 1 の `passive` と同じ道で、値も区間の割り方も変わらない）。
- 時間で変わる状態は、時刻表の段で窓を作る。見る側も同じ分け方に従う（`targetState` は、今回は静的な状態だけを見る）。

### 3.5 名前は目録の 1 か所、中身は付与を書いた定義

- 目録が持つのは、どの状態か（同一性）・画面の名前・持ち主の側だけ。スタックの上限・維持・対象・中身は付与に書く（上限はスキルの Lv で変わる `maxStacksRef` があり、目録の固定値と二重になる）。
- 中身が効くのは、同じ定義の付与で付いた窓だけ。別のキャラが同じ id の状態を付けても、中身は混ざらない（アイギスが自分に付けたペルソナに、クイーン（真）のペルソナの中身は乗らない）。見る側は、どの定義の付与で付いた窓も見る（ペルソナ・バニーモードのような共有の状態を 1 つの id で見られる）。

### 3.6 使い手のいない語彙は入れない

- 今回入れるのは、7 節の移し替えに要る語彙だけ。後の拡張は、家族（3.3 節）と段の位置（8.5 節）だけを決め、使うキャラの設計で確かめて足す（[design-persona.md](design-persona.md) 7 節と同じ方針）。
- 名前の付いた効果の、語彙の都合で付いた制限（条件・順位の対象・周期のトリガーと組めない）は、付与では外して `timed` にそろえる（3.1 節）。段の置き方をそろえた結果で、使い手のいない語彙を足すのとは違う。

## 4. 説明文の言い回しと語彙の対応

### 4.1 言い回しの型

全キャラの説明文（`data/characters/*.json` の `ja`）を、「〈名前〉」…機能、〜状態なら / の、〜が適用された時、〜適用中 で走査した（2026-10-09）。型ごとの語彙:

- **付与**: 「〈名前〉」：機能：…効果 1…（ペルソナ・カモフラージュ・フォーメーション・変身）と「〈名前〉：攻撃力▲」（追撃・バトンタッチ）は `kind: 'state'` + `contents`（何を中身にするかは 4.3 節）。敵の状態異常（ハッキング）は dot の `state`。
- **きっかけ**: 「〈名前〉が適用された時」（追撃・変身状態・シンガロング）は `{ applied }`。「〈名前〉が終了した時」（殲滅態勢・完全計算状態）は後の拡張の `{ ended }`。
- **対象の絞り込み**: 「〈名前〉状態の味方」（ペルソナ状態の味方・バニーモード：スタンス状態の味方）は `targetState`（時間で変わる状態は後の拡張）。
- **条件**: 「自分が / 対象が〈名前〉状態なら」（戦闘補助・火力チャージ・超感覚・ハッキング・予告状）は `enemyState`（今回）と `selfState`（後の拡張）。「〜のフルスタック状態なら」「〜状態でなければ」（ウォームアップ・射撃マニュアル・シンガロング）は `selfState` の `stacks`・`present`（後の拡張）。
- **窓の積**: 「〈名前〉状態の間」「自分に〈名前〉適用中」（射撃マニュアル状態の間・フォーメーションAS 適用中）は中身（自分の状態）と `while`（他人の状態。後の拡張）。
- **解除・切り替え**: 「解除条件：〈出来事〉」「〈名前〉解除」（鉄・拳・制・裁！・マターシグマ）は今の `durationUntil` と後の拡張の `removeOn`。「〈A〉状態 / 〈B〉状態」（スタンス / エンゲージ・ソードコイン / シールドコイン・ボーカル / ダンス）は目録の `group`（後の拡張）。
- **語彙にしない**: 前提の外（バリア適用状態・気絶状態・戦闘不能状態、カモフラージュの被弾での解除）は notes のまま。名前の付いた状態でない「〜状態」（命中率増加状態・私だけの星 / みんなの星）は今の語彙のまま（7.2 節）。
- 敵は 1 体の前提なので、「〈名前〉状態の敵に」（予告状状態の対象など）は、対象の絞り込みではなく条件の `enemyState` で書く。

### 4.2 見る側の多い少ないと、付与の出どころ

同じ走査（名前の付いた状態でない一般語は除いた）から分かったこと:

- 見る側は「自分が〈名前〉状態なら」（フルスタック状態を含む）が大半。次いで「〈名前〉状態の味方 / 敵」と「対象（敵）が〈名前〉状態なら」で、「〈名前〉が適用された時」「自分に〈名前〉適用中」・否定・終了の形は少ない。
- 付与のほとんどは同じキャラの中で閉じる。別のキャラが付ける状態を見るのは、次の組の中だけ（どれも説明文で互いを見ていることを確かめた）: クイーン（真）・雪子（ペルソナ・追撃・バトンタッチ。定義あり）、エマ：TU・ウンファ：TU（フォーメーションAS / LT。`withCharacter` と読んだ）、ギルティ：マイティバニー・シン：スウィフトバニー（バニーモード：スタンス / エンゲージ）、レイ（仮称）・アスカ：WILLE（殲滅態勢・アンチA.T.フィールド）、ミント・プリカ（ステージパート：ボーカル・シンガロング）。
- 設計への意味: 後の拡張の `selfState` がいちばん多く使われる（足すのは使うキャラが出たとき。論点 5）。キャラをまたぐ参照は少ないが、コラボやペアで必ず起きるので、名前は 1 か所の目録で持つ（論点 1）。敵の状態を見る条件も多いので、目録の id で指す `enemyState` にする。

### 4.3 状態として書かない「〈名前〉：機能…」

「〈名前〉：機能：…効果 1…」の形は、いつも「状態の間だけ効く中身」ではない（2026-10-09 に説明文を見た）。

- 殲滅態勢（アスカ：WILLE のバースト）: 3 つの▲▼がそれぞれ「N 秒間維持」、1 つは即時の弾丸チャージ。状態そのものの維持は書かれていない。
- アンコール（プリカの S2）: 項目ごとに対象が違う（シンガロングのスキル発動者・味方全体・自分）。1 つは別の状態（ステージパート：ボーカル）の付与。
- ペルソナ - コノハナサクヤ（雪子の S1）: 「N 秒ごとに味方全体に回復」（状態の中の周期）。
- フォーメーションLT（エマ：TU の S2）: 「自分が生存している限り」。項目の対象は同じ部隊の味方全体・味方全体・自分で、持ち主と項目の対象が一致しない。

中身（`contents`）に書くのは、**状態の窓の間だけ持ち主に効く**項目だけ（ペルソナ - ヨハンナ・カモフラージュ・追撃・バトンタッチ）。自分の維持・即時・別の対象を持つ項目は、今と同じく同じトリガーの別の効果で書き、状態を見る効果があるときだけ付与を中身なしで足す（論点 9）。状態の中の周期は、周期のトリガーと後の拡張の `selfState` で書ける。中身の対象を持ち主以外に広げるのは後の拡張（8.4 節）。

## 5. 語彙（今回入れるもの）

### 5.1 目録

```ts
// packages/core/src/skills/states.ts
export const NAMED_STATES = {
  persona: { name: { ja: 'ペルソナ', en: 'Persona' }, holder: 'ally' },
  followUp: { name: { ja: '追撃', en: 'Follow Up' }, holder: 'ally' },
  batonPass: { name: { ja: 'バトンタッチ', en: 'Baton Pass' }, holder: 'ally' },
  camouflage: { name: { ja: 'カモフラージュ', en: 'Camouflage' }, holder: 'ally' },
  hacked: { name: { ja: 'ハッキング', en: 'Hacked' }, holder: 'enemy' },
} as const satisfies Record<string, NamedStateInfo>;

export type NamedStateId = keyof typeof NAMED_STATES;
```

- 定義が状態を指すのは、この目録の id だけ（付与・きっかけ・絞り込み・条件・dot のどれも同じ id）。`parseSkillDefinition` が目録にあるかを検べる。`SkillState`・`EffectName`・dot の `status` はこの 1 つに置き換える。
- `holder`: 状態を持つ側（`ally` = 味方の枠、`enemy` = 敵）。味方の状態を敵の条件で見る、のような食い違いを検証で落とす。
- 画面と CLI の名前は目録の `name` から引く（`EFFECT_NAME_LABEL` と `'persona'` の分岐は消す）。状態を足すのは、この表の 1 行と、それを付ける・見る定義だけ。目録に後で足す欄は `group`（8.2 節）だけの見込み。
- **id の付け方**（論点 7）:
  1. 英語版の説明文（`description.en`）の状態名を lowerCamelCase にする。記号（`-`・`:`・`.`・`'`）は落とし、ローマ数字・段階は数字にする（Bunny Mode / Stance → `bunnyModeStance`、時間延長 II → `timeExtension2`）。
  2. 付与の名前と見る側の名前が違うときは、見る側の共通の名前を取る（付与は「Persona - Johanna」、見る側は「Persona state」→ `persona`）。`state`・`status`・`effect` の語尾は付けない。
  3. 英語の形は書き換えない（「Hacked」→ `hacked`）。日本語から作った今の id は、移し替えで改める（`batonTouch` → `batonPass`、`hacking` → `hacked`）。
  4. 同じ名前は同じ状態として 1 行にするのが既定（中身は付与の定義に属するので、id を共有しても混ざらない。3.5 節）。複数のキャラに同じ名前で出る付与は、いまはゲーム全体で共通の仕組み（挑発・ヘイト・無敵・デコイ）だけで、無関係な状態の名前の衝突は無い（2026-10-09 の走査）。衝突が出たら、後から足す側の id の頭にキャラの短い名前を付けて分け（例: `redHoodCombatAssist`）、`name` は同じでよい。分けるかは、説明文で互いを見ているかで決め、その設計に根拠を書く。
  5. 一度付けた id は変えない。英語版の文言が変わったら、目録の `name.en` だけを直す。

### 5.2 付与: `kind: 'state'`

カモフラージュ（ウンファ：TU S1。いまの 4 件の `timed` と同じ中身）:

```json
{
  "kind": "state",
  "state": "camouflage",
  "trigger": "burstUse",
  "target": "self",
  "durationRef": 1,
  "contents": [{ "stat": "trueDamageConversion" }, { "stat": "trueDamage", "ref": 2 }],
  "claims": ["C-0311"]
},
{
  "kind": "state",
  "state": "camouflage",
  "trigger": { "count": "fullChargeShot" },
  "condition": { "inFullBurst": true },
  "target": "self",
  "durationRef": 1,
  "claims": ["C-0314", "C-0311"]
}
```

- **欄**: 新しいのは `state`（目録の id。`holder: 'ally'`）と `contents`（中身。5.3 節）。トリガー・対象と絞り込み・維持（ちょうど 1 つ）・スタック（中身の値は 1 スタックあたり）・条件（編成の条件を含む）・`claims`・`assumes` は、`timed` と同じ欄で同じ意味。
- **書けない欄**: `stat`・`ref`・`scaling`・`decrease`（中身に書く）、`name`（この付与に置き換える）、`amplifies`（値を参照する語彙で、状態ではない）。トリガーの確率のきっかけ（`chance`・`chanceRef`）は、窓が期待値の小片（`skills/chance.ts`）になり見る側の「付いているか」に使えないので書けない。`{ applied }` は連鎖させないので書けない（回復のトリガーに `healed` を書けないのと同じ）。
- **状態の窓**: 持ち主 × 状態 × 出どころごとに、出どころの定義にあるその状態のすべての付与の発火（付与ごとのトリガー・対象・条件）を集め、上書き延長（和集合）かスタックの段ごとの窓にする。値を持たないので区間の鍵には入らない。同じ定義の同じ状態の付与は、維持とスタックの上限が同じであること（窓を作る関数が維持を 1 つしか受けない。違う付与が要るキャラが出たら、そのとき決める）。
- **段**: 付与は、同じ欄の `timed` と同じ段に置く（条件なしは 1 段目、条件つきは 1.5 段目、順位の対象は 2 段目）。状態の窓は、その状態の付与のうちいちばん後の段で確定し、中身の窓も同じ段で確定する。確定より前の段の判定（1.5 段目の `selfBuffed`・2 段目の順位）には入らない（今の、条件つきの効果どうしを連鎖させない規則と同じ）。カモフラージュは 2 つ目の付与が条件つきなので 1.5 段目で確定する。
- **静的な状態**: トリガーが `battleStart`・維持が `durationUntil: "battleEnd"`・対象が `self`・条件なしの付与。編成の段で持ち主が決まり、中身は常時パッシブとして解く（3.4 節）。

### 5.3 中身: `contents`

- 項目は `stat`・`ref`・`scaling`・`decrease`・`claims`（`timed` の値の欄と同じ意味）。項目に `kind` が無ければ stat の▲▼と読む決まりにしておき、ほかの種類は後の拡張で `kind` を持つ項目として足す（8.4 節。今の定義を書き換えずに広げられる）。
- 効く相手は持ち主。効く窓は「同じ定義の付与で、その持ち主に付いた状態の窓」（スタックの段も）。きっかけの窓が重なっても▲は 1 回しか乗らない（2.2 節の 2）。
- `ref` は中身を書いた付与があるスロットの説明文の値で、そのスロットの Lv で解く（中身の値は説明文の「〈名前〉：効果…」を書いたスロットの値）。`scaling: "casterAttack"` の発動者は付与の出どころ。
- 中身は状態ごとに 1 回だけ書く（同じ定義に同じ状態の付与が 2 つ以上あるとき、`contents` を持てるのは 1 つ）。この規則で書けないもの（きっかけによって中身の値が違う同じ名前の状態、スタック数で中身の種類が変わる状態）は検証で落ちるので、黙って誤らない。出てきたら、そのキャラの設計で書き方を決める。
- 中身の無い付与も書ける（状態を見る側があるときだけ意味がある）。付与と中身が同じスロットにあるなら、中身は同じ付与に書く（ペルソナ）。
- 根拠の結論は付与の `claims` に書く。中身ごとに根拠が違うときは、項目にも `claims` を書ける。

### 5.4 見る側

どれも目録の id で指す。

| 言い回し                     | 欄                                            | いま                                     | 今回                                                                |
| ---------------------------- | --------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------- |
| 〈名前〉が適用された時       | トリガー `{ "applied": id }`（`damage` だけ） | 名前の付いた `timed` が付いたフレーム    | 状態の付与が持ち主に付いたフレーム。付き直しも 1 回ずつ（今と同じ） |
| 〈名前〉状態の味方           | `targetState: id`                             | 定義の最上位の `states`                  | 静的な状態（5.2 節）を持つ枠                                        |
| 対象（敵）が〈名前〉状態なら | `damage` の `condition.enemyState: id`        | `condition.targetStatus`（自由な文字列） | 改名だけ。付いている区間は今と同じ（5.5 節）                        |

- `targetState` は名前を残す（「対象の状態」で意味が合う）。`targetStatus` は `targetState` と紛らわしいので `enemyState` に改める。
- 付き直しで `{ applied }` を起こす今の規則は、[design-persona.md](design-persona.md) 4 節の 3 の読み（見分けていない）で、回復の規則（C-0082）とはそろっていない（6 節）。根拠が無いので変えない。
- 静的な付与も、フレーム 0 に適用の記録を作る（見る側の規則を状態の種類で分けない）。

### 5.5 敵の状態: dot の `state`

- dot の `status` を `state` に改め、目録の id（`holder: 'enemy'`）にする（クルミ S1 の `"status": "hacking"` は `"state": "hacked"`）。同じキャラの同じ `state` の dot を 1 つの持続ダメージとして扱う規則（C-0136）はそのまま。
- 付いている区間は今と同じ（同じ状態の dot の最初の発火から最後の tick まで。編成のどの枠の dot でもよい）。今は最後の tick を含む閉区間で見ているのを、[最初の発火, 最後の tick + 1) の半開区間で持ち、ほかの窓と同じ判定にする（値は同じ）。区間は今の場所（`frame/plan.ts`）で dot から作り、敵への付与（8.3 節）を足すときに時刻表の状態の窓の列にまとめる。

### 5.6 検証の規則

- id は目録にあり、`holder` が欄と合うこと（付与・`targetState`・`{ applied }` は `ally`、dot の `state`・`enemyState` は `enemy`）。名前の打ち間違いと、味方と敵の取り違えを落とす。
- 付与: トリガーに確率のきっかけと `{ applied }` を書かない。欄と中身の項目を合わせた `timed` が今の `timed` の規則を通る（3.2 節）。同じ定義の同じ状態の付与で `contents` を持つのは 1 つだけ、維持とスタックの上限は同じ（Lv で決まるものは解決のときに見る）。編成の条件は `timed` と同じに書ける（`parseEffect` の受け口に `state` を足す）。
- 付与が、自分の付ける状態を条件・対象の絞り込みで見ない（循環の禁止。[design-stage11-modernia.md](design-stage11-modernia.md) 11.2 節の 7）。

## 8. 後の拡張（形の見込み）

今回は入れない。使うキャラの設計で、根拠と一緒に足す。どれも 3 節の原則に従う。

### 8.1 見る側を広げる

- **自分が〈名前〉状態なら**: `condition: { "selfState": id }`。`timed` は 1.5 段目（同じフレームの窓を入れる。`selfBuffed` と同じ）、`damage` は `frame/plan.ts`。戦闘補助（ラピ：レッドフード）・火力チャージ（ネオン：ビジョン・アイ）。
- **フルスタック・否定**: `"selfState": { "state": id, "stacks": "full" }`・`{ "state": id, "present": false }`（文字列の形は `{ "state": id }` の略。引数の要らないときは文字列で書くトリガーの流儀と同じ。`present` は編成の条件と同じ名前）。ウォームアップ（ラプラス：アルティメットヒーロー）・射撃マニュアル（ミサト）・シンガロング状態でなければ（ミント）。
- **時間で変わる状態の対象の絞り込み**: `targetState` を、発火のフレームにその状態の窓の中にいる枠に広げる（`topAttack` と同じく、状態の窓ができた後の段）。バニーモード：スタンス状態の味方。
- **`{ applied }` を `timed` などに開く**: 回復と同じ 2 段で閉じる（付与の記録 → 出来事の列に `applied` を書き込む → ほかの効果を流す。`planHeals` → `replayEvents` と同じ形）。変身状態が適用された時（アークレンジャー・ブラック）。
- **〈名前〉が終了した時**: トリガー `{ "ended": id }`（状態の窓の終わり。`fullBurstEnd` と同じ関係）。殲滅態勢が終了した時（アスカ：WILLE）。

### 8.2 窓を途中で閉じる

- **解除**: 付与に `removeOn: <トリガー>`（その出来事で状態の窓を閉じる）。ほかの維持が無い「解除条件：〈出来事〉」は今の `durationUntil` で書ける（鉄・拳・制・裁！）。効果の行の「〈名前〉解除」も、きっかけが同じキャラの出来事なら `removeOn` で書く（マナのマターシグマ: フルバースト開始）。同じフレームの判定には付いているものとして入れる（窓は出来事の次のフレームで閉じる）見込み。
- **切り替え**: 目録の `group`。同じ `group` の状態が付いたら、ほかの状態の窓を閉じる。スタンス / エンゲージ（ギルティ：マイティバニー・シン：スウィフトバニー）。
- どちらも状態の窓を作る関数の「解除で切る」段（実装の別紙 1.4 節）に足す。中身と見る側は状態の窓を参照するので、閉じた窓がそのまま効く。

### 8.3 敵に付く状態

- `kind: 'state'` の `target: 'enemy'`（敵は 1 体の前提）。状態だけを付ける付与（予告状（ファントム）・ブームインストール（エレグ））。
- 敵の状態の中身（「アンチA.T.フィールド：受けるダメージ▲」など）は、今の `damageTaken` と同じく味方全体の窓に写す（3.2 節の検証がそのまま効く）。
- dot が付ける状態（5.5 節）と同じ列にまとめ、`enemyState` はどちらも同じに見る。

### 8.4 中身を広げる

- **中身の対象**: 項目に `target`（と絞り込み）。持ち主から見た対象。フォーメーションLT（エマ：TU。読み直すなら。7.2 節）。
- **他人の状態の間だけ効く**: 効果に `while: id`（その枠に状態が付いている窓で切る）。中身と同じ `whileState` に解く。フォーメーションAS 適用中（読み直すなら）。
- **stat 以外の中身**: 項目に `kind`（`dot` など）。アークブラックコレダー（「変身解除まで」の持続ダメージ）。同じ種類の今の効果と同じに扱い、窓だけ状態の窓にする（dot なら、付き直しで tick の刻みを変えない規則（C-0129）を状態の窓の延長に当てる）。

### 8.5 段の位置と循環の禁止

- 条件なしの付与と中身は 1 段目、条件つきの付与（後の `selfState` も）は 1.5 段目、順位の対象の付与と時間で変わる `targetState` は 2 段目。`{ applied }` の `damage` は時刻表の後、`timed` などの `{ applied }` は出来事の列の流し直し（回復と同じ 2 段）。`removeOn`・`group` は状態の窓を作る関数の「解除で切る」段。
- 状態を付ける付与が、その状態の窓を見て発火を決めることは禁じる（[design-stage11-modernia.md](design-stage11-modernia.md) 11.2 節の 7）。条件つきの付与が付ける状態は、ほかの条件の材料にしない（1.5 段目を 1 回で閉じる）。

1. この設計の承認（10 節の論点）。
2. 今回の語彙（5 節）と、実装の別紙 1 節の実装、7.1 節の移し替え、退化の確かめ（実装の別紙 2 節）、表示を 1 つの PR にする。
3. 文書: [skills-guide.md](skills-guide.md) 1 節に「説明文に名前の付いた状態が出たら、目録を見て、付与と中身を `kind: 'state'` で書く。中身に書くのは状態の間だけ効く項目だけ（4.3 節）」を足す。[design-stage11-modernia.md](design-stage11-modernia.md) 11.2 節・[design-persona.md](design-persona.md) 3.1・3.3 節・[design-kurumi-s2.md](design-kurumi-s2.md)・[design-true-damage-element.md](design-true-damage-element.md) 3.4 節に、この設計で置き換えたことを 1 行ずつ足す。

## 10. 論点

1. **状態の名前の置き場所**。
   - 推奨: core の 1 つの目録（`skills/states.ts`。5.1 節）。他のキャラが付ける状態を見る組（4.2 節）があり、名前を 1 か所で検証・表示できる。
   - 代案 A: JSON の目録（`data/states.json`）。データとして足せるが、core はいま JSON を静的に読み込んでおらず、`parseSkillDefinition` に目録を渡す道が要る。
   - 代案 B: 定義ごとの宣言（[design-stage11-modernia.md](design-stage11-modernia.md) 11.2 節の 2）。他のキャラの状態を見るときに、参照先の定義を引く仕組みが別に要る。
2. **中身の書き方**。
   - 推奨: 付与に入れ子の `contents`（5.3 節。組み直しで欄の名前を `effects` から改めた。スロットの `effects` と紛れず、場所を `effects[i].contents[j]` と書ける）。説明文の形のまま読め、中身を状態ごとに 1 回だけ書ける。解いた後は、状態の窓を参照する平らな効果（`whileState`）にそろえ、後の拡張の `while` も同じ形に解く（計算の道は 1 つ）。
   - 代案: 平らに書く（中身は別の `timed` に `while: id`）。入れ子は無いが、どの中身がどの状態に属するかが離れ、トリガー・維持の欄が要らない `timed` の例外が増える。
3. **追撃・バトンタッチ（中身 1 つの名前の付いた効果）**。
   - 推奨: 付与 + 中身 1 つに書き換える（7.1 節）。名前の付いた効果をすべて同じ形にし、`timed` の `name` を消す。
   - 代案: `timed` の `name` を残し（id は目録に寄せる）、書き換えない。定義の変更は小さいが、状態の形が 2 通り残る。
4. **移し替えの範囲**。
   - 推奨: 7.1 節の 4 体を同じ PR で移す。古い形（`states`・`name`・`status`・`targetStatus`）は消す。
   - 代案: 新しい形は次に定義するキャラから使い、今の 4 体はそのまま。古い形と新しい形が並ぶので、この設計の目的（1 つにそろえる）に合わない。
5. **後の拡張の語彙を今回入れるか**。
   - 推奨: 入れない。家族と段の位置だけを 8 節に決めておき、使うキャラの設計で確かめて足す（根拠のある使い手がいない語彙は入れない）。
   - 代案: `selfState`・`removeOn`・`group` を今回まとめて入れる。使う定義が無いので、退化テストしか書けない。
6. **ペルソナの効果 1（核熱ブースタ）を中身に入れるか**。
   - 推奨: 入れる（7.1 節）。静的な状態の中身は常時パッシブとして解くので、値も区間の割り方も変わらない。状態と中身の関係が定義に出る。
   - 代案: `passive` のまま残し、付与は中身なしにする。変更は小さいが、効果 1 が状態と無関係に見える今の問題（2.2 節の 2）が残る。
7. **状態の id の付け方**（5.1 節）。
   - 推奨: 英語版の状態名の lowerCamelCase。名前の出どころが CDN のデータにあり、誰が付けても同じ id になる。英語の名前が日本語と違っても（Hacked・Calling Card（予告状））、画面は目録の `name.ja` を出すので困らない。
   - 代案 A: 日本語の状態名から付ける（意訳かローマ字）。日本語の説明文との対応は見やすいが、付け方が人によって揺れる。今の `batonTouch`・`hacking` はこの形。
   - 代案 B: 連番（`S-0001` など）。揺れは無いが、定義を読んでも何の状態か分からない。
8. **条件の形をそろえるか**（組み直しで足した。2.2 節の 4）。
   - 推奨: 条件を 1 つの型（鍵の AND）にし、`damage` の `fullBurst` を `timed` の `inFullBurst` に改める（クルミ S2 の 1 件。7.1 節で同じ条件を触るので一緒に直す。値は変わらない）。どの効果がどの鍵を受けるか（`timed` は `selfBuffed`・`inFullBurst`、`damage` は `inFullBurst`・`enemyState`）は今のまま。後の拡張の `selfState` は両方に同じ名前で足す。
   - 代案: `enemyState` だけ足し、型と名前の違いは残す（backlog に別の行）。同じ意味の鍵が効果の種類ごとに違う名前のまま残る。
9. **「〈名前〉：機能…」のまとまりのうち、何を中身に書くか**（組み直しで足した。4.3 節）。
   - 推奨: 状態の窓の間だけ持ち主に効く項目だけ。自分の維持・即時・別の対象を持つ項目は、今と同じく同じトリガーの別の効果で書く。中身の窓の規則が 1 つで済む。
   - 代案: まとまりをそのまま入れ子にし、項目ごとに維持・対象・種類を持たせる。説明文と 1 対 1 だが、同じ意味の書き方が 2 通りになり、中身の窓の決め方が項目ごとに分かれる。
