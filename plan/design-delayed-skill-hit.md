# 発動の後に遅れて出る倍率ダメージ（クイーン（真）・雪子の 1more の分配ダメージ）

- 関連: [design-true-damage-element.md](design-true-damage-element.md) 3.6 節（1more の読みと `enemyElement`）、[design-burst-landing.md](design-burst-landing.md)（バーストの着弾の遅れの表）、[skills-guide.md](skills-guide.md) 1.4 節

- 状態: 2026-10-06 にオーナーが承認（5 節の論点はすべて推奨どおり）し、同日に実装した（6 節の 1〜5）。C-0310 を確定にし、V-0212 を閉じた

## 1. 何が困っているか

- クイーン（真）（870）の S1「1more が適用された時、敵全体に最終攻撃力の X% の分配ダメージ」を、`damage`・`burstUse`・`enemyElement: Wind` で書いて撮った（V-0212）。
- 実測のヒット（`229-05`）は、モデル（C-0309）と合わなかった。合ったのは G3（V-0212 の手書きの表）で、次の 2 点がモデルの規則と違う。
  - **バフ**: フルバースト補正に加えて、同じ発動で付いた 1more の攻撃力▲（C-0308）と S2 の▲（C-0307）も乗る。いまの規則では、バースト使用時の倍率ダメージは発動の直前のバフで固定する（`frame/plan.ts` の `BURST_HIT_USES_PRE_ACTIVATION_BUFFS`）ので、これらが乗らない。
  - **時刻**: ヒットはバーストの倍率ダメージのヒットの 23〜24f 後に出る（`229-07`。5 回）。いまの規則では、発動と同じフレームに出る。
- バーストの倍率ダメージのヒットそのもの（`229-04`・`230-04`）は、いまの規則（発動の直前のバフ）で合っている。変えるのは、1more のような発動の後に出る倍率ダメージだけ。

### 1.1 同じ言い回しのほかのキャラ

全キャラの説明文から「1more」を拾った。

| キャラ                | スロット | 言い回し                                                                |
| --------------------- | -------- | ----------------------------------------------------------------------- |
| クイーン（真）（870） | S1       | 1more が適用された時、敵全体に最終攻撃力の X% の分配ダメージ            |
| 雪子（871）           | S1       | 同じ                                                                    |
| どちらも              | バースト | 対象が風圧コードなら自分に 1more（攻撃力▲）。1more のきっかけはこれだけ |

- 雪子は所持の記録に無く、撮っていない。遅れの値は雪子では測っていない（3.2 節）。

## 2. 実測で分かっていること

- 回数: 風圧の敵へのバーストのたびに 1 つ（`229-06`）。灼熱の敵では 0（`230-05`）。`enemyElement` の読み（設計 3.6 節）のとおり。
- 値: G3 と端数まで合う（`229-05`）。式はバーストのヒットと同じ分配ダメージ（分配ダメージ▲が乗る）で、そのフレームのバフで決まる。
- 時刻: バーストの倍率ダメージのヒットから 23〜24f 後（`229-07`）。クイーン（真）のバーストのヒットは III の発動から 1f（モデルのフレーム。C-0231）なので、発動から 24〜25f。
- 試しに、きっかけを `fullBurstStart` にした定義（いまの語彙）では値が 4,735,556.9 で合うが、時刻が 24f ほど早く、クイーン（真）以外の III がバーストを撃ったフルバーストでも出てしまう（V-0212 の検討。採らない）。

## 3. 語彙の案

### 3.1 `damage` に遅れ `delayFrames` を足す

```json
{
  "kind": "damage",
  "trigger": "burstUse",
  "ref": 3,
  "damageType": "distributed",
  "enemyElement": "Wind",
  "delayFrames": 24
}
```

- きっかけのフレームの `delayFrames` 後に出す。バフはそのフレームのもの（同じ発動で付いた効果も入る）で、フルバースト補正もそのフレームがフルバースト中かで決める。
- `delayFrames` を書いた効果には、発動の直前のバフで固定する規則（`BURST_HIT_USES_PRE_ACTIVATION_BUFFS`）を当てない。書かない効果は、いまと同じ。
- 戦闘の終わりを越えるヒットは出さない。
- 書けるきっかけは `burstUse` だけにする（いま要るのはこれだけ。ほかのきっかけで要るキャラが出たら開く）。

### 3.2 遅れの値

- 値はスキル定義の即値にする。キャラの表（`burst/landing.ts` の `MEASURED_BURST_DELAYS`）には入れない。理由は、遅れがバーストのヒットではなくスキルの効果のものだから。
- クイーン（真）は 24 にする。`229-07` の 5 回は 23f が 3 回・24f が 2 回なので、最頻値の 23f にバーストのヒットの 1f（C-0231）を足した値。値には結論 C-0310 を結び付ける。
- 23 と 24 の違いで与ダメージは変わらない（フルバーストの窓の真ん中で、バフの窓の切れ目から遠い）。
- 雪子は測っていないので、定義するときに撮って決める（それまでは雪子を定義しない）。

## 4. 退化の見込み

- `delayFrames` は省略できる。書かない定義の計算は変わらない（既存のテストと照合の結果は変わらない）。
- 変わるのは、クイーン（真）の S1 に 1more の効果を入れたときの風圧の敵の値だけ（`229-05` が許容内になる。灼熱の録画の値は変わらない）。
- calc は、共通のフレームループの倍率ダメージの列（`frame/plan.ts` の `planSkillHits`）をそのまま使うので、sim と calc は同じ値になる。

## 5. 論点

1. **語彙の形**: (a) `damage` に `delayFrames` を足す（3.1 節）、(b) 新しいきっかけ `oneMore`（「1more が適用された時」）を作り、遅れとバフの扱いをそのきっかけに持たせる。
   - 推奨: (a)。1more のきっかけはバーストと同じ発動で、バーストのきっかけと条件 `enemyElement` で書ける。遅れて出る倍率ダメージは、ほかのキャラにも出うる形で、名前の付いたきっかけより使い回しが効く。
2. **遅れの値**: 24 でよいか（3.2 節）。
   - 推奨: 24。
3. **結論の確定**: 実装して `229-05` が許容内になったら、C-0310 を確定にするか。予測（G3）は撮る前に手で書いたが、録画は 1 本。
   - 推奨: 確定（厳密一致）。G3 は撮る前に書いた 8 通りの 1 つで、ほかとは 17% 以上離れ、端数まで合っている。予測ファイルの H1 ではなく手書きの値なので、`records:close` の「合う仮説」には数えられない。判断を結論の根拠に書く。

## 6. 実装の順

1. `skills/types.ts` の `DamageEffect` に `delayFrames` を足し、`parseDamageEffect` で検証する（1 以上の整数、きっかけは `burstUse` だけ）。単体テストを足す。
2. `frame/plan.ts` の `planSkillHits` で、`delayFrames` のある効果はきっかけのフレーム + `delayFrames` に、そのフレームのバフ（`pre` = false）で出す。既存のテストが数値を変えずに通ることを確かめる。
3. `data/skills/870.json` の skill1 に効果を戻し（`delayFrames: 24`、`claims: C-0310`）、未対応の notes を消す。
4. 画面のラベル（`apps/web/src/components/SkillSection.tsx`）と CLI の表示に遅れを出す。
5. `npm run records:check` で `229-05` が許容内になることを確かめ、C-0310 の `model` を書き、V-0211・V-0212 を閉じる。
