# V-0203: ユニのバーストのヒットの遅れを最小構成で確かめる（ココア + ユニ）

- 問い: ユニ（II）のバーストの倍率ダメージのヒットは、機構の確定した I との 2 体の編成でも、II の発動からモデルのフレームで 124f（C-0230）遅れるか
- 話題: スキル・キャラ固有
- 日付: 2026-10-05
- Stage: plan/design-burst-landing.md 5 節の 2（ほかのキャラの遅れ）。backlog 2-4
- 状態: 調査中
- 待ち: 撮影（この記録の「次に撮るもの」）
- 派生元: `V-0146`

## 条件

**何を確かめるか**

- C-0230（仮説・単独実測）は、録画 `080`（I-DOLL・フラワー + ユニ + アスカ）の 1 本だけから出した値で、アスカの機構が未確定なので最小構成でない。最小構成の新しい録画で同じ値が出るかを見る。予測を撮る前に commit し、値を決めるのに使っていない録画で再現すれば、等級の候補は反復実測になる（plan/skills-guide.md 1.8 節）。
- ユニのバーストには「バースト使用時」の効果が無い（移動不可だけ）ので、効果の遅れは無い。

**編成**

- ココア（311。I）+ ユニ（160。II・操作・AUTO 射撃 ON）の 2 体、オートバースト ON。射撃場・灼熱の BigArms・3 分モード・スペック固定。ニヒリスターの `081`（ココア + ニヒリスター）と同じ形。
- 機構の確定した III がいない（どの III も未確定）ので、III は入れない。III がいないとフルバーストは起きず、II の発動の後はチェーンが切れるのを待つ（`081` と同じ）。`080` のつながらなかった回（II の発動 → ヒットに止まりが入らない回）と同じ形になる。
- **最小構成**: ココアは定義が効果なし（V-0031）で、機構が確定している。2026-10-05 に `records/minimal.ts` の検査（`minimalWarnings`）にこの編成をかけ、警告が出ないことを確かめた（未確定はユニだけ）。I-DOLL・フラワー（機構は確定）でも組めるが、ほかの 5 本（V-0200〜V-0202・V-0204・V-0205）と I を揃えてココアにする（ココアのバーストにはダメージが無く、HUD の増分が増えない）。
- モデルでは、ユニの発動は 7 回（予測ファイルの編成で `npm run sim -- --ids 311,160 --fixed-spec --controlled 2 --enemy range-bigarms-fire --events range-3min-jump`）。

**読み方の前提**

- II の発動は、右のバースト欄の六角形が II から次の表示（III の段）に替わったフレーム（V-0131・V-0146）。フルバーストが起きないので、遅れ（モデル）= 動画のフレームでの「II の発動 → ヒット」（止まりは入らない）。
- バーストの倍率ダメージの値は、HUD の増分で、ほかの枠の 1 発と見分けて取る（ユニの 1 発のロケットより大きい）。

## 予測（撮る前に書く）

撮る前に書いた（2026-10-05）。H0 はいまのモデル（遅れの表のユニの行）で、値は予測ファイル（records/predictions/V-0203.json）。

| 仮説                            | 7 回の「II の発動 → ヒット」（動画のフレーム） | 1 回目のヒットの値                                 |
| ------------------------------- | ---------------------------------------------- | -------------------------------------------------- |
| H0: いまのモデル（C-0230 の値） | 予測ファイルの `yuni-delays` ± 1f              | `yuni-burst-hit`・`yuni-burst-hit-crit` のどちらか |
| D2: 毎回同じだが C-0230 と違う  | どの回も同じ値 ± 1f で、H0 から 2f 以上ずれる  | （H0 と同じ）                                      |
| D0: 毎回違う                    | 2f 以上ずれる回がある                          | （H0 と同じ）                                      |

- **H0 を予想する**。遅れの表のどのキャラも回ごとに揃い、I・II の顔ぶれを替えた録画でも同じ値だったため。`080` のつながらなかった回（止まりの入らない回）も 124〜125f だった（V-0146）。
- 1f の揺れは録画の重複フレームの位置で出る（V-0146）ので、± 1f を合うとみる（観測値の許容 `abs: 1`）。
- 実機の発動が 7 回に満たないときは、読めた回数で観測値を作り、予測ファイルとの結び付きを `observations` で明示する（V-0140 の `037` のように回数が違うと自動では結び付かない）。
- 当たったときの影響: C-0230 を確定（反復実測）にできる。遅れの表の値は変わらない。
- 外れたときの影響: D2 なら、遅れが I・III の顔ぶれ（フルバーストにつながるか）で変わることになり、遅れを演出の長さで決まる値とみる前提（plan/design-burst-landing.md）を見直す。D0 なら、何で決まるかを調べる。

## 読み方

1. 取り込む: `node tools/captures/intake.ts <元ファイル> --id NNN --name sr+rl_cocoa+yuni_yuni-auto --rid 311,160 --controlled 2 --target BigArms --element Fire --mode range-3min --fixed-spec on --auto-fire on --auto-burst on`。台帳を埋めて `npm run records:table`。この検証記録の冒頭に「録画」を足す。
2. 右のバースト欄を 1 フレームずつ並べて、各回のユニの II の発動（六角形が II から次の表示に替わるフレーム）を読む。替わり目は、前のフレームと次のフレームの画で確かめる。
3. HUD の増分（`npm run records:read -- <録画 id> --recipe hud-jumps`）から、各回のユニのバーストの倍率ダメージのヒットのフレームと値を取る。
4. II の発動 → ヒットを観測値（`burstHitDelays`。許容 `abs: 1`）、1 回目のヒットの値を観測値（`burstHitDamage`。会心かどうかで `crit` を選ぶ）にする。`args`・`setup` は予測ファイルの指標と同じにする。
