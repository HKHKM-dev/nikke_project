## 1. 何が困っているか

トーブ（192）の基礎版は 3 スロットとも未対応（`data/skills/192.json` の `skills`）。宝物版（`treasureSkills`）は 3 スロットとも定義と確定の結論がある。

基礎版と宝物版の説明文の違いは次だけ（`data/characters/192.json`。値はスキル Lv10）。

| スロット      | 基礎版                                                                                                  | 宝物版                                    | 違い                      |
| ------------- | ------------------------------------------------------------------------------------------------------- | ----------------------------------------- | ------------------------- |
| S1 のきっかけ | 攻撃した時、{01}%（5%）の確率で代用弾丸                                                                 | 通常攻撃を {01}（10）回行った時、代用弾丸 | **確率**。Lv1〜4 は 2〜4% |
| S1 の中身     | 弾丸チャージ 5.31%・応急改造（最大装弾数 2 発▲・3 スタック・5 秒）・クリティカルダメージ 5.24%▲（5 秒） | 同じ                                      | なし                      |
| S2            | 応急改造のフルスタックの時、味方全体にクリティカル確率 3.32%▲、SG の味方に攻撃速度 42.24%▲              | 同じ形（クリティカル確率は 10.08%）       | 値だけ                    |
| バースト      | 発動者基準の攻撃力 2.32%▲・SG にさらに 24.21%▲、応急改造スタックコピー、10 秒                           | 同じ形（15 秒）                           | 維持の秒だけ              |

基礎版の S2 とバーストは、宝物版と同じ語彙（`while.selfState` の `stacks: "full"`、`stacksFrom`）で書ける。書けないのは S1 の確率のきっかけで、いまの確率の語彙（design-soldier-eg.md 3.1 節）は timed にしか書けない（`skills/parse/timed.ts` の `validateChanceTimed`）。代用弾丸は弾丸チャージ（即時効果）と状態の記録で、その先の応急改造はスタックを持つ付与なので、どちらも確率で付けられない。応急改造が付かないので、S2（フルスタックの時）もバースト（スタックのコピー）もモデルでは効かない。

### 1.1 撮れない

オーナーのトーブは宝物の段階 3 で、宝物は外せない（2026-11-07 のオーナーの回答。ドレイクも同じ。design-c0641-n-version.md の経過）。基礎版の録画は撮れない。skills-guide.md 0 節の「撮影で確かめるキャラだけ定義する」に当たらない。

ただし、基礎版の機構のうち確率のきっかけ以外は、宝物版の録画で確定している（応急改造の付き方・付き直し・スタック、S2 のフルスタックの判定、バーストのコピーの固定）。撮らずに残る問いは、(a) 確率のゲームでの振る舞い（「攻撃した時」が 1 発ごとか、毎発独立に {01}% か）と、(b) モデルが確率をどう持つか（期待値の計算が正しいか）の 2 つ。(b) はゲームの事実ではなく計算で、テスト（乱数で何度も回した平均と、期待値の計算を突き合わせる）で確かめられる。

## 2. 案（確率で付く応急改造をどう持つか）

| 案                                  | 中身                                                                                                                                                                                                               | 長所                                                                                                                                                   | 短所                                                                                                                                                        |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. 期待値のスタック分布**（推奨） | 確率の機会ごとに、応急改造のスタック数の確率分布をフレームごとに追い、線形の効果は「値 × スタック数の期待値」、フルスタックの条件は「値 × フルスタックの確率」、コピーは「バーストの時のスタック数の期待値」にする | ソルジャーE.G. の期待値の窓と同じ考え方で、期待値が厳密（線形の stat なら 1 発の期待値と同じ）。区間・鍵・calc・sim の読み方は変えない（期待値の小片） | 射撃の列を変える効果（弾丸チャージ・最大装弾数▲・SG の攻撃速度▲）は書けず、未対応のまま。クリティカル確率とクリティカルダメージの積は相関の分ずれる（4 節） |
| B. 確率の累計で決定的に発火         | {01}% を発ごとに足し、累計が整数をまたいだ発で代用弾丸を付ける（5% なら 20 発ごと）。宝物版の語彙をそのまま使う                                                                                                    | 語彙がほぼ足りる。射撃の列を変える効果も書ける                                                                                                         | フルスタックの割合を大きく外す（3 節の見積もりで、Lv10 で実際の平均約 0.78 に対し 0.97、Lv1 で約 0.28 に対し 0）。乱数の揺れで切れることを持てない          |
| C. 乱数で何度も回して平均           | 1 パス目に乱数を入れ、種を変えて回した平均を出す                                                                                                                                                                   | 射撃の列を変える効果も含めて正しい平均                                                                                                                 | モデルが決定的でなくなる。16-C で凍結した乱数（design-stage16.md）を開け直す大きな変更で、1 キャラのためには重い                                            |
| D. 線形の 1 つだけ                  | クリティカルダメージ▲だけを、いまの確率の timed（`normalShot`・`chanceRef` 1）で書く（代用弾丸が付く発と同じなので同値）。ほかは未対応のまま                                                                       | 語彙を足さない                                                                                                                                         | S2 とバースト（基礎版の効果の大半）が効かないまま                                                                                                           |

### 2.1 案 A の語彙

- 付与（`kind: "state"`）の回数トリガーに、確率（`chance`・`chanceRef`）を書けるようにする。`count` は `normalShot` か `normalHit`（timed と同じ）。`maxStacks`・`maxStacksRef`・`durationRef` を持てる。付き直しは `STACK_REFRESH`（`'all'`。発火のたびに 1 スタック足し、全スタックの維持を数え直す。C-0559）。
- 確率の付与の中身（`contents`）は、timed の確率と同じ制限（足し合わせて意味のある stat だけ。`isFiringStat` などは不可）。最大装弾数▲は書けないので、応急改造は中身を空にして書き（スタックの入れ物だけ）、最大装弾数▲は未対応の notes に残す。
- 確率の付与を読む側:
  - `while.selfState`（`stacks: "full"` か数）: 窓を期待値の小片にし、値に「その条件が成り立つ確率」を掛ける。読む側の stat にも timed の確率と同じ制限を掛ける（SG の攻撃速度▲は射撃に効くので書けず、未対応のまま）。
  - `stacksFrom`: 付いた時の数の代わりに、付いた時のスタック数の期待値（小数）で値を掛ける。維持の間は固定（C-0670）。
  - `{ applied: <確率の付与> }` のきっかけ: 書けないことにする（基礎版のクリティカルダメージ▲は、案 D と同じく確率の timed で書く）。
- 確率の即時効果（弾丸チャージ）は書けないまま（射撃の列を変える）。

### 2.2 案 A の計算

機会 i（発の次のフレーム sᵢ、付く確率 qᵢ）を昇順に並べる。Aᵢ(k) を「機会 i で付き、付いた後のスタック数が k」の確率とすると、

- Aᵢ(k) = qᵢ × ( Σⱼ Aⱼ(k − 1) × Πⱼ<ₗ<ᵢ (1 − qₗ) + [k = 1] × P(i の直前に付いていない) )。上限 K では k − 1 = K の項も K に入れる。j は sⱼ + D > sᵢ の機会（それより前に付いた分は切れている）。
- フレーム t でスタック数が k の確率は Σᵢ Aᵢ(k) × Πᵢ<ₗ, sₗ≤t (1 − qₗ)（i は sᵢ ≤ t < sᵢ + D）。
- 計算は機会の数 × 維持の中の機会の数。AR の 180 秒で約 2,000 機会 × 60 程度。

期待値の小片は、機会の始まりと終わりで割る（`skills/chance.ts` の `chancePieces` と同じ境目）。小片の値の丸め（`chanceValueOf`）も同じ。機会は 1 パス目が発ごとに貯める（`skills/holders.ts`。timed の確率と同じ所）。

### 2.3 案 A での 192 の基礎版の定義（案）

- S1: 付与 `temporaryModification`（`{ count: "normalShot", chanceRef: 1 }`・味方全体・`maxStacksRef` 4・`durationRef` 5・中身なし）、timed のクリティカルダメージ▲（`{ count: "normalShot", chanceRef: 1 }`・味方全体・`ref` 6・`durationRef` 7）。未対応の notes: 弾丸チャージ（確率の即時効果）、応急改造の最大装弾数▲（確率の付与の中身に射撃に効く stat は書けない）。
- S2: 宝物版と同じ形の passive（クリティカル確率▲）。SG の攻撃速度▲は未対応の notes。
- バースト: 宝物版と同じ形（`durationRef` が 10 秒の値）。
- 根拠: 機構は宝物版の結論を指し、確率と基礎版の値は説明文のデータ明記の結論を 1 つ足す（7 節の論点 3）。

## 3. 見積もり（案 A と案 B の差）

簡単な時刻表（AR・720 発/分・マガジン 60 発 + 応急改造・リロード 1 秒・180 秒・的のジャンプなし）で、毎発独立に p の確率で付けて 200 回回した平均と、案 B（累計で決定的）を比べた。案 A の期待値は、この平均と同じ値になる（射撃の列を変える効果を入れない分を除く）。

| p（スキル Lv） | フルスタックの割合（乱数の平均） | 同（案 B） | スタック数の平均（乱数） | 同（案 B） |
| -------------- | -------------------------------- | ---------- | ------------------------ | ---------- |
| 2%（Lv1〜2）   | 0.28                             | 0.00       | 1.37                     | 1.19       |
| 3%（Lv3〜5）   | 0.54                             | 0.95       | 2.00                     | 2.90       |
| 4%（Lv6〜8）   | 0.66                             | 0.96       | 2.27                     | 2.93       |
| 5%（Lv9〜10）  | 0.78                             | 0.97       | 2.53                     | 2.95       |

案 B は、5% で 20 発（約 1.7 秒）ごとに必ず付くので、5 秒の維持の中で切れない。実際は 60 発続けて付かないこと（5% で約 5%）やリロードの間に切れ、作り直すのに 3 回要る。

## 4. 既存の語彙との関係・退化・リスク

- 退化: 確率の付与を持つ定義が無ければ、窓・区間・数値は変わらない（いまのテストが数値を変えずに通ることを確かめる）。宝物版の 192 も変わらない。
- 相関: S2 のクリティカル確率▲（フルスタックの確率）と S1 のクリティカルダメージ▲（付いている確率）は同じ代用弾丸から出るので、会心の期待値（確率 × ダメージ）の積は、期待値どうしの積より少し大きい。モデルは期待値どうしの積で、少し小さく出る。
- 書けないもの: 弾丸チャージ・最大装弾数▲（味方全体）・SG の攻撃速度▲は、射撃の列を変えるので期待値で持てず、未対応のまま。モデルは基礎版のトーブを少し小さく出す（リロードの回数・SG の味方の発の数）。
- 撮れない: 基礎版の確率のゲームでの振る舞い（1 発ごと・毎発独立）は確かめられない。ソルジャーE.G. の確率（C-0372）は頻度が説明文と矛盾しないことを撮って確かめたが、トーブの基礎版ではそれができない。

## 5. テスト

- 2.2 節の分布を、乱数で多数回回した平均（種を固定）と突き合わせる（スタック数の各値の確率・フルスタックの確率・バーストの時の期待値）。
- 192 の基礎版を含む編成で、S2 とバーストの窓が期待値の小片で出ること。

## 6. 実装での差分

- **確率の付与の検査**（`skills/parse/state.ts` の `validateChanceGrant`）: 条件・発数や出来事の維持・stacksFrom・stacksPerFireRef・leadFrames・stackRefresh・stackImmutable・delayFrames・敵への付与・発火の文脈で決まる対象とは組み合わせない。中身の規則には付与のスタックの欄を渡さない（中身は段ごとの期待値の小片になる）。
- **見る側の検査**（`skills/parse/crossChecks.ts` の `validateChanceStates`）: 確率で付く状態は、その付与が定義に 1 つだけで、ほかの効果は while の selfState と stacksFrom の state でしか見られない（条件・{ applied }・{ fullStack } などで見ると読み込みで止める）。1 パス目の `holdsAt`・`stackLevelAt` も、確率の状態を見たら止める。
- **件**（`skills/holders.ts`）: 確率の付与の件の列は、機会を持ち主の件の列で共有し（1 パス目が発ごとに貯める。timed の確率と同じ）、件を `chanceStackPieces` の段の小片（`stack` と `scale`）にする。`whileItems` は、段の小片のうち条件の段（フルスタックなら上限の段）の小片を scale ごと出す。stacksFrom は `chanceLevelsAt` で段ごとの確率を取り、確率が正の段の数だけ段を付け、件の段に scale を掛ける（`scaleLevels`）。
- **速さ**: 確率の状態は、段ごとの小片が持ち主ごとに付くので小片が多い。`chanceStackPieces` は、1 パス目が機会を足すたびに前から作り直さず、最後の機会までの状態を持って後ろだけを作り直す。区間を組む `buildSegments`（`skills/timeline.ts`）は、区間 × 小片の二重の走査をやめ、始まりの順に入れて終わったものを外す走査にした（足す順は並びの順のままで、数値は変わらない）。

## 7. 論点

1. **撮れない基礎版を定義に入れるか** — 推奨: **入れる**（skills-guide.md 0 節の例外として、機構を宝物版の録画の結論に結び付ける。基礎版で残る問いは確率の振る舞いだけで、計算はテストで確かめられる）。別案は、入れない（notes を「宝物を外せず撮れない」理由に直して閉じる）。
2. **確率の持ち方** — 推奨: **案 A（期待値のスタック分布。2 節）**。別案は案 B・C・D。
3. **根拠の結論の等級** — 推奨: 基礎版の値（S2 の 3.32%・バーストの 10 秒など）と「攻撃した時、{01}% の確率で」は説明文のデータ明記の結論（確定）にし、「基礎版の確率のきっかけは 1 発ごとに毎発独立に {01}%（攻撃した時 = `normalShot`）」は撮れないので仮説の結論にする。そのため基礎版のトーブは「機構が確定したキャラ」にならない。
4. **射撃の列を変える 3 つ（弾丸チャージ・最大装弾数▲・SG の攻撃速度▲）** — 推奨: 未対応の notes に残す（案 C の乱数を開けるまで）。
