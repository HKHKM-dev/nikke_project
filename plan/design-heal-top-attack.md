## 1. 何が困っているか

フォルクヴァン（242）のバーストの 2 行目だけが、[skills.md](skills.md) で未対応（`unimplemented`）の notes のまま残っている。

| 部品                                      | 語彙                                       | 根拠                                    |
| ----------------------------------------- | ------------------------------------------ | --------------------------------------- |
| バースト使用時（スロットがバースト）      | `trigger: "burstUse"`                      | —                                       |

足りないのは組み合わせだけ。`skills/types.ts` が「`heal` は `topAttack` を対象にできない」（`heal cannot target "topAttack"`）で落としている。理由は循環で、回復 → 回復を受けた時の攻撃力▲（アスカの S1）→ 最終攻撃力の順位 → 回復の対象、と回る。どの時点の順位で対象を選ぶかを決めれば、循環は断てる。

- 説明文の走査（`data/characters/` の全キャラ・全スロット）で、「最終攻撃力が最も高い味方」に回復が付くのは、フォルクヴァンのバーストと、クレア（842。定義なし）の S1（フルチャージ攻撃が N 回命中した時、最終最大HP の X% 回復）だけ。ほかの「受けるHP回復量▲」（フォルクヴァン S1・ラプンツェル・マルチャーナ）は回復ではない。
- ゲーム内のヘルプ（[game-help.md](game-help.md)）に、順位を決める時点の記述は無い。

## 2. 循環の断ち方（比べる時点の候補）

1 パス目の手順 3 の順番は、回復 → 攻撃力の窓の登録 → 射撃に効く窓の登録 → 即時効果（design-stage11.md 19.3 節）。`timed` の `topAttack` は攻撃力の窓を登録した後に順位を出すので、同じフレームに付いた窓も順位に入る（18 節。録画 0043 で確定）。

| 案                                                    | 回復の対象を選ぶ順位                                                                                                                                      | 根拠                                                                                                                                                                                                                                          | 実装                                                                                                                                                                  |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A（推奨）: 回復の前の時点**                         | 発火のフレーム f の、手順 3 の前に登録済みの攻撃力の件（`start ≤ f < end`）で出す。そのフレームの手順 3 で付く窓（回復を受けた時の▲を含む全部）は入れない | 実測の根拠は無い。読みとして素直（スキルを使った瞬間に対象を選び、その回復で起きる効果は後）。循環が手順の順番だけで閉じる（`heal` のトリガーに `healed` を書けないのと同じ流儀。design-stage11.md 3.3 節）                                   | 小さい。回復のループで順位の文脈（`HolderLists.rankContext`）を引くだけ。順位の材料（段 1・1.5 の攻撃力の件）はいまも追っている                                       |
| B: 同じフレームの窓を入れ、回復を受けた時の窓だけ外す | 手順 3 で回復を受けた時の窓より前に、そのフレームのほかの攻撃力の窓を登録してから順位を出す                                                               | `timed` の `topAttack` の規則（同じフレームの窓を入れる）とそろう。ただし録画 0043 で確かめたのは、モデルで III の発動とフルバーストの開始が同じフレームになる分（実機ではフルバーストが数 f 後）で、同じ瞬間に付いたものを入れる根拠ではない | 大きい。件の登録（`registerFrame`）を、回復を受けた時のきっかけの件とそれ以外に分ける。射撃の回数起点の回復を前のフレームから送った分（`pendingHeals`）の扱いも分ける |
| C: 前のフレーム（f − 1）の順位                        | f − 1 に効いている件                                                                                                                                      | 無い                                                                                                                                                                                                                                          | 小さい。A との違いは、前のフレームまでに登録して f に始まる件（射撃の回数のきっかけの窓）と、f に切れる件だけ。利点が無い                                             |
| D: 入れて選び直す（落ち着くまで）                     | 回復を受けた時の▲も入れた順位で選び直す                                                                                                                   | 無い                                                                                                                                                                                                                                          | 落ち着かない形がありうる（▲で入った枠が、選び直しで外れる）。採らない                                                                                                 |

推奨は A。B と A で対象が変わるのは、回復の発火と同じフレームに、回復を受けた時のきっかけでない攻撃力▲が付き、それで上位 N の境目が入れ替わるときだけ。いまの定義でそれを付けうるのは、シンデレラ（511）の S1「バースト 3 段階突入時、自分に最終最大HP の X% 分の攻撃力▲」だけ（モデルではバースト 3 段階への突入は II の発動と同じフレーム）。回復の対象が変わっても、与ダメージが変わるのは、境目の枠が回復を受けた時の効果を持つとき（アスカの S1・クラウンの S2）だけ（3 節）。

- 順位の材料は、`timed` の `topAttack` と同じ（常時パッシブと段 1・1.5 の攻撃力の件。順位で対象が決まる効果の件は数えない。18 節）。同値は枠の若い順（仮定。未検証）、自分も候補（確定。design-stage11.md 27 節）。
- 射撃の回数起点の回復（クレア型）も同じ: 順位はトリガーのフレーム f の手順 3 の前で出し、当てるフレームは今の規則（撃った枠より後ろの枠は f、自分と前の枠は f + 1。`skills/heals.ts` の `healFrameOf`）。

## 3. 録画 0710 で見分けられるか

見分けられない。A〜C のどれでも対象は同じ。

- 録画 0710 の編成（ラム・I-DOLL・サン・フォルクヴァン（操作）・アスカ、スペック固定）のモデルの最終攻撃力は、アスカ 119,896・フォルクヴァン 79,954・サン 67,895・ラム 63,368（`npm run sim -- --ids 822,308,242,830 --fixed-spec --controlled 3 --element Fire`。A の試作で）。アスカとほかの差が大きく、どの案でもアスカは 1 位。
- この編成で攻撃力▲を持つのはアスカの S1（回復を受けた時）だけで、フォルクヴァンのバーストのフレームに始まるほかの攻撃力の窓は無い。前の回の S1 は 25 秒で切れていて、40 秒ごとの次の発動の時には効いていない。
- 2 機目は、モデルではフォルクヴァン自身（自分も候補）。V-0517 が「2 番目はラムかサン」と書いたのは、自分を候補に入れない読みで、モデルの順位とは違う。どちらでも、回復を受けた時の効果を持たないので録画には見えない（C-0695 の範囲の外）。
- A の試作で、アスカの S1 は各発動から 25 秒（ゲーム内）付き、吸収回復の窓の中で付き直さない。C-0695 の読み（`0710-07`・`0710-08`）と同じ形。

A と B を見分けるには、回復の発火と同じフレームに付く攻撃力▲で、上位 2 機の境目が入れ替わり、境目の枠が回復を受けた時の効果を持つ編成が要る。

- シンデレラの S1 は、モデルでは II の発動のフレームに 80,485 → 173,543 にする（`npm run sim -- --ids 822,242,511,830 --fixed-spec --controlled 2 --element Fire`）。ラム・フォルクヴァン・シンデレラ・アスカの編成では、A ならアスカとシンデレラ（80,485 でフォルクヴァンより上）、B ならシンデレラとアスカで、どちらでもアスカに届く。見分けられない。
- 見分けるには、そのフレームにアスカより上の枠がもう 1 機要る（A ではアスカが 2 位、B では 3 位になる）。スペック固定では攻撃型の攻撃力が同じで、アスカと同じ値の攻撃型を置くと同値の決め方（枠の若い順。未検証）が混ざる。前のフレームまでに付いた▲でアスカより上になる枠を使うなら、その▲の機構も確定のものに限る。いまの最小構成の候補が無いので、撮影は計画しない（7 節の論点 1）。

## 4. 語彙と定義

### 4.1 語彙（足すものは無い。組み合わせを許す）

- `skills/types.ts`: `heal` の `topAttack` を許す（`targetCount` / `targetCountRef` はちょうど片方。`targetWeapon`・`targetElement`・`targetClass`・`excludeSelf` は `timed` の `topAttack` と同じに書ける）。`heal` のトリガーに `healed` を書けない規則はそのまま。
- `frame/firstPass.ts`: 回復のループで、`targetsAt` に渡す文脈を `lists.rankContext(...)` にする（A。回復は `registerFrame` の前なので、そのフレームの窓は入らない）。冒頭のコメントに A の規則を書く。
- 順位の記録（`HolderHistory.rankings`）には回復を入れない。回復の対象は `heals` の記録に残る。`rankings` は画面の「最終攻撃力の上位（対象）」の列が窓の始まりで引くもので、回復は窓を持たない（同じフレームの窓の行に回復の順位が混ざる）。
- 画面（`apps/web/src/skillLabels.ts` の `formatInstantTarget`）: 「（最終攻撃力が最も高い味方 N 機）」。
- `skills/catalog.ts` の分類（`ally:topAttack` は語彙あり）は変えない。

- フォルクヴァンを含む編成で、回復を受けた時の効果を持つ味方（アスカの S1 など）の発動が変わる。含まない編成は変わらない（退化）。

## 5. テスト

- DSL（`skills/__tests__/`）: `heal` の `topAttack` が通り、`targetCount` / `targetCountRef` の両方・どちらも無しは落ちる。
- 時点（1 パス目）: 小さな編成で、(1) 回復の発火と同じフレームに付く攻撃力▲（`burstUse` の `timed`）は順位に入らない、(2) 前のフレームまでに付いた攻撃力▲は入る、(3) 回復を受けた時の▲で順位が上がる枠がいても、そのフレームの対象は変わらない（循環が閉じる）。
- 編成（録画 0710 の編成）: フォルクヴァンの各発動で回復がアスカとフォルクヴァンに届き、アスカの S1 の窓は発動から 25 秒（ゲーム内）で、吸収回復の窓の中で付き直さない。
- 退化: 既存のテストが数値を変えずに通る（フォルクヴァンを含む既存の編成のテストがあれば、変わる値を確かめて直す）。

## 6. 確定までの道（[verification-guide.md](verification-guide.md) 2.2 節）

C-0695 は仮説・単独実測（録画 0710 の 1 本）。根拠の観測値 `0710-07`〜`0710-09` は、モデルに吸収回復が無かったので比べない観測値（`use: record`）。

- 仮説（V-0517 の H1）は撮る前に説明文と C-0082 から立てたもので、録画 0710 で値を合わせていない。録画 0710 の 4 回のチェーンは、モデルに入れた後なら回ごとに比べられる。
- そこで撮り足しはせず、録画 0710 を読み直す（レシピ `buff-edge` の `pair` で、フォルクヴァンの各発動の後のアスカの S1 の付き始めと切れ目をモデルと比べる観測値を作り、結論の `runs` に回を書く）のが先。最小構成の検査（`npm run records:minimal`）で、ラム・I-DOLL・サンの未確定の要素がアスカの S1 の窓に効かないと出れば、1 本で反復実測の候補になる。警告が残るときだけ、撮影を計画する。
- 読み直しは、この PR の後の別の検証にする（新しい検証記録。この PR では C-0695 を仮説のまま、`model` だけを書き換える）。
- 比べる時点（2 節の A）と 2 機目は、確定にしても C-0695 の範囲の外のまま（効果の `assumes` に「確かめていない」と書く）。

## 7. 論点（推奨を先に書く）

1. **比べる時点**: A（回復の前の時点。そのフレームに付く窓を入れない）。代わりは B（同じフレームの窓を入れ、回復を受けた時の窓だけ外す）。根拠はどちらにも無く、対象が変わるのはシンデレラと組んで上位 2 機の境目が入れ替わるときだけで、それを見分ける最小構成も無い（3 節）ので、実装の小さい A。撮影はしない。
2. **確定までの道**: 撮り足しはせず、録画 0710 の読み直しを別の検証で行う（6 節）。この PR では C-0695 は仮説のまま。
3. **順位の記録**: 回復の順位は `rankings` に入れない（対象は `heals` に残る。4.1 節）。
