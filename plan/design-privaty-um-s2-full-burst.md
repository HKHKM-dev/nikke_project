## 2. 論点

### 2.1 論点 1: 「フルバーストタイムの持続時間中、ペレットが 30 回命中した時」の数え方

- 当たったペレットは `pelletHit`（`everyRef: 4`）で数える（S1 と同じ量。C-0408・C-0830）。フルバーストとの関係は、既存の語彙で 3 つの形が書ける。
  - **H1**: `firesDuring: "fullBurst"`。戦闘の始めからフルバーストの外も通して数え、30 の倍数に届いた発がフルバーストの中のときだけ付く。
  - **H2**: `during: "fullBurst"`・`reset: "fullBurstStart"`。フルバーストの中の命中だけを数え、フルバーストの始まりで 0 に戻す。
  - **H3**: `during: "fullBurst"`・`reset: "never"`。フルバーストの中の命中だけを数え、端数を次のフルバーストへ持ち越す。
- 先例: 同じ「フルバーストタイム持続中に〜回」の言い回しは、ソーダ：トゥインクルバニーの S1（C-0580）とミハラ：ボンディングチェーンの S2（C-0751）で、どちらも H1 だった（ミハラでは H2・H3 の形が合わなかった）。
- **推奨: H1 を予測の主にして、録画で H1〜H3 を見分ける**。H1 なら、フルバーストの中の付く発は S1 のヒット（同じ `pelletHit` の 30 回。戦闘の始めから数える）が出る発と同じになる。H2・H3 では、フルバーストの始まりの端数の分だけずれる。試作の定義で鈴原サクラ + デルタ + プリバティ：アンカインド・メイドを回すと、弾丸チャージの時刻は仮説の間で 1 発ぶん（約 0.7 秒）ずれる回がフルバーストごとにある（V-0875「予測」）。

### 2.2 論点 2: 弾丸チャージにフルバーストの窓を書けるようにする

- いまの `ammoRefill` のきっかけに書ける数える窓は、自分の状態の窓（`during: { state }`）だけ（`skills/parse/instant.ts` の `during: 'stateOnly'`）で、`during: "fullBurst"` も `firesDuring` も書けない。
- **案 A（推奨）**: `ammoRefill` に、timed と同じ窓（`during: "fullBurst"`＋`reset`、`firesDuring`）を許す（`parseTrigger` の `during` を `'withState'` にする）。射撃の回数のきっかけの発火は、即時効果でも timed と同じ追い手（`skills/triggers.ts` の `createTriggerTracker`）で決まり、窓の扱いはそこにある。試作で、弾丸チャージがフルバーストの中だけで起きることを確かめた。
- 案 B: 弾丸チャージを、状態（「フルバースト中」の名前つきの状態）の窓で数える形に書き換える。説明文に無い状態を作ることになり、H1 の形（窓の外も数える）は書けない。採らない。

### 2.3 論点 3: 攻撃力▲の 5 スタック・2 秒の付き直し

- モデルの既定は、発火のたびに 1 スタック足し、全スタックの維持時間を数え直す（`skills/stacks.ts` の `STACK_REFRESH` の `'all'`）。状態の付与には、スタックごとに独立の維持時間（`stackRefresh: "each"`）もある。
- 近の帯で的の胴体の中央を撃つと、1 発の当たったペレットは 8〜10 個（`0857-01`）で、30 回は約 3 発（発の間 約 39f で約 117f）ごと。2 秒（120f）とほぼ同じなので、`'all'` なら途切れずに 5 スタックまで積み、`'each'` なら 1〜2 スタックにとどまる。録画の通常攻撃の増分（1 スタックで 1.1122 倍、5 スタックで 1.561 倍）で見分けられる。
- **推奨: 既定（`'all'`）を予測の主にして、録画で見分ける**。`'each'` が合えば timed にも `stackRefresh` を書けるようにする変更が要るので、そのときは決定を足す。

### 2.4 「弾丸チャージ 1 発」

- 発数の弾丸チャージ `scaling: "flat"`（ルドミラ：ウィンターオーナーの S1。[design-ludmilla-wo.md](design-ludmilla-wo.md) 2.1 節）で書く。最大装弾数で止まる。
