## 0. 範囲

「〈状態〉が終了した時」のフレーム（持ち主のその状態の件が外れ、そのフレームを覆う件が無いフレーム）を判定するコードが 3 か所にある。食い違う入力を確かめ、判定を 1 つにまとめる形を決める。

- 判定の意味（どのフレームを終わりと見るか）は、いまの使い手の値を変えない範囲でだけ揃える。実機で確かめていない入力の見え方は決めない（AGENTS.md「根拠のない変更は行わない」）。

## 2. 確かめたこと

### 2.1 食い違い (2): 終わりのフレームに同じ状態を付け直す

合成した定義のテスト（`packages/core/src/skills/__tests__/stateEnded.test.ts`）で確かめた。完全計算（`prediction`）を 2 秒ごとに付け、持続を周期と同じフレーム数にして、件の終わりのフレーム f に次の付与を登録させる。付け直しは同じ件を延ばし、件は 1 つにつながる。

| 読み手                                            | f を終わりと見たか      |
| ------------------------------------------------- | ----------------------- |
| `{ stateEnd }` の窓（`registerEnds`。付与より前） | 見た（窓が f で閉じる） |
| 段 1 の付与のうち、付け直す付与より前に書いたもの | 見た（付く）            |
| 段 1 の付与のうち、付け直す付与より後に書いたもの | 見ない                  |
| `counterChange`（`registerCounters`）             | 見ない                  |
| `ammoDecrease`（即時効果）                        | 見ない                  |
| damage（2 パス目）                                | 見ない                  |
| 指標 `event: stateEnd`                            | 見ない                  |

- 課題のファイルの見立て（付与より前に読む手続きは終わりと見て、後に読む手続きと 2 パス目・指標は見ない）のとおりだった。段 1 の中でも、定義に書いた順で答えが変わる。
- 付け直しが前のフレームに登録された件（射撃の回数のきっかけの付与は次のフレームから付く、など）なら、どの読み手も終わりと見ない。食い違うのは、f に登録されて f から付く件だけ。

### 2.2 いまの使い手は (2) にも (1) にも当たらない

- 1 パス目に一時的な計装を入れ、全部の観測値を回して、`endedAt` の答えを、そのフレームの登録が済んだ後の件での答えと比べた。食い違いは 0 件。`endedAt` が読む状態で、件の終わりと次の件の始まりが同じフレームになる所も 0 件。計装はコミットしていない。
- `{ ended }` の使い手（グレイブ `prediction`・アスカ：WILLE `annihilationState`・ネオン：ビジョン・アイ `firepowerCharge`）と、指標 `event: stateEnd` の使い手（`drunken` だけ）は、どれも家族の根（`barrier`・`intoTheFray`）を指さない。

## 3. 案

### 案 A: 2 パス目と指標を 1 つの関数にする（推す）

- 出そろった件から終わりのフレームの列を出す関数を 1 つにし（`skills/holders/history.ts` に置く。家族も見る）、`frame/plan.ts` と指標の両方がこれを呼ぶ。指標は家族の根を指すと家族も見るようになる（いまの使い手は指さないので値は変わらない）。
- 1 パス目の `endedAt` は、フレームごとの真偽を登録の途中で答える形のまま残す。読む件の選び方（持ち主・`kind: 'state'`・家族）は、上の関数と同じ述語を使う。
- 1 パス目の読みが、そのフレームの登録が済んだ後の件での答えと食い違ったら記録に残し、2 パス目が枠の注記にする（4 節）。

### 案 B: 1 パス目が判定した終わりのフレームを記録に残し、2 パス目と指標がそれを読む

- 1 パス目の判定は、2.1 節のとおり 1 フレームの中で読み手ごとに答えが違うので、記録に残す前に「どの時点の答えを正とするか」を決める必要がある。
  - 登録が済んだ後の答えを正とするなら、記録は出そろった件から作るものと同じになり、案 A と結果が変わらない。そのうえで、前に読む手続き（`{ stateEnd }` の窓・段 1 の前の付与）を登録の後へ動かすことになる。
  - フレームの始まり（登録の前）の答えを正とするなら、2 パス目と指標の値が変わる。後に読む手続き（カウンタ・即時効果・段 1 の後の付与）も、フレームの始まりの答えを覚えて読むよう変える。
- どちらも、実機で確かめていない入力の見え方を決めることになる。2.2 節のとおり、いまの使い手はこの入力に当たらず、根拠になる録画が無い。
- 指標 `event: stateEnd` は `{ ended }` の読み手がいない状態（`drunken`）も見るので、1 パス目がすべての状態の終わりを記録するか、指標の状態を 1 パス目に渡すことになる。

## 4. 推す形の中身（案 A）

1. `skills/holders/history.ts` に、持ち主のその状態（家族も）の件か（述語）と、出そろった件から終わりのフレームの列を出す関数を置く。`frame/plan.ts` の `endedFramesOf` と指標の `stateEndFramesOf` を消し、この関数を呼ぶ。`conditions.ts` の `endedAt` は、件の列を集めるときに同じ述語を使う。
2. 1 パス目は、`endedAt` に聞かれた（持ち主・状態・フレーム）を覚え、そのフレームの登録の後にもう一度判定する。答えが変わっていたら記録に残す（`removeDebuffGuesses` と同じ形）。2 パス目（`sim/engine.ts`）は、その枠の注記（`approx`）にする: 「〈状態〉の終わりのフレームに同じ状態が付け直された時が N 回あった。終わりと見るかは確かめていないので、付け直しより前に読む効果は終わりと見て、後に読む効果とダメージは終わりと見なかった」。いまの使い手では出ない。
3. テスト: 2.1 節の編成で、読み手ごとの答えと注記が出ることを確かめる。2 パス目の関数と指標が家族の根で家族を見ること。いまの使い手の照合（`npm test` の照合のテスト）と残差が変わらないこと。

## 5. 論点（オーナーに決めてもらうこと）

1. 案 A と案 B のどちらにするか。推す: 案 A。案 B は、確かめていない 1 フレームの中の見え方を決めることになり、いまの使い手の値は変わらないので、得るものが範囲に見合わない。
2. (2) の入力が起きたときの扱い。推す: 注記で知らせる（4 節 2）。ほかの形は、何もしない（いまのまま）か、計算を止める（例外）。計算を止めると、画面で編成を組んだ利用者の計算が出なくなる。
3. 課題 2-69 は閉じる（消す）。(2) の見え方を録画で確かめる課題は起票しない。推す: 起票しない（いまの使い手が当たらず、撮る編成も無い。使い手が出たら、注記がそれを知らせる）。
