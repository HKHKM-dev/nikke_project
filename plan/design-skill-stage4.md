## 1. 語彙

### 1.1 `{ applied }` を `timed`・付与に開く

- **形**: `"trigger": { "applied": "<id>" }`（`damage` と同じ形）を、`timed` と状態の付与に書ける。
- **意味**: その状態が、この効果を持つ枠（自分）に付いたフレームに発火する。窓はそのフレームから。付いたフレームは付いた記録（履歴の `applications`）のフレームで、`damage` の `{ applied }` と同じ（[design-named-state.md](design-named-state.md) 5.4 節）。どの枠の付与で付いたかは問わない。付き直しも 1 回ずつ発火し、同じフレームに 2 つの出どころから付いても 1 回。スタック量の増加（`stackChange`）の記録も入る（いまの `appliedFrames` と同じ）。
- **段**: `{ applied }` の効果の段は、見る状態を付ける付与とスタック量の増加（編成のどの枠でも。`{ applied }` のものを除く）の段のいちばん後のもの（静的な状態だけなら段 1）。その段の登録の後に、そのフレームの手順 3 で付いた記録を読んで発火する（論点 3）。条件なしの付与で付く状態を見る効果は段 1 の件になり、同じフレームの段 1.5 の条件と段 2 の順位の材料に入る。いまの段の規則（条件と順位は、同じフレームに付いた件も入れる）と同じ見え方になる。
- **連鎖させない**: `{ applied }` の付与で付いた記録は、`timed`・付与の `{ applied }` を起こさない（1 段だけ。論点 4）。同じ定義の中で、`{ applied }` の付与が付ける状態をほかの `{ applied }` が見ることは、検証で落とす。編成の別の枠の定義をまたぐ連鎖は追わない（使い手がいない）。`damage` の `{ applied }` はいまのまま、どの付与の記録でも発火する（ダメージは記録を作らないので閉じる）。
- **書けない欄**: 条件（`condition`）、順位の対象（`topAttack`）、強化（`amplifies`）。どれも使い手がいないので、足す時にその段の規則を決める（論点 6）。付与は、自分の付ける状態を `{ applied }` で見ない（循環の禁止。[design-named-state.md](design-named-state.md) 8.5 節）。
- 発火の文脈（`burstUsers` など）は持たない。対象「直前にバーストスキルを使用した味方」は書けない（いまの検証のまま）。
- **calc の射撃の数え方**: 自分の射撃の回数で開く件を持つ枠は、calc が全グループを射撃の列から数える（[design-ludmilla-wo.md](design-ludmilla-wo.md) 2.5 節。`hasOwnShotCountItem`）。`{ applied }` の件は、出どころの枠の射撃の回数のきっかけで付いた記録（トーブの代用弾丸）から発火したとき、射撃の回数で開く件に数える（件の列の `shotCount`）。数えないと、窓の外の平均レートが発数を外し、sim と calc がずれる。

### 1.2 名前の付いた即時効果: 維持 0 秒の中身なし付与

- 「〈名前〉：弾丸チャージ X%」のように、名前の付いた効果の中身が即時効果のときは、段 1 の決まり（[design-skill-stage1.md](design-skill-stage1.md) 1.4 節）で、即時効果を別の効果（`ammoRefill`）で書き、付与は中身なしで足す。即時効果には維持が無いので、付与の維持を 0 秒（`durationSeconds: 0`）にする。件の窓は無く、付いた記録だけが残る。`{ applied }` と画面の付いた回数が、この記録を読む（論点 2）。
- 付与と即時効果は、同じトリガーで書く。即時効果は発のフレームに効き（`frame/firstPass.ts` の手順 3）、付与の記録は、射撃の回数のきっかけなら次のフレームになる（窓の始まりの規則。`skills/holders.ts` の `startOfFire`）。〈名前〉が適用される時の効果は、記録のフレーム（発の次のフレーム）から付く。射撃の回数のきっかけの効果が次のフレームから付く、いまの規則（例: C-0556）と同じ見え方になる。
- **検証**: 維持 0 秒の付与は、中身・スタックの上限・解除不可を書けない（持つものが無い）。

### 1.3 `{ ended }`（形だけ）

- **形**: `"trigger": { "ended": "<id>" }`。その状態の、この効果を持つ枠（自分）の件が外れたフレームに発火する。外れたフレームは件の終わり e で、e に同じ状態の件が続いていない（e に始まる件・e より後まで続く件が無い）とき。`fullBurstStart` に対する `fullBurstEnd` と同じ関係（[design-named-state.md](design-named-state.md) 8.1 節）。時間切れ・解除・消費のどれで外れても起きる。
- 件の終わりは、付き直し・解除・消費・発数の維持で後から変わるので、1 パス目では e の手順 3 の登録の後に、e で外れたかを決める。段・連鎖・書けない欄は `{ applied }` と同じ。
- 実装は、使い手を定義する PR で行う（0 節）。

### 2.2 撮影の結果と、弾丸チャージの直し（V-0435）

- 2026-10-17 の録画 467・468 で、弾丸チャージの発数が 3・3・4・4・…（30 発目から 4）になり、予測の H1〜H3 のどれとも合わなかった。会心の比（クリティカルダメージ▲）と、リロードの明けの最大装弾数 66（応急改造 3 スタック）は合った。数値と読み方は V-0435 の「結果」。
- 30 発目の 4 には、その時の最大装弾数 66 が要る。いまのモデルでは、30 発目の代用弾丸で付く 3 スタック目は付いた記録のフレーム（発の次のフレーム）からで、発のフレームの弾丸チャージは 64 で数える（四捨五入でも 3）。
- 直し（論点 7・8）:
  1. 弾丸チャージの端数は四捨五入にする（`frame/firstPass.ts` の `AMMO_REFILL_ROUNDING` の「仮」を外す）。切り捨ては最大装弾数 66 の時の 4 と、切り上げは 10 発目の 3 と合わない。
  2. 射撃の回数のきっかけの弾丸チャージは、同じ発のきっかけで付く件（次のフレームから付く件。`{ applied }` の付与で付くものも含む）を入れた最大装弾数で数える。残弾に足すのは、いまのまま発のフレーム（最後の弾丸と同じ発の弾丸チャージがリロードを取り消す規則（V-0163）も、いまのまま。録画でも、90 発目は残弾 0 から 4 発入って撃ち続けた）。
- 実装: `frame/firstPass.ts` の弾丸チャージで、射撃の回数のきっかけなら最大装弾数を f + 1 の件で読む（`paramsAt(target, f + 1)`）。f + 1 から付く件は、同じフレームの段の登録（`{ applied }` の発火を含む）で登録済み。窓の始まりの規則（次のフレームから）と、1 ヒットの値（10 発目には▲が乗らない。録画でも 10 発目の会心は▲なし）は変えない。
- 影響: 割合の弾丸チャージを射撃の回数のきっかけで持つ定義は、トーブの宝物版 S1 だけ（ルドミラ：ウィンターオーナーは発数の弾丸チャージで、最大装弾数を見ない）。フルバーストの時の弾丸チャージ（紅蓮：ブラックシャドウ・ノワール）は、四捨五入にした分だけ変わる（録画 19 のノワールは満タンに近く、どちらでも 14）。既存の観測値の残差は変わらない。

## 5. 論点

決定（2026-10-16）: オーナーの指示（段 3 の PR 3 を後にして段 4 に進む）で、論点 1〜6 を推奨どおりにして進めた。

1. **`{ applied }` の発火のフレーム**
   - 推奨: 付いた記録のフレーム（窓の始まりと同じフレーム）。`damage` のいまの規則と同じ。
   - 代わりの案: 記録の次のフレーム。トーブの撮影では見分けられない（2.1 節）。
2. **名前の付いた即時効果（代用弾丸）の書き方**
   - 推奨: 維持 0 秒の中身なし付与と、同じトリガーの即時効果（段 1 の 1.4 節の決まりのまま、維持だけ 0 秒）。適用される時の効果は `{ applied }` で書く。
   - 代わりの案: `{ applied }` を使わず、応急改造とクリティカルダメージ▲を代用弾丸と同じトリガーで書く（クイーン（真）の「1more が適用された時」を `burstUse` で書いた C-0310 と同じ）。値はどちらも同じだが、段 4 の語彙の使い手がいなくなる。
3. **`{ applied }` の効果の段**
   - 推奨: 見る状態を付ける付与・スタック量の増加の段のいちばん後。
   - 代わりの案: いつも段 2 の後（強化の前）に発火し、件は段 2 にする。簡単だが、件が条件・順位の材料に入らない（トーブの S2 のフルスタックの条件が応急改造を見られない）。
4. **連鎖**
   - 推奨: 1 段だけ。`{ applied }` の付与の記録は `{ applied }` を起こさない。同じ定義の中は検証で落とす。
   - 代わりの案: 同じフレームの中で記録が増えなくなるまで流す（効果ごとに 1 フレーム 1 回で止める）。使い手がいない。
5. **`{ ended }`**
   - 推奨: 形だけ決め、使い手を定義する PR で実装する。
   - 代わりの案: いま単体テストだけで入れる。確かめる使い手がいない。
6. **`{ applied }` に条件・順位の対象・強化を書くこと**
   - 推奨: いまは書けない（使い手がいない）。
   - 代わりの案: いまの段の規則（条件つきは段 1.5、順位は段 2）を当てて開く。

V-0435 の撮影の後（2026-10-17。2.2 節）。決定（2026-10-17）: 論点 7 は案 A、論点 8 は四捨五入（オーナーの決定）。

7. **30 発目の弾丸チャージが 4 になることの読み方**
   - 推奨（案 A）: 代用弾丸が適用される時の応急改造は、その代用弾丸の弾丸チャージより先に付く（説明文の「適用される時」のとおり、1 回の代用弾丸で 1 スタック）。モデルは、射撃の回数のきっかけの弾丸チャージを、同じ発のきっかけで付く件を入れた最大装弾数で数える（2.2 節の直しの 2）。
   - 代わりの案 B: 1 回の代用弾丸で応急改造が 2 スタック付き、弾丸チャージは付く前の最大装弾数で数える（10・20・30 発目の最大装弾数が 60・64・66 になり、弾丸チャージは A と同じ 3・3・4）。説明文と合わず、2 回付く仕組みの根拠が無い。
   - 代わりの案 C: 弾丸チャージを `{ applied: emergencyCraftedBullets }` で書き、付いた記録のフレームで応急改造の付与の後に数える。弾丸チャージが発の次のフレームになり、残弾 0 の発（90 発目）でリロードが先に始まる（録画では撃ち続けた）ので、リロードの取り消しの規則も変える要がある。
