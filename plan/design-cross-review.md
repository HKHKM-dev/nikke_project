# Claude Code と Antigravity の相互検証 設計書

- 何のための文書か: 一方のエージェントの成果物（設計書・コード・検証記録）を、もう一方のエージェントが見直すときの基本の決まりを決める。
- 関連: [AGENTS.md](../AGENTS.md)「併用ルール」「コミット手順」「事実と記録」、[design-review-steps.md](design-review-steps.md)（PR の前の見直しの段）、[design-stage20-reviews.md](design-stage20-reviews.md) 8・9・11 節（Antigravity のレビューを受けた例）
- 作成日: 2026-11-28
- 状態: 承認（4 節）

## 1. 目的

- 同じエージェントが書いて同じエージェントが見直すと、同じ思い込みを見落としやすい。別のエージェントの目を入れて、設計・コード・結論の誤りを早く見つける。
- 受け取った指摘の扱いを、どちらのエージェントも同じ手順で行えるようにする。いまは手順が Claude Code のメモリにだけあり、Antigravity からは読めない（AGENTS.md「記録の置き場所」の方針に合わない）。

## 2. いまの形

- **Antigravity から Claude Code へ**: これまでに受けたのは、設計書のレビュー（Stage 20 の 3 回）と提案書（レイヴン S1、スキルの目録）。どれもオーナーが頼み、本文はリポジトリの外にあり、オーナーが Claude Code に渡した。ツールの名の無い外部のレビュー（[design-named-state-reviews.md](design-named-state-reviews.md) 9・10 節）も、同じ形で受けた。
- **受けた側の扱い**: Claude Code は指摘を 1 件ずつコード・データ・記録と照らして確かめ、判断を設計書の節に残した。Stage 20 の別紙 8 節の形（指摘ごとに「確かめたこと・判断・反映先」）が典型。確かめると、件数の前提が当たらない指摘（同 8 節の 1）や、指摘の見立てとは別の危険（同 11 節の 2）が見つかり、同じ観点で自分でも 1 点見つけた（同 9 節の末尾）。
- この扱いは、Claude Code のメモリ（「指摘は検証してから取り入れる」）にだけ書いてある。リポジトリの決まりには無い。
- **Claude Code から Antigravity へ**: Antigravity の成果物を Claude Code が見直した例は、上の提案書の判断のほかに無い。origin と main の履歴に `antigrav/` のブランチ・commit は無い（[design-workflow-simplification-19.md](design-workflow-simplification-19.md) 4 節）。
- **PR の前の見直し**: AGENTS.md「コミット手順」の整理とバグの 2 段は、Claude Code が自分の差分を自分の道具（`/simplify`・`/code-review`）で見る。別のエージェントの目は入らない。
- AGENTS.md「併用ルール」は、作業ツリー・ブランチ名・worktree の場所だけを決めている。

## 3. 論点

### 3.1 基本の決まり

次の 8 つを、両エージェントが守る決まりにする。

**頼む側**（見直しの依頼の文面を書くエージェント。依頼を渡すのはオーナー）

1. 未マージの対象は push してから渡す。ファイルのパスだけでなく、ブランチ名（PR があれば番号）を添える。commit のハッシュは、フックのリベースと強制 push で変わるので、添えるならブランチ名と併せる。
2. 依頼の文面で結論を誘導しない。「案 A で問題ないか」ではなく、対象と、確かめたい問い・観点を渡す。設計書に書いた推奨はそのままでよい（推奨も見直しの対象になる）。

**見る側**

3. 最新の origin/main と対象のブランチを基準に、一次資料（コード・データ・結論）と照らして指摘する。確かめた根拠と、確かめていない推測を分けて書く。

**受け取った側**

4. 指摘は 1 件ずつ、関係するコード・データ・記録と照らして確かめる。採る・一部採る・採らないを決め、採らないときは理由を書く。根拠を確かめられない指摘は採らない（AGENTS.md「事実と記録」の「根拠のない変更は行わない」）。
5. 確定の結論・凍結の記録・AGENTS.md と食い違う指摘は、採る前にオーナーに確かめる（AGENTS.md「事実と記録」と同じ）。
6. 判断は指摘ごとに「確かめたこと・判断・反映先」の 3 つで残す（置き場所は 3.3 節）。

**分かれたとき・時期**

7. 同じ論点で 1 往復（指摘 → 判断 → 再指摘）しても合意できないときは、両方の言い分と推奨をそろえてオーナーに上げる。
8. コードの見直しを頼むときは、PR の前の見直し（`/simplify`・`/code-review`）を始める前に頼む。始めた後は、自動マージの予約まで止めずに進める決まりなので（AGENTS.md「コミット手順」、[design-review-steps.md](design-review-steps.md) 3 節）、間に受け渡しを挟めない。設計なら起案の後、承認の前に頼む。

推奨: 8 つとも入れる。4〜6 はこれまでの扱いを書き起こしたもの、1〜3・7・8 は受け渡しで詰まった点（7 節の 1・3）を防ぐもので、手間はほとんど増えない。

### 3.2 いつ相互検証をするか

| 案  | 中身                                                                                                                                                                                    |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A   | オーナーが頼んだときだけ。頼む価値の高い場面を目安として挙げる（Stage 規模の設計書、確定の結論を棄却・訂正する変更、`packages/core/src/frame/`・`packages/core/src/sim/` の機構の変更） |
| B   | A の目安の場面では必ず行う。終わるまで PR を出さない                                                                                                                                    |
| C   | すべての PR で行う                                                                                                                                                                      |

推奨: 案 A。

- 受け渡しはいまオーナーが手で行っている（2 節）。B・C にすると、オーナーが受け渡すまで PR が止まり、「見直しから自動マージの予約まで止めずに進める」決まり（AGENTS.md「コミット手順」、[design-review-steps.md](design-review-steps.md) 3 節）とぶつかる。
- これまでの例（2 節）はどれもオーナーが頼んだもので、それで働いていた。
- C は、業務の簡素化（見直しの段を絞った [design-review-steps.md](design-review-steps.md) 2 節）と逆の向きになる。

### 3.3 指摘と判断の置き場所

| 案  | 中身                                                                                                                                                                                                                                                                   |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A   | 指摘の本文はリポジトリの外のまま。判断は、対象の設計書に節（「起案後のレビュー（日付、<見た側>）」。見た側は `Antigravity` か `Claude Code`）として残す。設計書の無い検証記録の見直しは、その検証記録に同じ形の節を足す。設計書の無いコードの見直しは、PR の本文に残す |
| B   | 指摘の本文もリポジトリに入れる（`records/reviews/` に 1 件 1 ファイル、ID を振る）                                                                                                                                                                                     |
| C   | PR のコメントでやりとりする                                                                                                                                                                                                                                            |

推奨: 案 A。

- これまでの形と同じで、道具を足さずに済む。判断の節に指摘の要点が残るので、本文が無くても後から追える。
- B は、新しい記録の型（ID・生成・検査）が要る。リポジトリは公開なので、外の本文をそのまま入れると、書いてはいけないこと（オーナーの所持など）が混ざるおそれもある。
- C は、判断がリポジトリの外（PR のコメント）に散り、設計書や検証記録から追いにくい。設計の見直しは PR を出す前に行うので（3.1 節の 8）、コメントを書く PR もまだ無い。

あわせて、判断の節を設計書を縮めるとき（[design-design-doc-trim.md](design-design-doc-trim.md) 3 節）にどう扱うかを決める。採った指摘は、反映先の決定と理由に要点が入っていれば、判断の節から消してよい（git の履歴で引ける）。採らなかった指摘とその理由は「採らない案とその理由」に当たるので残す。

### 3.4 決まりを書く場所

| 案  | 中身                                                                                                                                                           |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A   | AGENTS.md「併用ルール」に、3.1 節の 8 つと 3.2・3.3 節の決定を数行で足す。Claude Code のメモリの「指摘は検証してから取り入れる」は、AGENTS.md を指すだけにする |
| B   | 手引き（`plan/cross-review-guide.md`）を新しく作り、AGENTS.md からは 1 行で指す                                                                                |

推奨: 案 A。決まりは 10 行ほどで収まり、別の文書を作るほどではない。両エージェントが毎回読む AGENTS.md に置けば、読み落としが無い。

### 3.5 Antigravity の PR

Antigravity は、レビューと提案書のほかに、`antigrav/` のブランチでコードや記録を書き、PR を出す（オーナーの答え）。AGENTS.md「コミット手順」の PR の前の見直し（整理とバグの 2 段）は、Claude Code の道具（`/simplify`・`/code-review`）とフックで書いてあるので、Antigravity の PR での扱いを決める。

| 案  | 中身                                                                                                                                      |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| A   | Antigravity も、同じ 2 段を自分の道具で行う。Claude Code の目を入れるのは、Claude Code の PR と同じく、オーナーが頼んだときだけ（3.2 節） |
| B   | `antigrav/` の PR は、必ず Claude Code のバグの段を通す（オーナーが受け渡す）                                                             |
| C   | A に加えて、`packages/core/src/frame/`・`packages/core/src/sim/`・`tools/git/` を変えた PR だけ、Claude Code のバグの段を通す             |

推奨: 案 A。3.2 節の案 A と向きをそろえる。B・C は、オーナーの受け渡しを待つ間 PR が止まり、自動マージの予約まで止めずに進める決まりとぶつかる。

Antigravity は、PR の手順（`pr:prep` → PR → 自動マージの予約）を自分で最後まで行う（オーナーの答え）。見直しから自動マージの予約まで止めずに進める決まりも同じく当てはまる。Antigravity には、それを止めるフックが無い。

## 4. 決定（2026-11-28、オーナー）

1. 3.1 節の 8 つの決まりを、すべて入れる。
2. いつ相互検証をするか: 案 A（オーナーが頼んだときだけ。目安の場面を挙げる）。
3. 指摘と判断の置き場所: 案 A（判断を対象の設計書・検証記録の節か、PR の本文に残す。採った指摘の判断は、設計書を縮めるときに消してよい）。
4. 決まりを書く場所: 案 A（AGENTS.md「併用ルール」に足す。Claude Code のメモリは AGENTS.md を指すだけにする）。
5. Antigravity の PR の前の見直し: 3.5 節の案 A（Antigravity も同じ 2 段を自分の道具で行う）。AGENTS.md「コミット手順」の 2 段の書き方を、Antigravity にも当てはまる形にする。

## 5. 採らない案

- **検証記録の読み取りを、もう一方のエージェントが独立に読み直す**: 録画から値を読む誤りには効くが、1 件ごとに読み取りの手間が倍になる。全件で手間を倍にするほどの効果は見込めない。疑わしい記録（残差がはねたもの・読み方に迷ったもの）は、3.2 節の案 A のとおりオーナーが個別に読み直しを頼める。

  - 判断: 取り入れる。commit のハッシュは変わりうるので、ブランチ名と併せて渡すことも足す
  - 反映先: 3.1 節の 1・3
- **2. 「推奨を先に渡さない」が、推奨を書く設計書の形と食い違う**

  - 判断: 取り入れる。決まりを「依頼の文面で結論を誘導しない」に改め、依頼の文面を書く側の決まりと分かる形にした

  - 判断: 取り入れる
  - 反映先: 3.1 節の 8

  - 反映先: 3.3 節
