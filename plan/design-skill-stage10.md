## 2. 語彙

### 2.1 値 × 数（`perCount`）

- **形**: 効果の値の欄に `"perCount": { "state": "<id>" }`（状態のスタック数）か `"perCount": { "counter": "<id>" }`（カウンタの値。PR 2）。値 = ref の値 × 数。
- **読む時刻**: 発火のフレームの、効果を出した枠（自分）の数（段 1 の件。条件の `selfState` が見るものと同じ）。維持のある効果（`timed`・状態の中身）は、付いた時の数で維持の間は固定する（説明文の「コピー」の読み。トーブで確かめる。PR 3）。数が 0 の時は効果を出さない（説明文の「〈名前〉をスタックしている場合」「火力ゲージがある状態なら」は、条件 `selfState`・カウンタの条件でも書く。値 0 の件を作らない）。
- **書ける効果**: PR 1 は `burstDamage`・`damage`（即時のダメージ）、PR 2 は `timed`（バーストゲージのチャージ速度▲）、PR 3 は状態の中身（`contents`）。使い手のいない組み合わせは書けないようにする。
- **説明文の言い回し**: 「〈名前〉スタックコピー」「X% × 〈名前〉のスタック数」「X% × 〈カウンタ〉のチャージ量」。コピーの読みが「数倍の 1 ヒット」か「数だけのヒット」かは、シンデレラの録画で決める（3.1 節の H1・H2）。
- 段 3 の 1.4 節（スタック数の条件）と同じ件を読むので、段は 1.5（条件つきの件と同じ）。
- 画面: 効果の出どころに「（× 美しさのスタック数）」のように出す。
- **PR 2 の実装で決めたこと（2026-10-26）**: フルバーストの終わりの「バーストゲージのチャージ速度 X% × 火力ゲージのチャージ量▲」は、`timed` の `perCount: { counter }` ではなく、状態の付与の `stacksFrom: { counter }`（1 回の発火で付けるスタックの数をカウンタの値にする）で書いた。ゲーム自身が、火力ゲージの値をスタック数にした「超火力チャージ」（1 スタックが 5%）として付けていた（V-0503 の一時停止画面。C-0666）。スタックの状態の件と読み方（段ごとに値を足す）をそのまま使え、件の値を発火ごとに変える仕掛けが要らない。`perCount` は damage の状態のスタック数のまま（PR 1）。

### 2.2 順番の攻撃（`burstDamage` の `hitDelays`）

- 「ランダムな敵に 最終攻撃力の X% のダメージ」「N 回順番に攻撃」。敵 1 体の前提では、N 回のヒットがすべてその敵に当たる（`assumes` に書く）。
- **形**: `burstDamage` に `hitDelays?: number[]`（バーストの発動からの各ヒットの遅れ。フレーム。昇順。長さ N）。段の `gaugeHits`（`DamageEffect`）と同じ流儀で、遅れは録画で読む即値。省略はいままでどおり 1 ヒット。
- **実装で決めたこと（2026-10-26）**: ヒットの遅れの列は、定義の欄ではなく、既存の分かれたヒットの表（`burst/landing.ts` の `MEASURED_BURST_DELAYS` の `hitFrames`・`hitOffsets`。[design-burst-split-hits.md](design-burst-split-hits.md)）に置いた。キャラごとの実測の遅れはこの表に置く決まりで、ラピ・ミハラの分かれたヒットと同じ所になる。表は 1 回の発動の倍率をヒットの数で等分するので、`burstDamage` には回数の欄 `hitsRef`（回数の description_value。倍率を回数倍にする）だけを足した。回数と表のヒットの数がそろうことはテストで確かめる。論点 4 の決定（遅れの列で書き、自動攻撃にしない）の中身は変えていない。
- 自動攻撃（`autoAttack`。周期と維持で書く）にしないのは、ヒットの間が等間隔かが分からず、回数が説明文で決まっているため（論点 4）。録画で等間隔と分かっても、回数で書く形のほうが説明文に近い。
- ヒットがバーストゲージを溜めるかは、いまのバーストスキルダメージと同じ扱い（溜めない）にし、録画のゲージで食い違えば直す。

### 2.3 キャラ固有のカウンタ（PR 2。論点 2）

カウンタは、「火力ゲージ 100 チャージ」「火力ゲージ 100 消費」のように、上限と増減を持ち、時間では外れず、値が「X% × チャージ量」のように数で決まる（分類の別紙 4.2 節）。スタックの状態で書くか、別の語彙にするかが論点 2。

- **推奨: 別の語彙（カウンタ）にする**。スタックの状態と次の所が違い、スタックの状態に寄せると例外の印が増える:
  - 0 まで減る。スタック量の減少は最後の 1 段を残す（段 3 の 1.5 節。V-0437）が、火力ゲージの消費は 0 にする。
  - 付与なしで始まる。スタックの状態は付与（`kind: 'state'`）が上限と維持を決め、スタック量の増減はその付与に足す。火力ゲージは付与の行が無く、戦闘開始時のチャージだけがある。
  - 1 回の増減が大きく、上限も大きい（火力ゲージは 0〜100）。スタックの状態は段ごとに件を持つので、段の数が増えると件の列も増える。
  - 時間で外れない（維持の秒が無い）。
  - 定義の無い使い手には、値の到達で別の出来事を起こすもの（オーバーエネルギーの段階増加・廃品の自家製弾倉への変換）があり、スタックの「フルスタックでスタック解除後」とは形が違う。
- **形（推奨の案）**:
  - 目録: カウンタの id と上限（`skills/states.ts` の目録に `counter` の区分で置くか、別の目録にするかは実装で決める）。最初の値は 0。
  - 操作: `kind: "counterChange"`（`counter`・`amount` か `amountRef`・`decrease`・`trigger`・`condition`）。足した結果は上限で切り、減らした結果は 0 で切る（上限で切るかは撮影で確かめる。3.2 節の H1・H2）。
  - 条件: `condition.selfCounter: { "counter": "<id>", "atLeast": N }` か `{ "counter": "<id>", "below": N }`（「100 の場合」は上限なら `atLeast: 100`、「100 未満」は `below: 100`、「ゲージがある状態なら」は `atLeast: 1`）。
  - 値: 2.1 節の `perCount: { "counter": "<id>" }`。
- **時刻の規則（見込み）**: カウンタは 1 パス目のフレームのループで持ち（射手・ゲージと同じ）、条件はフレーム f − 1 の終わりの値を読み、フレーム f の増減は f のすべての条件を見た後に足す。同じバーストの 2 つの行（「100 未満なら火力チャージと 1 チャージ」「100 なら超火力と 100 消費」）は、どちらも発動の前の値を見る（1 チャージで 100 に届いても、同じ発動で超火力にはならない）。
- **循環**: 火力チャージの付与は火力ゲージを見て、火力ゲージは火力チャージの間の通常攻撃と火力チャージの終わりで増える。時間をまたぐ循環で、同じフレームの中では閉じている（上の時刻の規則）。[design-named-state.md](design-named-state.md) 8.5 節の禁止（付与が自分の付ける状態を見る）には当たらない（付与が見るのはカウンタ）。検証では、カウンタの増減が自分を条件にする行（カウンタを見てカウンタを変える）だけを、同じフレームの値を見ないことで許す。
- **代わりの案: スタックの状態で書く**。火力ゲージを「持続」・上限 100 の状態にし、戦闘開始時の付与（N スタックで付ける形を足す）・スタック量の増減・消費（減少に「0 まで」の印を足す）・スタック数の条件（段 3 の 1.4 節）で書く。条件・`while`・画面の状態の表示がそのまま使える。違いは上の点の印（N スタックの付与・0 までの減少・維持なし）で吸収する。

- **PR 2 の実装で決めたこと（2026-10-26）**: 推奨の案（別の語彙）で入れた。目録は `skills/counters.ts`（id と上限。状態の目録とは別のファイル）、増減は `counterChange`（きっかけは parseTrigger のものと { ended }。条件は selfState・selfCounter）、条件は `selfCounter`（atLeast・below）。`skills/holders.ts` が 1 パス目のループでカウンタの値を持ち、条件は前のフレームの終わりの値を見て、増減はそのフレームのすべての判定（強化の受け付けを含む）の後に足す（時刻の規則のとおり）。カウンタの増減の条件 selfState は、段によらずそのフレームに効いている状態の件を見る（増減がすべての判定の後なので連鎖しない）。履歴に値の変わった記録（`counters`）を残し、比べる指標（`counterAtBursts`）が読む。
- **画面の火力ゲージの減り方**（V-0503）: 超火力の間、画面の火力ゲージは約 10 秒かけて同じ速さで 0 まで減り、フルバーストの終わりより前に 0 になる。ゲージを読むのはバーストの使用（次の回）とフルバーストの終わりだけで、どちらの時も 0 なので、モデルは使った時に 100 減らす（説明文の「100 消費」のまま）。

### 2.4 `{ ended }`（PR 2）

- 形は段 4 の 1.3 節のまま（`"trigger": { "ended": "<id>" }`。その状態の、この効果を持つ枠の件が外れたフレームに発火する）。PR 2 で実装する（`counterChange` のきっかけとして。ほかの効果に開くのは使い手がいる時）。
- 火力チャージは「解除不可」（効果解除で外れない）で、10 秒の時間切れで外れる。外れたフレームに火力ゲージを足す（S2 の「火力チャージ状態が終了した時」）。外れたフレームちょうどか次のフレームかは、録画では見分けにくい（フレームの差がダメージに効かない）ので、段 4 の 1.3 節の見込みのまま入れる。

## 6. 論点

決定（2026-10-26、オーナー）: 論点 1〜6 は推奨どおり。論点の文は諮った時のまま。

1. **段 10 の対象**（0.3 節）（決定: 推奨どおり）
   - 推奨: 「数で決まる値」（スタックのコピーとキャラ固有のカウンタ）。定義のある使い手がいちばん多く、「値 × 数」の 1 つの読み方で両方が書け、最初の PR が既存の録画で確かめられる。
   - 代わりの案: バースト段階の変更（ラピ：レッドフード）。1 体で未対応の notes がいちばん多いキャラが片付くが、語彙の重なり（粘着榴弾・発射体付着ダメージ・有利コードの適用）が多く、撮影も戦闘補助の有無の 2 編成が要る。
2. **カウンタの書き方**（2.3 節）（決定: 推奨どおり）
   - 推奨: 別の語彙（カウンタ。`counterChange`・`selfCounter`・`perCount: { counter }`）。0 まで減る・付与なしで始まる・増減が大きい・時間で外れない、がスタックの状態と違う。値の読み（× 数）はスタックと共通にする。
   - 代わりの案: スタックの状態で書く（N スタックの付与・0 までの減少・維持なしの印を足す）。条件・`while`・画面の状態の表示がそのまま使える。
3. **PR 1 を既存の録画の読み直しにするか**（3.1 節）（決定: 推奨どおり）
   - 推奨: する。0480 で読み方を決め、0481 で再現を見る。撮影を待たずに値 × 数と順番の攻撃を入れられる。
   - 代わりの案: シンデレラのバーストも新しく撮る（ヒットの時刻を一時停止やスロー再生で見やすくする撮り方）。
4. **順番の攻撃の形**（2.2 節）（決定: 推奨どおり）
   - 推奨: `burstDamage` にヒットの遅れの列（`hitDelays`）を足す。回数が説明文で決まり、間が等間隔でなくても書ける。
   - 代わりの案: 自動攻撃（`autoAttack`。間隔と維持）で書く。等間隔なら今の語彙のまま書ける。
5. **トーブのバースト（PR 3）を段 10 に入れるか**（3.3 節）（決定: 推奨どおり）
   - 推奨: 入れる。維持のある効果での値 × 数（付いた時の数で固定か）を確かめる、コピーの 2 体目になる。
   - 代わりの案: 段 10 は PR 1・2 で閉じ、トーブのバーストは段の外で 1 体ずつ足す（[design-skill-stages.md](design-skill-stages.md) 3 節の 1 点目と同じ扱い）。
6. **PR の順**（1 節）（決定: 推奨どおり）
   - 推奨: PR 1 → PR 2 → PR 3（PR 1 は撮影を待たない。PR 2 は語彙が大きく、撮影の計画も大きい）。
   - 代わりの案: PR 2 を先にする（カウンタの語彙を先に決め、値 × 数をその上で書く）。
