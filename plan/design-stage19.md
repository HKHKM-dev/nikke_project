これからは、種類の違う検証を何度も繰り返すことになる。いまの記録は Stage ごとに時系列で書き足す形で、検証が 18 Stage・録画 63 本までは回ってきた。ただ、2026-09-26 の業務フローの見直しで、**回数と種類が増えると詰まる所**が見えた（0.2 節）。

1. **録画**: 誰を・どの条件で撮ったか
2. **観測値**: 録画から読んだ値
3. **結論**: 観測値から言えること

### 0.2 回数と種類が増えると詰まる所

1. **結論を問いから引けない。** 記録の単位が Stage（時系列）なので、同じ問いの記述が散る。例: 「エーテルは FB 中に敵の防御力を下げる」は、設計書 2 冊・verification.md・台帳の 4 か所にある。訂正（距離ボーナスは射撃場の初期位置では AR・SMG だけ、FB は 4 回ではなく 5 回など）は後から追記しているので、**いまの結論を知るには関係する節をすべて読むしかない**。
2. **モデルとの照合が Stage ごとの手書き。** 実測値と許容幅を、Stage ごとのテストに直に書いている。モデルを変えたとき、**過去の全録画に対して予測がどう動いたかを一覧で見る方法がない**。残差の一覧は Stage 12 で予定したまま、まだ作っていない。新しい種類の検証のたびに、専用のテストを書くことになる。
3. **台帳が散文の表。** 「用途」列に結果まで書いていて、verification.md と重なる。機械では読めず、条件（スペック固定・操作枠・3 分モード・的の属性）で絞り込めない。
4. **読み取りの道具が残らない。** HUD の総ダメージの全フレーム OCR（Stage 11 モダニア・17・18 で使用）や区間の集計は、セッションの一時フォルダに書いて消えている。**同じ読み方をしても同じ値が出る保証がない**。
5. **番号と名前。** 連番は 2 桁で、5 日で 63 本まで来た。規約は「その日の撮影順」だが、実態は通し番号。旧プロジェクトの録画は別の名前（AD・AI など）で呼んでいる。ファイル名に編成をすべて入れていて長く、2026-09-26 には Windows のパス長の上限でチェックアウトが失敗した。
6. **読む量。** 設計書は、後から実装と実測の記録を足していくので 400〜670 行になる。エージェントが全部を読まずに書くほど、重複と食い違いが増える。

## 1. 何を決めるか

- 新しい種類の検証を足すとき、**決まった場所に決まった形で足せば**、全録画の照合と結論の一覧が更新されること。
- 結論を、問い（機構・定数）から 1 か所で引けること。結論が訂正されても、古い結論と根拠を追えること。
- Claude Code と Antigravity が、同じ手順で読み書きできること。

## 2. 構造の案

### 2.1 3 層に分ける

```
録画（recordings）     1 本 = 1 件。条件と置き場所。結果は書かない
  └ 観測値（observations）  録画の区間から読んだ値。読み方（ツールと引数）と証拠フレームを持つ
       └ 結論（claims）     観測値から言えること。状態（確定・仮説・棄却・範囲外）とモデル側の対応を持つ
```

- 機械が読むもの（録画・観測値）は JSON、人が読むもの（結論）は Markdown の表にする。
- 置き場所は、リポジトリ直下の `records/`（録画・観測値）と `plan/claims.md`（結論）。どちらも公開してよい中身だけにする（画像・プレイヤー名は入れない）。

### 2.2 録画（`records/recordings.json`）

台帳の表の機械が読む部分を、ここへ移す。

```json
{
  "id": "063",
  "file": "20260926-63_RL+SR+AR_idoll-flower+delta+asuka.mp4",
  "kind": "range",
  "sha256": "122c6f2204ad",
  "date": "2026-09-26",
  "mode": "range-3min",
  "fixedSpec": true,
  "target": { "name": "BigArms", "element": "Fire" },
  "team": [
    { "slot": 1, "rid": 304, "controlled": false },
    { "slot": 2, "rid": 20, "controlled": false },
    { "slot": 3, "rid": 830, "controlled": true }
  ],
  "autoBurst": true,
  "notes": "18-B。アスカのバースト（命中率▲）"
}
```

- 旧プロジェクトの録画も、`id: "L-AD"` のように登録する（置き場所は旧のまま）。
- 台帳（`index.md`）の表は、このファイルから生成して埋め込む。撮影プロトコルなどの散文は index.md に残す。

### 2.3 観測値（`records/observations/<録画 id>.json`）

```json
{
  "id": "063-01",
  "recording": "063",
  "kind": "total",
  "subject": { "slot": 3 },
  "range": { "from": 0, "to": 10800 },
  "value": 137577675,
  "method": { "tool": "probe-result.ts", "note": "戦闘履歴のパネル" },
  "evidence": ["frames/20260926-63_RL+SR+AR_idoll-flower+delta+asuka_f12090_panel.jpg"],
  "compare": { "model": "sim", "tolerance": 0.02 }
}
```

- `kind` の語彙を決めて、足すときは一覧に足してから使う（台帳の種別と同じ運用）。

  | kind       | 読むもの                                    |
  | ---------- | ------------------------------------------- |
  | `hit`      | 1 ヒットの値と種類（コア・会心・距離）      |
  | `interval` | 射撃の間隔・リロード                        |
  | `count`    | FB の回数、発動回数など                     |
  | `timing`   | 出来事の時刻（満タン、FB の開始、的の停止） |
  | `total`    | 区間や戦闘の合計ダメージ                    |
  | `rate`     | コア命中率・弾丸命中率など                  |

- `compare` がある観測値は、照合ランナー（2.5 節）がモデルと比べる。多人数の録画は、合計・比・ばらつきといった事実だけを持たせる（AGENTS.md の規則どおり）。

### 2.4 結論（`plan/claims.md`）

| 列       | 中身                                           |
| -------- | ---------------------------------------------- |
| ID       | `C-0001` から通し番号。変えない                |
| 結論     | 1〜2 文                                        |
| 状態     | 確定・仮説・棄却・範囲外                       |
| 根拠     | 観測値の ID と、verification.md の節           |
| モデル側 | 定数名・コードの場所（無ければ「未実装」）     |
| 置き換え | 訂正で置き換えた結論の ID（例: FB 回数 4 → 5） |
| 更新日   | —                                              |

- 訂正は、古い結論を消さずに状態を「棄却」にし、新しい結論に置き換え先を書く。
- 「較正した定数」の表の 18 行を起点に作る。verification.md の既存の記述は書き直さず、節から結論の ID を引けるようにする。

### 2.5 照合ランナーと残差の一覧

- `npm run records:check` で、`compare` のある観測値すべてについて録画の条件から編成を組み、sim（と calc）の予測と比べる。
- 結果は `plan/residuals.md` に生成する（手で書かない）。1 行が 1 観測値で、予測・実測・差・許容幅・判定・関係する結論を並べる。
- テスト（`vitest`）では、**状態が「確定」の結論にひもづく観測値だけ**を、許容幅の外なら落とす。仮説や範囲外のものは残差の一覧に出すだけにする。
- 既存の Stage ごとのテストは消さない。新しい検証から照合ランナーに載せ、既存のものは触ったときに移す。

### 2.6 番号と名前

- 録画の番号は、次から **3 桁の通し番号（064〜）** にする。規約の文面も「通し番号」に直す。
- ファイル名から編成を外す（`<YYYYMMDD>-<番号>_<種別>_<短い識別子>.mp4`）。編成は `recordings.json` に持たせる。
- 証拠フレームの名前は `<番号>_f<フレーム>_<内容>.jpg` にする。既存の録画とフレームは改名しない（Drive 側に旧名が残る問題を避ける）。

### 2.7 読み取りの道具

- **2 回使った読み方は `tools/captures/` に上げる**。観測値の `method` に、ツールの名前と引数を残す。
- 最初に上げるのは、HUD の総ダメージの全フレーム OCR（Stage 11 モダニア・17・18 で使った読み方）。

## 5. やらないこと

- モデルの変更。残差の一覧で見つかった差は、別の Stage で扱う。

- 既存の録画・証拠フレームの改名、撮り直し。
- 乱数と分布（16-C、凍結中）。

## 6. 決めてほしいこと

1. **3 層（録画・観測値・結論）に分けるか** — 推奨: **分ける**（2.1 節）。
2. **置き場所と形式** — 推奨: **録画・観測値は `records/` の JSON、結論は `plan/claims.md` の Markdown の表**。別案は、すべて Markdown（機械で読みにくい）か、すべて JSON（人が読みにくい）。
3. **照合で落とす範囲** — 推奨: **「確定」の結論にひもづく観測値だけをテストで落とし、他は残差の一覧に出すだけ**（2.5 節）。
4. **既存の Stage テストの扱い** — 推奨: **消さない。新しい検証から照合ランナーに載せ、既存は触ったときに移す**。別案は 19-B で全部移す案で、確かだが手間が大きい。
5. **台帳の表** — 推奨: **`recordings.json` から生成して index.md に埋め込む**。別案は、表の列を短く絞って手書きを続ける案。
6. **番号と命名** — 推奨: **次から 3 桁の通し番号（064〜）、ファイル名から編成を外す、既存は改名しない**（2.6 節）。
7. **結論と verification.md の関係** — 推奨: **verification.md は根拠の記録（追記のみ）、結論の状態は `claims.md` で管理する。訂正は claims の状態を変え、verification.md に訂正の節を足す**。
8. **PR の分け方** — 推奨: **19-A〜D の 4 つ**（3 節）。19-A と 19-B だけでも、全録画の照合と残差の一覧はそろう。
