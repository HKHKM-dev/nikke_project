## Context

Stage 11 は、実戦で使う主力キャラを **1 体ずつ**（1 体 1 PR）、そのキャラに要る語彙と専用の撮影で正確にする Stage。順番はユーザー指定のリター → クラウン → アリスで、リターは Stage 10 で完成したので **クラウン（330）から**始める。

クラウンは「現環境最強のバッファー」で、効果の大半はいまの語彙で書ける（攻撃ダメージ▲・リロード速度▲・発動者基準の攻撃力▲）。書けないのは次の 2 つだけ。

1. **対象「直前にバーストスキルを使用した味方」**（S1）。いまの対象は「自分」「味方全体（武器種で絞れる）」の 2 つで、**どの枠に掛かるかは効果ごとに固定**。クラウンの S1 は発火のたびに対象が変わる（III が 2 体いれば交互に入れ替わる）。
2. **トリガー「回復効果が適用された時」**（S2）。クラウンは通常攻撃 43 回ごとにリラックスを 1 スタック溜め、20 スタックで解除して自分を回復し、その回復をきっかけに味方全体へ攻撃ダメージ▲を配る。「回復」という出来事がいまのモデルに無い。

**設計の芯は「対象を発火のたびに決める」ことと、「回復を出来事として 1 つ足す」こと。** どちらも既存の窓の作り方（Stage 6・8）と 1 パス目のループ（Stage 10）の形はそのままに、入力を 1 つずつ広げるだけにする。

### 0.3 いまのモデルとの差

- **対象が効果ごとに固定**: `planBuffTimeline` は効果ごとに発火フレームの窓を和集合にしてから、`isEffectTarget` で対象の枠へ同じ窓を配る。`firstPass.ts` の `FiringSource.targets` も効果ごとに 1 つ。クラウンの S1 は発火ごとに対象が違うので、**窓を「効果 × 対象の枠」ごとに作る**形に広げる（3.2 節）。
- **チェーンの記録が無い**: `BurstSchedule` は発動を 1 回ずつ並べているが、「どの発動がどのフルバーストを開いたか」は持っていない。状態機械（`burst/controller.ts`）はチェーンを知っているので、そこで記録する（3.1 節）。
- **回復が無い**: 出来事は射撃・発動・フルバースト開始 / 終了・ゲージ満タンの 5 種類（`FrameEvents`）。ここに「回復を受けた」を足す（3.3 節）。

## 1. Stage 11 の進め方

- **1 体 1 PR**。この設計書にクラウン編（本文）を書き、クラウンの PR がマージされたら、アリス編を同じファイルに章として足して起案 → 承認 → 実装する（11 節）。
- 各キャラで**足す語彙はそのキャラに要るものだけ**。ただし同じ言い回しの他キャラ（0.2 節）でもそのまま使える形にする（対象に武器種の絞り込みを許す、`fullBurstEnd` でも使える、など）。定義を作るのは撮影で確かめるキャラだけ（Stage 8 以来の方針）。
- 主力キャラは実戦の編成で使うので、完了条件に「そのキャラを含む実戦的な編成で sim と calc が整合する」を入れる。

## 2. DSL の追加（`skills/types.ts`）

### 2.1 対象「直前にバーストスキルを使用した味方」

```ts
export type BuffTarget = 'self' | 'allies' | 'burstUsers';
```

- `burstUsers` = そのフルバーストを開いたチェーンでバーストを撃った枠（3.1 節）。
- 「使用していない味方」（`nonBurstUsers`）は**足さない**（レビュー ③）。クラウンでそれを対象にする効果は、防御力▲（ダメージに関係しない）と、`allies` にまとめるリロード速度（下）だけで、0.2 節のほかのキャラも使わない。
- **トリガーが `fullBurstStart` か `fullBurstEnd` のときだけ書ける**（「直前」の意味がフルバーストに結び付いているため。アルカナは終了時）。それ以外は検証エラー。
- `targetWeapon` を併用できる（レイ（仮称）の「直前にバーストを使用したマシンガンの味方」）。`parseTargetWeapon` の「`allies` のときだけ」を「`self` 以外」に広げる。
- `passive` には書けない（フルバーストが無いと意味がない）。`timed` と即時効果（`cooldownReduction` / `ammoRefill` / 下の `heal`）に書ける。

**クラウンの S1 のリロード速度は `allies` 1 効果にまとめる**（レビュー ③）。説明文では「使用した味方」「使用していない味方」に 1 行ずつあるが、どちらも 44.35%・15 秒なので全員に付く。2 効果に分けると、`planBuffTimeline` は効果ごとに和集合を作って区間で加算するため、**同じ枠が 15 秒以内に「使った → 使っていない」と入れ替わると 2 つの窓が重なり、+88.7% になる**。重なるのは、フルバーストの間隔が 15 秒未満（フルバースト 10 秒 + ゲージの溜め直し + チェーン）で、同じ段階の 2 体が交互に撃つ編成に限られる。この場合に実機で 2 つが重なるかどうかは確かめられていないが、1 効果なら上書き延長になり、ふだんの編成では 2 効果のときと数値が変わらない。説明文の 2 行をまとめたことは `notes` に書く。

### 2.2 フルスタックで発火する射撃の回数トリガー

```ts
export type ShotCountTrigger = {
  count: ShotCountKind;
  every?: number;
  everyRef?: number;
  /** フルスタックの数の description_value_NN。every 回ごとに 1 スタック、満ちたら解除して発火（every × スタック数 回ごと） */
  stacksRef?: number;
};
```

- クラウンの S2 は `{ count: 'normalShot', everyRef: 1, stacksRef: 3 }`（43 回 × 20 スタック = 860 回ごと。スキル Lv で 43 が変わるので `ref` で持つ）。
- **スタック自体に効果が無い場合だけ**使う（リラックスの「受ける HP 回復量▲」はダメージに関係しない）。スタックごとに攻撃力が上がるような「効果のあるスタック」はモダニアの Stage で扱う。
- 途中でスタックが消えることはないとみなす（クラウンの説明文にも無い）。

### 2.3 即時効果「回復」とトリガー「回復効果が適用された時」

```ts
/** 「HP を X% 回復」。数値はダメージに関係しないので、対象に「回復を受けた」出来事を起こすだけ（即時効果） */
export type HealEffect = {
  kind: 'heal';
  trigger: EffectTrigger; // 'healed' は不可（回復の連鎖で無限ループしないように）
  target: BuffTarget;
  targetWeapon?: WeaponType;
  /** 回復量の description_value_NN（UI の表示用） */
  ref: number;
  assumes?: LocalizedText;
};

export type BuffTrigger = /* 既存 7 つ */ 'healed'; // 自分に回復効果が適用された時
```

- `healed` は**その効果を持つ枠自身**が回復を受けたときに発火する（クラウン・アスカ・ネロ・シラツルの説明文はどれも主語が自分）。
- 回復の出どころは、いまは定義にある `heal` 効果だけ。**編成の外（ヒーラーを定義していないキャラ）の回復は扱わない**（10 節 4）。
- HP の値は持たない。**満タンでも回復は「適用された」とみなす**（射撃場で確かめる。7.5 節の 3）。

## 3. 時刻表・トリガー・窓の変更

### 3.1 チェーンの記録（`burst/schedule.ts`・`burst/controller.ts`・`burst/fixedCycle.ts`）

```ts
export type FullBurstWindow = {
  start: number;
  end: number;
  /** このフルバーストを開いたチェーンでバーストを撃った枠（発動順）。「直前にバーストスキルを使用した味方」 */
  burstUsers: number[];
};
```

- **動的サイクル**: 状態機械が `ready`（ゲージ満タン）に入ってから `StepFull` の発動までに撃った枠を集める。リエントリー（段階 I → I）も同じチェーンに含める。**チェーンが途切れた（タイムアウトした）発動は含めない**（フルバーストを開いていないため）。
- **固定サイクル**: そのサイクルで割り当てた I・II・III の 3 枠。
- `FrameEvents` の `fullBurstStart` / `fullBurstEnd` に、その窓の `burstUsers` を添える（`replayEvents` とループの両方で）。

### 3.2 対象を発火のたびに決める

`isEffectTarget(effect, source, target, weapon)` に 5 つ目の引数「発火の文脈」（`{ burstUsers: readonly number[] } | null`）を足す。`burstUsers` はこれを見て、`self` / `allies` は今までどおり見ない。

| 場所                           | いま                                                     | 変更後                                                                                            |
| ------------------------------ | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `planBuffTimeline`             | 効果ごとに発火フレーム → 和集合 → 全対象へ同じ窓         | 効果ごとに発火（フレーム + 文脈）→ **対象の枠ごとに**自分が対象だった発火だけで和集合             |
| `firstPass.ts`（射撃系・即時） | `FiringSource.targets`（固定）・`windows`（効果に 1 列） | 発火のたびに対象を決め、`windows` を**対象の枠ごとの列**にする。即時効果も発火ごとに対象を決める  |
| `triggerFrames` の戻り値       | フレームの列                                             | `trackTriggerFires`（フレームと文脈の列）を足し、`triggerFrames` はそのフレームだけを返す（互換） |

- **退化**: `burstUsers` を使う効果が無ければ、どの枠の窓も今と 1 フレームも変わらない（対象が固定なら「対象ごとの和集合」=「効果ごとの和集合」）。Stage 10 までの全テストが数値を変えずに通ることを退化条件にする。
- 同じ効果が続けて発火し、1 回目は対象・2 回目は対象外という枠は、1 回目の窓だけを受ける（上書き延長は「その枠が受けた発火どうし」でだけ起きる）。

### 3.3 回復の出来事

- `FrameEvents` に `healed: readonly boolean[]`（枠ごと）を足す。
- **回復のフレーム** = `heal` 効果の窓が始まるはずのフレーム。つまり射撃の回数トリガー（クラウン）なら**トリガーになった射撃の次のフレーム**、バースト系なら発火と同じフレーム（Stage 6・8 の窓の規則をそのまま使う）。
- `healed` で付く窓は**回復のフレームから**始める（回復は 1 フレームの中で「回復 → バフ」と続けて起きるとみなす）。クラウンなら 860 発目の射撃の次のフレームから 7 秒。
- **2 段で解く（バッチ側。レビュー ①）**: いまの `replayEvents(schedule, shots, frames)` は定義（`slots`）を受け取らないので、`heal` の発火は判定できない。そこで `replayEvents` は定義を知らないまま据え置き、段を分ける。
  1. `planHeals(slots, schedule, shots, frames): HealRecord[]`（`skills/heals.ts` 新設）が、`healed` の無い出来事の列（今の `replayEvents` の結果）に各枠の `heal` 効果を `TriggerTracker` で流し、回復の記録 `{ frame, sourceSlotIndex, slotIndex }` を返す。`frame` は上の規則（射撃の回数起点なら + 1、戦闘時間の外は捨てる）。
  2. `replayEvents(schedule, shots, frames, heals = [])` に 4 つ目の引数を足し、`heals` の `frame` に `healed[slotIndex] = true` を立てる（回復だけが起きるフレームも出来事の列に入れる）。
  3. `planBuffTimeline` は冒頭で 1 回だけ `planHeals` を呼び、以降の `triggerFrames` / `buffStartFrames` に `heals` を渡す（どちらも省略可能な引数を足す。省略時は回復なし = 今と同じ）。
  - `heal` のトリガーに `healed` を許さないので 2 段で閉じる。
  - **キャッシュ**: `eventsOf` の鍵に `heals` を足す（`schedule` / `shots` と同じく参照の一致で見る。`planBuffTimeline` の中では同じ配列を渡し続けるので効く）。1 段目の「`healed` の無い列」と 2 段目の列は別物なので、鍵が違えば作り直す。
- **ループ側（1 パス目。レビュー ②）**: いまの即時効果（`cooldownReduction` / `ammoRefill`）は発火したフレーム `f` でその場で当てている。`heal` だけは回復のフレームの規則に合わせ、**射撃の回数起点なら `f + 1` に保留**し、`f + 1` の手順 3 で出来事を組むときに `healed` を立てる（`pendingHeals`）。バースト系の起点なら `f` のうちに立て、同じ `f` の手順 3 の残りの効果（`healed` を条件にするもの）より先に処理する。`f + 1 ≥ frames` なら捨てる。回復の記録（`instants`）は立てたフレームで残す。
  - 既存の `cooldownReduction` / `ammoRefill` の当てるフレームは変えない（射撃の回数起点のものは定義に無く、変えると Stage 10 の退化が崩れる）。
  - いまの定義に `healed` を条件にする射撃系の効果は無いが、ループと `planBuffTimeline` が同じ意味になるよう `TriggerTracker` を通し、**ループが記録した回復と `planHeals` の結果が一致する**ことをテストで固定する（Stage 10 の 1.2 節と同じ考え方）。
- `BurstSchedule` と同じ流儀で、`SimResult` / `TeamSlotResult.instants` に回復の記録（フレーム・出どころ・受けた枠）を出す。

## 5. calc・UI・CLI

- **calc の計算は変えない**。クラウンの効果はどれも窓（区間）で表せ、S2 の窓は射撃の列から決まる（Stage 8 の射撃の回数トリガーと同じ扱い）。S1 のリロード速度は射撃系の `timed` なので、掛かっているグループは Stage 10 のハイブリッドで「実数」になる。

## 9. リスク・留意点

- **満タンで回復が「適用された」ことになるか**: ならない場合、射撃場（被弾が少ない）では S2 がほぼ発動しない。実戦でも発動がクラウンの被弾に依存するので、仮定のトグル（「クラウンは常に被弾している」）が要るかもしれない。録画 41 の 3 で決まる。
- **「直前に」の範囲**: チェーンが途切れた後の I の発動（次のゲージで撃ち直す前のもの）を含むかどうか。3.1 節では含めない。録画 41 はチェーン切れが 4 回あるので、1 で確かめられる（途切れた回のフラワーに付いていなければ整合）。
- **HP を持たない**: 「残り HP が最も低い味方を回復」（I-DOLL・オーシャンなど）は対象が決められない。ヒーラーを定義する Stage で HP の扱いを決める（10 節 4）。
- **1 フレームの前後**: 回復とバフを同じフレームにしたので、860 発目の次の射撃から攻撃ダメージ▲が乗る。実機で 1 発ずれていても 7 秒の窓では誤差が小さい。
- **クラウンのバフ前攻撃力**: 発動者基準の固定加算は Stage 4 で確かめた式（発動者のバフ前攻撃力 × 比率）を使う。Defender はスペック固定の攻撃力が低い（80,485）ので、Attacker の自己バフより値が小さい点は UI にそのまま出る。

## 10. 決めてほしいこと（推奨付き）

1. **対象の書き方** — 推奨（レビュー ③ で変更）: **`BuffTarget` に `burstUsers` だけを足し、トリガーが `fullBurstStart` / `fullBurstEnd` のときだけ許す。S1 のリロード速度は `allies` 1 効果にまとめる**（2.1 節）。当初案（`nonBurstUsers` も足してリロード速度を 2 効果に分ける）は、フルバーストの間隔が 15 秒未満の編成で窓が重なって二重に足されるので採らない。

2. **「直前にバーストを使用した」の範囲** — 推奨: **そのフルバーストを開いたチェーン（ゲージ満タン後〜フルバースト開始）で撃った枠。途切れたチェーンの発動は含めない**（3.1 節）。録画 41 で確かめる。

3. **S2 の書き方** — 推奨: **即時効果 `heal` とトリガー `healed`、スタックは `stacksRef` で表す**（2.2・2.3 節）。「43 回で 1 スタック → 20 スタックで回復 → 回復でバフ」を説明文どおりに書け、アスカ（所持・S1 が回復トリガー）・ネロ・シラツルやヒーラーの定義にそのまま使える。代替: 射撃の回数トリガーで「860 回ごとに攻撃ダメージ▲」と直に書く（語彙は `stacksRef` だけで済むが、回復の出来事が無いのでヒーラーの回復と合わせられない）。

4. **編成の外の回復（ヒーラー）** — 推奨: **この PR では扱わない**。回復の出どころは定義にある `heal` 効果だけにし、S2 に「編成の外からの回復は数えない」の仮定を付ける。ヒーラー（ラプンツェル・I-DOLL・オーシャンなど）の回復は、そのキャラを定義するとき（HP の扱いを決めるとき）に `heal` 効果として足す。代替: calc に「クラウンの S2 を常時発動とみなす」のトグルを足す（ヒーラー同伴の実戦に近い値がすぐ出るが、根拠の無い仮定になる）。

5. **回復・`healed` の窓の開始** — 推奨: **回復は `heal` の窓の開始と同じフレーム（射撃の回数起点なら次のフレーム）、`healed` の窓もそのフレームから**（3.3 節）。

6. **撮影** — 推奨: **録画 41（I-DOLL・フラワー + クラウン + デルタ（操作）+ ラピ、3 分モード・自動バースト ON）の 1 本**（7.5 節）。所持を確認したい: I-DOLL・フラワー（射撃場の録画に写っていたので所持と見ている）。代替: 外部の回復で S2 が起きるかを見る録画をもう 1 本（I-DOLL・オーシャンを I にする）。4 を「扱わない」にするなら今は要らない。

7. **設計書の構成とブランチ** — 推奨: **この `design-stage11.md` に共通の進め方とクラウン編を書き、アリス編はクラウンの PR のマージ後に同じファイルへ章を足す**。実装は今のブランチ `claude/stage11-design-cf2026`（main = Stage 10 マージ後）で行い、main 向けの PR にする。

## 13. 実装時の差分と知見（2026-09-23）

1. **`isEffectTarget` に発火の文脈（`FireContext`）を足した**（`skills/targets.ts`）。`burstUsers` は文脈の枠だけ、文脈が無ければ誰にも掛からない。対象が文脈で変わる効果かどうかは `dependsOnContext` で見分け、変わらない効果は今までどおり効果ごとに 1 回だけ和集合を作る（退化の保証）。
2. **出来事（`FrameEvents`）には `fullBurstStartUsers` / `fullBurstEndUsers` と `healed` を足した**。発火の文脈は `fireContextOf(trigger, ev)` で取り、`trackTriggerFires` がフレームと文脈の組を返す（`trackTriggerFrames` / `triggerFrames` / `buffStartFrames` はフレームだけの互換版として残した）。
3. **回復の 1 段目は `skills/heals.ts` の `planHeals`**。`planBuffTimeline` は heal 効果があるときだけ呼び、結果を `BuffTimeline.heals` に残す（sim・calc・UI・テストから見える）。`eventsOf` のキャッシュの鍵には `heals` の参照を入れ、回復が無いときは共有の空配列を渡してキャッシュが効くようにした。
4. **1 パス目のループでは、回復を手順 3 の最初に当てる**。射撃の回数起点は `pendingHeals`（フレーム → 受ける枠）に積み、次のフレームの出来事を組むときに `healed` を立てて `instants` に記録する。射撃系の窓は `FiringSource.windows` を対象の枠ごとの列にし、`FiringWindow` に `slotIndex` を足した。
5. **`ShotCountTrigger.stacksRef` は解決時に `every = 1 スタックの回数 × スタック数` にし、`stacks` を残す**（UI の「通常攻撃 43 回 × 20 スタックごと」）。発火の判定は Stage 8 の `every` のまま。
6. **クラウンの定義**: S1 = `burstUsers` の攻撃力（`casterAttack`）と `allies` のリロード速度（説明文の 2 行をまとめた旨を `assumes` に）、S2 = `heal`（`{ count: normalShot, everyRef: 1, stacksRef: 3 }` / self）と `healed` の攻撃ダメージ、バースト = 攻撃ダメージ。3 スロットとも `partial`（防御力▲・リラックス・無敵・挑発・バリアは notes）。
7. **UI**: トリガー「回復を受けた時」、対象の出どころ「（直前にバーストを使った味方）」、即時効果「回復（最大 HP の 5.23%）」（回数だけ出し、「計 0 発」は出さない。仮定も出す）。CLI は時刻表にフルバーストごとの `burstUsers` の列を足した。
8. **テスト**: `skills/__tests__/stage11.test.ts`（DSL・解決・対象・チェーンの枠・対象ごとの窓・回復の 2 段）と `__tests__/stage11Team.test.ts`（録画 41 の実測値の回帰、2 編成の sim / calc 整合）。180 → 18,000 秒の収束の確認は 1 件 10〜30 秒かかるので、この Stage のテストには入れなかった（既存の `simCalc.test.ts` の範囲）。
9. **予測（7.5 節）の補足**: クラウンの定義を入れた後の sim では、録画 41 の編成の回復は 7 回（22.65・49.98・75.12・100.25・127.58・152.72・177.77 秒）、フラワーの攻撃力はフルバーストから 15 秒 106,237、デルタは 63,368 のまま。
