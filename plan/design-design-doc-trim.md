# 設計書: 設計書から、設計書として要らない記述を消せるようにする

- 何のための文書か: 設計書に経緯が積み重なって大きくなるので、設計書として大事な記述のほかは、適宜消せるようにする。決まり（AGENTS.md「文書の書き方」と「記録の置き場所」の表）の直しと、消したときに参照が切れないための確かめを決める。
- 関連: [design-doc-roles.md](design-doc-roles.md)（文書の 4 つの型）・[design-code-comments.md](design-code-comments.md)（コードのコメントの書き方）
- 状態: 一部完了（決まりと道具は 9 節。50KB を超えた設計書を縮めるのは 6 節）

## 1. いまの困りごと

- 設計書（`plan/design-*.md`・`plan/burst-effect-delay-candidates.md`）は「記録」の型で、「書いた事実は書き換えず、訂正は棄却か新しい記録で行う」。設計書から記述を消す根拠が無い。
- 目安の 50KB を超える設計書が多くある（design-stage12・stage18・stage11・stage11-modernia・stage10・stage16・split-first-pass・stage20・stage6 など。一覧は `npm run pr:prep` の大きさの知らせと同じ見方で出せる）。
- 大きくなる中身は、設計書として読み返すことが少ないもの: 設計の前の調査の途中経過、実装の時の差分と知見（コードと git の履歴にある）、実測（検証記録・観測値と重なる）、「次に撮るもの」のような済んだ段取り、経過の細かい行（modern-ui は経過だけで約 40KB）。
- 開いている PR（design-modern-ui の整理。claude/design-modern-ui-trim）が、オーナーの指示で design-modern-ui.md を 58KB から 16KB にした。消したもの・残したものの線引きは PR の本文にある。ほかの設計書が番号で指す 2.5 節の決定の番号は残した。これを一般の決まりにする。

## 2. 型の分け方

### 案 A: 設計書の型を「記録」から分け、「設計」の型を足す（採る）

AGENTS.md「文書の書き方」の型に「設計」を足し、「記録の置き場所」の表の設計書の行の型を「設計」にする。記録の型から、設計書の経過の書き方の文を「設計」へ移す。

- 良い点: 記録の型（検証記録・結論・観測値・録画の台帳・予測・backup-log.md）の「書き換えない」はそのまま強く保てる。結論の根拠になる記録と、変更の案を持つ設計書とで、消してよいかが違うことが表で分かる。
- 悪い点: 型が 5 つになる。

### 案 B: 記録の型に、設計書だけの例外を足す

記録の型の文に「設計書は、設計書として要らない記述を消してよい（…）」を足す。

- 良い点: 型の数が変わらない。
- 悪い点: 「書いた事実は書き換えない」の直後に例外が来て、記録の型の決まりが読みにくくなる。表を見ても、設計書だけ消してよいことが分からない。

## 3. 残すもの・消してよいもの

残すもの（設計書として要る記述）:

- 目的・範囲・関連。
- 案・論点・決定と理由・採らない案とその理由。決定と理由の中身は変えない（言い回しを詰めるのはよい）。決定を変えるときは新しい決定を足す。前の決定は、代わりの決定に理由が書いてあれば消してよい。
- 経過のうち、設計・実装・状態が変わった行（1 日に 1〜数行にまとめてよい）。
- 現状の文書とコードのコメントが指している節の中身（4 節）。

消してよいもの（消したものは git の履歴で引ける）:

- 設計の前の調査の途中経過（結論は決定と理由に残す）。
- 実装の差分と、実装の時の細かい知見（コードと git の履歴にある。次の設計に効く知見は決定と理由に残す）。
- ほかに置き場所がある実測（検証記録・観測値の ID で指せばよい）。
- 済んだ段取り（「次に撮るもの」「次の PR でやること」など）と、PR の完了の印。
- 細かい見た目の直し（数 px・色・影など）と、前の見た目との比べ。
- 取りやめて取り消した変更。
- 作業のいきさつ（どのセッションが何をしたか）・日付付きの「（オーナーの指示）」の前置き（中身は決定として書き直す）。

## 4. 消してよいときと、守ること

- 消してよいとき: その設計書を触るどの PR でもよい（オーナーの言う「適宜」）。消すだけの PR でもよい。消したら PR の本文に、消したもの・残したものを短く書く。
- 現状の文書・コードのコメント・データが指している節（「理由が要るときは、設計書の節を 1 つ指す」）は、中身を消さないか、指している側を直す。5 節の道具が見つける。
- 節の番号と決定の番号は振り直さない。中身を全部消した節・決定は番号を欠番にする（見出しも消す）。ほかの設計書・検証記録・結論は番号で指すことがあり、記録の側は書いた時点の版を指す決まり（AGENTS.md「文書の書き方」）なので切れても直さなくてよいが、同じ番号が別の中身を指すと読み違えるため。

## 5. 参照の切れを pr:prep で止める

いま、`packages`・`apps`・`tools` のコードから設計書の節（「design-x.md 3 節」「design-x.md の 2.5 節」の形）を指す所は多く、現状の文書（plan の手引きなど）からもある。調べたら、コードからの参照は全部、指す節の見出しがあった。現状の文書からは、生成物を除くと 1 か所（requirements.md が指す design-ui-rebuild.md 5.3 節）が無かった。

`npm run pr:prep` に次の確かめを足す（実装で変えた所は 9 節の 3）:

- 見る側: 現状の型のファイル（`packages`・`apps`・`tools` のソース、AGENTS.md・README.md、`plan/` の現状の文書、`records/backlog/`、records の README）。設計書・記録・生成物・凍結の文書は見ない（記録は書いた時点の版を指す）。
- 見るもの: 「design-x.md」（リンクの形も）の直後の「N 節」「の N 節」が、その設計書に「## N」「### N.M」などの見出しとしてあるか。
- 範囲: ブランチで変えた設計書を指す参照と、ブランチで変えたファイルにある参照だけ（main に切れた参照があっても、関係の無いブランチを止めない）。
- 見出しが無ければ止め、参照の場所と指す節を出す。
- この PR で requirements.md の切れた参照を直す。

「設計書 6.1 節」のように設計書の名前を書かない参照（cloud-guide.md など）と、「design-x.md「経過」」のように見出しの名前で指す参照（コードに 1 か所）は見ない。

## 6. 50KB を超えた設計書を、いつ削るか

### 案 i: 触ったときに削る

- 50KB を超えた設計書をブランチで変えると、いまも `pr:prep` が知らせる（止めない）。そのときに、3 節の線引きで消す。
- 触らない設計書は、大きくても読む人がいないので困らない。

### 案 ii: いま、まとめて削る（採る）

- 50KB を超える設計書を、別の PR（数本ずつ）で削る。この PR では課題を `records/backlog/` に起票する。
- 一度に済むが、読まれていない設計書の整理に手間がかかる。

## 9. 決定（2026-11-21。オーナー）
