# デプロイキーを使えるジョブを main の版のコードに限る（2026-11-22）

- 何のための文書か: 書き込みのできるデプロイキー（secret の `GENERATED_DEPLOY_KEY`）を使えるジョブを、main で動く、main の版のコードだけを回すジョブに限る変更の、目的・案・決定を残す。
- 関連: デプロイキーを足した回（[design-pr-conflicts.md](design-pr-conflicts.md) 5 節）、自動マージを待つ PR の衝突の直し（[design-auto-conflict-fix.md](design-auto-conflict-fix.md)）、道具（`tools/git/auto-rebase.ts`・`tools/git/auto-rebase-jobs.ts`・`tools/git/ci-generated.ts`）。

## 1. 目的

- デプロイキーは ruleset「automerge」の Bypass list に入っていて、main の規則（PR 必須・必須チェック）を通らずに main に書き込める。
- そのため、この鍵は、main に入って CI を通った版のコードのほかには見せない。PR のブランチの版のコード（ワークフローのファイル・道具・依存のパッケージ）が動くジョブには渡さない。
- いまは次の 2 か所で、この線が守られていない。
  - 鍵はリポジトリの secret なので、どのブランチのどのワークフローの実行からも読める（フォークの PR を除く）。
  - 衝突の直し（`auto-rebase.yml` の `--fix`）は、PR のブランチを取り出して、そのブランチの版の `records:renumber`・`pr:prep` を、鍵を持ったジョブの中で回す（design-auto-conflict-fix.md 7 節の「制約」）。同じジョブの中では、子の環境変数から鍵を外しても、後の段を守れない。

## 2. 決定（案 A）

決定（2026-11-22、オーナー）: 案 A。鍵は替えない。コードの直しを先に main に入れる準備をし（自動マージを予約しない）、オーナーが GitHub の設定を変えてからマージする。

決定（2026-11-22、オーナー）: 鍵は作り直す。GitHub の secret は値を読み出せず、前の秘密鍵の値が手元に無かったため。新しい鍵を Deploy keys と environment の secret に置いてからマージし、main の CI が新しい鍵で動くのを見てから、古い鍵とリポジトリの secret を消す（止まる時間を作らない）。

### 2.1 GitHub の設定（オーナー）

1. Settings → Environments に environment `main-push` を作り、「Deployment branches and tags」を「Selected branches and tags」にして `main` だけを足す。
2. 秘密鍵をその environment の secret `GENERATED_DEPLOY_KEY` に置き、リポジトリの secret（Settings → Secrets and variables → Actions）の `GENERATED_DEPLOY_KEY` を消す。

environment の secret は、その environment を指したジョブにしか渡らない。使えるブランチを main に限ると、PR の実行（`refs/pull/N/merge`）とほかのブランチの実行は、その environment を使えない。

### 2.2 ワークフローと道具

- 鍵を使うジョブには `environment: main-push` を付ける。`deployment: false`（Deployments の一覧に記録を作らない指定）は付けない。この指定のジョブにもブランチの制限がかかるかを、文書と手元で確かめられなかったため（記録が増えるだけで、制限は確実にかかる）。
- **CI（`ci.yml`）**: 生成物の commit を `commit` のジョブに分ける。
  - `check` のジョブ（依存のパッケージを入れて確認を回す）は、作り直した生成物を全部 `ci-generated.ts --export` で写し、artifact で渡すだけにする。
  - `commit` のジョブは、main の版を取り出しただけの作業ツリーで（`npm ci` もしない）、`ci-generated.ts --commit` が生成物のパスのものだけを戻して commit し、push する（artifact にほかのファイルがあっても読まない）。
- **衝突の直し（`auto-rebase.yml`）**: 3 つのジョブに分ける。
  - `find`: 今のまま（API だけ。鍵なし）。
  - `prepare`: 鍵も token も渡さない（PR は `find` が出力で渡す）。PR のブランチの版の道具で振り直し・まとめ・`pr:prep` を回し、main の先頭からの commit を git bundle にして、結果の一覧（`manifest.json`）と一緒に artifact で渡す。観測値のモデルの予測値の覚え（キャッシュ）は戻すだけで、保存しない。
  - `push`: 鍵あり。main の版を取り出しただけの作業ツリーで（`npm ci` もしない）、`auto-rebase.ts --push` が一覧の形を確かめて `find` の選んだ PR に限り、直せなかった PR に先にコメントしてから、PR を API で引き直し、対象のままで head が `prepare` の時と同じなら、bundle を取り込んで、そのブランチにだけ lease つきで push する。題名の書き換えとコメントもここで行う。
  - bundle と一覧の中身は、PR のブランチの道具が決められる。ただし push の先は、API で引き直した `claude/`・`antigrav/` のブランチだけなので、そのブランチに書き込める者ができることは増えない。
- あわせて直したもの（同じ所の組み替えで済むもの）:
  - 振り直しも main の新しい commit も無い PR は、まとめて push し直さない（前は `mergeable` が決まらなかった PR を、直すものが無くてもまとめて push し直した）。
  - `push` のジョブは、PR ごとの API の失敗で残りの PR を止めない（最後に 1 で終わる）。
  - `pr:prep` が通信の失敗で止まったときは、「直せない」のコメントをせず、次の実行で直し直す（`transientFailure`）。

## 3. 採らない案

- **案 B（鍵は同じく囲い、衝突の直しは知らせるだけに戻す）**: コードは一番少ないが、衝突のたびにセッションが起きて直すまで止まる。2026-11-21 に決めた、Actions が直す利点（design-auto-conflict-fix.md 5 節）を手放す。
- **案 C（衝突の直しだけ直し、environment は使わない）**: 鍵がリポジトリの secret のままなので、1 節の 1 つ目が残る。
- **案 D（何もしない）**: ブランチに書き込めるのはオーナーとエージェントだけだが、エージェントは外の文章や依存のパッケージの影響を受けうる。鍵が漏れると、必須チェックも main の履歴も迂回され、気づく手立てが無い。

## 4. 残ること

- エージェントは、CI を通るコードを自動マージで main に入れられ、そのコードは main の CI で鍵の近くで動く。この変更で変わるのは、鍵に届くコードが「main に入って CI を通り、履歴に残ったもの」に限られること。
- `prepare` のジョブはブランチの道具を main の push の実行の中で回すので、そのジョブの中のもの（作業ツリー・artifact）はブランチの道具が書き換えうる。鍵のジョブは、それを data として形を確かめて使う（2.2 節）。キャッシュは書けない（6 節）。
- `prepare` は同じジョブで PR を続けて直し、PR の間の片付け（`cleanUp`）は作業ツリーの変更と追跡していないファイルだけを戻す。前の PR の道具が残したもの（無視されたファイル・`~/.gitconfig`・`.git/config`・`.git/hooks`・作業ツリーの外）は、次の PR の結果を変えうる。これは受け入れる（6.3 節）。

## 5. find から prepare に渡す PR の大きさ

### 5.1 問題

- `find` は直してみる PR を、ジョブの出力 `prs` で `prepare` に渡し、`prepare` はそれを環境変数 `PRS` で受ける（`prepare` は token を持たないため。2.2 節）。
- `find` は REST の PR オブジェクトを丸ごと（1 本で約 18KB）渡していた。Linux では環境変数 1 つは 128KiB（MAX_ARG_STRLEN）までなので、直す PR が 7 本ほどになると `prepare` の node が起動できず（E2BIG）、どの PR も直らない。

### 5.2 案

- **案 1（採る）: `prepare` が読む欄だけにする**。`find` の版の道具が欄を絞り、ワークフローは変えない。
- **案 2: ファイルで渡す**。`find` が JSON を artifact に置き、`prepare` が取り出す。大きさの上限は無くなるが、ワークフローに段が 2 つ増える。

### 5.3 決定と理由

決定（2026-11-28）: 案 1。あわせて、上限に入りきらない PR は次の実行に回す。

- `prepare` が読む欄は、番号・状態・題名・`mergeable`・自動マージの予約・head（ブランチ・sha・リポジトリの名前）だけ（`auto-rebase.ts` の `fix`、`auto-rebase-jobs.ts` の `prepareEntries`、`isTarget`）。本文は読まない（題名と本文の書き換えは、`push` が API で引き直した PR で行う）。自動マージの予約は、有無だけを残す（予約の中身にはマージの commit の文が入り、大きくなりうる）。
- 絞ると 1 本で約 0.3KB になる（この時点の閉じた PR 30 本で 276〜397 バイト）。`find` が見るのは開いた PR の 1 ページ（100 本）までなので、題名が全部 256 文字の日本語でも、上限に収まる（テストで確かめる）。
- ブランチの名前の長さには決まった上限が無いので、それでも超える場合に備え、`find` は上限（120KiB）に入りきらない PR を `targets` からも外して次の実行に回す（ワークフローの warning に出す）。詰める順は API の返す順なので、回される PR は毎回同じになりうる。1 本で上限を超える PR は直らないままになるが、ブランチの名前が 100KB を超えるときだけなので扱わない。
- 案 2 を採らないのは、案 1 で上限に届かず、ワークフローの段（artifact の受け渡し）を増やす理由が無いため。`prepare` に渡すものが減るだけで、ジョブの権限・鍵の扱い（2 節）は変えない。

## 6. prepare のジョブのキャッシュと、PR の間の片付け

### 6.1 問題

- main の push で始まった実行のジョブは、main のスコープにキャッシュを書ける。書く権限はジョブのトークン（`ACTIONS_RUNTIME_TOKEN`）にあり、`permissions` では止まらない。GitHub のランナーは sudo が使えるので、`run:` の中のコードもトークンを取り出せる。`prepare` はブランチの道具をこの実行の中で回すので、ブランチの道具は鍵を選んで main のスコープにキャッシュを書ける。
- 鍵の当て方は名前だけで決まる。`key` に当たらないと、`key` の前方一致と `restore-keys` で探し、いちばん新しいものを戻す。中身は確かめずに tar で展開するので、作業ツリーのどのファイルでも上書きできる。
- そのため、main の CI の `check` が戻すキャッシュ（観測値のモデルの予測値の覚え `residuals-`・`setup-node` の npm）を通して、`check` の作業ツリーを書き換え、生成物を変えられる。変えた生成物は、`commit` のジョブが main に push する。Pages のビルドも、npm のキャッシュで同じように書き換えられる。鍵は漏れないが、悪いコードが PR にも main の履歴にも残らないまま、main の生成物と配る画面が変わる（1 節の線が、main に書く経路で崩れる）。
- 起こるのは、`claude/`・`antigrav/` のブランチにわざと悪いコードが入り、衝突の直しが回ったときだけ（ブランチは ID をわざと重ねて衝突の直しを起こせる）。

### 6.2 決定と理由（キャッシュ）

決定（2026-11-28、オーナー）: `prepare` のジョブにキャッシュを書かせない。`auto-rebase.yml` は、ワークフローの既定を `cache-mode: none` にし、`prepare` だけを `cache-mode: read` にする（覚えは戻すだけ）。

- `cache-mode` は、ジョブのトークンに与えるキャッシュの権限で、GitHub がトークンの側で強制する。`cache-mode: read` のジョブから保存すると、この設定を読まない版の `actions/cache/save`（v4）でも、サーバーが「cache write denied: token has no writable scopes」で断った（2026-11-28 にトピックブランチで回した試しのワークフロー。付けないジョブからは保存できた）。
- 書けるトークンを、ブランチの道具を回すジョブに渡さなくなるので、どのキャッシュの経路にも効く。main のスコープに書けて、ブランチのコードを回すジョブはほかに無い（PR の CI は PR のスコープに書き、Pages は `workflow_run` で動くので既定で読むだけ）。
- ジョブごとの権限は `tools/git/auto-rebase-workflow.test.ts` が見る（ジョブを足したら、そこで権限を決める）。

### 6.3 決定と理由（PR の間の片付け）

決定（2026-11-28、オーナー）: `cleanUp` は今のまま、残るもの（4 節）を受け入れる。

- 悪意のある道具は、次の PR の bundle の中身を決められる。ただし push の先は、`push` のジョブが API で引き直したそのブランチ（`claude/`・`antigrav/`）だけで、そこには道具を書いた者も直接 push できるので、できることは増えない（2.2 節と同じ理由）。push したブランチは、PR の CI が新しいランナーで確かめ直す。
- うっかり残ったものの影響も小さい。観測値の予測値の覚えはモデルの hash ごとに分かれ、`node_modules` は main の版のまま（`pr:prep --no-ci` は入れ直さない）。残りうるのは、前の PR の道具が書いた無視されたファイルを、次の PR の道具が読む場合で、結果は「直せない」のコメントか、PR の CI で見つかる差に留まる。

### 6.4 採らない案

- **main の push の `check` で `restore-keys` を使わない**: `key` の前方一致で戻すので、`residuals-<hash>` で始まる鍵を先に書かれると防げない。npm のキャッシュと Pages も残る。
- **main の push の `check` でキャッシュを戻さない**: 覚えの経路は防げるが、`records:minimal` が 1 回あたり約 50 秒遅くなる（1 回のマージで main の CI は 2 回回る）。npm のキャッシュと Pages は残る。
- **受け入れて 4 節に書く**: 6.2 節がワークフローの 2 行で済むので、受け入れる理由が無い。
- **`cleanUp` を強める**（無視されたファイル・フック・git の設定も戻す）: うっかりは防げるが、作業ツリーの外（sudo で書ける）は戻せず、悪意は防げない。6.3 節の理由で、道具とテストを増やすほどの得が無い。
- **PR ごとにジョブを分ける**（matrix）: PR どうしを完全に分けられるが、PR ごとに `npm ci` と全部の履歴の取得がかかり、`push` が複数の artifact と出力をまとめる組み替えが要る。6.3 節の理由で得が無い。

## 経過

- 2026-11-22: 起案し、案 A をオーナーが承認した。ワークフローと道具を直した（2.2 節）。GitHub の設定（2.1 節）は、マージの前にオーナーが行う。
- 2026-11-22: オーナーが 2.1 節の設定をし（鍵は作り直した）、マージした。main の CI の `commit` のジョブは、古い鍵とリポジトリの secret を消した後の実行でも、environment の secret の鍵で origin を読み書きできた（ls-remote と push --dry-run）。衝突の直しの `prepare`・`push` は、直す PR が無く、まだ回っていない。
- 2026-11-28: `find` が `prepare` に渡す PR を読む欄だけにし、上限に入りきらない PR を次の実行に回すようにした（5 節）。
- 2026-11-28: 衝突の直しのワークフローで、`prepare` のキャッシュを読むだけにし、ほかのジョブは使わないようにした。PR の間の片付けは今のまま受け入れた（6 節）。
