## 1. 目的

『勝利の女神：NIKKE』のソロレイド / ユニオンレイド（単体ボス・180秒）において、編成全体が戦闘開始から終了までに与えるダメージを算出するツールを作る。
最終的には通常攻撃・スキル・バースト・バフ/デバフをすべて含んだ総ダメージを扱うが、**最初は通常攻撃のみの簡素なモデルから始め、段階的に拡張する**。

## 2. 進め方の原則

- **小規模 PDCA サイクル**: 各 Stage で「仕様・sim 実装 → calc 実装 → 実測・整合性テスト」の短いサイクルを回し、確実に固めてから次の段階へ進む。
- **sim 先行（sim → calc 順）**: メカニクスの追加はまずフレームシミュ（sim）で逐次処理として動かして物理的挙動（グラウンドトゥルース）を確立し、その後に calc（数式モデル）へ期待値・近似として落とし込む。
- **UI・グラフィックは最小限**: UI 装飾やリッチな演出は後回しにし、CLI やヘッドレスな自動テスト、最小限の機能検証画面で素早く検証する。
- **番号規則**: Stage・バージョンはすべて 1 始まりの整数。v0 や v0.5 は使わない。
- **未対応は明示**: 未定義のキャラやスキル効果は「未対応」と表示し、黙って無視しない。
- **公開前提**: 将来的に GitHub で一般公開する（ソースコードはパブリックリポジトリ、サイトは GitHub Pages）。ライセンス・データの扱い・ホスティングを設計段階から考慮する。

## 4. ツール構成と役割

```
core  … Blablalink 取得・キャラデータ・武器データ・共通ダメージ式。calc / sim で共有
sim   … 60fps フレーム単位で戦闘を逐次再現。メカニクスの「基準挙動」を確定する（ヘッドレス・テスト駆動）
calc  … 数式ベースの期待値計算。sim の挙動を期待値モデル化し、即座に結果を返す（最小限 Web UI）
```

両者は同じダメージ式・同じキャラデータ・同じスキル定義を使う。

### calc と sim の連携についての認識

- calc の区間期待値モデルは、バースト短縮（CT 短縮）や弾数・リロード依存の非線形トリガーで数式化が難しくなる。
- したがって、**新メカニクスはまず sim（逐次処理）で実装して正しい時間軸の挙動を確認** し、その後に calc へ数式化・近似モデルとして落とし込む（sim → calc 順）。
- sim の結果と calc の計算結果を自動テストで照合することで、calc のモデル妥当性を常に検証する。

## 5. スコープ

### 5.1 最終的に扱いたいメカニクス（到達目標）

ダメージ式（コミュニティ検証済みの一般形。係数は設計フェーズで再検証する）:

```
最終ダメージ = ( 基本攻撃力 × (1 + 攻撃力バフ合計) + 固定攻撃力加算 − 敵防御力 )
             × 武器/スキル倍率
             × ( 1 + コアヒット(1.0) + 会心(0.5 + 会心ダメバフ) + フルバースト(0.5) + 距離ボーナス(0.3)
                   + 被ダメ増加デバフ )
             × ( 1 + 攻撃ダメージ増加バフ )        ← 2026-09-22 実測で加算グループの外と確認（verification.md Stage 4・Stage 6）
             × 属性有利(1.1 + 属性ダメバフ)
             × チャージダメージ倍率(SR/RL)
             × その他固有倍率（分配ダメージ・追加ダメージ等）
```

上の式について 2026-09-22 の実測で分かったこと（[verification.md](verification.md) Stage 5・Stage 6 節）:

- **バースト枠の倍率ダメージ（`burstDamage`）には、フルバースト(0.5)・コア・距離ボーナスのいずれも乗らない**（`skill` 型: ノワール 480,611、ラピ 624,393。`distributed` 型: クイーン（真）6,323,975）。会心が乗るかは未確定。
- **被ダメ増加デバフは加算グループではなく別枠の乗数らしい**（デルタのコアヒットが `x × 2 × 1.039`。加算なら `x × 2.039`）。上の式では加算グループに入れてあるので、段階 C 以降で実際に扱うときに再確認する。
- **最終攻撃力は整数に丸められてから防御力を引く**。calc は小数のまま計算しているので 1 未満の差が出る。

- 武器種別（AR/SMG/SR/RL/SG/MG）の発射レート・装弾数・リロード時間・チャージ仕様・コア命中率の扱い
- バーストゲージ蓄積（武器種・発射数依存）とバースト I → II → III → フルバースト のサイクル、バーストCT
- バフ/デバフの種類（攻撃力・攻撃ダメージ・会心率・会心ダメ・属性ダメ・防御無視・被ダメ増加・弾数・リロード速度・チャージ速度/ダメ等）、重複規則、持続時間、対象
- スキル発動トリガー（戦闘開始、N発ごと、フルチャージ、フルバースト時、味方バースト時、HP条件 等）
- コアヒット・会心・フルバースト・距離ボーナス・属性有利
- 敵は「防御力・属性・コア有無」を持つ静止単体ボス（行動パターンなし）

### 5.2 当面扱わないもの

- ボスの行動パターン・パーツ破壊
- 敵からのデバフ、被弾による HP 変動、回復・シールド（生存計算）
- 貫通・範囲攻撃の複数ヒット、ダメージ分配の細かい仕様
- OL装備・キューブ・好感度アイテム・企業タワー・リコレクション（育成入力の拡張として後の Stage で対応）
- アカウント連携

## 6. データソース

### 6.1 Blablalink 公開CDN（認証不要）

- ベース URL: `https://sg-tools-cdn.blablalink.com`
- キャラ一覧: `/character/{locale}/nikke_list_{locale}_v2.json`
  - 返却: resource_id, name, original_rare, class
- キャラ詳細: `/roledata/{resourceId}-v2-{locale}.json`
  - 返却: レベル別の攻撃/HP/防御曲線（`character_level_*_list`）、ステータス強化（`stat_enhance_detail`）、会心率/会心ダメ、属性、武器種、`skill1_detail` / `skill2_detail` / `ulti_skill_detail`（説明文 + `description_value_list` に Lv1〜10 の数値配列）
- 注意点:
  - パスは djb2 ハッシュ + MD5 による難読化がかかっており、変換ロジックの実装が必要（nikke-sim の `scripts/blablalink-stats.mjs` が実装例）。
  - 取得はスクリプトで行い、結果 JSON をリポジトリに同梱する。ブラウザから直接 CDN を叩かない。
  - ロケールは ja を基本とし、en も保持する。

### 6.2 スキル効果定義（自前・Stage 4 から着手）

- Blablalink から取れるのは「説明文」と「Lv別数値」だけ。「どの条件で・誰に・何を・何%・何秒」という構造は手書き JSON（DSL）で定義する。
- 数値は `description_value` のインデックス参照にし、スキル Lv 変更に自動追従させる。
- DSL は段階 A（常時パッシブ）の最小語彙から始め、段階 B / C / D で語彙を追加する。最初から全語彙を設計しない。段階 B（Stage 6）で `timed`（トリガー + 維持秒数）を足した。維持秒数も `description_value` の参照にでき、Lv に追従する。
- 使うキャラから順に定義を増やす。

### 6.3 GitHub 公開を見据えた留意点（設計フェーズで確定）

- ソースコードは GitHub のパブリックリポジトリで公開する。サイトは GitHub Pages でホスティングする。
- コードのライセンス（MIT 想定）を `LICENSE` に置き、ゲームデータ・画像は SHIFT UP / Level Infinite の権利物でありライセンス対象外である旨を README に明記する。
- Blablalink 取得データをリポジトリに同梱してよいか規約を確認する。不可なら利用者側で取得スクリプトを実行する形にし、取得結果は `.gitignore` に入れる。
- 公開リポジトリにするため、個人アカウント情報や認証トークンをコミットしない構成にする（アカウント連携を将来入れる場合も同様）。
- GitHub Pages への配信は GitHub Actions でビルド・デプロイする想定。
