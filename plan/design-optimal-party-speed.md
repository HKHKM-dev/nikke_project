## Context

最適編成計算（`OptimalPartyPanel`・`optimalParty.ts`）は、選んだスロットを候補のニケに 1 人ずつ入れ替え、編成ごとに `runSimulation` を丸ごと回す。オーナーの指示は「速い方法を探す。候補のキャラは全員計算する」。候補を省く・粗い計算で絞る案は取らず、**全員を、いまと同じ値で計算したまま**速くする方法を探した。

## 1. 測り方と値

### 1.1 条件

- 編成: ラピ：レッドフード（16）・クラウン（330）・ノワール（271）・ラプラス（100）・ドレイク（101）。スロット 3 を入れ替える。
- 候補: スキル定義のあるニケのうち、編成にいない 173 人（フルバーストが起きなくなる候補も省かない）。いまの編成と合わせて 174 件。
- 入力は画面と同じ作り（`buildCalcView`・`swappedTeam`）。育成は既定（育成状況なし）。180 秒・バーストあり・射撃場の敵。
- 脚本はリポジトリに入れない（scratchpad に置いた）。

### 1.2 値

| 測り方                                           | 174 件の時間                                                         |
| ------------------------------------------------ | -------------------------------------------------------------------- |
| Node・1 本で順に                                 | 約 31 秒（1 件の中央値 約 150 ms・90% 点 約 220 ms・最大 約 1.6 秒） |
| Chromium・実際の `worker.ts` を 1 / 2 / 3 / 4 個 | 23.4 / 14.8 / 12.0 / 12.1 秒                                         |
| Node・`worker_threads` を 1 / 2 / 3 / 4 本       | 31.3 / 19.0 / 17.6 / 17.0 秒                                         |

- Worker を増やしても、3 個で頭打ち（1 → 3 個で 1.95 倍。4 個でも変わらない）。
- 画面の側（メインスレッド）の手間は 1 件あたり、入力の鍵（`inputKey`）約 2 ms・構造化複製 約 1 ms。入力 1 件は約 218 KB で、そのうちキャラのデータ（5 人分）が 176 KB、スキル定義が 28 KB。
- 1 パス目の回し直し（`settleLeadShots`）は 174 件とも 1 回だけ。
- 同じ列を 2 周しても、同じ入力を続けて回しても 1 件の時間は変わらない（JIT が慣れる分は無い）。
- 最も重い 1 件はトーブ（192）を入れた編成の約 1.6 秒（中央値の約 10 倍）。次がクエンシー：エスケープクイーン（403）の約 0.8 秒。

## 2. どこで時間を使うか

`node --cpu-prof` で 60 件を回したプロファイル。

| 見方               | 上位                                                                                                                                                                    |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 包含時間           | `runSimulation` 77%（1 パス目のフレームループ `runFirstPass` 55%・`planSkillHits` 10%・`buffTimelineOf` 6.5%）。件の一覧などの準備は 1% 未満                            |
| フレームループの中 | 射手を進める `stepShooters` 29%（発の記録 `recordShot` 15%・`paramsAt` 6%）・フレームの出来事 `collectFrameEvents` 11%・件の登録 `registerFrame` 8%                     |
| 自己時間           | GC 9.9%・`collectFrameEvents` 7.6%・`recordShot` 2.7%・`keyOf`（timeline.ts）2.6%・`landingPartsWith` 2.6%・`inputKey` 2.5%（画面の側の手間を同じプロセスで測ったもの） |

- 重い所が 1 か所に集まっていない。design-first-pass-perf.md の段 1・段 2 で件の作り直しを 1/100 にした後に残る、フレームごとの固定の費用（同 2.3 節・3.4 節）が大半を占める。
- V8 の最適化の取り消し（deopt）の多くは「wrong map」。毎フレーム形の違うオブジェクト（任意の欄を広げて足す `FrameEvents`、`??=` で後から欄を足す射撃の記録）が出どころとみられる（未確かめ）。
- `planSkillHits` の 10% のうち 5.6% は `triggerFires`。倍率ダメージのきっかけごとに、出来事の列（10,800 フレーム分）を流し直している。
- トーブの 1.6 秒は、確率の状態の件から作る while の件の作り直し（`readWhileItems` → `whileItems`）と、発ごとに件の全部を `filter` する `critUpAt` が重い。
- Worker が 3 個で頭打ちになるのは、割り当て（GC）とメモリーの帯域で詰まるためとみられる（未確かめ。Node は 1 本でも CPU を約 1.7 コア使う）。

## 3. 案（どれも候補は全員計算し、値は変えない）

### 3.1 案 A: Worker を増やす（実装済みの延長）

いまは「コア数 − 1、最大 8」。このコンテナでは 3 個で頭打ちなので、上限を上げても速くならない。コアの多い機械では伸びる余地があるが、割り当てが減らない限り伸びは鈍い。**これ以上は手を入れない。**

### 3.2 案 B: 1 パス目のフレームごとの固定費を削る（design-first-pass-perf.md 3.4 節の段 3）

入れたもの（どれも値を変えない）:

1. フレームの出来事（`FrameEvents`）と発の出来事（`ShotEvent`）の形を 1 つにする。任意の欄も省かずに `undefined` で、型の順に書く（`skills/triggers.ts` の `emptyFrameEvents`、1 パス目の `collectFrameEvents`・`recordShot`、流し直しの `replayEvents`）。毎フレーム形の違うオブジェクトが、読む側の最適化を取り消していた（2 節）。
2. `collectFrameEvents` の毎フレームの `flatMap` 4 つ（使用武器の変更の終わり・リロードの込め終わり・溜めの周期・満ちた時）を 1 つのループにし、拾うものがあったときだけ配列を作る。
3. 流し直し（`replayEvents`）は、フレームの表を `Map` から配列にし（添字の順に拾えば並べ直さずに昇順）、欄に足すたびに配列を写し直さない。
4. 当たり（`hitRateAt`）・会心（`critUpAt`）・ペレット（`pelletsAt`）・ゲージ速度（`gaugeSpeedAt`）に、射手の実効値と同じ使い回し（`createSpanMemo`）を入れる（`skills/holders/views.ts`）。
5. 発ごとに出し直していた持続の命中率▲の区間の値（`frame/firstPass/gauge.ts` の `spanValueAt`）を、区間と▲の和が同じ間は使い回す（4 で▲の和は件の境目まで同じものになる）。

結果（1.1 節の 174 件。main と同じプロセスで交互に回した中央値）:

| 測り方                             | main          | 案 B                          |
| ---------------------------------- | ------------- | ----------------------------- |
| Node・1 本で順に（3 回）           | 30.8 秒       | 25.1 秒（約 18% 減）          |
| Chromium・`worker.ts` 1 個（2 回） | 25.1〜25.2 秒 | 20.9〜22.0 秒（約 15% 減）    |
| Chromium・`worker.ts` 3 個（2 回） | 13.4〜13.8 秒 | 12.6〜13.5 秒（ばらつきの中） |

- 174 件の総ダメージは main とすべて同じ値。
- Worker 3 個では差がばらつきに埋もれる。並列の頭打ち（2 節）は割り当てとメモリーの帯域で決まり、1 件の計算を軽くしても縮みにくい。
- 最適編成計算だけでなく、画面のふだんの計算・全編成の合計・`records:minimal` も同じだけ軽くなる。

入れなかったもの（残りの候補）:

- `triggerFires` の流し直しをやめ、1 パス目でトリガーの発火を記録しておく（流し直しを軽くした後も `planSkillHits` の数 % が残る）。
- 区間の鍵（`skills/timeline.ts` の `keyOf`。自己時間 3% 前後）。鍵の文字列は結果に出るので、形を変えずに速くする方法が要る。
- GC（自己時間 11% 前後）。発ごとの射撃の記録（配列 8 本への `push`）が主な割り当てとみられる（未確かめ）。

### 3.3 案 C: 外れ値の作り直しを減らす

トーブ（192）の while の件は、元の確率の状態の件が作り直されるたびに作り直され、使い回し（`createSpanMemo`）も効かない（試作 3 では 1.6 秒のまま）。確率の状態の件の作り直しの回数を、design-first-pass-perf.md 3.1 節と同じく「件を作る関数が読む入力」だけで決めるよう直す。174 件の合計では約 5% だが、並列のときに最後に回ると、その分だけ全体が延びる。

### 3.4 案 D: Worker に送る入力を軽くする

キャラのデータとスキル定義を Worker に 1 回だけ送り（ID ごとに覚えさせる）、入力からは ID で指す。メインスレッドの鍵と複製の手間（1 件約 3 ms、174 件で約 0.5 秒）と、Worker の側の複製の手間が減る。全体では 4% 前後だが、計算中に画面が固まる時間が減る。

### 3.5 案 E: 途中の結果を出す（体感の速さ。採らない。5 節）

いまは全部の結果が揃うまで何も出さない（`useBatchComputation` の `setShown` は最後に 1 回）。何人計算したか（例: 120 / 173 人）と、その時点の上位 10 人を出す。合計の時間は変わらないが、上位が早く見える。重そうな候補（前の計算で時間のかかったニケ）を先に渡すと、最後に重い 1 件が残って延びることも減る。

### 3.6 採らない案

- **候補を省く・粗い計算で絞ってから計算する**: 「候補は全員計算する」に反する。
- **入れ替えないニケ 4 人分の計算を、候補の間で使い回す**: 入れ替えたニケのバフ・ゲージは戦闘開始から 4 人に効くので、使い回せる区間が無い。
- **周期を見つけて先を外挿する**: 状態が完全に同じに戻るとは限らず、いまと同じ値になることを保証できない。
- **1 パス目のキャッシュ（B-3）**: 入れ替えでは編成が変わるので効かない（design-first-pass-perf.md 7.3 節）。

## 4. 論点: フルバーストが起きなくなる候補を省く判定

いまの最適編成計算は、入れるとフルバーストが起きなくなる候補を省いている（design-modern-ui.md の経過、2026-11-22）。オーナーの指示の「候補は全員計算する」とは合わない。外すと、レッドフードのいない編成では候補が約 55 人から約 170 人に増え、時間は約 3 倍になる（design-modern-ui.md の経過の測定）。

---

## 5. 決定

1. **案 B を進める。案 E（途中の結果を出す）は採らない**（オーナーの判断、2026-11-23）。案 C・案 D は、案 B の後のプロファイルで残っていれば行う。
2. **フルバーストの判定（4 節）**: 判断待ち。推奨は、省く判定を外して全員を計算する（指示どおり）。
