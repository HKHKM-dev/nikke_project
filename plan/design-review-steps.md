# PR の前の見直しの段の要否と、止めずに進める仕組み

- 何のための文書か: PR の前の見直し（[AGENTS.md](../AGENTS.md)「コミット手順」の整理とバグの 2 段）を毎回 2 段とも回す要否を決め、見直しから PR までの間で応答が止まる問題を仕組みで防ぐ。
- 関連: [AGENTS.md](../AGENTS.md)「コミット手順」、[design-workflow-simplification-11.md](design-workflow-simplification-11.md) 3 節（見直しとデイリーレビュー）、[design-capture-count.md](design-capture-count.md)（2 段の働きを見た PR #1113 の設計）
- 作成日: 2026-11-13
- 状態: 承認（2026-11-13。オーナーの指示「B で進めて」）。実施済み（4 節）

## 1. 問題

- `/simplify` と `/code-review` の間や、`/simplify` の裏のエージェントを待つ間に、応答が終わり、オーナーの入力を待って止まる。Claude Code のメモリに「止まらない」と書いても、2026-11-09・11-10・11-12 と繰り返した。
- オーナーの問い: そもそも 2 段とも回す必要はあるか。

## 2. 見直しの段の要否

**2 段の働き**

- 整理（`/simplify`）は、再利用・簡素化・効率・深さだけを見て、バグを見ない。バグ（`/code-review`）は正しさを見る（整理の指摘も一部出す）。正しさを守るのはバグの段だけ。
- PR #1113（予測が 1 本の中の回数を出す）では、整理の段が重複した関数の一本化や指標の側の口を足し、保守のしやすさに効いた。その直しの一部（`count` を外して 1 回で数える形）と直しの最中の編集（関係ない JSDoc の削除）がバグを持ち込み、バグの段が見つけた。2 段を回すなら「整理 → バグ」の順が要り、バグの段は外せない。
- 整理の段の費用は、裏のエージェント 4 本（PR #1113 では 1 本あたり約 8〜9 万トークン）と、直し・commit・テストのやり直し 1 回、止まりうる場所 1 つ。
- 設計書の経過（`design-split-first-pass.md`・`design-split-long-functions.md`・`design-observations-split.md` など）で整理の段が直したものは、関数の置き場所・共通の部品へのまとめなど、構造の変わる PR に寄っている。数十行の追加や直しの PR では細かい指摘に偏る。整理の段が無ければ何が残ったかを数えた記録は無い。

**案**

| 案  | 中身                                                                                                             |
| --- | ---------------------------------------------------------------------------------------------------------------- |
| A   | いまのまま 2 段とも毎回                                                                                          |
| B   | バグの段は毎回。整理の段は構造が変わる PR（新しいモジュール・ファイルの分割・コードの追加が 100 行を超える）だけ |
| C   | バグの段だけ                                                                                                     |

**決定**: B（2026-11-13）。

## 3. 止めずに進める仕組み

- メモリの文では止まりが直らなかったので、Claude Code のフックで止める（`tools/git/review-flow.ts`・`review-flow-lib.ts`。`.claude/settings.json` の PostToolUse と Stop）。
  - PostToolUse（Skill・Bash・GitHub の MCP の `create_pull_request`）: 見直しのスキル（`simplify`・`code-review`）を呼んだら、git のディレクトリに印（ブランチと時刻）を置く。`gh pr create` か `create_pull_request` で PR を作ったら消す。
  - Stop: 今のブランチの印があれば、応答の終わりを止め（`decision: block`）、PR まで続けるよう理由を返す。
  - 通すもの: 一度止めた後の終わり（`stop_hook_active`。オーナーの判断がどうしても要るとき）、別のブランチの印、6 時間より古い印。
- 裏のエージェントを待つ間の止まりは、フックでは防げない（待つ間は応答を終えるしかない）。止めた理由の文で、`/simplify` のエージェントを `run_in_background: false` で並べて呼ぶよう知らせる。
