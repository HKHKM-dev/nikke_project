## 2. 録画の同定に動画を全部走査する

**いま**

- オーナーの「撮りました」には録画の名前が無く、Drive の record は並行するセッションで共有している。セッションは record の新しいファイルを取り寄せ、`probe-result.ts` でパネルを探して、どの録画か・編成が計画どおりかを確かめる。
- `probe-result.ts` は動画を頭から全部デコードする（`step` フレームおき）。パネルは撮影の手順（[captures/protocol.md](captures/protocol.md)「撮る（射撃場）」の 3）で、録画を止める前の 2〜3 秒に映すので、ほとんどの録画で末尾にある。
- 6 本中 4 本で、この走査に 1 本あたり 7.5〜13.5 分かかった。打ち切りで 2 回回した例（エクシア）と、`ffprobe` が 5 分で止められた例（マルチャーナ）がある。

**案**

- `probe-result.ts` は、まず末尾の 15 秒（`-sseof`）だけを走査する。パネルが見つからなければ、今と同じく全部を走査する（`--full` で初めから全部）。
- 出すフレームの番号・時刻は、今と同じく録画の頭から数える。

**効果**: 同定が 1 本あたり数分から数十秒になる（推測。末尾 15 秒のデコードだけになるので）。

## 3. 「結論」の行で `records:check` と `records:close` が食い違う

**いま**

- `records:check` は、調査中・保留の検証記録に「結論」があると落とす（`verifications.ts`）。
- `records:close` は、閉じる前の検査で「結論」が 1 つ以上あることを求める（`close.ts`）。閉じる前の検証記録は調査中なので、`--mark` の前には必ず「結論」を書くことになる。[verification-guide.md](verification-guide.md) 5 節の手順も「冒頭の「結論」に ID を足し、`records:close -- V-NNNN --mark` で閉じる」。
- `records:new claim` は「検証記録の「結論」に ID を足してから npm run records:check を回す」と出す。その通りにすると `records:check` が落ちる。
- 6 本中 3 本で、「結論」の行を消しては足した（ベルベット 1 回・ロザンナ 2 回・マルチャーナ 1 回）。検査は 1 回 1.5〜2 分。

**案**: `records:check` は、調査中の検証記録の「結論」を許す（保留はいまのまま）。調査中に書いた結論の ID の検査（結論があるか・根拠の結び付き）は、ほかの状態と同じく `records:check` が見る。

## 4. 観測値を書く・モデルの値を出す・結論の根拠を絞る道具が無い

**いま**

- 6 本とも、録画の編成で指標のモデルの値を出すために、使い捨てのスクリプト（`scripts/zz-*.ts`・`__tests__/zz_scratch.test.ts` など）を書いた。`buildTeamInput`・`loadRecordsData` を探す grep が 1 本あたり 3〜6 回。
- 6 本とも、観測値を足すスクリプトを各自で書いた。うち 3 本は、後で `records:check` に落ちて scope・kind の語彙を直した。
- `records:new claim` は、その検証記録を source にする観測値を全部根拠にする（ボリュームは 42 件）。6 本とも手で絞り、5 本は状態と等級も手で直した。

**案**

- `npm run records:model -- <録画 id> <指標>[:<引数>] [--hypothesis <仮説の setup>]`: 台帳の編成・条件で sim を回し、指標の値を出す（`records:predict` と同じ組み立てを使う）。
- `npm run records:new -- observation --recording <録画 id> --metric <指標> --value <値> [--arg …] [--scope …] --from V-NNNN`: 観測値を足し、kind・unit・scope の語彙をその場で検査する。
- `records:new claim` に `--observations <ID,…>` を足し、根拠をそれに絞る（無ければ今の既定）。等級と状態は、絞った根拠から機械の候補で埋める（今と同じ）。

## 7. クラウドのセッションの手順のメモ

Claude Code のメモリ（リポジトリの外）に書いた手順のうち、クラウドで毎回つまずくもの。

- 並行の作業の確かめ（メモリ `check-parallel-work`）が `gh pr list` を指している。クラウドでは GraphQL が使えず毎回 403 で落ち、REST で取り直している（4 本で確認）。`gh api 'repos/HKHKM-dev/nikke_project/pulls?state=all&per_page=10'` に直す。
- 待ち方: `sleep` は拒まれ（4 本）、読み込んでいない Monitor を呼んで落ちた例が 2 本ある。メモリ `bash-pitfalls` に「長いコマンドは `run_in_background` で回し、終わりの知らせを待つ。`sleep` で待たない」を足す。
- PR の念のための確認（メモリ `pr-workflow`）は、最後の動きから 1・3・10・30 分・1・3 時間後。CI は 1 回 4〜5 分なので、1 分後と 3 分後の確認は空振りになる（その間隔で入れた 2 本で確認）。1 回ごとに 20〜30 万トークンの文脈を読み直す。**6 分後**・30 分後・1・3 時間後にする案。間隔はオーナーの依頼（2026-11-01）で決めたので、判断してほしい。
