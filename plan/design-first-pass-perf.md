## 2. 原因

### 2.1 件の列が読まない入力の変化でも作り直す

`readItems`（`holders.ts`）は、件の列の件（`items`）を、入力の長さ（`seen` の 9 個: 始まり・確率の機会・**持ち主の射撃の列**・使用武器の変更の終わり・リロードの込め終わり・**フルバーストの窓**・閉じるフレーム・消費のフレーム・減少）が前に作った時と変わったときだけ作り直す。ただし 9 個を**件の列の種類によらず全部**見ている。

持ち主の射撃の列（`log.frames`）は 1 発ごとに伸びるので、持ち主の件の列は、射撃の列を読まないもの（秒数の timed・状態など。射撃の列を読むのは「N 発の間」の効果だけ）まで、持ち主が撃つたびに古くなる。古くなった件の列は、次に読まれたとき、それまでの始まりの全部から作り直す（スタックする効果なら `stackItems` の `refreshAll`、解除・消費のある状態なら `closedStateItems` の区切りごとに）。始まりは戦闘の間に増えるので、作り直しの費用は時間とともに伸びる。

読み手は毎フレーム来る。`consumeFullStacks` は、フルスタックの消費を持つ状態ごとに持ち主の件の列を毎フレーム読み（さらに毎フレーム `tracks.filter` で件の列を探し直す）、射手は毎フレーム × 枠で射撃に効く件の列を読む。主力の 5 体は件の列（64。うち timed 53）にスタックする効果と射撃に効く効果が多く、フルスタックの消費のある状態も持ち、持ち主の発が多い（11,590 発）ので、作り直しが 4 万回を超える（1.3 節）。

件の列が実際に読む入力だけを見ると、作り直しは主力 431・LRNAM 308・Stage 8 の 5 人 27・録画 0037 24 回になる（試作。3.1 節）。design-unify-sim-calc.md 3.4 節の「フレームごとに閉じた件を作り直している」の中身はこれで、重いのは閉じること（作る関数）ではなく、作り直す回数。

### 2.2 射手の実効値を毎フレーム組み直す

`firingBuffsAt` は毎フレーム × 枠、射撃に効く件の列ごとに効いている件を `activeAt`（件の全部を `filter`）で数え、`applyResolvedEffect` で合計を新しく作る（`addRatioBuff`・`applyResolvedEffect` の自己時間 8%、割り当ては GC に出る）。効いている件の組は件の境目（始まりと終わり）でしか変わらないので、境目を跨がない間は前のフレームと同じ値になる。

### 2.3 小さい編成

Stage 8 の 5 人と録画 0037 は件の列も作り直しも少なく、時間の大半はフレームごとの固定の費用（10,800 フレーム × 枠の射手・ゲージ・出来事の組み立て・件の登録）。2.1・2.2 節を直してもほとんど変わらない（5 節）。

## 3. 直し方

### 3.1 段 1: 件の列が読む入力だけを見る

`readItems` の見比べを、件の列の種類ごとに、件を作る関数が読む入力だけにする。

| 件の列（`origin.kind`）                             | 見る入力                                                                                                                                                                                                                        |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `passive`・`cycleEvery`・`healWindow`・`enemyState` | 始まり                                                                                                                                                                                                                          |
| `timed`                                             | 始まり・確率の機会。`durationShots` は＋持ち主の射撃の列、`durationUntil` が `ammoSpent` は＋使用武器の変更の終わり、`reloadEnd` は＋リロードの込め終わり、`fullBurstEnd` は＋フルバーストの窓（`timedItems` の分かれ道と同じ） |
| `state`                                             | 始まり・閉じるフレーム・消費のフレーム・減少。付与の `durationShots` は＋持ち主の射撃の列、`durationUntil: 'fullBurstEnd'`（`durationShots` が無いとき）は＋フルバーストの窓（`stateItems` の分かれ道と同じ）                   |
| `while`（いまのまま）                               | 元の状態の件の列が作り直されたか（`readWhileItems`）、カウンタの記録の長さ（`readCounterWhileItems`）                                                                                                                           |

合わせて、同じ関数の中の次の 3 つも直す（どれも値は変えない）。

1. 見比べを、呼ぶたびに 9 個の配列を作らない形にする（件の列ごとに見る入力を最初に決めておき、長さを直接比べる）。
2. `consumeFullStacks` の「持ち主とその状態の件の列」を、毎フレーム `tracks.filter` で探さず、最初に 1 回引いておく（件の列は `createHolderLists` の中で作り終わり、ループの間に増えない）。
3. 見比べの帳簿（`seen`）を `HeldTrack` から外し、`createHolderLists` の中の表に持つ。いまは `seen` が履歴（`history.tracks`）に載り、`TeamResult` と Worker の構造化複製にまで出ている（帳簿は読み手がいない）。

**前提（いまと同じ）**: 件を作る関数は、表の入力と戦闘のフレーム数だけで決まり、入力はどれも追記か挿入だけで伸びる（長さで変化が分かる）。調べた範囲（`insertSorted`・`splice` の挿入・`push`、フルバーストの窓は終わりを決めてから `push`）では成り立つ。段 1 は、この前提の下で見る入力を減らすだけなので、作る件は変わらない。

### 3.2 段 2: 射手の実効値を件の境目まで使い回す

`firingBuffsAt` に枠ごとの使い回しを持たせる。前に計算したフレームを含む区間 [from, until)（射撃に効く件の列の件の始まり・終わりのうち、そのフレーム以前で最も遅いものと、より後で最も早いもの）と、計算に使った件（件の列ごとの `items`）と基礎の値（`base`）を覚えておき、次の呼び出しのフレームが区間の中で、どの件の列も作り直されておらず（`items` が同じもの）、基礎の値が同じなら、前の値を返す。

- 値は「その区間で効いている件の組」だけで決まる（効果の値・付けた枠のバフ前攻撃力・最大HP は件の列ごとに一定）ので、使い回しても値は変わらない。
- フレームは前に進むだけではない（射撃の回数のきっかけの弾丸チャージは f + 1 で読む。`firstPass.ts` の `paramsAt` の説明）ので、区間は前後とも持つ。
- 区間と使い回しの判定は小さな関数に切り出し、その関数の単体テスト（境目のちょうど・作り直し・前のフレームへの戻り）を書く。

当たり（`hitUpAt`・`critUpAt`）・ゲージ速度（`gaugeSpeedAt`）・バーストの CT（`burstCooldownAt`）にも同じ形が使えるが、段 1・段 2 の後のプロファイル（3.4 節）で目立たないので入れない。

### 3.3 採らない案

- **件の一覧を増分で持つ**（始まりが足されたら、後ろの件だけ作り足す）・**閉じた件のキャッシュ**: 段 1 の後は作り直しが 1/100 になり、作る関数の自己時間は `refreshAll` 1.7%・`closedStateItems` 1.2%・`stackItems` 0.7%（試作のプロファイル）まで下がる。スタックのチェーンの段の延長・解除と消費の区切り・減少の切り方を増分にすると、作る関数が 2 通りになり、食い違いの検査も要る。得るものが小さいので採らない。
- **作り直しを遅らせる**（フレームの終わりにまとめて作る）: 読み手は同じフレームの中で前の段の登録を読む（段の順）ので、まとめると見え方が変わる。

### 3.4 段 1・段 2 の後に残るもの（段 3 の候補。やらない）

段 1・段 2 の試作のプロファイル（主力）: `runFirstPass` 本体 20%（フレームループと、フレームの出来事 `FrameEvents` の組み立て・使用武器の変更の終わりの `flatMap` などの毎フレームの割り当て）・`readItems` の見比べ 16%（試作は使い回しの判定で毎回全部の件の列を読む。3.2 節の実装では作り直しの印で軽くできる）・GC 12%・`consumeFullStacks` 8%・`registerFrame` 7%・`buffTimelineOf` 7%。目立つ 1 か所は無く、小さい編成の固定の費用（2.3 節）と同じ所なので、ここで止める。

## 7. B-3 の判断の材料

### 7.1 画面の測り直し（クラウド、いまと試作）

design-unify-sim-calc.md の経過（B-1・B-2 の項）と同じ作り: 本番ビルド（`vite preview`）をヘッドレスの Chromium で開き、主力（82, 330, 271, 870, 225。スペック固定・操作 3・条件は既定の自動）の防御力の欄で ↑ キーを押す。合計の横の「計算中…」が外れて描かれた時刻（`data-computing` が true → false になった次の描画）までを測る。Worker の `postMessage` と受け取りの時刻も取った（脚本は使い捨て）。いまの main（f3da18b）と、5 節の段 1 + 2 の試作のビルドを交互に 2 回ずつ測った。

| 測り方                                                        | いま（中央値・幅） | 段 1 + 2 の試作（中央値・幅） |
| ------------------------------------------------------------- | ------------------ | ----------------------------- |
| 1 回押して描き変わるまで（30 回）                             | 268 ms（204〜359） | 115 ms（87〜205）             |
| うち 打鍵 → Worker への送信                                   | 15 ms              | 14 ms                         |
| うち Worker の往復（計算と結果の複製）                        | 211 ms             | 63 ms                         |
| うち 受け取り → 描き変わり（画面の描き直し）                  | 34 ms              | 32 ms                         |
| 40 ms ごとに 20 回押し、最後の打鍵から描き変わるまで（12 回） | 367 ms（250〜550） | 162 ms（103〜221）            |

合計総ダメージは、いまと試作で同じ値になった。連打の値は、最後の打鍵の時に Worker で回っている古い入力の残り（0〜計算 1 回分）と、最後の入力の計算 1 回分の和なので、1 回押しより幅が広い。

### 7.2 デスクトップの見込み

デスクトップの B-2 の後の「最後の打鍵から描き変わるまで」は 115〜180 ms（design-unify-sim-calc.md 経過の B-2 の項）。クラウドの同じ測り方は 250〜550 ms で、比はおよそ 2.2〜3。試作のクラウドの 103〜221 ms から、**最適化の後のデスクトップは約 40〜90 ms**、1 回押しは約 40〜55 ms と見込む（クラウドの 1 回押しの 268 → 115 ms と同じ比）。どちらも、応答が途切れずに感じられる目安の 100 ms を下回る。値は段 2 の PR の後にデスクトップで B-2 と同じ測り方で取り直す。

### 7.3 B-3（6.1 節の差し替えの経路）を足す価値

- B-3 で省けるのは、攻撃力・最大HP・防御力・値だけの stat の変更（6.1 節の表の「回し直さない」の行）のときの `runFirstPass` だけ。差し替えの経路（件の値の差し替え → `buffTimelineOf` → `planSkillHits` → 2 パス目 → `simTeamResult`）と、結果の複製・画面の描き直しは残る。
- 最適化の後の主力で、省ける `runFirstPass` はクラウドで約 65 ms（5 節）、デスクトップで約 25〜30 ms。1 回押しはデスクトップで約 40〜55 ms → 約 15〜30 ms になる見込み。編成・キャラの変更、射撃・ゲージに効く stat の変更では縮まない。小さい編成では省ける分が 10 ms 前後。
- 費用: 6.1 節の回し直す規則の表（`enemyElement`・`topAttack`・`targetDefense`・`casterFinalMaxHp` の見分け、スキル Lv の扱い）と、履歴の件の値の差し替え、表示用の記録（`history.rankings` など）の扱い、差し替えと丸ごと回し直しの一致のテスト。規則の漏れは「古い 1 パス目の結果で値を出す」誤りになり、画面からは気づきにくい。スキルの語彙が増えるたびに、規則の表の見直しが要る。

### 7.4 推奨

**B-3 は見送る。** 最適化（段 1・段 2）の後、主力の打鍵から描き変わりまでは、デスクトップで 100 ms を下回る見込みで（7.2 節）、B-3 で縮むのは一部の入力の変更での 20〜30 ms。規則の漏れが誤った値になる危うさと、語彙が増えるたびの保守に見合わない。段 2 の PR の後にデスクトップで測り、主力で最後の打鍵から描き変わるまでが 100 ms を下回れば backlog 5-6 を閉じる。次のときは見直す: 定義が増えて主力の 1 パス目が再びデスクトップで 100 ms を超えたとき、複数部隊（ソロレイド 5 部隊）の同時計算を入れるとき（design-unify-sim-calc.md 9 節）、遅い端末（スマホなど）での利用を要件にするとき。

## 8. 決めてほしいこと（推奨つき）

1. **直し方** — 推奨: **段 1（件の列が読む入力だけを見る）と段 2（射手の実効値を件の境目まで使い回す）**（3.1・3.2 節）。代わりの案: 件の一覧を増分で持つ・閉じた件のキャッシュ（3.3 節。段 1 の後は作る関数の割合が小さく、得るものが小さい）。段 1 だけで止める（主力は約 3 分の 1 まで）。
2. **一致の保証** — 推奨: **4 節の表のとおり**（値を変えない。`npm test`・`records:check`・`records:minimal -- --all` で差が無いこと、使い捨ての比べ、段ごとのテスト）。代わりの案: 使い回しを切る切り替えを残し、両方の経路を常に比べるテストを置く（確かめは強いが、本番に使わない経路を保守する）。
3. **PR の分け方** — 推奨: **2 段 2 PR**（6 節）。代わりの案: 1 PR にまとめる。
4. **段 3（3.4 節の残り）** — 推奨: **やらない**。小さい編成の固定の費用で、目立つ 1 か所が無い。
5. **B-3** — 推奨: **見送る**（7.4 節）。段 2 の後にデスクトップで測り、100 ms を下回れば 5-6 を閉じる。代わりの案: B-3 も実施する（6.1 節のまま。主力の攻撃力などの変更で、デスクトップで 20〜30 ms 縮む）。判断を段 2 の後のデスクトップの測り直しまで待つ。
