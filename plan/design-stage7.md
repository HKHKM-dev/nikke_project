## Context

Stage 5 / 6 は「20 秒ごとに必ずバースト I → II → III が同じフレームで発動し、10 秒のフルバーストに入る」固定サイクルを前提にしている。時刻表は `burst/fixedCycle.ts` の `planFixedCycle` が作り、sim（フレーム逐次）と calc（区間期待値）が同じ時刻表を共有する。持続バフの区間分割（`skills/timeline.ts`）もこの時刻表から作る。

実機はそう回らない。射撃場の実測（録画 0018〜0022）では、III が 1 体の編成でフルバーストが **CT 40 秒周期・180 秒に 5 回**で回る（0 節）。固定サイクルはフルバーストを 9 回と数えるので、バーストスキルダメージの回数とフルバーストの稼働率がどちらも実機の 1.8 倍になる。

Stage 7 の要求（[roadmap.md](roadmap.md)）:

- 固定 20 秒サイクルの仮定を外し、武器種・弾丸命中によるゲージ蓄積と、バースト CT に基づく動的サイクルを扱う。
- **sim**: 射撃ヒットごとのバーストゲージ蓄積、段階 I → II → III の移行、各ニケのバースト CT（20 秒 / 40 秒）の待機をシミュレートする。
- **calc**: sim で計測したサイクル（平均サイクル秒数・フルバースト稼働率）を取り込む近似モデル。
- **検証**: 録画解析で武器種別のゲージ蓄積量を較正し、sim のサイクル再現性を確認する。

**Stage 7 は新しいスキル語彙を足さない。** 足すのは「いつバーストが起きるか」を決める時刻表の作り方だけ。持続バフ（`timed`）の区間分割・ダメージ式・sim のフレームループ本体は Stage 6 のまま使う。Stage 6 の 9 節に書いた「`planBuffTimeline` は時刻表を受け取るだけなので、動的サイクルの時刻表に差し替えればタイムラインの作り方は変えずに済む」を実行する Stage になる。

## 1. 時間モデルとバーストの状態機械

Stage 5 の時間モデル（60fps・180 秒 = 10,800f・発射はフレーム単位）はそのまま。**バーストの状態を 1 本の状態機械（`BurstController`）で表す。** sim も calc もこの同じ状態機械を回す（3 節・5 節）。

```
          ゲージ ≥ 上限
charging ───────────────▶ ready ──(I の候補の CT 明け)──▶ chain(step)
   ▲                                                         │
   │ ゲージ = 0                                               │ step の候補の CT 明け → 発動
   │                                                         │   次の段階 = 発動したニケの nextStep
   │                     タイムアウト（最後の発動から 600f）  │
   ├─────────────────────────────────────────────────────────┤
   │                                                         │ nextStep が StepFull
   │   フルバースト終了（600f）                               ▼
   └──────────────────────────────────────────────────── fullBurst
```

- **charging**: 通常攻撃が敵に当たるたびにゲージを足す。上限で止める（あふれは捨てる）。
- **ready**: 満タン。I の候補が出るまで**時間制限なしで待つ**（録画 0019）。満タン後に I の CT を待った場合は、CT 明けのフレームですぐ撃つ（`BURST_READY_DELAY_FRAMES` は「満タンから I まで」だけに掛ける。CT 明けにも演出時間を足すかは実測で決まっていない）。
- **chain(step)**: 段階 `step` の候補（`burstStep === step` か `AllStep`、かつ CT が明けている、かつこのチェーンでまだ使っていない）が出たら発動する。**候補が複数なら枠番号の若い順**（9 節 4）。発動したニケの CT が `skill_cooltime` だけ始まり、段階は `nextStep` に進む（`Step2` / `Step3` / `StepFull`、`Step1` なら I に戻る＝リエントリー、`NextStep` なら 1 つ上）。**最後の発動から 600f 候補が出なければチェーン失敗**（ゲージ 0 で charging に戻る。録画 0022）。`AllStep` のニケは専任が CT 中の段階を埋める（その結果チェーンが切れることもあり、録画 0022 と同じ規則）。
- **fullBurst**: `nextStep === 'StepFull'` の発動から始まる 600f。終わったらゲージ 0 で charging に戻る。フルバースト中はゲージが溜まらない。
- **CT の初期値**: 戦闘開始時は全員 0（すぐ使える）。

段階の間の演出時間は定数にして較正する（初期値は録画 0018 の目視）:

```ts
/** バーストゲージの上限（CDN の target_burst_energy_pershot と同じ単位） */
export const BURST_GAUGE_MAX = 1_000_000;
/** 満タン（または CT 明け）から I の発動までのフレーム */
export const BURST_READY_DELAY_FRAMES = 20;
/** I → II の発動の間隔（フレーム） */
export const BURST_STEP1_TO_STEP2_FRAMES = 20;
/** II → III の発動の間隔（フレーム） */
export const BURST_STEP2_TO_STEP3_FRAMES = 20;
/** StepFull の発動からフルバースト開始まで（フレーム）。Stage 6 の実測で 3f 未満 */
export const FULL_BURST_START_DELAY_FRAMES = 0;
/** フルバースト時間（フレーム）。burst_duration は取り込むが使わない（9 節 3） */
export const FULL_BURST_FRAMES = 600;
/** チェーン中に次の段階の候補が出ないまま待てるフレーム（録画 0022 で約 600f） */
export const BURST_CHAIN_TIMEOUT_FRAMES = 600;
```

演出時間は 3 つに分けて export し、実測で個別に直せるようにする。カットインやモーションの長さはキャラ・端末で少しぶれる可能性があるので、値は 1 フレーム単位で読んだ**中央値**を採り、回帰テストの許容幅はばらつきから決める。キャラごとに明らかに違うと分かったら、そのときにキャラ別の上書きを検討する（Stage 7 では全員共通）。フレーム落ちの多い録画は時間計測の母数から外す。

1 発あたりのゲージ（9 節 5。係数は 12 節で確定）:

```
energyPerTrigger = shot.targetBurstEnergyPerShot × shot.shotCount × (チャージ武器 ? shot.fullChargeBurstEnergy : 1)
```

1 トリガーは「弾薬を 1 消費する 1 回の射撃」。`maxAmmo` はトリガー数で数える（SG の装弾数 9 = 9 トリガー）。`ShotParams.shotCount` は **1 トリガーで出るペレット数**（SG は 10、ツバイだけ 5、それ以外の武器は 1。弾薬の消費数ではない）で、Stage 1 以来この意味でダメージ側も同じ変数を使っている。ペレット数のために新しい変数は作らず、JSDoc を直す。`muzzleCount = 2`（二丁持ち）はダメージ側と同じく「未対応」の注記を出し、ゲージは銃口 1 つとして数える。

**射撃がフレーム f に起きたら、そのフレームでゲージに入る**（弾速・着弾遅延は無視）。ずれが数フレームなら 40 秒周期には効かないのでこのままにし、それを超えるなら武器種ごとの遅れの定数を足す。

**スコープ外**: ゲージ充填速度を上げるスキル（段階 C で `stat` を足す）、CT 短縮（段階 D = Stage 9）、敵ごとのゲージ補正（レイドボス。射撃場の的だけを較正する）、手動バースト（常に自動バーストの挙動を再現する）。

## 3. core の共通部分 — 時刻表の一般化

### 3.1 `BurstSchedule`（`burst/schedule.ts` 新設）

Stage 5 / 6 の `FixedCycleSchedule` は「全段階が同じフレーム」「段階の割当は固定」を前提にした形なので、動的サイクルでは表せない。**発動 1 回ずつを列挙する形**に一般化する。

```ts
export type BurstActivation = {
  frame: number;
  step: BurstStepKey;
  slotIndex: number;
  /** この発動でフルバーストに入るか（nextStep が StepFull） */
  startsFullBurst: boolean;
};

export type BurstSchedule = {
  /** 発生順 */
  activations: BurstActivation[];
  /** [start, end) の列。末尾は戦闘時間で切る */
  fullBurstWindows: FullBurstWindow[];
  fullBurstFramesTotal: number;
  /** 表示・テスト用。ゲージが満タンになったフレーム、チェーンが切れたフレーム */
  gaugeFullFrames: number[];
  chainTimeouts: number[];
  model: 'fixed' | 'dynamic';
};
```

- `planFixedCycle` は**この形を返すように書き換えて残す**（9 節 2）。各サイクルの発動フレームに I / II / III を同じフレームで並べるだけで、Stage 6 の数値はそのまま再現できる（6.2 節の退化テスト）。
- 段階の割当の差し替え口は `activations` から引く形に、`isFullBurstFrame`（サイクル内の位置で判定）は `fullBurstWindows` を見る `isInWindows(frame, windows)` に置き換える。

### 3.2 状態機械（`burst/controller.ts` 新設）

1 節の状態機械を、**「このフレームに入ったゲージ量」を受け取って 1 フレーム進める**純粋な状態機械（`stepBurstController`）にする。ゲージ量の出どころ（sim の実射撃か calc の平均レートか）は知らない。1 フレーム進める形にしておくのは、1 パス化（10 節）で再利用するため。

### 3.3 動的時刻表（同上ファイル）

`planDynamicSchedule(slots, frames, model)` は、**各枠の射手（`sim/shooter.ts`）を 1 フレームずつ回し、撃ったフレームに `energyPerTrigger` をゲージに入れて `stepBurstController` を進める。** Stage 7 の範囲では射撃のタイミングがバフにもバーストにも依存しない（弾数・リロード・チャージ速度のバフは段階 C / D）ので、射撃列は Stage 5 / 6 の sim と 1 フレームも変わらない。つまり時刻表は編成だけから決まる純関数で、**sim と calc が同じ時刻表を共有できる**（9 節 1）。

## 4. sim（`sim/engine.ts`）

**2 パス**にする。

1. `planDynamicSchedule` で時刻表を作る（射手を 1 回回してゲージを溜める）。
2. その時刻表で Stage 6 のフレームループをそのまま回す（`planBuffTimeline` → 区間ごとの 1 トリガー値 → 射撃の加算、発動フレームでバーストヒット）。

ループの中でゲージを溜めて発動を決める 1 パス方式にしないのは、**持続バフの区間（`planBuffTimeline`）を先に作る Stage 6 の構造を崩さないため**。1 パスが要るのは射撃がバフに依存するようになる段階 C / D で、そのときに考える（10 節）。

バーストヒットは `schedule.activations` の各発動（`slotIndex` がその枠）について、Stage 6 と同じ `burstSnapshotState`（発動直前のバフ）で計算する。**同じ段階の 2 体が CT で交互に撃つ編成では、発動する枠が回ごとに変わる**。

## 5. calc — sim の時刻表を取り込む

### 5.1 core（`team.ts`）

`TeamInput.burstModel?: 'dynamic' | 'fixed'`（省略 `'dynamic'`。`'fixed'` は固定 20 秒サイクルでテスト・比較用）を足し、`planTeamSchedule` が `planDynamicSchedule` / `planFixedCycle` を選ぶ。**calc の時刻表は sim と同じ `planDynamicSchedule` の結果**で、calc が期待値で置くのは Stage 5 / 6 と同じく**通常攻撃の区間ごとのトリガー数**だけ。したがって Stage 5 / 6 の不変条件「sim と calc の差は発射サイクルの離散化だけ」が Stage 7 でもそのまま成り立つ。

結果に `BurstSummary`（フルバーストの回数・稼働率・平均サイクル秒数・初回の秒数・チェーン失敗の回数）を足す。ロードマップの「sim で計測された平均サイクル秒数やフルバースト稼働率を取り込む」は、これを時刻表と一緒に sim 側の計算から受け取ることで満たす。平均レートからサイクルを式で出す近似（9 節 1 の代替案）は採らない。

### 5.3 UI（最小限）

apps/calc の入力は `burst: boolean` のトグルのままで、ON は動的サイクル（固定サイクルは UI に出さない。9 節 2）。フルバーストの回数・稼働率・平均サイクル・初回と、バーストの時刻表は、編成全体のものなので枠ごとのパネルではなく `TeamBreakdown` に置く。

## 6. テスト・検証（PDCA）

### 6.1 状態機械の単体テスト（`burst/__tests__/controller.test.ts`）

ゲージ量を手で与え、射手は使わない。ゲージ律速・CT 律速（フルバースト開始の間隔がちょうど 2,400f）・同じ段階の 2 体（交互に撃つ）・段階の欠け（II の後 600f でチェーン失敗。I の CT 待ちはタイムアウトしない）・II の CT 待ちで失敗（録画 0022 の 2 回目の挙動）・リエントリー・`AllStep` / `NextStep`・フルバースト中・戦闘終了で切る、を固定する。

### 6.2 退化テスト（Stage 6 との厳密一致）

- `burstModel: 'fixed'` で、Stage 6 の既存テストの数値が**そのまま**通る（`FixedCycleSchedule` → `BurstSchedule` の書き換えで数値が 1 ビットも変わらない）。
- `burst: false` は Stage 4 と一致。
- sim の射撃フレーム列が Stage 5 / 6 と一致。

### 6.3 sim と calc の整合（`simCalc.test.ts` を拡張）

Stage 6 の 3 段構成（厳密一致・離散化誤差・収束）のまま、時刻表を動的にする。

### 6.4 録画 0018〜0022 の再現（回帰テスト `__tests__/burstRegression.test.ts`）

スペック固定の 4 編成で、フルバーストが **180 秒で 5 回**、2 回目以降の間隔が CT 40 秒の周期、1 回目の満タンまでの時間が録画の幅の中。III のいない編成で、フルバースト 0 回・チェーン失敗が録画と同じ回数。

### 6.5 ゲージの較正（新規撮影）

**0 節の読み取りでは係数が決まらない**。操作キャラと AI とでゲージ量が違うらしいと分かったので、同じキャラを (a) 操作してコアを狙う、(b) 操作して胴体を撃つ、(c) AI にする、の 3 通りで、単騎・自動バースト OFF・射撃場の通常モードで撮り、1 発ずつのゲージの増分を読む。武器種は AR・SG・SR・RL・MG（結果は 12 節）。

## 8. Stage 6 までの数値への影響

`burst: true` の結果はすべて変わる（固定サイクルが前提だったため）。III 1 体・CT 40 秒の編成では、フルバーストの回数・稼働率・バーストスキルの回数・`burstUse` のバフの稼働率がおよそ 5/9 になる。Stage 6 までに verification.md に書いた calc の数値は**固定サイクルの値として**残し、Stage 7 節に動的サイクルの値を並べる。

## 9. 決めてほしいこと（推奨付き）

2026-09-23 に 9 点とも推奨案で承認された。

1. **calc の時刻表** — **sim と同じ `planDynamicSchedule` を使う**（3.3 節・5.1 節）。射撃がバフに依存しない Stage 7 では時刻表が編成だけで決まるので、calc が近似する必要がない。Stage 5 / 6 の不変条件（sim と calc の差は通常攻撃の離散化だけ）がそのまま保てる。計算量は 10,800f × 5 枠の加算で、calc の再計算 1 回あたり数ミリ秒。採らない案: 平均ゲージ量（秒間トリガー数 × 1 発のゲージ）からサイクル秒数を式で出す。軽いが、満タンのタイミングが 1 秒ずれるだけで 180 秒内の回数が 5 ↔ 4 と跳ぶことがあり、sim との差が離散的に開く。

2. **固定 20 秒サイクルを残すか** — **core に `burstModel: 'fixed'` として残し、UI には出さない**。Stage 5 / 6 の数値（verification.md）とテストの期待値をそのまま守れる。退化テスト（6.2）の相手にもなる。採らない案: 削除して Stage 6 のテストを動的サイクルの値に書き換える（テストの期待値を大量に作り直すことになる）。

3. **フルバースト時間** — **全員 10 秒固定**。`burst_duration` は取り込むが使わない。500 と 1,500 の意味が「フルバースト時間」なのか「バーストスキル効果の時間」なのか確かめていないため。採らない案: III の `burst_duration` をフルバースト時間にする。

## 10. リスク・留意点

- **射撃がバフ・バーストに依存するようになると 2 パスが使えない**: Stage 8 / 9 で弾数・リロード・チャージ速度のバフや CT 短縮が入ると、射撃列 → ゲージ → 時刻表 → バフ → 射撃列…が循環する。そのときは sim を 1 パス（フレームループの中で状態機械を回し、持続バフも逐次付与）にし、calc は sim の時刻表を受け取る形（9 節 1 の延長）にする。
- **180 秒の境界で回数が跳ぶ**: 5 回目のフルバーストは戦闘 約 165 秒に始まる。1 回目が 15 秒以上遅れると 5 回目が 180 秒に入りきらず、フルバースト稼働率とバーストスキルの回数が段で落ちる。1 回目の満タンまでの時間の較正の精度はこのために要る。
- **読み取りの分解能**: BURST バーは 1px ≈ 0.85%。1 発 0.4% の AR は 1 発ずつは読めず、マガジン単位の傾きで読む。フルバースト中と CT 待ち中はバーの位置に別の UI が出るので、その間の値は捨てる。
- **`burstUse` と `fullBurstStart` が別フレームになる**: I の `burstUse` のバフはフルバーストより早く付いて早く切れる。持続バフの区間が 1 つ増えるだけで、Stage 6 のタイムラインはそのまま扱える。
- **マナ S2 の `assumes`**: 「毎サイクル自分がバーストする（マターシグマが再付与される）」は、III がマナ 1 体なら動的サイクルでも成り立つ。III 2 体の交互編成では成り立たないが、その判定は段階 C（状態フラグ）まで持ち越す。

## 12. ゲージの較正の結果（2026-09-23、録画 0023〜0035）

6.5 節の撮影（同じキャラを操作・コア / 操作・胴体 / AI）で、1 トリガーのゲージ量を次の式に確定した（数値は [verification.md](verification.md) Stage 7 節）。

```
energyPerTrigger = targetBurstEnergyPerShot × 1.2 × ペレット数 × (SG ? 0.75 : 1) × (操作キャラのチャージ武器 ? fullChargeBurstEnergy : 1)
```

- **×1.2**（`BURST_ENERGY_MULTIPLIER`）: AR・MG・RL・SR のどれも CDN 値の約 1.2 倍。コアと胴体で差はない。射撃場の的固有かもしれない。
- **SG 0.75**（`SG_PELLET_GAUGE_HIT_RATE`）: SG の 1 トリガーが全ペレット命中の予測の約 0.75 倍。
- **フルチャージ倍率は操作キャラだけ**: AI のチャージ武器は倍率なし。9 節 5 の仮説（全員にフルチャージ倍率）を訂正し、`TeamInput.controlledSlot`（省略は全員 AI）を足した。calc には「操作キャラ」の選択を出した（9 節 2 の「UI には出さない」は固定サイクルの話で、こちらは新しい入力）。
- 2 回目以降のフルバーストは CT 律速で、回数（5 回）と周期（2,400f）は録画と一致する。1 回目の満タンまでの時間に残る差は、演出時間の定数（20f の仮の値）と MG のスピンアップの読み直しで詰める。
- SG のダメージ計算は全ペレット命中の仮定のままなので、射撃場の距離で 1/4 が外れているなら SG の総ダメージは過大かもしれない（Stage 8 以降で確認）。
