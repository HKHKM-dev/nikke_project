## 1. 背景

- calc（区間期待値のモデル）は一本化（[design-unify-sim-calc.md](design-unify-sim-calc.md)）で消えたのに、1 パス目・区間・ダメージの式のコメントが、まだ「calc と sim で共通」「calc はグループごとに computeDamage を呼ぶ」と書いている。読む人は、いまも 2 つのモデルがあると読み違える。
- ファイルの冒頭の注釈に、Stage や「〜編」ごとに「〜を足した」が 1 行ずつ積み重なったものがある（`skills/types.ts`・`frame/firstPass.ts`・`scripts/sim-run.ts` など）。いまの形を知るには全部を読んで頭で重ね直す必要があり、前の形の記述（「〜までは」「〜をやめた」）は読む人に要らない。
- 文書には「現状の型」の決まり（AGENTS.md「文書の書き方」）があるが、コードのコメントの書き方の決まりは無い。決まりが無いので、新しい PR も冒頭の注釈に「〜編で〜を足した」を 1 行足す形で増え続けている。

## 3. コメントの書き方の決まり（案）

文書の「現状」の型（AGENTS.md「文書の書き方」）を、コードのコメントにも当てる。

1. いまの振る舞い・形・制約（不変条件・呼ぶ順番・入力の前提）だけを書く。変わったら書き換え、古い記述は消す。
2. 書かないもの:
   - いつ・どの段で足した・変えた・移したか（「Stage N で」「〜編で」「段 X で」「2026-MM-DD に」）
   - 前の形と、前の形との比べ（「〜までは」「〜をやめた」「〜から移した」「Stage 5 とまったく同じ」）
   - もう無いもの（calc・`calc/model.ts`・`planBuffTimeline` など）との比べや、それを消したこと
3. 理由が要るときは、設計書の節を 1 つ指す（`plan/design-x.md N 節`）。根拠の ID（`C-NNNN`・`V-NNNN`・録画の番号・観測値の ID）は、いまの振る舞いの根拠なので残す。
4. 冒頭の注釈には、そのファイルが持つもの・入口・ほかのファイルとの分担と、ファイル全体にかかる約束（フレームの中の順番など）を書く。効果の種類やオプションを、足した順に並べない（効果の語彙は型の定義の JSDoc に置き、CLI のオプションは使い方の出力と同じ並びで 1 か所に書く）。
5. 識別子・文字列（エラー文・CLI の出力・保存キー）は、この決まりで変えない。

決まりは AGENTS.md「文書の書き方」に 1 行で足す（「コードのコメントも現状の型で書く。経緯は設計書と git の履歴に置く」）。

## 4. 直す範囲（案）

### 4.1 直すもの

- 段 1: 2.1 節の A・B・C の全部（テストを除く）。
- 段 2: 2.2 節の冒頭の注釈（41 ファイル）を、3 節の決まりで書き直す。冒頭から出したいまの説明は、その説明が当たる関数・型の JSDoc へ移すか、冒頭に残す。
- 段 2 のうち、冒頭の注釈が本体のコメントで書いていることを繰り返しているときは、冒頭の側を消して本体を残す。
- 2.3 節の本体の前置き（「Stage N:」「〜編:」）は一括では直さない。前の形を書いた記述（「〜までは」「〜では passive にだけ書けた」など）だけを段 2 で直し、前置きは、そのコメントの近くを別の PR で直すときに外す（7 節の論点 1）。

### 4.2 対象外

- 2.1 節の D（古いデータを弾く検査のエラー文）: 古い観測値・予測の JSON を持つ人に、なぜ弾かれるかを伝える出力で、コメントではない。検査の上のコメント（「一本化の段 A-3: calc の経路は消した」）だけを「model は sim だけを受ける（古い calc の指定を弾く）」に直す（段 1）。
- 2.1 節の E（`CalcView`・変数の `calc`・保存キー `nikke-calc.*`・vitest の project 名）: 識別子と文字列。保存キーを変えると利用者の保存データが読めなくなる。`CalcView` の名前を変えるかは、この設計の範囲外。
- テスト（`*.test.ts`・`__tests__/`）: ファイル名・describe 名が経緯で付いているもの（`stage10Shooter.test.ts` など）が多く、直すと差分が大きい。テストは利用者の読む所ではない。
- 本番のコードから呼ばれない関数（2.1 節の `simGroupTotals`）をテストの側へ移すこと: コードの変更で、コメントを直すこの設計とは別の課題。
- 設計書・検証記録（記録の型）。コメントが指す設計書の節は、その時点の版（AGENTS.md「文書の書き方」）なので、そのまま指してよい。

## 5. 段取り

- 1 段 1 PR。段 1（calc）→ 段 2（冒頭の注釈）の順。段 2 は差分が `packages/core/src/frame/`・`skills/`・`sim/` に広がり、並行する PR と冒頭の注釈で衝突しやすいので、出す前に `npm run pr:prep` で main を取り込み、衝突したら main の側の足した行をこの決まりで書き直して取り込む。

- 見直し（AGENTS.md「コミット手順」）: コメントだけの変更でも数行の直しではないので、どちらの段も `/simplify` と `/code-review` を回す。段 1・段 2 とも `frame/`・`sim/` を触り、段 2 は `tools/git/` も触るので `high`。見るのは、直したコメントがいまのコードと合っているか（呼ぶ側・順番・型の名前）。
- どちらの段も `npm test` を通す（コメントだけなので振る舞いは変わらないが、lint・書式の確認を含む）。

## 6. 起こりうること

- 段 2 の書き直しで、経緯の行に混じっていたいまの説明（例: `frame/firstPass.ts` の手順 3 の順番、`skills/timeline.ts` の段の印）を落とす。直すときは、経緯の段落ごとに「いまも正しい説明か」を見て、正しいものは 1 か所にまとめて残す。順番の説明は、コードの並び（`firstPass.ts` の手順 3 の呼ぶ順）と照らして書く。
- 並行する PR が、段 2 の後に冒頭へ「〜編で〜を足した」を足す。AGENTS.md の 1 行で防ぐ。足されたら、その近くを直すときに直す。
