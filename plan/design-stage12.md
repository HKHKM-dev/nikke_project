## Context

Stage 1〜11 で、**スペック固定の射撃場**を基準に、ダメージ式・発射サイクル・バースト・スキル語彙・主力キャラ（リター・クラウン・アリス・モダニア。紅蓮：ブラックシャドウは設計書レビュー待ち）を固めてきた。ロードマップの残りは「Stage 12+: 育成拡張（OL・キューブ）& 公開準備」の 1 行だけで、中身が 4 つ（育成入力の拡張・calc の入力フォーム・実戦録画との突き合わせ・公開）まとめて書いてある。

この 4 つは依存関係がある。**実戦（迎撃戦・レイド）ではスペック固定が無く、装備・OL・キューブ・好感度・コレクションがすべて乗る**ので、育成入力を先に広げないと実戦の総ダメージは突き合わせられない。また育成入力そのものも、「戦闘中の攻撃力を作るもの」（装備の攻撃力、キューブ・好感度・コレクションのステータス）と「戦闘中にバフとして効くもの」（OL の攻撃力▲・属性ダメ▲・クリ率・クリダメ・チャージ系・最大装弾数、キューブの固有効果、コレクションの武器種効果）の 2 層に分かれ、前者は Stage 1 の `computeStat` と `fixedSpec.ts` の式の一般化、後者は Stage 4 の常時発動パッシブ（`passive`）と同じ形で既存の `BuffTotals` に合成できる。

そこで **Stage 12 = ステータス層、Stage 13 = 効果層、Stage 14 = 公開、Stage 15 = 実戦との突き合わせ**の順に切り、Stage 5 以降と同じ「sim → calc → 実測」の小さな PDCA を 1 Stage ずつ回す。**設計の芯は「スペック固定を、一般の育成入力の 1 つのプリセットにする」こと。** Stage 2-A で 9 体誤差ゼロを確かめた `computeFixedSpecAttack` を捨てず、一般化した式の退化テストとして残す。

## 2. Stage 12: 育成入力の拡張 A — ステータス層

### 2.1 モデル（`packages/core/src/build.ts`、新規）

```ts
export type GearTier = 'T1' | ... | 'T9' | 'T10';
export type GearPart = 'head' | 'body' | 'arm' | 'leg';          // CDN の Module_A〜D
export type GearInput = { tier: GearTier; level: number; overload: boolean } | null;   // null = 未装備

export type BuildInput = {
  growth: GrowthInput;                                            // Stage 1 のまま
  affectionRank: number;                                          // 1..40（好感度）
  gear: Record<GearPart, GearInput>;
  cube: { id: number; level: number } | null;                     // level 1..15
  collection: { stage: number } | null;                           // R/SR のお気に入り（Lv 0..15）。SSR（宝物）は treasurePhase と別に「宝物のステータス」を足す
  recycleRoom: { personal: number; class: number; corporation: number };   // 研究段階（0 = 未研究）
  extraAttack: number;                                            // 企業タワー・アウトポスト等の固定加算（CDN に無いもの。ユーザー入力）
};

export type CombatAttack = {
  attack: number;          // 戦闘中の攻撃力（バフ前）。キャラ画面の表示値と一致させる
  gradeBase: number; affection: number; withCore: number; gear: number; cube: number; collection: number; recycleRoom: number; extra: number;
};
export function computeCombatAttack(character, build: BuildInput, masters: BuildMasters): CombatAttack;
```

- **`computeFixedSpecAttack` は `computeCombatAttack(character, fixedSpecBuild(character), masters)` に置き換え、`fixedSpec.ts` の固定値（T9 Lv5 のクラス別攻撃力・好感度 rank 別の加算）はマスタから引いた値と一致することをテストで固定する**（退化）。固定値の定数は消さずに「マスタとの一致テスト」の期待値として残す。
- 合成順は 0.1 節のスペック固定の式を出発点にする。**キューブ・コレクション・リサイクルルームの加算が「コアが掛かる側」（好感度と同じ）か「掛からない側」（装備と同じ）かは、2.4 節の実測 (b) で決める**。設計時点の仮定: **好感度と同じ側（コアが掛かる）** — 理由は、別プロジェクトの式がどれも「素と同列の加算」として扱っており、装備だけが別扱い（スペック固定の実測）だから。仮定は `BUILD_CORE_APPLIES_TO` のような定数で 1 箇所に置く（Stage 10 の仮の定数と同じ運用）。
- `TeamSlotInput` は `growth` の隣に `build?: BuildInput` を持ち、**`build` があれば `computeCombatAttack`、無ければ従来の `computeStat`（素のステータス）**。`attackOverride` は残す（実測の逆算に使う）。calc の `fixedSpec: true` は `build` を `fixedSpecBuild` にする経路に変える。

### 2.2 データ取得（`fetch-data.ts` の拡張）

- 取得先は 0.2 節。正規化して `packages/core/data/masters/{gear,affection,cubes,collections,recycleRoom}.json` に書き出す（`formatVersion: 1`）。キューブは `cube_{id}.json` を 1000301 から連番で探索し、404 で止める（別プロジェクトと同じ方法。取得済みの id は `index.json` に残す）。
- 装備マスタは Stage 12 で使う `Atk` だけを正規化する（HP・防御は保持のみ）。**T9 Lv5 のクラス別攻撃力（7,349 / 5,879 / 8,818）が復元できることをテストにする**。
- コレクション（R/SR）は Stage 9 の `TreasureData` の取得経路を R/SR に広げる。ステータス（Lv 別）を足し、スキル（武器種効果）は Stage 13 で使う。
- OL オプションの数値は取れないので、Stage 12 では扱わない（Stage 13、3.2 節）。

### 2.3 calc・CLI・保存形式

- **calc の枠カード**（`SlotCard.tsx`）に「育成」の折り畳みを足す: 好感度ランク・装備 4 部位（ティア / Lv / OL）・キューブ（種類 / Lv）・コレクション Lv・リサイクルルーム・その他加算。**スペック固定 ON のときは全部グレーアウト**して固定プリセットを表示する（今の挙動と同じ）。
- **CLI** `sim-run.ts` に `--build <file.json>`（枠ごとの `BuildInput` の JSON）を足す。射撃場の実測の予測はこれで出す。
- **保存形式**: `parseTeamState` は `build` の欠落を「素のステータス」（従来どおり）として読む。Stage 14 で `formatVersion` を付けるまでは追加フィールドだけで済ませる。
- **ビルドの取り込み**: アカウント連携はしない（要件 3 節）。ただし **枠ごとの `BuildInput` を JSON で貼り付け / 書き出しできる欄**を calc に足す（Stage 15 の入出力の前倒し。9 節 3）。
