# 育成データの取得のルーティン化 設計書

- 対象: ShiftyPad（Blablalink）からのオーナーの育成データの取得（[design-stage12.md](design-stage12.md) 11.1 節の手順）、`--build` の育成入力（`packages/core/scripts/sim-run.ts`・`packages/core/src/build.ts`）、録画の台帳（`records/recordings/`）、`private/`
- 状態: **起案（2026-10-29）**。12 節の判断待ち
- 関連: [design-stage12.md](design-stage12.md) 11.1 節（API とフィールドの写し方）、[captures/guide.md](captures/guide.md)「実ビルド」の行、[captures/protocol.md](captures/protocol.md)、[design-cloud-environment.md](design-cloud-environment.md)（`private/` の同期）、[references.md](references.md)（ExiaInvasion の規約の注意）、V-0462・V-0486
- 作成日: 2026-10-29
- 調べた時点: main の 12dce19（#747）。このクラウドのセッションには `private/`・`scratch/` が降りていなかったので、取得済みのデータとその変換の跡は見ていない

## Context

スペック固定 OFF の録画（迎撃戦の特殊個体・射撃場の実ビルド）を読むには、撮った時点のオーナーの育成（装備・OL・キューブ・コレクション・好感度・リサイクルルームの研究・スキル Lv）が要る。今はこれを、撮る日ごとに次の手作業で用意している。

1. Claude のブラウザペインで ShiftyPad を開き、オーナーがログインする。
2. ページが送るリクエストのヘッダを拾って 3 つの API を呼び、ページに足したボタンでクリップボードへ出し、PowerShell の `Get-Clipboard` で受ける（11.1 節）。
3. アカウントを特定できる値を除いて `scratch/` に置き、そのつど `--build` の JSON（resourceId → `BuildInput` と `growth`）に手で（その場のスクリプトで）写す。
4. どの育成で読んだかは、録画の台帳の `conditionNote` に自由文で書く（例: 録画 0577「2026-10-24 に ShiftyPad から取った育成」）。

困ること:

- 取り方が毎回の手作業で、ブラウザペインとクリップボードを経るので、撮る日の手間が大きい。
- 写し方（11.1 節「写し方」）がコードに無い。毎回書き直すので、写し方の誤りがテストで捕まらない。
- 前の取得との差が見えない。V-0462 は、企業の研究の Lv が古い育成データのまま 5 体を読み、防御力を誤った（V-0486 で棄却）。差が出ていれば、撮る前に気づけた。
- 録画とその育成の対応が自由文なので、ツール（読み取り・残差）が辿れない。
- クラウドと worktree のエージェントは所持を確かめられず、設計書ごとに「所持はオーナーに聞く」と書いている（[design-persona.md](design-persona.md)・[design-heal-vocabulary.md](design-heal-vocabulary.md) ほか）。

## 1. 目標

- 1 つのコマンドで「取る → アカウントの値を除く → `--build` の形に写す → 前回との差を出す」まで終わる。
- 写し方は core の純関数にし、テストで固定する（テストのデータは作った値。実データはコミットしない）。
- 録画の台帳が、読むのに使う育成のスナップショットを構造で指す。
- 守ること（11.1 節のまま）: パスワード・トークン・Cookie をツールが読まない・保存しない。API は読み取りだけ。アカウントのデータは公開リポジトリに入れない。

## 2. 取る（デスクトップ）

### 2.1 案

| 案          | 中身                                                                                                                                                                                                                                                          | 良い点                                                                                                     | 弱い点                                                                                                                    |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| A（推奨）   | `npm run build:fetch` が Playwright で、インストール済みの Chrome（`channel: 'chrome'`）を画面ありで開く。ユーザーデータのフォルダはリポジトリの外の専用のもの（パスは `private/`）。ログインが切れていれば、開いた窓でオーナーがログインするのをツールが待つ | 2 回目からはコマンド 1 つ。ファイルに直接書けるので、ページの CSP を避ける細工（クリップボード）が要らない | 依存（`playwright-core`）が増える。デスクトップで 1 回試すまで、ShiftyPad が自動操作のブラウザを拒まないかは分からない    |
| B           | ブックマークレット。ShiftyPad のページで押すと、ページの `fetch` を包んでヘッダを拾い、3 つの API を呼んで JSON をダウンロードさせる                                                                                                                          | 依存が増えない                                                                                             | ニケを 1 体開く操作が要る。受け取ったファイルを `npm run build:import` に渡す手順が残る。ページの作りが変わると壊れやすい |
| C（不採用） | クラウドの Routine で定期的に取る                                                                                                                                                                                                                             | 手が要らない                                                                                               | クラウドにログインの状態（Cookie かトークン）を置くことになり、1 節の「守ること」に反する                                 |

### 2.2 A の流れ

1. 専用のプロファイルで ShiftyPad を開く。ログインの画面なら、ログインし終わるまで待つ（ツールは入力に触れない）。
2. ページ自身が送る `GetUserCharacterDetails` などのリクエストを `page.on('request')` で拾い、同じヘッダを得る（11.1 節の手順と同じ。ヘッダは処理の間だけメモリに置き、書き出さない）。
3. ページの文脈（`page.evaluate`）で 3 つの API を呼ぶ: `Game/GetUserCharacters`・`Game/GetUserCharacterDetails`（20 体ずつ）・`Game/GetUserProfileOutpostInfo`。Cookie はブラウザが付けるので、ツールは値を見ない。
4. 応答から `intl_open_id` などアカウントを特定できる値を除いて、生のスナップショット（`private/builds/<YYYY-MM-DD>.raw.json`）に書く。生を残すのは、写し方の誤りが後で見つかったときに取り直さずに写し直すため。
5. 3 節の写し方を通し、4 節の差を出す。

- 同じ日に 2 回取ったら、`<YYYY-MM-DD>-2` のように枝番を付ける（撮影の合間に育成を変えた日のため）。

## 3. 写す（コミットするコード）

- `packages/core/src/build/shiftypad.ts`（純関数）: 生のスナップショットとマスタ（CDN のキャラ一覧・`ItemEquipTable` など）から、スナップショットを作る。写し方は 11.1 節「写し方」をそのままコードにする（`name_code` → resourceId、装備の tid → 部位・T9 / T10・企業、OL のオプション ID → 種類・Lv、キューブ、コレクション、好感度、研究の Lv、スキル Lv）。
- スナップショット（`private/builds/<YYYY-MM-DD>.json`）の形: `takenOn`・`synchroLevel` と、resourceId ごとの `growth`・`build`（`BuildInput`）・`skillLevels`・`treasure`。resourceId → `growth` と `BuildInput` の部分は、今の `--build` の JSON（`sim-run.ts` の `BuildFile`）と同じ形にして、そのまま `--build` に渡せるようにする。
- `skillLevels` は今の `BuildFile` に無い（`--skill-levels` で別に渡している）。`--build` のエントリにも `skillLevels` を書けるようにし、`--skill-levels` が指定されていればそれを優先する。
- 宝物の段階: API の `favorite_item_lv` と段階の対応は分かっていない（11.1 節「分からないまま残るもの」）。写し方では決めず、`treasure: { level, phase: null }` とし、差の表示と CLI に「宝物の段階は未確定（`--treasure` で指定する）」と出す（AGENTS.md のプレースホルダーの規則）。
- マスタの表に無い tid・オプション ID は、黙って捨てずに「写せなかった値」として一覧に出す（Stage 13 の `CUBE_SKILL_EFFECTS` と同じ考え方）。
- テスト: 作った生のデータ（2〜3 体、OL・企業装備・キューブ・R / SR コレクション・宝物を 1 つずつ含む）で、写した結果と、計算した攻撃力が手計算と合うことを固定する。

## 4. 前回との差

- 取るたびに、直前のスナップショットとの差を出す（標準出力と `private/builds/<YYYY-MM-DD>.diff.md`）。
  - 増えた所持キャラ・凸・コア
  - キャラごとの装備・OL の行・キューブ・コレクション・好感度・スキル Lv の変化
  - リサイクルルームの研究の Lv の変化（アカウント全体に効くので、効くキャラの数も出す）
  - `computeCombatAttack` で出した戦闘中の攻撃力の変化（キャラごと）
- V-0486 の見落とし（研究の Lv）は、この差の一覧の「研究」の行に出る。

## 5. 置き場所

- `private/builds/`（AGENTS.md「記録の置き場所」で、育成状況は `private/`）。生のスナップショットは 1 回で数百 KB 以下の見込みで、クラウドの始めのフックが中身まで取る 1 ファイルの上限（`tools/drive/cloud-sync.ts` の 5MB）に収まる。クラウドのセッションも、始めのフックで降りてきたものを読める。
- 今の `scratch/` の下にある取得済みのデータ（`scratch/blablalink/` など）は、オーナーの手元で生のスナップショットの形にそろうなら `private/builds/` に移す。そろわないものは `scratch/` に残し、台帳は 6 節の欄を付けない（自由文のまま）。

## 6. 録画との結び付け

- 録画の台帳に `buildSnapshot`（`"2026-10-24"` か `"2026-10-24-2"`）を足す。スペック固定 OFF（`fixedSpec` が `true` でない）で、実ビルドの録画に書く。既存の録画は書き直さない（`conditionNote` の自由文のまま）。
- `tools/captures/intake.ts`: 取り込む録画の日付以前で最新のスナップショットを既定にして聞く。その日に取ったスナップショットが無ければ「撮った日の育成が無い（最新は YYYY-MM-DD）」と知らせる。
- `records:check`: `buildSnapshot` の形だけを確かめる（スナップショットの実体は `private/` にあり CI から見えないので、有無は確かめない）。
- 読み取りのレシピ・残差で使う育成は、この欄から引ける（使い方は、要る検証が出たときに足す）。

## 7. いつ取るか

時刻ではなく、出来事で取る（推奨）。育成データが要るのはスペック固定 OFF の録画を読むときと所持を確かめるときだけで、決まった間隔で取っても使われない。

- スペック固定 OFF の撮影の日に、撮る前に `npm run build:fetch`（`protocol.md` に 1 行）。
- 育成を変えたとき（オーナーが任意で）。
- 取り忘れは、6 節の `intake.ts` の知らせで気づく。

代替: Windows のタスクスケジューラで週 1 回回す（ログインが切れていたら、取れなかったことだけ知らせる）。12 節 5。

## 8. 所持の一覧

- 取るたびに、スナップショットから所持の一覧（`private/roster.md`。キャラ名・resourceId・凸・コア・スキル Lv・キューブ・宝物）を作り直す。
- `private/owner.md` の手書きの内容は変えない。所持の一覧の正は `roster.md`（生成）に移し、`owner.md` の所持の節はそこを指す（移すかはオーナーの判断。12 節 6）。
- これで、クラウドと worktree のエージェントも、撮影の候補が所持キャラかを確かめられる（クラウドは始めのフックで `private/` が降りるので）。`protocol.md` の「所持の一覧はメインのチェックアウトの `private/`」の行を、`private/roster.md` に直す。

## 9. 規約とアカウント

- 読むのはオーナー自身のアカウントの、ShiftyPad の画面に出るのと同じデータで、頻度は撮影の日に 1 回程度。書き込む API は呼ばない。
- [references.md](references.md) の ExiaInvasion は、Blablalink の自動取得に規約違反の可能性があると README に書いている。今の手順（11.1 節）も同じ API を呼んでいるので、ルーティン化で増えるのは手間の削減だけで、呼ぶ API と頻度は変わらない。それでも、自動操作のブラウザを使うこと（案 A）を許すかはオーナーの判断（12 節 1）。

## 11. 分からないこと

- ShiftyPad が自動操作のブラウザ（Playwright の Chrome）でのログインを拒むか。段 2 の最初にデスクトップで試す。拒まれたら案 B に切り替える。
- 今ある取得済みのデータ（`scratch/` の下）の形。このセッションからは見えないので、段 1 のデスクトップでの確かめで合わせる。
- 宝物の Lv と段階の対応（11.1 節。この設計では決めない）。

## 12. 判断してほしいこと

1. **取り方** — 推奨: **案 A（Playwright・インストール済みの Chrome・専用プロファイル）**。拒まれたら案 B。代替: 案 B から始める（依存を増やさない）。
2. **依存** — 推奨: **`playwright-core` を devDependencies に足す**（ブラウザは落とさず、`channel: 'chrome'` でインストール済みの Chrome を使う）。代替: デスクトップにだけ入れて、リポジトリの依存には足さない。
3. **置き場所** — 推奨: **`private/builds/`**（生・写した結果・差）。代替: `scratch/blablalink/` のまま。
4. **台帳の欄** — 推奨: **`buildSnapshot` を足し、これからのスペック固定 OFF の録画に書く。既存は書き直さない**。代替: 足さず、`conditionNote` の自由文のまま。
5. **いつ取るか** — 推奨: **出来事で取る（撮影の日・育成を変えたとき）。定期実行はしない**。代替: タスクスケジューラで週 1 回。
6. **所持の一覧** — 推奨: **`private/roster.md` を生成し、所持の正をそちらに移す**。代替: 生成だけして、`owner.md` はそのまま。
7. **段の順** — 推奨: **段 1 → 2 → 3**（段 1 はクラウドで始められる）。
