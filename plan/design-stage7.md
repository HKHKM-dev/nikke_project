## Context

Stage 5 / 6 は「20 秒ごとに必ずバースト I → II → III が同じフレームで発動し、10 秒のフルバーストに入る」固定サイクルを前提にしている。時刻表は `burst/fixedCycle.ts` の `planFixedCycle` が作り、sim（フレーム逐次）と calc（区間期待値）が同じ時刻表を共有する。持続バフの区間分割（`skills/timeline.ts`）もこの時刻表から作る。

実機はそう回らない。射撃場の実測（録画 18〜22）で分かっていることは、III が 1 体の編成でフルバーストが **CT 40 秒周期・180 秒に 5 回**で回ること（0 節）。固定サイクルはフルバーストを 9 回と数えるので、バーストスキルダメージの回数とフルバーストの稼働率がどちらも実機の 1.8 倍になる。

Stage 7 の要求（[roadmap.md](roadmap.md)）:

- 固定 20 秒サイクルの仮定を外し、武器種・弾丸命中によるゲージ蓄積と、バースト CT に基づく動的サイクルを扱う。
- **sim**: 射撃ヒットごとのバーストゲージ蓄積、段階 I → II → III の移行、各ニケのバースト CT（20 秒 / 40 秒）の待機をシミュレートする。
- **calc**: sim で計測したサイクル（平均サイクル秒数・フルバースト稼働率）を取り込む近似モデル。
- **検証**: 録画解析で武器種別のゲージ蓄積量を較正し、sim のサイクル再現性を確認する。

**Stage 7 は新しいスキル語彙を足さない。** 足すのは「いつバーストが起きるか」を決める時刻表の作り方だけ。持続バフ（`timed`）の区間分割・ダメージ式・sim のフレームループ本体は Stage 6 のまま使う。Stage 6 の 9 節に書いた「`planBuffTimeline` は時刻表を受け取るだけなので、動的サイクルの時刻表に差し替えればタイムラインの作り方は変えずに済む」を実行する Stage になる。

## 1. 時間モデルとバーストの状態機械

Stage 5 の時間モデル（60fps・180 秒 = 10,800f・発射はフレーム単位）はそのまま。**バーストの状態を 1 本の状態機械（`BurstController`）で表す。** sim も calc もこの同じ状態機械を回す（3 節・5 節）。

```
          ゲージ ≥ 上限
charging ───────────────▶ ready ──(I の候補の CT 明け)──▶ chain(step)
   ▲                                                         │
   │ ゲージ = 0                                               │ step の候補の CT 明け → 発動
   │                                                         │   次の段階 = 発動したニケの nextStep
   │                     タイムアウト（最後の発動から 600f）  │
   ├─────────────────────────────────────────────────────────┤
   │                                                         │ nextStep が StepFull
   │   フルバースト終了（600f）                               ▼
   └──────────────────────────────────────────────────── fullBurst
```

- **charging**: 通常攻撃が敵に当たるたびにゲージを足す。上限で止める（あふれは捨てる）。
- **ready**: 満タン。I の候補が出るまで**時間制限なしで待つ**（録画 19）。
- **chain(step)**: 段階 `step` の候補（`burstStep === step` か `AllStep`、かつ CT が明けている、かつこのチェーンでまだ使っていない）が出たら発動する。**候補が複数なら枠番号の若い順**（9 節 4）。発動したニケの CT が `skill_cooltime` だけ始まり、段階は `nextStep` に進む（`Step2` / `Step3` / `StepFull`、`Step1` なら I に戻る＝リエントリー、`NextStep` なら 1 つ上）。**最後の発動から 600f 候補が出なければチェーン失敗**（ゲージ 0 で charging に戻る。録画 22）。
- **fullBurst**: `nextStep === 'StepFull'` の発動から始まる 600f。終わったらゲージ 0 で charging に戻る。フルバースト中はゲージが溜まらない。
- **CT の初期値**: 戦闘開始時は全員 0（すぐ使える）。

段階の間の演出時間は定数にして較正する（初期値は録画 18 の目視）:

```ts
/** バーストゲージの上限（CDN の target_burst_energy_pershot と同じ単位） */
export const BURST_GAUGE_MAX = 1_000_000;
/** 満タン（または CT 明け）から I の発動までのフレーム */
export const BURST_READY_DELAY_FRAMES = 20;
/** I → II の発動の間隔（フレーム） */
export const BURST_STEP1_TO_STEP2_FRAMES = 20;
/** II → III の発動の間隔（フレーム） */
export const BURST_STEP2_TO_STEP3_FRAMES = 20;
/** StepFull の発動からフルバースト開始まで（フレーム）。Stage 6 の実測で 3f 未満 */
export const FULL_BURST_START_DELAY_FRAMES = 0;
/** フルバースト時間（フレーム）。burst_duration は取り込むが使わない（9 節 3） */
export const FULL_BURST_FRAMES = 600;
/** チェーン中に次の段階の候補が出ないまま待てるフレーム（録画 22 で約 600f） */
export const BURST_CHAIN_TIMEOUT_FRAMES = 600;
```

1 発あたりのゲージ（9 節 5）:

```
energyPerTrigger = shot.targetBurstEnergyPerShot × shot.shotCount × (チャージ武器 ? shot.fullChargeBurstEnergy : 1)
```

**変数の中身（レビュー反映）**: 1 トリガーは「弾薬を 1 消費する 1 回の射撃」。`maxAmmo` はトリガー数で数える（SG の装弾数 9 = 9 トリガー）。

| 変数（`ShotParams`）       | CDN の元                      | 中身                                                                                               |
| -------------------------- | ----------------------------- | -------------------------------------------------------------------------------------------------- |
| `shotCount`                | `shot_detail.shot_count`      | **1 トリガーで出るペレット数**。SG は 10（ツバイだけ 5）、それ以外の武器は 1。弾薬の消費数ではない |
| `muzzleCount`              | `shot_detail.muzzle_count`    | 銃口数。2 は二丁持ちの SMG 6 体・ノア（RL）・ツバイ（SG）                                          |
| `targetBurstEnergyPerShot` | `target_burst_energy_pershot` | **1 ペレット（SG 以外は 1 発）あたり**のゲージ量                                                   |
| `fullChargeBurstEnergy`    | `full_charge_burst_energy`    | フルチャージ時の倍率（/ 10000、チャージなしは 1）                                                  |

`shotCount` は Stage 1 の正規化（`scripts/normalize.ts`）以来この意味で、ダメージ側も同じ変数を使っている（武器倍率 `damage` は SG の全ペレット合計。1 ペレットのダメージは `damage / shotCount`）。**ペレット数のために新しい変数（`pelletsPerShot` など）は作らない**が、紛らわしいので実装時に `ShotParams.shotCount` の JSDoc を「1 トリガーのペレット数（弾薬の消費数ではない）」に書き直す。`muzzleCount = 2` の 8 体はダメージ側と同じく「未対応」の注記を出し、ゲージは銃口 1 つとして数える（二丁持ちが 1 トリガーで 2 発ぶん溜めるのかは未確認）。

Stage 2 以来、チャージ武器は常にフルチャージで撃つモデルなので、チャージの途中解放は考えない。**射撃がフレーム f に起きたら、そのフレームでゲージに入る**（弾速・着弾遅延は無視）。RL は弾速が遅いうえ 1 発でゲージの 7〜10% を稼ぐので、ここは実測で確かめる（6.5 の 4）。ずれが数フレームなら 40 秒周期には効かないのでこのままにし、それを超えるなら武器種ごとの `BURST_ENERGY_DELAY_FRAMES`（発射からゲージに入るまでのフレーム）を足す。

**スコープ外**: ゲージ充填速度を上げるスキル（マナ S2 など。段階 C で `stat` を足す）、CT 短縮（段階 D = Stage 9）、敵ごとのゲージ補正（レイドボス。射撃場の的だけを較正する）、手動バースト（常に自動バーストの挙動を再現する）。

## 3. core の共通部分 — 時刻表の一般化

### 3.1 `BurstSchedule`（`burst/schedule.ts` 新設）

Stage 5 / 6 の `FixedCycleSchedule` は「全段階が同じフレーム」「段階の割当は固定」を前提にした形（`activationFrames` + `assignment`）なので、動的サイクルでは表せない。**発動 1 回ずつを列挙する形**に一般化する。

```ts
export type BurstActivation = {
  frame: number;
  step: BurstStepKey;
  slotIndex: number;
  /** この発動でフルバーストに入るか（nextStep が StepFull） */
  startsFullBurst: boolean;
};

export type BurstSchedule = {
  /** 発生順 */
  activations: BurstActivation[];
  /** [start, end) の列。末尾は戦闘時間で切る */
  fullBurstWindows: FullBurstWindow[];
  fullBurstFramesTotal: number;
  /** 表示・テスト用。ゲージが満タンになったフレーム、チェーンが切れたフレーム */
  gaugeFullFrames: number[];
  chainTimeouts: number[];
  model: 'fixed' | 'dynamic';
};
```

- `planFixedCycle` は**この形を返すように書き換えて残す**（9 節 2）。各サイクルの発動フレームに I / II / III を同じフレームで並べるだけで、Stage 6 の数値はそのまま再現できる（6.2 節の退化テスト）。
- `assignment` / `assignedStepOf` / `activationFramesOfStep`（Stage 6 で Stage 7 用に置いた差し替え口）は `activations` から引く形に置き換える。
- `isFullBurstFrame`（サイクル内の位置で判定）は固定サイクルでしか使えないので、`fullBurstWindows` を見る `isInWindows(frame, windows)` に置き換える（`skills/timeline.ts` の区間の `fullBurst` 判定もこちらを使う）。

### 3.2 状態機械（`burst/controller.ts` 新設）

1 節の状態機械を、**「このフレームに入ったゲージ量」を受け取って 1 フレーム進める**純粋な状態機械にする。ゲージ量の出どころ（sim の実射撃か calc の平均レートか）は知らない。

```ts
export type BurstUnit = {
  slotIndex: number;
  burstStep: BurstStep;
  nextStep: BurstNextStep;
  cooldownFrames: number;
} | null;

export type BurstControllerState = {/* phase, gauge, step, cooldownEnd[], usedInChain, lastUse, … */};

export function initialBurstController(units: readonly BurstUnit[]): BurstControllerState;

/** frame を 1 つ進める。gauge は charging のときだけ足される。発動したら activation を返す */
export function stepBurstController(state: BurstControllerState, frame: number, gauge: number): BurstActivation | null;

export function finishSchedule(state: BurstControllerState, frames: number): BurstSchedule;
```

### 3.3 動的時刻表（同上ファイル）

```ts
export function planDynamicSchedule(
  slots: readonly ({ character: CharacterData } | null)[],
  frames: number,
  model: WeaponModel,
): BurstSchedule;
```

**各枠の射手（`sim/shooter.ts`）を 1 フレームずつ回し、撃ったフレームに `energyPerTrigger` をゲージに入れて `stepBurstController` を進める。** Stage 7 の範囲では射撃のタイミングがバフにもバーストにも依存しない（弾数・リロード・チャージ速度のバフは段階 C / D）ので、射撃列は Stage 5 / 6 の sim と 1 フレームも変わらない。つまり時刻表は編成だけから決まる純関数で、**sim と calc が同じ時刻表を共有できる**（9 節 1）。

## 4. sim（`sim/engine.ts`）

**2 パス**にする。

1. `planDynamicSchedule` で時刻表を作る（射手を 1 回回してゲージを溜める）。
2. その時刻表で Stage 6 のフレームループをそのまま回す（`planBuffTimeline` → 区間ごとの 1 トリガー値 → 射撃の加算、発動フレームでバーストヒット）。

2 パス目の射手は 1 パス目と同じ初期状態から同じ手順で進むので、射撃フレームは一致する（テストで固定する）。ループの中でゲージを溜めて発動を決める 1 パス方式にしないのは、**持続バフの区間（`planBuffTimeline`）を先に作る Stage 6 の構造を崩さないため**。1 パスが要るのは射撃がバフに依存するようになる段階 C / D で、そのときに考える（10 節）。

`SimResult.schedule` の型が `BurstSchedule` になる。バーストヒットは `schedule.activations` の各発動（`slotIndex` がその枠）について、Stage 6 と同じ `burstSnapshotState`（発動直前のバフ）で計算する。**同じ段階の 2 体が CT で交互に撃つ編成では、発動する枠が回ごとに変わる**（Stage 5 の「割当枠だけ」は `activations` の `slotIndex` で置き換わる）。

`trace` に `{ frame, kind: 'gaugeFull' | 'chainTimeout' }` を足す。

## 5. calc — sim の時刻表を取り込む

### 5.1 core（`team.ts`）

`TeamInput` に 1 つ足す:

```ts
export type TeamInput = {
  // …（既存）
  burst?: boolean;
  /** burst が true のときの時刻表の作り方。省略 'dynamic'。'fixed' は Stage 5 / 6 の固定 20 秒サイクル（テスト・比較用） */
  burstModel?: 'dynamic' | 'fixed';
};
```

`planTeamSchedule` が `burstModel` で `planDynamicSchedule` / `planFixedCycle` を選ぶ。**calc の時刻表は sim と同じ `planDynamicSchedule` の結果**で、calc が期待値で置くのは Stage 5 / 6 と同じく**通常攻撃の区間ごとのトリガー数**だけ。したがって Stage 5 / 6 の不変条件「sim と calc の差は発射サイクルの離散化だけ」が Stage 7 でもそのまま成り立つ。

`TeamResult` に集計を足す（UI とテスト用）:

```ts
export type BurstSummary = {
  model: 'dynamic' | 'fixed';
  fullBursts: number; // フルバーストの回数
  fullBurstUptime: number; // fullBurstFramesTotal / frames
  /** 隣り合うフルバースト開始の間隔の平均（秒）。1 回以下なら null */
  meanCycleSeconds: number | null;
  firstFullBurstSeconds: number | null;
  chainTimeouts: number;
```

## 9. 決めてほしいこと（推奨付き）

2026-09-23 に 9 点とも推奨案で承認された。

1. **calc の時刻表** — 推奨: **sim と同じ `planDynamicSchedule` を使う**（3.3 節・5.1 節）。射撃がバフに依存しない Stage 7 では時刻表が編成だけで決まるので、calc が近似する必要がない。Stage 5 / 6 の不変条件（sim と calc の差は通常攻撃の離散化だけ）がそのまま保てる。計算量は 10,800f × 5 枠の加算で、calc の再計算 1 回あたり数ミリ秒。代替: 平均ゲージ量（秒間トリガー数 × 1 発のゲージ）からサイクル秒数を式で出す。軽いが、満タンのタイミングが 1 秒ずれるだけで 180 秒内の回数が 5 ↔ 4 と跳ぶことがあり、sim との差が離散的に開く。

2. **固定 20 秒サイクルを残すか** — 推奨: **core に `burstModel: 'fixed'` として残し、UI には出さない**。Stage 5 / 6 の数値（verification.md）とテストの期待値をそのまま守れる。退化テスト（6.2）の相手にもなる。代替: 削除して Stage 6 のテストを動的サイクルの値に書き換える（テストの期待値を大量に作り直すことになる）。

3. **フルバースト時間** — 推奨: **全員 10 秒固定**。`burst_duration` は取り込むが使わない。500（ミハラ・イサベル・ベスティー）と 1,500（モダニア）の意味が「フルバースト時間」なのか「バーストスキル効果の時間」なのか確かめていない。所持していれば 6.5 に 1 本足して確かめる。代替: III の `burst_duration` をフルバースト時間にする。

4. **同じ段階の候補が複数いるときの順** — 推奨: **CT が明けている中で枠番号の若い順**（Stage 5 の `assignBurstSteps` と同じ規則）。自動バーストの実際の優先順は未確認なので、6.5 の 6 で確かめる。代替: 最後に撃ってからの時間が長い順（交互になりやすい）。

5. **ゲージの式** — 推奨: **`targetBurstEnergyPerShot × shotCount × fullChargeBurstEnergy` / 上限 1,000,000 の仮説で実装し、6.5 の撮影で確定する**。Stage 5 / 6 と同じく定数・仮説は名前を付けて export し、実測で覆せるようにする。0 節のとおりチャージ 1 発と SG の編成に 1〜2 割のずれがあるので、撮影前の数値は「仮」と表示する。代替: 撮影で係数を決めてから実装に入る（撮影がボトルネックになる）。

6. **SG のペレット命中率** — 推奨: **ダメージ式と同じく全ペレット命中**を既定にする。6.5 の 2 で外れが分かったら、`SlotCondition` に「ゲージ計算用のペレット命中率」を足す（既定 1）。ダメージ側は Stage 2 以来 1 ペレットの値で検証していて、全ペレット命中は射撃場の距離での仮定。代替: 最初から命中率の入力を作る。

7. **リエントリー・`AllStep` / `NextStep`・CT 60 秒を扱うか** — 推奨: **状態機械はデータどおりに扱う**（`nextStep` を読むだけで追加の仕組みは要らない）。単体テスト（6.1）で挙動を固定するが、実測はしない（該当キャラ 9 体: ティア・アリス：ワンダーランドバニー・ルピー：ウィンターショッパー・アビスタ（`Step1 → Step1`）、チャイム（`Step2 → Step2`）、レッドフード（`AllStep → NextStep`）、ラプンツェル・ブラン・エヌ：ミラクルフェアリー（CT 60 秒）。所持していれば教えてほしい）。代替: 標準の `Step1 → Step2 → Step3 → StepFull` だけにして、該当キャラは「未対応」表示。

8. **ゲージ・CT に触るスキル** — 推奨: **Stage 7 では扱わない**。ゲージ充填速度▲（マナ S2 の notes にある）は段階 C（Stage 8）で `stat` を足し、CT 短縮はロードマップどおり段階 D（Stage 9）。Stage 7 の時刻表はスキルの影響を受けない。代替: 「バーストゲージ充填量 +X%」の常時パッシブだけ入れる（`passive` の `stat` に 1 つ足すだけで済むが、該当キャラの定義も要る）。

9. **撮影（6.5）に使えるキャラ** — 推奨: 1〜5 は既に使ったキャラ（ラピ・ノワール・デルタ・I-DOLL・フラワー / ベロータ・エマ）で撮る。6 は **III を 2 体**（例: ノワール + クイーン（真）、どちらも SG・CT 40 秒）+ I + II。I にはエーテル以外を使う（Stage 6 の注意）。所持していて使えるキャラを教えてほしい。

## 10. リスク・留意点

- **射撃がバフ・バーストに依存するようになると 2 パスが使えない**: Stage 8 / 9 で弾数・リロード・チャージ速度のバフや CT 短縮が入ると、射撃列 → ゲージ → 時刻表 → バフ → 射撃列…が循環する。そのときは sim を 1 パス（フレームループの中で状態機械を回し、持続バフも逐次付与）にし、calc は sim の時刻表を受け取る形（今回の 9 節 1 の延長）にする。Stage 7 で `BurstController` を「1 フレーム進める」形にしておくのは、1 パス化で再利用するため。
- **180 秒の境界で回数が跳ぶ**: 5 回目のフルバーストは戦闘 約 165 秒に始まり、10 秒後の 175 秒に終わる。1 回目が 15 秒以上遅れると 5 回目が 180 秒に入りきらず、フルバースト稼働率とバーストスキルの回数が段で落ちる。較正の精度（6.7 の ±30f）はこのためにある。
- **読み取りの分解能**: BURST バーは 118px なので 1px ≈ 0.85%。1 発 0.4% の AR は 1 発ずつは読めず、マガジン単位の傾きで読む。SR / SG の 1 発（5〜15%）は 1 発ずつ読める。フルバースト中と CT 待ち中はバーの位置に別の UI（タイマー・六角形のアイコン）が出るので、その間の値は捨てる。
- **段階の演出時間**: 20f という初期値は 60f 刻みの目視。1 チェーンで 40〜60f、180 秒で 5 チェーンなら合計 3〜5 秒ぶんのずれになりうる。カットインやモーションの長さはキャラ・端末（描画負荷によるフレーム落ち）で少しぶれる可能性がある（レビュー反映）。そこで:
  - 演出時間は `BURST_READY_DELAY_FRAMES` / `BURST_STEP1_TO_STEP2_FRAMES` / `BURST_STEP2_TO_STEP3_FRAMES` の 3 つに分けて export し、実測で個別に直せるようにする。
  - 値は録画 18〜22（計 20 チェーン）と 6.5 の 6 から 1 フレーム単位で読み、**中央値**を採る。ばらつき（最小〜最大）は verification.md に残し、回帰テスト（6.4）の許容幅はこのばらつきから決める。
  - キャラごとに明らかに違う（例: 特定のニケのカットインだけ長い）と分かったら、そのときにキャラ別の上書きを検討する。Stage 7 では全員共通の定数にする。
  - フレーム落ちの多い録画（台帳で平均 fps が 60 を大きく下回るもの）は時間計測の母数から外す（Stage 2-B と同じ）。
- **`burstUse` と `fullBurstStart` が別フレームになる**: Stage 6 で語彙を分けておいた効果がここで出る。I（エマ：TU）の `burstUse` 10 秒バフはフルバーストより 40f ほど早く付いて早く切れる。持続バフの区間が 1 つ増えるだけで、Stage 6 のタイムラインはそのまま扱える。
- **マナ S2 の `assumes`**: 「毎サイクル自分がバーストする（マターシグマが再付与される）」は、III がマナ 1 体なら動的サイクルでも成り立つ。III 2 体の交互編成では成り立たないが、その判定は段階 C（状態フラグ）まで持ち越す。
- **3 分モードの的の反撃**: 回帰テストに使う録画 18〜21 は 3 分モードで、被弾トリガーのスキル（ラピ S1）が後半で発動する。時刻表（ゲージ・CT）には影響しないので、Stage 7 の回帰には問題ない。
- **データの再生成**: 203 ファイルが一度に変わる。値の追加だけで既存フィールドは変わらないことを、`git diff --stat` と「既存フィールドの削除行が 0」で確認してからコミットする。

## 11. 実装時の差分と知見（2026-09-23）

- **時刻表の表示は `ResultPanel` ではなく `TeamBreakdown` に置いた（5.3 節からの変更）**: 時刻表は編成全体のもので、枠ごとのパネルに置くと 5 枠に同じ表が並ぶ。「フルバースト N 回（稼働率・平均サイクル・初回）」の 1 行も同じ場所にまとめ、`TeamSettingsForm` はトグルの説明文だけを直した。
- **満タン後に I の CT を待った場合は、CT 明けのフレームですぐ撃つ**: `BURST_READY_DELAY_FRAMES` は「満タンから I まで」だけに掛ける。CT 明けにも演出時間を足すかは実測で決まっていない（CT 律速の録画 18〜21 で周期が 2,400f ± 数十f なので、どちらとも言えない）。
- **テスト用フィクスチャの `nextStep` を `burstStep` から決めるようにした**: 既定を `StepFull` にしていたため、I のニケがそのままフルバーストに入り、整合テストでフルバーストが 10 回になった。実データと同じ遷移（I → II → III → フルバースト、`AllStep` は `NextStep`）にした。
- **`AllStep` のニケは専任が CT 中の段階を埋める**: 5 体の整合テストで、MG（`AllStep`）が I の CT 中に I を撃ち、II が CT 中なのでチェーンが切れる、という動きが出た。録画 22 の「I が撃って II を待ち、600f で切れる」と同じ規則なので仕様どおり。
- **`tools/captures/gauge.ts` を作って録画 18〜22 を 1 フレームずつ読み直した**（verification.md Stage 7 節）。分かったことは次のとおり。
  - デルタの照準画面に「CHARGE 250%」と並んで「BURST 250%」が出ていた（録画 22）。`full_charge_burst_energy` がゲージのチャージ倍率であることは画面の表示で確かめられた。
  - **AI のデルタは 1 発 6.2%、操作中のデルタは 15.9%**。AI のデルタとエーテルは `burst_energy_pershot`（`target` の半分）× チャージ倍率で説明できる。ただし AI のエマ：TU は `target` どおりで、操作中のデルタは `target × 2.5` よりさらに 2 割多い。「操作キャラは `target`、AI は `burst`」だけでは合わない。コアヒットが効いている可能性もある。
  - 1 回目の満タンまでの時間は、実測と calc で −167f〜+163f ずれ、符号もばらばら。上限の値を 1 つ直すだけでは合わないので、較正は 6.5 の撮影（操作 / AI、コア / 胴体）を待つ。回帰テストは「回数・周期・チェーン失敗」を厳しく、「満タンまでの時間」を ±200f で固定した。
  - **マナ（録画 20）は S2 の「バーストゲージのチャージ速度▲」が戦闘開始から乗っている**（未対応。段階 C で `stat` を足す）。満タンまでの時間の比較から外した。
  - 満タンからバーが消える（I のアイコンが出る）までが 10〜82f とばらつく。自動バーストが、射撃中・リロード中の枠を待っている可能性がある。演出時間の定数（20f）はまだ仮の値。

## 12. ゲージの較正の結果（2026-09-23、録画 23〜35）

6.5 節の撮影（同じキャラを操作・コア / 操作・胴体 / AI）で、1 トリガーのゲージ量を次の式に確定した（詳細は [verification.md](verification.md) Stage 7 節）。

```
energyPerTrigger = targetBurstEnergyPerShot × 1.2 × ペレット数 × (SG ? 0.75 : 1) × (操作キャラのチャージ武器 ? fullChargeBurstEnergy : 1)
```

- **×1.2**（`BURST_ENERGY_MULTIPLIER`）: AR・MG・RL・SR のどれも CDN 値の 1.17〜1.21 倍。コアと胴体で差はない。射撃場の的固有かもしれない。
- **SG 0.75**（`SG_PELLET_GAUGE_HIT_RATE`）: ノワールの 1 トリガーが全ペレット命中の予測の 0.75〜0.78 倍。
- **フルチャージ倍率は操作キャラだけ**: AI のデルタは倍率なし。9 節 5 の仮説（全員にフルチャージ倍率）を訂正し、`TeamInput.controlledSlot`（省略は全員 AI）を足した。calc には「操作キャラ」の選択を出した（9 節 2 の「UI には出さない」は固定サイクルの話で、こちらは新しい入力）。
- **6.7 節の完了条件との関係**: 1 回目の満タンまでの時間は録画 18・19・21 で −37f〜−2f、録画 22 で +61f。「±30f 以内」には録画 21（−37f）と 22（+61f）が届いていない。ただし 2 回目以降のフルバーストは CT 律速で、回数（5 回）と周期（2,400f）は一致しているので、180 秒のダメージへの影響は小さい。残りの差は演出時間の定数（20f の仮の値）と MG のスピンアップの読み直しで詰める。
- 6.5 節の撮影で分かった副産物: SG のダメージ計算は全ペレット命中の仮定のままなので、射撃場の距離で 1/4 が外れているなら SG の総ダメージは過大かもしれない（Stage 8 以降で確認）。
